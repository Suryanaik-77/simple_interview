INDEPENDENT WORK Tool: Synopsys Formality Design: cva6 (RISC-V core) Difficulty: ** Medium Estimated time: 90 min

Challenge

The CVA6 RISC-V application-class processor has been synthesized targeting TSMC 28nm. You must run RTL-to-gate LEC to confirm the synthesized netlist is functionally equivalent to the 174-file SystemVerilog RTL.

This testcase differs from Testcase 1 in three important ways:

  • 174 RTL source files — loaded via a TCL filelist variable, not a direct file list. You must source the filelist and use the resulting $ver_files variable.
  • SRAM macro libraries — CVA6 instantiates two SRAM types. Their .db files are in inputs/, not in the PDK tree. You must load them with read_db.
  • Larger design — the netlist is significantly larger than the AES design. Match and verify will take longer.

Your task: complete scripts/formality.tcl so that make all produces Verification SUCCEEDED and generates all six report files.

Hints

Hint 1 — How to load 174 RTL files using the filelist

Instead of listing 174 files manually, use the TCL filelist:

RTL loading via filelist

Sourcing the filelist populates the TCL variable $ver_files with the complete ordered list of SV/V source paths. Pass that variable directly to read_verilog -r.

Hint 2 — Which libraries to load and where to find them

Unlike Testcase 1 which used PDK standard-cell .db files, CVA6 requires only the two SRAM macro libraries that are already in inputs/:

Standard-cell gates in the netlist will be treated as black boxes without standard-cell .db files, but Formality can still verify the surrounding RTL logic using the SRAM models.

Complete Script Reference: scripts/formality.tcl

Show complete formality.tcl solution
scripts/formality.tcl — CVA6 RTL-to-Gate LEC
# Step 1: Global verification settings
set synopsys_auto_setup                    true
set verification_clock_gate_reverse_gating true
set verification_clock_gate_hold_mode      low
set verification_clock_gate_edge_analysis  true

# Step 2: Load SVF -- must be done BEFORE any read_verilog
#   cva6.svf records all naming changes and transformations from synthesis.
set_svf ../inputs/cva6.svf

# Step 3: Read Reference design (RTL -- 174 SystemVerilog files via filelist)
#   cva6.rtl.flist defines the TCL variable $ver_files with all file paths.
#   source populates $ver_files; read_verilog -r then loads all RTL.
set rtl_filelist ../inputs/cva6.rtl.flist
source $rtl_filelist
read_verilog -r $ver_files

# Set top module for the reference (RTL) container
set_top r:/WORK/cva6

# Step 4: Read technology libraries (SRAM macro .db files)
#   CVA6 instantiates two SRAM macro types. Load their Liberty .db files
#   from inputs/ so Formality can model their port logic.
read_db {
    ../inputs/tc_f_spsram_256x128_ssg_cworstt_0p81v_0p81v_m40c.db
    ../inputs/tc_f_spsram_256x45_ssg_cworstt_0p81v_0p81v_m40c.db
}

# Step 5: Read Implementation design (synthesized gate-level netlist)
#   set_top -auto detects the top module from the netlist automatically.
read_verilog -i ../inputs/cva6.v
set_top -auto

# Step 6: Match compare points (guided by cva6.svf)
match

# Step 7: Verify logical equivalence
verify

# Step 8: Generate equivalence reports
report_passing_points   > ../reports/report_passing_points.rpt
report_verify_points    > ../reports/report_verify_points.rpt
report_failing_points   > ../reports/report_failing_points.rpt
report_matched_points   > ../reports/report_matched_points.rpt
report_unmatched_points > ../reports/report_unmatched_points.rpt
report_black_boxes      > ../reports/report_black_boxes.rpt

exit

1. Formality constructs a miter circuit for each matched compare point during the verify phase. What does the miter circuit prove?

  • It simulates both logic cones with random input vectors and reports the percentage of matching outputs.
  • It measures the number of logic levels in both cones to detect structural changes introduced by synthesis.
  • It XORs the outputs of both logic cones and asks a SAT solver whether that XOR can ever produce a 1. If no input can make it 1, the two cones are formally proven equivalent for every possible input combination.
  • It traces SVF transformation records in reverse to reconstruct the RTL from the netlist and compares them.
Correct! XOR outputs 1 only when the two functions disagree. The SAT solver searches for any input that makes XOR=1. If it finds one, that is a counterexample and the point fails. If it proves none exists, the pair is equivalent for all inputs — a mathematical proof, not a sample. This is what makes LEC exhaustive while simulation is not.

2. Which of the following signal boundaries does Formality recognize as compare points during LEC?

  • Every internal wire inside a combinational cone between two flip-flops.
  • Only the primary output ports of the top-level module, since those are the only externally observable signals.
  • Flip-flop D-pin inputs, primary module output ports, hard-macro input pins, and clock-gating enable pins — any observable boundary where RTL intent must be preserved after synthesis.
  • Only signals that appear in the SDC file as timing endpoints.
Correct! Compare points are the boundaries where Formality checks equivalence. Primary outputs cover what the module delivers externally. Flip-flop D-pins cover the next-state logic synthesis must preserve. Hard-macro input pins cover the interface to black-boxed IPs. Clock-gate enable pins ensure the gating condition was not corrupted. Internal combinational wires are not compare points — they are part of the logic cones feeding into these boundaries.

3. LEC reports 12 Matched+Failing points. How is this different from 12 Unmatched points, and which is more serious?

  • Both are equally serious — either type always causes Verification FAILED and blocks tape-out sign-off.
  • Matched+Failing means a counterpart was found and the SAT solver proved the two cones differ for at least one input — a confirmed functional bug. Unmatched means no counterpart was found, so the logic is not checked at all — a coverage gap. Matched+Failing is always more serious.
  • Unmatched is more serious because it indicates entire logic blocks exist in the netlist with no RTL equivalent.
  • They represent the same underlying problem and are both fixed by reloading the SVF file correctly.
Correct! Matched+Failing is a proven bug: Formality paired the points, the SAT solver found a concrete input that produces different outputs, and Formality reports FAILED. Unmatched points are not checked at all — they are a coverage gap, not proof of a bug. While both need investigation, Matched+Failing is definitively more critical because it is a confirmed functional difference between RTL and netlist.

4. Which synthesis transformations make RTL-to-Gate LEC necessary? Choose the most accurate answer.

  • Only clock-gate insertion — all other synthesis optimizations are lossless and cannot introduce functional bugs.
  • Only register retiming — combinational restructuring preserves logic by definition.
  • Any synthesis transformation — logic restructuring, register merging, constant propagation, clock-gate insertion — can silently alter functional behavior. Simulation only checks the vectors you provide; LEC proves correctness for every possible input.
  • None — synthesis tools are formally verified and guaranteed to preserve RTL intent. LEC is only required after manual netlist edits.
Correct! No synthesis transformation is automatically guaranteed to be bug-free. Logic restructuring can produce wrong Boolean functions. Register merging can silently change state machine behavior. Clock-gate insertion can disable valid cycles. Constant propagation with incorrect don’t-care assumptions can alter outputs. Simulation misses corner cases in rarely exercised logic. LEC closes this gap by exhaustively proving correctness across all inputs.
