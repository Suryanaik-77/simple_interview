Problem Statement

GUIDED

You will perform Logical Equivalence Checking (LEC) between the AES cipher top RTL and its synthesized gate-level netlist using Synopsys Formality interactively.

The synthesis run inserted clock-gating cells. This guided testcase walks you through every Formality command interactively — type each command at the fm_shell> prompt, observe what fails when clock gating is ignored, and apply the fix. When done, type exit and run make verify.

⚙ Verification Flow Overview

Formality compares a reference design (RTL) and an implementation design (netlist) by breaking the design into compare points such as registers and outputs.

Each compare point is analyzed through its logic cone, and equivalence is proven by ensuring both designs produce identical outputs for the same inputs. The process involves reading designs, mapping compare points, and verifying equivalence.

📝 Execution Flow and Command Understanding

  • Launch fm_shell

    Navigate to the testcase directory and launch Formality interactively:

    cd ~/pd/labs/LEC-SNPS-CG/TC-LEC-SNPS-CG-GD-001
make run

    make run launches fm_shell in interactive mode. You will see the fm_shell> prompt. Type each command from the steps below directly at this prompt and observe the tool's output.

  • Initial Setup

    set synopsys_auto_setup true

    This command enables automatic configuration inside Formality. It simplifies setup by handling RTL interpretation, undriven signals, and default verification settings.

  • Load SVF

    set_svf ../inputs/default.svf

    SVF provides synthesis guidance such as mapping information and optimizations, helping Formality match RTL and netlist more efficiently.

  • Read Reference Design (RTL)

    read_verilog -r {/efs/semicon_labs_pd/designs/aes_core/aes_cipher_top.v \
                 /efs/semicon_labs_pd/designs/aes_core/aes_key_expand_128.v \
                 /efs/semicon_labs_pd/designs/aes_core/aes_rcon.v \
                 /efs/semicon_labs_pd/designs/aes_core/aes_sbox.v \
                 /efs/semicon_labs_pd/designs/aes_core/timescale.v}

    Loads RTL into the reference container. This is treated as the golden design for comparison.

  • Load Technology Libraries

    read_db {/efs/semicon_labs_pd/pdk/foundries/tsmc/N28/versions/v1.0/stdcells/9T/svt/lib/nldm/tcbn28hpcplusbwp40p140ssg0p81vm40c.db \
         /efs/semicon_labs_pd/pdk/foundries/tsmc/N28/versions/v1.0/stdcells/9T/lvt/lib/nldm/tcbn28hpcplusbwp40p140lvtssg0p81vm40c.db \
         /efs/semicon_labs_pd/pdk/foundries/tsmc/N28/versions/v1.0/stdcells/9T/hvt/lib/nldm/tcbn28hpcplusbwp40p140hvtssg0p81vm40c.db}

    Loads technology libraries required to understand standard cells used in the netlist.

  • Set Reference Top

    set_top aes_cipher_top

    After reading the source RTL files, set_top elaborates (links) the design and defines the top-level module. This ensures Formality correctly understands the design hierarchy starting from the specified top module.

  • Read Implementation (Gate-Level Netlist)

    read_verilog -i ../inputs/aes_cipher_top.v

    Loads the synthesized netlist into the implementation container (-i). The implementation design represents the post-synthesis version of the RTL, where logic has been mapped to standard cells from the technology library.

    Unlike RTL, the netlist is a gate-level representation that includes:

    • Standard cell instances (AND, OR, flip-flops, etc.)
    • Optimizations introduced during synthesis
    • Structural transformations such as clock gating, register merging, or register inversions
    Key Insight: The implementation design may look structurally very different from RTL due to synthesis optimizations. However, Formality focuses on verifying functional equivalence, not structural similarity.

  • Set Implementation Top

    set_top -auto

    For the implementation design, set_top -auto allows Formality to automatically detect and assign the top-level module based on the netlist structure.

  • Match Compare Points

    match

    The match command aligns compare points between the reference (RTL) and implementation (netlist) designs. During this phase, Formality identifies corresponding elements such as registers, primary outputs, and black-box interface points.

    Key Concept: Most compare points are matched automatically based on naming. If structural differences exist due to synthesis optimizations, guidance (like SVF) helps improve matching.

  • Verify Equivalence

    verify

    The verify command checks functional equivalence between matched compare points by analyzing their logic cones. For each compare point, Formality evaluates whether the logic driving that point produces identical outputs in both RTL and netlist for all possible inputs.

    Important Note: If mismatches exist due to structural transformations such as clock gating, verification may fail even if functionality is correct. These cases require additional guidance or attributes to resolve.

🔍 Understanding the Issue

The root cause lies in synthesis optimizations. During synthesis, clock gating logic is inserted to reduce power consumption. This modifies the structure of the design by introducing gating elements between the clock and registers.

Although functionality remains unchanged, this structural difference prevents Formality from correctly mapping RTL and netlist. Specifically:

  • New compare points are created for clock-gating latches
  • These points do not have corresponding matches in RTL
  • The logic feeding register clock pins is altered
  • As a result, multiple register compare points fail verification
Why Clock Gating Causes Failure: Formality performs equivalence checking based on structural mapping of logic cones. Clock gating modifies the structure by inserting gating latches and changing clock paths, making it difficult for the tool to correlate RTL and netlist directly.

✅ Resolution Approach

To resolve this issue, Formality provides a mechanism called Reverse Clock Gating (RCG), enabled using the following command: 

set verification_clock_gate_reverse_gating true
What Reverse Clock Gating (RCG) Does:

When this attribute is enabled, Formality identifies clock gating latch structures inserted by synthesis and internally removes them. The tool reconnects the clock and enable signals directly to the receiving registers.

In effect, the gated clock structure is transformed back into a load-enable representation, which closely matches the original RTL behavior. This transformation does not change the functional behavior of the circuit, but allows Formality to correctly verify clock-gated designs.

Important Behavior:

When verification_clock_gate_reverse_gating is enabled:

  • Clock gating latches are automatically identified and reversed
  • Both reference and implementation designs are normalized for comparison
Critical Limitation: This attribute cannot be applied after entering the verification phase. Once the verify command is executed, the design is already elaborated and internal models are fixed. Therefore, to apply this fix correctly, the entire LEC flow must be re-executed with the attribute set in setup mode.

After re-running the flow with this attribute enabled, the tool successfully maps the transformed structures and proves equivalence between RTL and netlist.

Verification Outcome

After applying the fix, all compare points were successfully verified, confirming functional equivalence between RTL and netlist.

🧠 Knowledge Assessment

1. What is the main goal of LEC?

  • Improve timing in the synthesized netlist
  • Check functional equivalence between RTL and netlist
  • Reduce dynamic power consumption
  • Optimize area after place-and-route
✓ Correct! LEC formally proves that RTL and netlist behave identically for all possible inputs. It does not optimize timing, power, or area.

2. Why does clock gating cause LEC failures?

  • The RTL source files are incorrect
  • Synthesis inserts extra gating logic that changes the structural representation
  • The clock stops working after synthesis
  • The technology libraries are missing
✓ Correct! Clock gating inserts latch-based ICG structures not present in RTL, creating compare points that Formality cannot match without the RCG attribute.

3. What is a compare point in Formality?

  • A timing path endpoint in the netlist
  • A signal (register output or primary output) where equivalence is checked between reference and implementation
  • A clock signal that controls register updates
  • A library cell definition used during verification
✓ Correct! Compare points are register outputs and primary outputs where Formality proves Boolean equivalence between the reference and implementation logic cones.

4. What does setting verification_clock_gate_reverse_gating true do?

  • Adds more clock gate cells to improve power savings
  • Internally reverses the clock gating transformation so Formality can correctly verify clock-gated designs
  • Modifies the RTL to add enable logic
  • Stops verification and generates an error report
✓ Correct! RCG internally reverses the clock gating transformation, converting gated-clock structures back to enable logic so Formality can correctly match them to RTL.
