📖 Theory and Background

What is Design Initialization?

Design initialization (init_design) is the first stage of physical implementation in the ASIC design flow. It loads all design data into the Innovus database — technology files, cell libraries, the synthesized netlist, timing constraints, and RC parasitic models — before any physical operations (floorplanning, placement, CTS, routing) can begin.

At the end of a successful init_design run, Innovus has a complete picture of your design: every logic gate, every timing constraint, every physical cell geometry, and every PVT corner it needs to analyze. Only then can the tool make reliable placement and optimization decisions.

ASIC Flow Stage What Happens Output
Synthesis RTL compiled into standard cells; timing constraints applied Gate-level netlist + SDC
init_design ← We are here Netlist, LEFs, MMMC config loaded into Innovus; init_design called Initialized Innovus database (.db)
Floorplanning Die area, power rings, macro placement defined Floorplan database
Placement Standard cells placed on the die using place_opt_design Placed database
CTS Clock tree synthesized and balanced using ccopt_design CTS database
Routing Signal nets routed using route_global / route_detail Routed database
Chip Finish DRC/LVS clean-up, metal fill, sign-off GDSII

📅 Innovus MMMC Model

Innovus uses a named object model for MMMC setup. Each layer of the timing analysis stack is defined as an explicit named object using create commands, then wired together into analysis views. The setup hierarchy is:

Library Set + Operating Condition → Timing Condition → Delay Corner (+ RC Corner) → Analysis View → set_analysis_view

Innovus Command Purpose
create_library_set Groups timing .lib files for a given PVT corner into a named set.
create_opcond Defines a named operating condition with specific voltage and temperature.
create_rc_corner Defines a parasitic extraction corner by linking to a QRC tech file (cworst, rcworst, cbest, rcbest).
create_timing_condition Pairs an operating condition with a library set.
create_delay_corner Combines a timing condition and an RC corner — the fundamental timing analysis unit in Innovus.
create_constraint_mode Loads the SDC constraints file (clocks, I/O delays, exceptions) for a functional mode.
create_analysis_view Pairs a delay corner with a constraint mode into a named analysis view.
set_analysis_view Activates analysis views: -setup uses slow corners, -hold uses fast corners.

📂 Inputs to Design Initialization

File / Input Description
.tlef Technology LEF — metal layers, via types, and DRC rules for the process node.
.lef (cell) Cell LEF — physical geometry of standard cells and macros: boundaries, pin locations, routing obstructions.
.lib Liberty timing library — cell delay, setup/hold, and power data per PVT corner.
QRC Tech File Cadence parasitic model for each extraction corner (cworst, rcworst, cbest, rcbest).
.v netlist Post-synthesis gate-level Verilog describing the design as standard cell instances.
.sdc Timing constraints: clock definitions, I/O delays, false paths, multicycle paths.
mmmc_config.tcl MMMC setup script defining library sets, delay corners, analysis views, and setup/hold assignments.

📝 Knowledge Assessment Quiz

Test your understanding of init_design concepts. Select your answer then click Check Answer.

1. In the Innovus MMMC flow, what does create_delay_corner combine?

  • A timing library set and an SDC constraints file
  • A gate-level netlist and a technology LEF file
  • A timing condition (library set + operating condition) and an RC corner (QRC parasitic model)
  • An analysis view and a constraint mode
Correct! A delay corner in Innovus combines a timing condition (library set + operating condition) with an RC corner (QRC parasitic model). This gives Innovus everything needed to compute accurate cell + wire timing at a specific PVT and extraction condition.

2. Why must read_physical -lefs include SRAM macro LEF files in addition to standard cell LEFs?

  • Because SRAM macros require a separate technology LEF at the 28nm node
  • Innovus needs the physical boundary, pin locations, and routing obstruction data for each SRAM instance to perform legal macro placement and route signals around it
  • SRAM macros are not included in the gate-level netlist and must be added via LEF
  • The SRAM LEF supplies timing data — without it init_design will fail timing analysis
Correct! LEF files provide physical geometry — boundaries, pin locations, and routing obstructions. If an SRAM macro's LEF is missing, Innovus cannot legally place it or route around it. Timing data for SRAMs comes from .lib files in the library set, not from LEF.

3. What is the purpose of connect_global_net VDD -type pg_pin -pin_base_name VDD* after init_design?

  • It routes the VDD power ring around the chip boundary
  • It adds a tie-hi cell to every floating VDD net in the netlist
  • It connects the logical VDD supply to every standard cell PG pin whose base name starts with VDD, establishing power network connectivity in the database
  • It verifies that VDD is defined as a power net in the SDC file
Correct! After init_design, cell power pins are not yet connected to the global supply. connect_global_net makes those connections so that power analysis, IR drop checks, and DRC tools know which supply drives each cell's PG pin.

4. What does time_design -pre_place analyze at the init_design stage?

  • Post-route timing using actual extracted parasitics from the routed design
  • Clock skew after the clock tree has been synthesized
  • Estimated timing using ideal wire delays (no routing yet), giving a baseline view of critical path slack before physical optimization
  • SDC constraint syntax errors before constraints are applied to the design
Correct! At the init stage there is no physical placement or routing. time_design -pre_place uses estimated wire loads to compute timing slack across all analysis views. This baseline reveals fundamental timing closure risk before you invest time in placement and routing.
