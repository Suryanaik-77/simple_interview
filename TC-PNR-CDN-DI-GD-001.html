Problem Statement

GUIDED

You are about to perform the Design Initialization stage in Cadence Innovus for the first time on a real, complex design — the tile processor core. This is the very first step in the Innovus physical design flow, and getting it right is critical: every subsequent stage (floorplan, placement, CTS, routing) reads the database you save here.

The init_design.tcl script you will study and run contains 11 commands that load the MMMC configuration, read all physical LEF files, read the synthesized netlist, initialize the database, connect power/ground nets, run quality checks, and save the output database.

📄 Design Init — Step-by-Step Command Explanation

Follow each step below. Navigate to the testcase directory, run make all to launch Innovus, then source scripts/init_design.tcl to execute the flow.

  • Navigate to Testcase 1 and Launch Innovus

    Open a terminal, navigate to the testcase directory, and launch Innovus using the Makefile:

    cd ~/pd/labs/PNR-CDN-DI/TC-PNR-CDN-DI-GD-001
make all

    Innovus opens an interactive shell session. From the Innovus prompt, source the init script:

    source ../scripts/init_design.tcl

  • Load MMMC Configuration (read_mmmc)

    What it does: read_mmmc sources the MMMC configuration file, which defines all timing library sets, RC corners, delay corners, analysis views, and the active setup/hold view assignments. The Innovus MMMC model builds a hierarchy of named objects:

    Command in mmmc_config.tcl What it sets up
    create_library_set -name cw_libsGroups all HVT/LVT/SVT/SRAM .lib files for the cworst (slow, -40C) corner.
    create_rc_corner -name cwLinks the cworst QRC tech file for RC parasitic extraction at -40C.
    create_timing_conditionPairs a library set with an operating condition (voltage/temperature).
    create_delay_cornerCombines a timing condition with an RC corner — the core timing analysis unit.
    create_constraint_mode -name func_constLoads tile.sdc — clocks, I/O delays, false paths.
    create_analysis_viewPairs a delay corner with the constraint mode into a named analysis view.
    set_analysis_view -setup [...] -hold [...]Activates slow corners for setup analysis, fast corners for hold analysis.
     
    read_mmmc ../inputs/mmmc_config.tcl
    What to check:
    • 4 delay corners created: cw_dc, rcw_dc, cb_dc, rcb_dc
    • 2 setup views (ssg0p81vm40_cw, ssg0p81v125_rcw) and 2 hold views (ffg0p99vm40_cb, ffg0p99v125_rcb) active
    • Constraint mode func_const loaded with tile.sdc

  • Read Physical LEF Files (read_physical -lefs)

    What it does: Loads all physical library files into Innovus. The -lefs list must include:

    • Technology LEF (.tlef): Metal layer definitions, via types, minimum spacing rules for TSMC 28nm 9-layer stack.
    • Standard cell LEFs (HVT, LVT, SVT): Cell geometries, pin locations, routing obstructions for all standard cell variants.
    • SRAM macro LEFs: Physical boundaries and pin locations for each of the 13 SRAM macros instantiated in tile.
    read_physical -lefs {../../pdk/metal_stack/1P9M_4X2Y2R/tlef/tsmcn28_9lm4X2Y2RUTRDL.tlef \
    ../../pdk/stdcells/9T/hvt/lef/tcbn28hpcplusbwp40p140hvt.lef \
    ../../pdk/stdcells/9T/lvt/lef/tcbn28hpcplusbwp40p140lvt.lef \
    ../../pdk/stdcells/9T/svt/lef/tcbn28hpcplusbwp40p140.lef \
    ../../pdk/memory/sram/tile_mems/sram_1rw_128x78/lef/sram_1rw_128x78.lef \
    ../../pdk/memory/sram/tile_mems/sram_l1d_data_128x144/lef/sram_l1d_data_128x144.lef \
    ../../pdk/memory/sram/tile_mems/sram_l1d_tag/lef/sram_l1d_tag.lef \
    ../../pdk/memory/sram/tile_mems/sram_l1i_data_256x136/lef/sram_l1i_data_256x136.lef \
    ../../pdk/memory/sram/tile_mems/sram_l1i_tag/lef/sram_l1i_tag.lef \
    ../../pdk/memory/sram/tile_mems/sram_l2_data/lef/sram_l2_data.lef \
    ../../pdk/memory/sram/tile_mems/sram_l2_dir/lef/sram_l2_dir.lef \
    ../../pdk/memory/sram/tile_mems/sram_l2_state/lef/sram_l2_state.lef \
    ../../pdk/memory/sram/tile_mems/sram_l2_tag/lef/sram_l2_tag.lef \
    ../../pdk/memory/sram/tile_mems/sram_l15_data/lef/sram_l15_data.lef \
    ../../pdk/memory/sram/tile_mems/sram_l15_hmt/lef/sram_l15_hmt.lef \
    ../../pdk/memory/sram/tile_mems/sram_l15_tag/lef/sram_l15_tag.lef \
}
    What to check: No "cannot open" or "not found" errors. Innovus prints a summary of layers and site definitions read from the TLEF — verify the 9-layer metal stack is recognized.

  • Read the Gate-Level Netlist (read_netlist)

    What it does: Loads the post-synthesis gate-level Verilog netlist into Innovus. This describes the design as instantiated standard cells and their connections.

    read_netlist ../inputs/tile_syn.v
    What to check: No unresolved module references. Innovus reads the netlist but does not yet link cells against the LEF — that happens in init_design.

  • Declare Power and Ground Nets

    What it does: Tells Innovus which net names are the power supply (VDD) and ground (VSS) before calling init_design. This is required so the tool knows how to handle pg_pin connections during initialization.

    set_db init_power_nets {VDD}
set_db init_ground_nets {VSS}

  • Initialize the Design (init_design)

    What it does: This is the core command of the flow. init_design links the netlist against the loaded LEF/timing libraries, builds the Innovus internal design model (cell instances, nets, ports, hierarchy), and prepares the database for physical operations. After this command, the design is ready for floorplanning.

    init_design
    What to check:
    • No unresolved cell references (all standard cells and SRAM macros should resolve against the loaded LEFs)
    • Design name tile appears in the Innovus title bar after initialization
    • Total instance count printed — matches expected synthesis output

  • Connect Global Power and Ground Nets (connect_global_net)

    What it does: After init_design, the cell power pins exist in the database but are not yet connected to the global supply nets. These two commands make those connections — VDD to all pg_pins whose base name matches VDD*, and VSS to all pins named VSS.

    connect_global_net VDD -type pg_pin -pin_base_name VDD*
connect_global_net VSS -type pg_pin -pin_base_name VSS
    Why two separate commands? Standard cells in TSMC 28nm use both VDD and VDDPE (or similar multi-power-domain variants). The wildcard VDD* ensures all VDD-class pins are connected in a single call.

  • Check Timing Library Consistency

    What it does: Validates that the timing libraries loaded for each analysis view are self-consistent — no PVT mismatches between library conditions and the declared operating conditions.

    check_timing_library_consistency > ../reports/check_timing_library_consistency.rpt
    What to check: The report should show no ERROR messages. Warnings about missing min/max timing arcs for specific cell pins are acceptable — errors about library PVT mismatches must be resolved.

  • Run Pre-Place Timing Analysis (time_design -pre_place)

    What it does: Runs Innovus's built-in timing analyzer with estimated (ideal) wire delays — no physical placement or routing has occurred yet. This gives you a baseline view of critical path slack across all analysis views before any physical optimization starts.

    time_design -pre_place -report_dir ../reports/init_time_design.rpt
    What to check:
    • The report directory ../reports/init_time_design.rpt/ is created with timing summary files
    • WNS (Worst Negative Slack) values for setup corners — negative WNS is expected at this stage; assess whether the magnitude is realistic
    • No errors about unconstrained clocks — if all endpoints show as unconstrained, the SDC was not applied correctly via the constraint mode

  • Report Timing Summary (report_timing)

    What it does: Generates a detailed timing report for the most critical paths in the design. Use this to review the critical path structure and understand which logic cones are driving the worst slack.

    report_timing > ../reports/report_timing.rpt
    What to check: The top critical paths are listed with start/end points, logic depth, and slack. Verify that the clock source and period match what was defined in the SDC.

  • Save the Initialized Database (write_db -sdc)

    What it does: Saves the complete initialized Innovus database — including the linked netlist, MMMC configuration, power connectivity, and timing setup — to disk as init_design.db. The -sdc flag also writes out the SDC constraints alongside the database. This file is the input to the floorplanning stage.

    write_db -sdc ../outputs/init_design.db
    Checkpoint convention: The output filename init_design.db is the required input to the floorplan stage (read_db ../inputs/init_design.db). Using a consistent naming convention across all PnR stages is essential for handoff reliability.

✅ Success Criteria

Design initialization is complete and correct when ALL of the following are true:

  • read_mmmc completes with 4 analysis views defined and setup/hold views activated
  • read_physical -lefs loads all 17 LEF files (1 TLEF + 3 cell LEFs + 13 SRAM LEFs) without errors
  • init_design completes with 0 unresolved cell references
  • connect_global_net runs without errors for both VDD and VSS
  • check_timing_library_consistency.rpt shows 0 ERROR messages
  • time_design -pre_place report directory created — contains timing summary files
  • report_timing.rpt generated in ../reports/
  • ../outputs/init_design.db exists on disk after write_db -sdc

📚 Knowledge Assessment Quiz

1. An MMMC scenario is defined by three components. Which of the following correctly lists all three?

  • Library set, constraint mode, and analysis view
  • Setup corner, hold corner, and functional mode
  • A functional mode (constraint mode), a PVT corner (process-voltage-temperature), and an RC corner (parasitic extraction corner)
  • A timing library, a physical library, and a design netlist
Correct! In MMMC (Multi-Mode Multi-Corner) setup, a scenario is the combination of one constraint mode (which SDC is active), one PVT corner (which .lib files and operating conditions apply), and one RC corner (which parasitic extraction files — TLUPLUS or QRCTECH — are used). An analysis view then maps a constraint mode to a PVT+RC corner pair for a specific check.

2. In the RTL-to-GDSII physical design flow, which stage immediately follows standard cell placement?

  • Floorplanning — the core area must be finalized before cells are placed
  • RC extraction — parasitic values are needed before routing begins
  • Clock Tree Synthesis (CTS) — the clock network is built after placement because it requires knowledge of actual flip-flop locations
  • Physical verification — DRC/LVS runs immediately after placement to check spacing
Correct! The standard PnR flow is: Design Init → Floorplanning → Power Planning → Placement → CTS → Routing → Chip Finishing. CTS follows placement because the clock tree must be built based on the actual physical distances between all sequential elements. Running CTS before placement would produce incorrect delay estimates and poor skew control.

3. Technology LEF (TLEF) and Standard Cell LEF are both used in PnR design initialization. What critical information does the Tech LEF provide that Standard Cell LEF does NOT?

  • Pin geometry and obstruction shapes for each cell
  • Cell boundary dimensions and site definitions for row alignment
  • Metal layer definitions, routing rules (minimum width, spacing, pitch), via definitions, and design rule tables that apply to the entire technology node
  • The drive strength and power consumption of each standard cell variant
Correct! Tech LEF describes the manufacturing process layers — metal layers (name, direction, min width, spacing, pitch), via definitions, and routing rule tables. Standard Cell LEF describes individual cell abstracts — boundary, pin shapes, and obstructions. Both are needed: Tech LEF tells the router what routing resources exist; Standard Cell LEF tells it where each cell's pins are located.

4. The ITF (Interconnect Technology File) is used for parasitic extraction during PnR. What accuracy advantage does an ITF-based extraction model have over a TLEF-based model?

  • ITF-based extraction is faster, reducing overall design turnaround time
  • ITF is calibrated using field-solver data and achieves approximately ±3% accuracy, whereas TLEF-based simplified models provide only ±15% accuracy
  • TLEF-based extraction is more accurate because it includes the actual metal geometry from the process design kit
  • Both methods have equivalent accuracy; the choice depends on tool availability
Correct! The ITF is a field-solver-calibrated file that captures the actual dielectric stack, layer thicknesses, and conductor geometry of the process. It generates accurate parasitic models (TLUPLUS, QRCTECH, NXTGRD) at roughly ±3% accuracy. TLEF-based extraction uses a simplified geometric approximation, giving only about ±15% accuracy — sufficient for early-stage PnR but not for sign-off. For final tape-out, dedicated extraction tools (Calibre xRC, StarRC) use ITF-derived models.
