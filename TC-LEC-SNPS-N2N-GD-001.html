Problem Statement

GUIDED

Your task: Prove mathematically that the PNR tool did not alter the functional intent of your logic. You will use Synopsys Formality to perform a Gate-to-Gate (G2G) Logical Equivalence Check between the golden post-synthesis netlist and the revised post-PnR netlist.

💡 Note on the shell prompt: Formality's prompt changes depending on what stage you are at — fm_shell (setup), fm_shell (match), or fm_shell (verify). This tells you which phase you have just completed.

📄 G2G LEC — Step-by-Step Command Explanation

Below is a complete walkthrough of every command used in the actual G2G run using the exact paths for your design.

  • Navigate and Start the Testcase

    You have already set up the lab directory structure using the provided setup guidelines. The required Input files are now available in the testcase directory. With the lab environment ready, proceed with the following steps.

    cd ~/pd/labs/LEC-SNPS-N2N/TC-LEC-SNPS-N2N-GD-001/
make all

  • Read Technology Libraries

    What it does: Loads the Synopsys binary technology library (.db) files. These define every standard cell in the technology library — AND gates, OR gates, flip-flops, buffers, and so on. Formality needs these to understand what each gate in your netlist actually does.

    Note: If there are macros in the design, we have to give their .db files as well.
    fm_shell (setup)> read_db {../../pdk/stdcells/9T/hvt/lib/ccs/tcbn28hpcplusbwp40p140hvtssg0p81vm40c_ccs.db ../../pdk/stdcells/9T/lvt/lib/nldm/tcbn28hpcplusbwp40p140lvtssg0p81vm40c.db ../../pdk/stdcells/9T/svt/lib/nldm/tcbn28hpcplusbwp40p140ssg0p81vm40c.db}

  • Read the Reference Design (Synthesis Netlist)

    The -r flag tells Formality to load this netlist into the reference container ("r"). This is your synthesis output netlist — the "golden" design. The set_top -auto command lets Formality determine the top-level module automatically.

    fm_shell (setup)> read_verilog -r ../inputs/aes_cipher_top.v

    fm_shell (setup)> set_top -auto
    💡 Important rule: set_top must complete successfully in the current container before you start reading anything into a new container. Always read the reference fully before switching to reading the implementation.

  • Read the Implementation Design (PnR Netlist)

    The -i flag loads the netlist into the implementation container ("i"). After PnR, this is the revised design you want to verify against the reference.

    fm_shell (setup)> read_verilog -i ../inputs/aes_cipher_top_lec.v.gz

    # Link and set top for the implementation
    fm_shell (setup)> set_top -auto

  • Save Containers (Checkpoint)

    What it does: Saves the current elaborated state of each container — including all design hierarchy, library mappings, and elaboration data — into a binary snapshot file (.fsc).

    # Save reference container snapshot
    fm_shell (setup)> write_container -r ref_g2g.fsc

    # Save implementation container snapshot
    fm_shell (setup)> write_container -i impl_g2g.fsc

    Why save containers? The upcoming match command can modify what's inside the containers. Having a saved snapshot means you can restore and rerun from this point without re-reading the large netlist files.

  • Run the Match Phase

    What it does: The match command is the first major computation step. It tries to pair up corresponding compare points between the reference and implementation containers using name matching, signature analysis, and topology analysis.

    fm_shell (setup)> match

    💡 Optional but Recommended for Interactive Work

    The match command is technically optional — verify also runs matching internally. However, running match separately is strongly recommended when working interactively so you can check matching results and fix any issues before investing time in the full verification run.

  • Investigate Unmatched Points

    What it does: After the match command runs, it is common to see a few points left unmatched between your reference (synthesis) and implementation (PnR) netlists. This command allows you to explicitly list and inspect exactly what Formality could not pair up.

    fm_shell (match)> report_unmatched_points -status unread

    Analyzing the Matching Log

    If you look at the matching summary in your terminal, you will see this specific line:

    0(1) Unmatched reference(implementation) unread points

    This notation means there are 0 unread points in the Reference design, but 1 unread point in the Implementation design. When you execute the report command, the tool explicitly identifies this single culprit:

    Impl DFF        i:/WORK/aes_cipher_top/spare_cell_6_0

    Why does this happen?

    During the physical design stage of the RTL-to-GDSII flow, it is standard practice to intentionally sprinkle unconnected "spare cells" (in this case, a D-Flip-Flop) across the floorplan. These act as physical backup gates. If a functional bug is found late in the design cycle or after tape-out, engineers can perform an Engineering Change Order (ECO) by routing wires to these already-placed spare cells without having to redo the entire placement.

    Because this dummy cell was added specifically during physical implementation, it never existed in the original synthesized reference netlist. Formality is simply doing its job by pointing out this extra cell. Since this is a known, expected addition to the layout, it is completely safe to ignore.

  • Run Verification

    What it does: This is the core formal proof step. For each matched pair of compare points, the Formality tool deploys mathematical solvers to prove whether the logic cones are equivalent or not.

    verify

    Four possible outcomes for each compare point:

    StatusMeaning
    ✅ PassingLogic cones are functionally equivalent
    ❌ FailingLogic cones are NOT equivalent — real logic bug
    ⚠️ Aborted/InconclusiveSolver timed out — too complex to prove
    🔍 Not ComparedUnmatched points (e.g., a cell swept/optimized away)

    Analyzing the Verification Log

    Looking at the terminal output, the most critical line is Verification SUCCEEDED. The detailed table at the end of the log breaks down exactly what passed:

      129 Ports: All primary input/output boundary logic matches.

      530 DFFs: All internal state elements (D-Flip-Flops) match.

      Total: All 659 compared points passed, with exactly 0 Failing points.

    This confirms that the physical layout (PnR) perfectly aligns with the original synthesis intent. No functional logic was broken during placement and routing.

  • 💾 The save_session Command

    After running verify, you can save the entire Formality session state — including all match results, verification results, and design data — into a single session file.

    # Save the session after verification
    save_session -replace g2g_session.fss

    # Restore the session in a new Formality run
    restore_session g2g_session.fss

    When is this useful?

      Debugging failures later: If your verification fails, you can save the session and restore it in a separate Formality run to debug the failing points at your convenience — without re-running the entire verification (which can take hours for large designs)

      Collaborative debugging: You can share the session file with a senior engineer so they can inspect the exact state of your failing run

      Incremental work: If you only fixed a few compare points, you can restore the session and continue verifying without starting over

    ⚠️ Important limitation: Session files (.fss) are NOT portable across Formality software versions. A session saved in Formality 2022.03 cannot be restored in Formality 2023.06. Container files (.fsc) from write_container are portable. Plan accordingly.

  • Exit Current Shell

    Before proceeding, ensure you have exited active tool shells. Type the following command to return to your main terminal.

    exit

✅ Validation & Verification

Use the automated verification command to validate your results.

make verify

📄 Complete G2G Script

# ============================================================
# G2G LEC Script — Gate-Level Netlist to PnR Netlist
# Design: aes_cipher_top
# Tool: Synopsys Formality
# ============================================================
# Step 1: Load technology libraries (shared to both containers)
read_db {../../pdk/stdcells/9T/hvt/lib/ccs/tcbn28hpcplusbwp40p140hvtssg0p81vm40c_ccs.db ../../pdk/stdcells/9T/lvt/lib/nldm/tcbn28hpcplusbwp40p140lvtssg0p81vm40c.db ../../pdk/stdcells/9T/svt/lib/nldm/tcbn28hpcplusbwp40p140ssg0p81vm40c.db}

# Step 2: Read reference design (post-synthesis gate-level netlist)
read_verilog -r ../inputs/aes_cipher_top.v
set_top -auto

# Step 3: Read implementation design (post-PnR netlist)
read_verilog -i ../inputs/aes_cipher_top_lec.v.gz
set_top -auto

# Step 4: Save container snapshots (checkpoint before match)
write_container -r ref_g2g.fsc
write_container -i impl_g2g.fsc

# Step 5: Match compare points (applies SVF, then name/sig matching)
match

# Step 6: Check unmatched logic mapping
report_unmatched_points -status unread

# Step 7: Verify equivalence
verify

# Step 8 (Optional): Save session for later debugging
save_session -replace g2g_session.fss

# Step 9: Exit the tool
exit

📝 Knowledge Assessment Quiz

1. What is the purpose of running write_container before the match command?

  • To export the netlist in a different file format for reporting
  • It is mandatory — Formality will not run match without a saved container
  • To save a snapshot of the elaborated design state before SVF processing modifies the containers, enabling you to restore and rerun without re-reading large netlist files
  • To lock the container so no other Formality process can modify it
Correct! SVF processing during the match phase can modify the contents of the containers. Saving containers beforehand with write_container gives you a restore point — you can reload with read_container and rerun match/verify without the expensive step of re-reading and re-elaborating the netlist files. This saves significant time on large designs.

2. What is the difference between a container file (.fsc) and a session file (.fss)?

  • There is no real difference — both store the same information in different formats
  • A container (.fsc) stores the elaborated design state and is portable across Formality versions; a session (.fss) stores the complete verification state (including results) but is NOT portable across versions
  • A container is only for the reference design; a session stores both reference and implementation
  • Session files are larger and slower to save than container files
Correct! Container files (.fsc from write_container) are snapshots of the elaborated design state — portable across Formality versions, good for sharing and archiving. Session files (.fss from save_session) capture the full verification state including match and verify results — ideal for later debugging — but are version-specific and cannot be moved between Formality releases.
