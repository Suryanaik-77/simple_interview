📖 Theory and Background

What is DMSA and Why Signoff ECO Matters

After place-and-route (PnR) is complete, the design must pass signoff-quality static timing analysis across all process/voltage/temperature (PVT) corners and operating modes. Inevitably, some timing paths will have negative slack or design rule violations that the PnR tool could not fully resolve. Re-running the entire PnR flow to fix a handful of paths is prohibitively expensive in both runtime and risk of disrupting already-clean paths.

This is where Distributed Multi-Scenario Analysis (DMSA) comes in. DMSA allows Tempus to analyze timing across multiple scenarios (corner/mode combinations) simultaneously and apply targeted ECO fixes that are valid across all scenarios. Instead of fixing one corner and breaking another, DMSA ensures that every change improves — or at minimum does not degrade — timing across the entire scenario space.

Signoff ECO is the final gate-keeping step before tapeout. It takes the signoff-quality timing database produced by Tempus STA (Lab 28) and applies surgical, incremental changes — cell resizing, buffer insertion, cell relocation — to close any remaining violations. The result is an ECO script that can be back-annotated into Innovus to update the physical design.

The ECO Optimization Flow

The signoff ECO flow in Tempus follows a well-defined sequence of stages. Understanding each stage and why they occur in this order is essential for producing clean results.

  • Read Timing Session Database: The flow begins by loading the timing database created during Tempus STA (Lab 28). This database contains the fully extracted and annotated timing graph for the design across all corners and modes.
  • Define Path Groups: Before optimization, you define path groups that tell Tempus which sets of timing paths to focus on. This allows targeted optimization of critical paths without wasting effort on paths that already have sufficient margin.
  • Fix Setup Violations: Setup violations are addressed first because setup fixes (upsizing cells, adding buffers) can introduce new hold violations but rarely create new DRV issues. Fixing setup first establishes the correct cell sizing baseline.
  • Fix Hold Violations: Hold fixes (inserting delay buffers) are applied after setup fixes are stable. Hold buffers add delay to short paths without affecting the critical setup paths that were just optimized.
  • Fix DRV Violations: Design rule violations (max_transition, max_capacitance, max_fanout) are fixed last. DRV fixes typically involve buffer insertion or cell resizing that can be done without disturbing the setup/hold closure achieved in the previous steps.
  • Generate ECO Script: Finally, Tempus writes out a TCL-based ECO script that captures all the incremental changes. This script is applied in Innovus to update the placed-and-routed design.

Path Groups: Targeted Optimization

In a real design with millions of timing paths, optimizing every path simultaneously is neither practical nor desirable. Path groups allow engineers to partition the design's timing paths into logical categories and apply different optimization strategies to each group.

Common path group strategies include grouping by clock domain, by hierarchical block, or by criticality. For example, you might create a path group for all paths in the most timing-critical clock domain and another for I/O paths. Tempus can then prioritize effort on the groups with the worst violations while leaving well-timed groups untouched.

Targeted optimization through path groups also reduces runtime significantly. Rather than analyzing and attempting changes on the entire design, the optimizer focuses its iterations on the paths most likely to benefit from ECO changes.

Setup vs Hold vs DRV Fixing Order

The order in which violations are fixed is not arbitrary — it reflects the physical dependencies between different types of timing changes.

Why Setup First: Setup fixes involve upsizing cells to reduce delay on critical paths or inserting buffers to break long interconnects. These changes alter cell sizes and drive strengths throughout the design. If hold were fixed first, the subsequent setup changes could undo hold fixes by changing the delay characteristics of nearby paths.
Why Hold Second: Hold fixes primarily involve inserting small delay buffers on short paths to ensure data does not arrive too early at the capturing flip-flop. Since these buffers are added to non-critical (fast) paths, they do not interfere with the setup-critical paths that were just optimized. This ordering ensures setup closure is preserved while hold is being fixed.
Why DRV Last: DRV fixes address electrical rule violations (excessive transition time, capacitance, or fanout) by inserting buffers or resizing drivers. These are localized changes that rarely affect the timing slack of distant paths. By fixing DRV last, you avoid a situation where a DRV buffer insertion creates a new setup or hold violation that would require re-optimization.

ECO Back-Annotation into Innovus

The final output of the Tempus DMSA ECO flow is a TCL script (commonly named eco.tcl) that contains all the cell changes — insertions, deletions, resizings, and reconnections — needed to close timing. This script is written in a format that Innovus can directly source.

Back-annotation is the process of applying this ECO script in Innovus so that the physical design (DEF, netlist) reflects the changes Tempus determined were necessary. After sourcing the ECO script, Innovus performs incremental placement of any newly inserted cells and incremental routing of any changed nets. The design can then be re-extracted and re-timed to confirm that all violations are resolved.

This iterative loop — Tempus ECO followed by Innovus back-annotation followed by re-extraction — may need to run more than once for designs with tight margins. However, each iteration should show significant convergence, with the number of remaining violations decreasing rapidly.

📝 Knowledge Assessment Quiz

Question 1: What is the primary advantage of DMSA over single-corner ECO optimization?

  • A. DMSA runs faster because it analyzes fewer paths
  • B. DMSA only requires one PVT corner to produce valid results
  • C. DMSA ensures ECO fixes are valid across all corners and modes simultaneously
  • D. DMSA eliminates the need for back-annotation in Innovus

Correct! DMSA analyzes all PVT corners and operating modes at the same time, ensuring that a fix applied for one scenario does not introduce new violations in another scenario. This multi-scenario awareness is the key benefit over single-corner optimization.

Question 2: Why are setup violations fixed before hold violations in the ECO flow?

  • A. Setup violations are always more numerous than hold violations
  • B. Setup fixes (cell resizing, buffering) can change delay characteristics that affect hold paths, so hold must be fixed after setup is stable
  • C. Hold violations cannot be detected until setup violations are resolved
  • D. The tool requires setup to be clean before it can read hold timing data

Correct! Setup fixes involve cell upsizing and buffer insertion that change delay characteristics across the design. If hold were fixed first, subsequent setup changes could undo those hold fixes. Fixing setup first establishes a stable baseline for hold optimization.

Question 3: What is the purpose of defining path groups before running ECO optimization?

  • A. Path groups are required by Tempus and the tool will not run without them
  • B. Path groups automatically fix all violations within the group
  • C. Path groups convert setup violations into hold violations for easier fixing
  • D. Path groups focus optimization effort on specific sets of timing paths, improving both effectiveness and runtime

Correct! Path groups allow engineers to partition timing paths by clock domain, hierarchy, or criticality. This enables the optimizer to concentrate on the most critical paths rather than spending effort on paths that already meet timing, significantly improving both optimization quality and runtime.

Question 4: What happens to the ECO script after Tempus generates it?

  • A. It is sourced in Innovus to apply incremental placement and routing changes to the physical design
  • B. It is sent directly to the foundry as part of the GDSII package
  • C. It replaces the original netlist and no further steps are needed
  • D. It is used to re-run the entire place-and-route flow from scratch

Correct! The ECO script is back-annotated into Innovus, where incremental placement and routing are performed to physically realize the changes. The design is then re-extracted and re-timed to confirm all violations are resolved.

Prerequisite: Complete Lab 28 (Tempus Signoff STA) First

This lab cannot be started until you have completed Lab 28 (lab-28-signoff-sta-tempus) and run make run in its testcase1. The timing session database generated in Lab 28 is the direct input to this lab.

How the Timing Database Flows from Lab 28 to This Lab

When you run make run in Lab 28 testcase1, Tempus performs multi-corner multi-mode STA and saves the complete timing state into a single session database: tile_session_timing.db. This database contains all 4 analysis views (PVT corners) in one file.

After make run completes in Lab 28, this database is automatically copied to this lab's inputs/ directory. No manual file copying is needed.

What the Session Database Captures

The tile_session_timing.db is a self-contained snapshot of the entire timing environment. It captures:

  • All loaded timing libraries for every PVT corner
  • Annotated SPEF parasitics for each RC extraction corner
  • Propagated clock trees and clock definitions
  • Signal integrity (SI) crosstalk settings
  • Fully computed delays, slacks, and violations across all views

Because the database captures everything, a single read_db command in this lab restores the complete multi-corner timing environment — no need to re-read LEFs, netlists, MMMC configurations, or SPEF files.

Why DMSA ECO Is Critical

After place-and-route and signoff STA, there are always residual timing violations that the PnR tool could not fully resolve. DMSA ECO fixes them in-place without going back to PnR, generating lightweight ECO scripts that can be applied in Innovus. This is the final step before tapeout signoff.

DMSA mode in Tempus reads the session database and runs opt_signoff, which automatically fixes setup, hold, and DRV violations across all corners simultaneously. Every fix is validated against all scenarios at once, so you never fix one corner at the expense of another.

This is where you close the loop. Every violation you saw in Lab 28 gets fixed here. The ECO script you generate is what goes back to the layout tool for the final tapeout-ready design. After this lab, the design is ready for the foundry.
