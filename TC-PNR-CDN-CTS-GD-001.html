Problem Statement

GUIDED

You will perform Clock Tree Synthesis (CTS) for the aes_cipher_top design in Cadence Innovus. Starting from the placed database (placement.db), you will configure CTS cells and parameters, define NDR routing rules for top/trunk/leaf clock segments, run ccopt_design, apply post-CTS timing constraints, run a comprehensive suite of clock and timing reports, and save the CTS database.

📄 CTS — Step-by-Step Command Explanation

  • Load the Placed Database

    cd ~/pd/labs/PNR-CDN-CTS/TC-PNR-CDN-CTS-GD-001
make all

    Source the CTS script from the Innovus prompt:

    source ../scripts/cts.tcl

    read_db restores the placed design state, ready for CTS:

    read_db ../inputs/placement.db

  • Set CTS Cell Library

    What it does: Tells Innovus which cell variants to use when inserting clock buffers and inverters. All cells are LVT (Low Voltage Threshold) for fast switching speed. Multiple drive strengths are listed so the tool can choose the right size based on fanout and transition time requirements.

    set_db opt_new_inst_prefix CTS_PLACE
set_db cts_buffer_cells { CKBD4BWP40P140LVT CKBD6BWP40P140LVT CKBD12BWP40P140LVT CKBD8BWP40P140LVT CKBD16BWP40P140LVT}
set_db cts_inverter_cells {CKND4BWP40P140LVT CKND6BWP40P140LVT CKND8BWP40P140LVT CKND12BWP40P140LVT CKND16BWP40P140LVT}
set_db cts_logic_cells {*CKMUX* *CKAN*}
    Cell naming convention: CKBD = Clock Buffer, CKND = Clock Inverter (NOT gate), number = drive strength index, BWP40P140 = TSMC 28nm 40-track 9T cell, LVT = Low Voltage Threshold. CKMUX / CKAN are clock mux and AND cells used for gated clocks.

  • Set CTS Optimization Parameters

    Configure the key CTS targets that guide ccopt_design optimization:

    Parameter Description
    cts_target_skew 0.1Target clock skew of 0.1 ns (100 ps) across all clock endpoints.
    cts_target_max_transition_time [expr Tclk_period/6]Max rise/fall time on clock nets — Tclk/6 ensures fast, clean clock edges.
    timing_analysis_cppr bothEnable CPPR (Common Path Pessimism Removal) for both setup and hold — removes excess pessimism from shared clock path segments in timing analysis.
    timing_analysis_type ocvUse On-Chip Variation (OCV) timing model — applies separate early/late derates to data and clock paths.
    cts_max_fanout 16Maximum loads on any single clock buffer — prevents excessive transition degradation at high fanout nodes.
    cts_cell_halo_sites 88-site exclusion zone around each inserted CTS cell — prevents DRC-spacing violations with nearby placed cells.
    cts_cell_halo_rows 11-row vertical halo around CTS cells.
     
    set_db cts_target_skew 0.1
set_db cts_target_max_transition_time [expr Tclk_period/6]
set_db timing_analysis_cppr both
set_db timing_analysis_type ocv
set_db cts_max_fanout 16
set_db cts_cell_halo_sites 8
set_db cts_cell_halo_rows 1

  • Create Clock Route Rules and Route Types

    What it does: Defines NDR (Non-Default Routing Rule) rules for each clock tree segment level, then creates named route types that assign preferred routing layers to each segment.

    # NDR rules: wider wire and increased spacing per segment level
create_route_rule -name cts_2s2w_top   -spacing_multiplier {M7:M6 2} -width_multiplier {M7:M6 2}
create_route_rule -name cts_2s2w_trunk -spacing_multiplier {M7:M4 2} -width_multiplier {M7:M4 2}
create_route_rule -name cts_2s1w_leaf  -spacing_multiplier {M5:M3 2}

# Route types: preferred layer ranges per segment
create_route_type -name top   -bottom_preferred_layer M6 -top_preferred_layer M7
create_route_type -name trunk -bottom_preferred_layer M7 -top_preferred_layer M4
create_route_type -name leaf  -bottom_preferred_layer M3 -top_preferred_layer M5

# Assign route types to CTS segments
set_db cts_route_type_top   top
set_db cts_route_type_trunk trunk
set_db cts_route_type_leaf  leaf
    Why 2x spacing on clock nets? Clock nets switch on every cycle and carry large currents. Wider spacing reduces capacitive coupling to adjacent signal nets, preventing signal integrity issues (glitches) that could cause false clock edges.

  • Clear Dont-Touch and Generate Clock Tree Spec

    Remove any dont-touch constraints on nets that could block clock buffer insertion, then generate the clock tree specification file:

    set_db [get_db [get_nets -hierarchical *] -if { .is_dont_touch == true}] .dont_touch false
create_clock_tree_spec -out_file cts.spec
source cts.spec
    create_clock_tree_spec analyzes the clock network and generates a spec file (cts.spec) describing the clock tree structure, clock domains, and optimization targets. Sourcing it activates those specifications before ccopt_design runs.

  • Run Clock Tree Synthesis (ccopt_design)

    What it does: Concurrent Clock and Data Optimization builds the clock tree by inserting LVT clock buffers throughout the hierarchy, optimizes data path timing simultaneously, and meets the skew, fanout, and transition time targets set in the previous steps. This is the most computationally intensive step in the CTS stage.

    ccopt_design
    What to check after completion:
    • Total CTS buffers inserted reported in the Innovus log
    • Achieved skew should be ≤ target skew (0.1 ns)
    • No DRC violations from CTS cell insertions — halo parameters prevent this

  • Apply Post-CTS Clock Uncertainty

    Update clock uncertainty to post-CTS values. These are tighter than pre-CTS values because the actual clock tree skew is now known and controlled:

    set_interactive_constraint_modes func_const
set_clock_uncertainty -setup 0.255 [get_clocks clk]
set_clock_uncertainty -hold  0.05  [get_clocks clk]
set_interactive_constraint_modes {}
    The set_interactive_constraint_modes calls bracket the uncertainty commands to apply them to the correct constraint mode and then exit interactive mode cleanly.

  • Run Post-CTS Checks and Timing Analysis

    check_place > ../reports/check_place.rpt
    What to check: No illegal placements or overlaps after CTS buffer insertion. 
    check_floorplan -report_density > ../reports/utilization.rpt
    What to check: Cell density — CTS adds buffers which increases utilization. Verify density is still within acceptable range (<80% typical). 
    create_basic_path_groups -expanded
time_design -expanded_views -post_cts > ../reports/time_design.setup.rpt
time_design -expanded_views -post_cts -hold > ../reports/time_design.hold.rpt
    What to check: WNS and TNS for setup (should be close to 0 or positive after CTS optimization). Hold WNS — hold violations after CTS are common and must be fixed during routing via buffer insertion.

  • Run All Timing and Clock Reports

    report_timing_summary > ../reports/report_timing_summary.setup.rpt
report_timing_summary -early > ../reports/report_timing_summary.hold.rpt
report_skew_groups -summary -out_file ../reports/report_skew_groups.rpt
report_clock_timing -type skew    > ../reports/report_clock_timing.skew.rpt
report_clock_timing -type latency > ../reports/report_clock_timing.latency.rpt
report_clock_timing -type summary > ../reports/report_clock_timing.summary.rpt
report_congestion -hotspot  > ../reports/report_congestion.hotspot.rpt
report_congestion -overflow > ../reports/report_congestion.overflow.rpt
report_timing -group reg2reg -max_paths 10 > ../reports/report_timing.reg2reg.setup.rpt
report_timing -group reg2reg -max_paths 10 -early > ../reports/report_timing.reg2reg.hold.rpt
report_timing -group in2reg  -max_paths 5  > ../reports/report_timing.in2reg.setup.rpt
report_timing -group in2reg  -max_paths 5  -early > ../reports/report_timing.in2reg.hold.rpt
report_timing -group reg2out -max_paths 5  > ../reports/report_timing.reg2out.setup.rpt
report_timing -group reg2out -max_paths 5  -early > ../reports/report_timing.reg2out.hold.rpt
    Key reports to review:
    • report_skew_groups.rpt — total skew by clock domain; look for any domain exceeding the 0.1 ns target
    • report_clock_timing.skew.rpt — per-path skew breakdown for the worst contributors
    • report_clock_timing.latency.rpt — max clock insertion delay (latency) from source to each endpoint
    • report_timing.reg2reg.setup.rpt — top 10 setup-critical register-to-register paths

  • Save the CTS Database

    write_db -sdc ../outputs/cts.db
    The routing stage reads this as read_db ../inputs/cts.db (or design-specific variant). The SDC written by -sdc includes the post-CTS clock uncertainty values.

✅ Success Criteria

CTS is complete when ALL of the following are true:

  • ccopt_design completes with achieved clock skew ≤ 0.1 ns target
  • check_place.rpt — no illegal placements after CTS buffer insertion
  • All 14 timing and clock report files created in ../reports/
  • report_skew_groups.rpt shows all clock domains within skew target
  • ../outputs/cts.db exists on disk

📚 Knowledge Assessment Quiz

1. CTS has four main goals. Which option correctly lists all four?

  • Minimize cell count, minimize power, maximize frequency, and minimize routing congestion
  • Minimize setup WNS, minimize hold WNS, control transition time, and reduce clock power
  • Minimize clock skew, minimize clock insertion delay (latency), meet design rule constraints (max transition, max capacitance), and build an AOCV-aware clock tree that is robust to on-chip variation
  • Equalize all path delays, eliminate hold violations, maximize clock frequency, and reduce cell count
Correct! The four CTS goals are: (1) Minimize Skew — control the difference in clock arrival time between flip-flops so setup and hold margins are preserved; (2) Minimize Latency — reduce insertion delay (clock source to flip-flop) to lower power and improve timing margins; (3) Meet DRVs — keep clock nets within max transition and max capacitance limits for reliable switching; (4) AOCV Awareness — design the tree to maintain skew balance even under process/voltage/temperature variation across the die. All four must be satisfied simultaneously, making CTS one of the most complex optimization steps in the PnR flow.

2. Clock Tree Synthesis is always performed after placement is complete. What would happen if CTS were run before placement?

  • Nothing — CTS results are independent of cell placement because it only inserts buffers, not data path cells
  • CTS before placement is actually preferred because it allows the placer to optimize data cells around the pre-built clock tree
  • CTS before placement would produce incorrect results because physical distances between flip-flops are unknown. Wire delays, buffer insertion points, and tree topology would all be based on wrong assumptions. After placement moves cells to their real locations, the pre-built clock tree would have incorrect delays and skew
  • CTS before placement is valid but slower, because the placer must preserve the pre-built tree topology as a fixed constraint
Correct! The clock tree's quality depends entirely on the actual physical locations of every sink (flip-flop clock input). Wire RC delays are proportional to length; buffer sizing and insertion points must match real wire loads. Before placement, cell locations are unknown or estimated. Running CTS on estimated positions would build a tree optimized for the wrong layout. After placement moves cells to their legalized positions, the actual wire lengths and loads would differ significantly from the tree assumptions, producing incorrect skew and latency. CTS must always see finalized placement to produce a meaningful result.

3. Dedicated clock cells (CK* cells) are preferred over regular buffers for the clock tree. What specific problem do regular buffers cause in the clock path that CK* cells avoid?

  • Regular buffers consume too much power because they switch at full VDD rather than a reduced voltage like clock cells do
  • Regular buffers cannot meet the max fanout rules required for clock distribution in 28nm technology
  • Regular buffers have unequal PMOS and NMOS sizing, causing unequal rise and fall delays. This imbalance accumulates at each buffer stage, progressively distorting the clock duty cycle (the ratio of high-to-low time per cycle). CK* cells are designed with balanced PMOS/NMOS to keep rise and fall delays equal
  • Regular buffers have higher input capacitance, making them unsuitable as clock sinks when their outputs drive the clock pins of flip-flops
Correct! In standard CMOS processes, PMOS mobility is roughly 2–2.5× lower than NMOS, so PMOS transistors must be made wider for equal drive strength. Regular logic cells are not always optimized for exactly equal rise/fall drive strength — their PMOS may be slightly over- or under-sized relative to the NMOS. This causes a small asymmetry (e.g., rise = 80 ps, fall = 70 ps). Across 10 buffer stages, this 10 ps asymmetry accumulates to 100 ps of duty cycle distortion — the clock high time and low time become measurably different. Dedicated CK* clock cells are specifically characterized and sized for matched rise/fall, minimizing duty cycle distortion across any number of buffer stages.

4. What is the difference between local skew and global skew, and which is more critical for timing closure?

  • Local skew is measured within a single clock domain; global skew spans multiple clock domains. Both are equally critical
  • Global skew is always larger than local skew, making it more critical because it bounds the maximum achievable clock frequency
  • Global skew is the difference between the earliest and latest clock arrivals across the entire design. Local skew is the difference between the specific launch and capture flip-flops on a particular timing path. Local skew is more critical because it directly determines setup and hold slack on each path — two flip-flops can have very different absolute latencies (high global skew) but if their local skew is small, the paths between them are not affected
  • Local skew refers to within-cell clock distribution; global skew refers to on-chip variation (OCV) across the die. Local skew is not measured during CTS
Correct! Timing analysis only evaluates the clock relationship between the launch and capture flip-flops of each path. If flip-flop A has 0.8 ns latency and flip-flop B has 1.5 ns latency (global skew = 0.7 ns), but on a path from A to B the local skew is 1.5 − 0.8 = 0.7 ns, that skew reduces the effective clock period seen by that path. However, a path from A to another flip-flop C at 0.85 ns latency has local skew = 0.85 − 0.8 = 0.05 ns — very manageable. CTS optimizes for local skew between communicating flip-flops to maximize timing margin on actual timing paths, not global skew which is a less useful single-number metric.
