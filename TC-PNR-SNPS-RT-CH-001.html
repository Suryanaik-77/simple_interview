📚 Knowledge Assessment Quiz

1. During routing of iguana_soc, check_routes shows 0 antenna violations on M1–M5 but 112 antenna violations on M6. The script has hop_layers_to_fix_antenna true and insert_diodes_during_routing true. What is the most likely explanation?

  • M6 is a thick global routing layer that is exempt from antenna rules — the violations reported are false positives from an incorrect antenna_rules.tcl.
  • Diode cells can only be placed on M1–M4 layers; M6 wires are too long to reach a diode insertion point during detail routing.
  • M6 is the topmost routing layer available for hopping — wires on M6 cannot hop higher, and if congestion prevented diode insertion, there is no fallback fix. The antenna_rules.tcl likely sets a tighter limit for M6, and the router ran out of fix options for those segments.
  • The route.detail.diode_libcell_names setting applies only to M1–M3 layers; M6 antenna fixes require a separate route.detail.m6_diode_libcell_names option.
Correct! Layer hopping works by moving the wire up to a higher metal layer to reset the antenna ratio. M6, being the topmost available routing layer in this stack, has nowhere higher to hop to. If the router cannot insert a diode (due to congestion at that wire location), and cannot hop, the antenna violation is left unresolved. The solution is to reduce M6 routing congestion, allow the router more space for diode cells near M6 wire ends, or manually add diodes in ECO mode post-route.

2. After fixing the script and running route_auto successfully, you notice the route.report_timing.max.rpt shows WNS = -0.38 ns across setup scenarios. Is this expected at this stage, and what happens next?

  • This is a sign-off failure — a WNS of -0.38 ns after routing means the design will never close timing and must be re-synthesized.
  • This indicates that SI analysis was not properly enabled — the coupling-induced setup violations caused this WNS and will be fixed when SI is activated.
  • A negative WNS after route_auto is expected and normal — the design has real routing parasitics for the first time and pre-route estimates may have been optimistic. The tightened clock uncertainty (0.204 ns) and route_opt are specifically designed to recover this margin.
  • This means the CTS stage was incorrect — the clock tree was not properly balanced, causing 0.38 ns of additional skew that must be corrected by re-running CTS before proceeding.
Correct! It is completely normal to have negative WNS in the route block before route_opt. Actual routing parasitics are extracted for the first time and may be worse than the estimates used during placement. Additionally, the clock uncertainty at this point still reflects the CTS value (0.255 ns). Once you tighten uncertainty to 0.204 ns and run route_opt, the tool has both a more accurate timing picture and a larger optimization window — recovering most or all of the apparent violation.

3. You have two designs: Design A uses only timing-driven routing (route.global.timing_driven true only) while Design B uses both timing-driven and crosstalk-driven routing (route.global.timing_driven true and route.global.crosstalk_driven true). After routing, SI analysis is enabled for timing sign-off on both. Which statement best describes the expected outcome?

  • Design A and B will show identical timing results because SI effects are always captured during sign-off analysis regardless of routing decisions.
  • Design B is more likely to pass SI-aware timing sign-off because the router actively separated aggressor-victim pairs during routing. Design A may show new setup or hold violations after SI analysis that were not visible pre-route, because the router placed coupling-sensitive nets on adjacent tracks without awareness of the SI impact.
  • Design A will have better setup timing because timing-driven routing alone produces shorter wires — crosstalk-driven routing increases wire length to add spacing, which adds resistance and worsens setup.
  • There is no difference between the two because ICC2's detail router always adds minimum spacing between all nets regardless of crosstalk settings.
Correct! Crosstalk-driven routing instructs the router to actively avoid placing aggressor-victim pairs on adjacent tracks or parallel segments. Without this setting, the router may legally (from a DRC standpoint) place two coupled nets on adjacent tracks. When SI analysis is applied at sign-off, these coupled nets generate large delta delays that can convert paths from passing to failing. Enabling crosstalk-driven routing at global, track, and detail stages prevents this class of SI violations from being introduced during wire placement.

4. After route_opt on iguana_soc, check_legality -verbose reports 3 illegal placements. How did these arise and what is the correct response?

  • Illegal placements after route_opt are always caused by the antenna diode cells inserted during route_auto — they must be manually removed and re-inserted by hand to legal positions.
  • route_opt is not permitted to move cells — illegal placements after route_opt indicate a tool bug that must be reported to Synopsys support.
  • route_opt performs ECO moves (cell resizing, buffer insertion, cell relocation) to fix timing violations. In rare cases, these moves can push a cell to a fractional site position or cause overlap with a nearby macro. The fix is to run legalize_placement -incremental after route_opt to resolve these violations without disturbing the routing.
  • Illegal placements are acceptable post-route and are automatically corrected during the chip finish stage — no action is needed before proceeding.
Correct! When route_opt moves or resizes cells to fix timing, it uses ECO placement which does not always re-legalize every affected cell. A small number of illegal placements (overlaps, off-site cells) can result. The correct fix is legalize_placement -incremental, which legalizes only the affected cells with minimal displacement — preserving the routing integrity. Running a full placement from scratch would destroy the routing. Illegal placements must be resolved before chip finish because they lead to DRC violations in the layout.
