Challenge

The AES cipher top design has been synthesized using Synopsys Design Compiler targeting TSMC 28nm. The synthesis run inserted clock-gating cells and produced an SVF file recording all structural transformations.

Your task is to run a complete Formality LEC session by typing each command interactively at the fm_shell> prompt. Launch the tool with make run and drive the verification flow yourself until you achieve Verification SUCCEEDED and all six equivalence report files are generated.

Apply everything you practiced in TC-GD-001. Pay particular attention to the clock-gate attributes — all three must be set, including the one that caused the guided testcase to fail initially.

Hints

Hint 1 — Which global settings are required at the top of the script

The design uses clock gating. You need four global settings, not two or three. One of them is the attribute that was missing and caused TC-GD-001 to fail initially. All four must appear before any other command:

  • set synopsys_auto_setup
  • set verification_clock_gate_reverse_gating
  • set verification_clock_gate_hold_mode
  • set verification_clock_gate_edge_analysis
Hint 2 — Command order and the top module for the implementation side

The required command sequence is:

  1. 4 global set attributes
  2. set_svf ../inputs/default.svf — before any read_verilog
  3. read_verilog -r { 5 RTL files }
  4. set_top aes_cipher_top
  5. read_db { 3 .db files }
  6. read_verilog -i ../inputs/aes_cipher_top.v
  7. set_top -auto — lets Formality infer the implementation top
  8. match then verify
  9. Six report_* commands to ../reports/
  10. exit
Hint 3 — Report commands

The six report commands are:

report_passing_points   > ../reports/report_passing_points.rpt
report_verify_points    > ../reports/report_verify_points.rpt
report_failing_points   > ../reports/report_failing_points.rpt
report_matched_points   > ../reports/report_matched_points.rpt
report_unmatched_points > ../reports/report_unmatched_points.rpt
report_black_boxes      > ../reports/report_black_boxes.rpt

Paths are relative to work/, which is the directory the Makefile changes into before invoking fm_shell.

Knowledge Assessment

Select the best answer. Wrong choices clear automatically so you can keep trying. The explanation appears once you find the correct answer.

1. Formality reports "Verification FAILED" with 4 failing points after you write your script. You confirm the SVF is loaded correctly and the libraries are right. What is the most likely cause?

  • The RTL source files are not in the correct order inside the read_verilog -r command.
  • The set_top command names a module that does not exist in the reference container.
  • One or more of the three clock-gate verification attributes is missing or set to the wrong value. The failing points are clock-gated registers whose enable polarity is being modeled incorrectly.
  • The exit command at the end of the script is preventing the reports from being written.
✓ Correct! When the SVF and libraries are correct and specific registers fail, the clock-gate attribute configuration is the first thing to check. Each of the three attributes addresses a different aspect of how clock-gated registers are modeled. A missing or wrong attribute produces false failures on those registers.

2. You run Formality on two different synthesis runs of the same RTL: one with clock gating enabled and one without. For the run without clock gating, do you still need to set verification_clock_gate_reverse_gating true?

  • Yes — the attribute must always be set regardless of whether clock gating was used, because it is part of the recommended synopsys_auto_setup bundle.
  • Not strictly required — if no clock-gate cells are present in the netlist, the attribute has no effect. However, leaving all three attributes set is harmless and is the standard practice to avoid issues if a later run does include clock gating.
  • No — setting it on a non-gated design causes Formality to incorrectly model non-gated flip-flops and produces false failures.
  • Yes — it is required because Formality always searches for clock-gate cells whether or not synthesis inserted any.
✓ Correct! The clock-gate attributes only affect the modeling of clock-gate cells found in the netlist. If there are none, the attributes are silently irrelevant. Standard practice is to include all three unconditionally so the script is reusable across designs regardless of power optimization settings.

3. Formality needs read_db to load technology libraries for the AES netlist. If you omit read_db entirely, what is the most likely outcome?

  • Formality aborts immediately with a fatal error because it cannot parse Verilog without knowing cell names.
  • Verification SUCCEEDED with all points passing — Formality infers cell functions from the cell names.
  • All instantiated standard cells become black boxes. Formality cannot evaluate the Boolean function of any gate, so most compare points cannot be proven and the run produces a large number of unmatched or aborted points.
  • Only HVT cells become black boxes; SVT and LVT cells are recognized from a built-in library.
✓ Correct! Without read_db, every instantiated gate is an opaque black box to Formality. The tool cannot determine what logic function the cell implements. This means it cannot build the combinational cones needed for equivalence checking, resulting in most compare points being unverifiable.

4. After a successful LEC run, a DFT engineer modifies the netlist to insert scan chains. Does the original formality.tcl and SVF from synthesis still apply for verifying the scan-inserted netlist against the original RTL?

  • Yes — the SVF covers all netlist transformations including DFT insertion, so no changes are needed.
  • Yes — since RTL-to-Gate LEC proved equivalence at synthesis, the scan-modified netlist is automatically trusted.
  • No — scan insertion modifies the netlist. A new LEC run is needed. The comparison type should be gate-to-gate (pre-scan vs. post-scan netlist), and a new SVF from the DFT tool (if available) or structural awareness of scan modifications is required. The original synthesis SVF does not cover DFT transformations.
  • No — scan-inserted netlists cannot be verified with Formality at all; simulation is required instead.
✓ Correct! Each netlist transformation creates a new LEC checkpoint. The synthesis SVF only captures synthesis transformations. After DFT insertion, you run gate-to-gate LEC (pre-DFT vs. post-DFT netlist) with a DFT-aware setup — typically using scan-enable pinning to verify functional equivalence with scan held inactive. The original synthesis SVF is not applicable here.
