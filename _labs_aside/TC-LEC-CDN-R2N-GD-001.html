Testcase 1 — AES Cipher Top: RTL-to-Gate LEC

GUIDED Tool: Synopsys Formality Design: aes_cipher_top Estimated time: 60 min

Problem Statement

The AES cipher top block has been synthesized using Design Compiler targeting TSMC 28nm. The synthesis tool applied logic optimizations, restructured combinational cones, and inserted clock-gating cells to meet timing and power targets. You need to confirm that all these transformations preserved the original RTL intent.

You have the following inputs:

  • Reference (RTL): 5 RTL source files from the central AES design directory
  • Implementation: inputs/aes_cipher_top.v — synthesized gate-level netlist
  • SVF: inputs/default.svf — generated by the synthesis run
  • Libraries: 3 TSMC 28nm standard-cell .db files (HVT / LVT / SVT)

Run make all first to see the unmodified environment, then follow this guide to complete scripts/formality.tcl and achieve Verification SUCCEEDED.

Step-by-Step Solution

  • Step 1 — Navigate to testcase1 and inspect inputs

    Confirm all required files are present before starting.

    Verify inputs
    cd testcase1
ls inputs/
# Expected: aes_cipher_top.v   default.svf
  • Step 2 — Set global verification options

    These four settings must appear at the very top of the script before any other command. They enable Formality’s auto setup mode and configure correct clock-gate handling for designs synthesized with Synopsys tools.

    scripts/formality.tcl — global settings
    set synopsys_auto_setup                    true
set verification_clock_gate_reverse_gating true
set verification_clock_gate_hold_mode      low
set verification_clock_gate_edge_analysis  true
    synopsys_auto_setup true activates a bundle of Formality recommendations: automatic constant propagation, register merge guidance, scan chain handling, and tie cell management. It is the recommended starting point for any Formality run.
  • Step 3 — Load the SVF before reading any designs

    The SVF (Synopsys Verification File) records every naming change, register merge, and structural transformation that synthesis applied. It must be loaded before any read_verilog command — Formality applies SVF hints during the read phase when building design containers.

    Load synthesis SVF
    set_svf ../inputs/default.svf
    Order matters: If you place set_svf after read_verilog, Formality ignores the SVF entirely. Matching degrades and you will see many unnecessary unmatched points.
  • Step 4 — Read the Reference design (RTL)

    Load all five AES RTL source files using the -r flag to designate the reference container. Then set the top module.

    Read RTL reference files
    read_verilog -r {/proj1/pd/users/testcase/TESTCASES/test_designs_central/aes_core/aes_cipher_top.v \
    /proj1/pd/users/testcase/TESTCASES/test_designs_central/aes_core/aes_key_expand_128.v \

    /proj1/pd/users/testcase/TESTCASES/test_designs_central/aes_core/aes_sbox.v \
    /proj1/pd/users/testcase/TESTCASES/test_designs_central/aes_core/timescale.v }

    The r: container holds behavioral RTL. Formality parses Verilog constructs directly — no library is needed to understand the reference logic.

Knowledge Assessment

1. Why must the SVF be loaded before reading any design files in Formality?

  • The SVF sets the library search path used during file reading.
  • Formality will abort with a fatal error if the SVF is loaded after the netlist.
  • Formality applies SVF transformation records during the read phase to guide container construction. If the SVF is loaded after reading, those records are missed and match quality degrades significantly.
  • The SVF is only needed for the implementation container, so its position relative to the reference read does not matter.
✓ Correct! The SVF records all naming changes and structural transformations synthesis made. Formality uses these during the read phase to build accurate containers. Loading the SVF after reading means the containers are already built without those hints — resulting in more unmatched points.

2. Formality reports "Verification SUCCEEDED" with 5 unmatched points. What does this mean?

  • The run failed — any unmatched points invalidate the SUCCEEDED result.
  • All 5 unmatched points were verified by a secondary method and are confirmed equivalent.
  • Every matched point was proven equivalent, but the 5 unmatched points had no counterpart found and were excluded from checking entirely — they are a coverage gap that must be investigated.
  • Unmatched points always correspond to scan flip-flops and can be safely ignored.
✓ Correct! SUCCEEDED applies only to matched points. Unmatched points are not checked at all — Formality simply could not pair them. They represent uncovered logic and must be reviewed to confirm they are benign before accepting the LEC result.

3. The AES netlist instantiates TSMC 28nm standard cells. Why does Formality need the Liberty .db files for the netlist side but not for the RTL side?

  • RTL files are compiled during synthesis and no longer need library support.
  • RTL describes logic behaviorally in Verilog constructs that Formality reads directly. The netlist instantiates standard cells whose Boolean functions are only defined in the Liberty .db files — without them, every cell is an unknown black box.
  • .db files are optional; Formality can infer gate logic from cell names alone.
  • .db files are only required when the design contains SRAM macros.
✓ Correct! RTL is behavioral — Formality parses always blocks and assign statements directly. A gate-level netlist references cells like NAND2 and DFF by name only; without the .db library, Formality has no way to know what logic function each cell implements and treats it as a black box.

4. After the AES LEC passes, CTS inserts clock buffer cells into the netlist. Does this require another LEC run, and which type?

  • No — CTS only changes the physical clock network, not the functional netlist, so no LEC is needed.
  • Yes — RTL-to-Gate must be re-run to compare the RTL against the post-CTS netlist.
  • Yes — Gate-to-Gate LEC should be run, comparing the pre-CTS synthesized netlist against the post-CTS netlist, to confirm the inserted clock buffers did not disturb any functional logic paths.
  • No — a single LEC run at tape-out covers all intermediate netlist changes.
✓ Correct! CTS inserts real cells into the netlist — this is a netlist change that triggers LEC. Gate-to-Gate is the correct type because both sides are gate-level netlists that understand the same cell vocabulary. RTL-to-Gate would be wrong here since RTL has no representation of physical clock buffers.
