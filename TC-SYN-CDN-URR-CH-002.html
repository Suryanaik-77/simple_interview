📝 Knowledge Assessment

1. In a complex SoC tile design, why does reports/check_design.rpt sometimes show a reduced but non-zero unresolved reference count after fixing one batch of SRAM macro libraries?

  • Genus randomly forgets previously resolved libraries between runs.
  • Elaboration resolves hierarchy top-down: deeper sub-instances inside an SRAM wrapper are only visible to the tool once the wrapper itself is resolved. Fixing the wrapper reveals the inner macro dependencies.
  • The synthesis script deletes library entries after each run.
  • Each run uses a different random subset of the full library list.
Correct! Genus elaborates top-down. If a top-level module A instantiates wrapper B which instantiates macro C, and both B and C are missing, only B appears in check_design.rpt on the first run. After B's library is added and elaboration re-runs, Genus descends into B and discovers C is also missing — the count drops by one but does not reach 0. This is the "peeling" effect in hierarchical debugging: check the report after every fix to track progress.

2. An SRAM macro shows up as an unresolved reference in reports/check_design.rpt because it is missing from set_db link_library. How does this fix differ from fixing a missing RTL module (as in the AES Cipher challenge)?

  • There is no difference — both require adding a .v file to read_hdl.
  • SRAM macros are hard macros delivered as compiled .lib files (not RTL). The fix is to add the macro's .lib path to set_db link_library, not to add a .v file to read_hdl.
  • SRAM macros never produce TUI-273 — they always use a different warning message.
  • You must add the SRAM .v model to read_hdl and the .lib to link_library.
Correct! SRAM memories are provided as pre-characterized hard macros, not as synthesizable RTL. Their cell definitions are in compiled .lib (Liberty format) timing models. You add them to set_db link_library — not to read_hdl — so Genus can resolve the macro's port interface during elaboration.

3. Why must set_db target_library not include the SRAM macro .lib files (only link_library should)?

  • Genus crashes if SRAM .lib files appear in target_library.
  • SRAM .lib files use a format incompatible with target_library.
  • target_library defines cells Genus can use for gate mapping during syn_map. SRAM macros are not cells the synthesizer replaces RTL with — they are fixed instances. Including them in target_library would confuse the mapper.
  • There is no distinction — both variables behave identically in Genus.
Correct! set_db target_library is the pool of cells the mapper uses when replacing RTL operators with standard gates during syn_map. SRAM macros are never targets for mapping — the RTL already instantiates them directly by name. They belong only in link_library so the elaborator can resolve their port interface.

4. How many unique SRAM macro .lib files must be added to set_db link_library to fully resolve the tile design?

  • 3 macro libraries
  • 5 macro libraries
  • 9 macro libraries (sram_l15_data, sram_l15_hmt, sram_l15_tag, sram_l1d_tag, sram_l1i_tag, sram_l2_data, sram_l2_dir, sram_l2_tag, sram_l2_state)
  • 12 macro libraries
Correct! The tile design uses 9 distinct SRAM macro types, each delivering a separate .lib file in the piton_mems directory tree. Each must be independently added to set_db link_library in genus_syn.tcl.
