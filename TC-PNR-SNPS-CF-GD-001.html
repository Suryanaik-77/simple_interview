Problem Statement

GUIDED

You will perform the complete Chip Finish stage in ICC2 for the tile processor core, starting from the final_eco.design block — the post-route optimized design after all engineering change orders. This is the last ICC2 stage before the design leaves the physical implementation team.

In this stage you will:

  • Insert standard cell filler cells to eliminate placement gaps and restore N-well continuity
  • Reconnect power and ground pins after filler insertion
  • Run incremental detail routing to fix any DRC violations introduced by filler cells
  • Write the gate-level Verilog netlist for LEC and LVS verification
  • Insert timing-aware dummy metal fill for CMP density compliance
  • Export the final GDSII for the foundry and DEF for back-annotation
  • Generate the full suite of sign-off reports

  • Set Design Variables

    Man page: set is a Tcl built-in that assigns a string value to a variable. There are no ICC2-specific flags. Variables persist for the duration of the session and are referenced with $variable_name.

    Why: Declaring design_name and stage at the top makes the script reusable — change one line to adapt it to a different design or stage name without editing every command.

    set design_name tile
set stage chip_finish
puts "MyInfo: Started $stage on $design_name @ [sh date]"
    Log output: MyInfo: Started chip_finish on tile @ Thu Jun 4 12:52:25 IST 2026 — this line confirms the script started and records the wall-clock time. Check this timestamp in the log to estimate total runtime.

  • Set Parallel Execution (set_host_options)

    Man page: set_host_options -max_cores <N> — controls the maximum number of CPU cores ICC2 is allowed to use for multi-threaded operations. Applies to routing, extraction, and timing analysis. Setting this too low on a multi-core server leaves compute capacity unused; setting it higher than the available core count has no benefit.

    set_host_options -max_cores 8
    Log output: 1 — ICC2 acknowledges the setting silently. The value 8 is confirmed later in the routing and extraction logs: Information: Using 8 threads for routing. (ZRT-444) and Information: Timer using 8 threads.

  • Open the Design Library and Final ECO Block (open_lib, open_block)

    Man page — open_lib: Opens an existing ICC2 design library (.ndm) from disk. This loads the library container and all its reference NDM links into the session. Does not open any design block automatically.

    Man page — open_block: Opens a named block within the currently open library in edit mode by default. The block name must exactly match a block that was previously saved with save_block -as <name>.

    open_lib ../inputs/tile.ndm
open_block final_eco.design
    Log output:
    • Information: Loading library file '.../tile.ndm' (FILE-007) — main library loaded
    • Followed by 15 FILE-007 messages loading each NDM reference library (3 stdcell + 12 SRAM)
    • Opening block 'tile.ndm:final_eco.design' in edit mode — block opened successfully
    • Information: User units loaded from library 'tcbn28hpcplusbwp40p140hvt' (LNK-040) — technology units (nm/DBU) loaded from the HVT stdcell NDM
    ⚠️ Why final_eco.design, not postroute.design?
    In production flows, after post-route optimization (route_opt), the design goes through one or more ECO (Engineering Change Order) iterations — targeted changes to fix specific timing or functional issues found during sign-off. The final_eco.design block is the result of these last manual ECOs. Chip Finish always starts from this final checkpoint, not from the raw post-route block. Starting from an earlier block would undo ECO fixes.

  • Build Sorted Filler Cell Lists (get_lib_cells, sort_collection)

    Man page — get_lib_cells: Returns a collection of library cell objects matching the specified names. When a list of names is passed inside {} braces (a single Tcl list argument), all cells in the list are retrieved in one call. If any name is not found in the loaded libraries, a warning is issued and only the found cells are returned.

    Man page — sort_collection: Sorts a collection of design objects by an attribute. -descending sorts from highest to lowest value of the attribute. area is a numeric attribute present on all lib_cell objects.

    Man page — get_object_name: Converts a collection of objects into a Tcl list of name strings. This is needed because create_stdcell_fillers -lib_cell takes a list of cell name strings, not a collection object.

    set DCAP_CELLS [get_object_name [sort_collection -descending [get_lib_cells {DCAP64BWP40P140HVT DCAP64BWP40P140 DCAP64BWP40P140LVT \
    DCAP32BWP40P140HVT DCAP32BWP40P140 DCAP32BWP40P140LVT \
    DCAP16BWP40P140HVT DCAP16BWP40P140 DCAP16BWP40P140LVT \
    DCAP8BWP40P140HVT DCAP8BWP40P140 DCAP8BWP40P140LVT \
    DCAP4BWP40P140HVT DCAP4BWP40P140 DCAP4BWP40P140LVT}] area]]

set FILL_CELLS [get_object_name [sort_collection -descending [get_lib_cells {FILL64BWP40P140HVT FILL64BWP40P140 FILL64BWP40P140LVT \
    FILL32BWP40P140HVT FILL32BWP40P140 FILL32BWP40P140LVT \
    FILL16BWP40P140HVT FILL16BWP40P140 FILL16BWP40P140LVT \
    FILL8BWP40P140HVT FILL8BWP40P140 FILL8BWP40P140LVT \
    FILL4BWP40P140HVT FILL4BWP40P140 FILL4BWP40P140LVT \
    FILL3BWP40P140HVT FILL3BWP40P140 FILL3BWP40P140LVT \
    FILL2BWP40P140HVT FILL2BWP40P140 FILL2BWP40P140LVT}] area]]
    Cell Type Purpose
    DCAP64/32/16/8/4 Decoupling capacitor cells — fill gaps while also adding local charge reservoirs between VDD and VSS. Reduces supply noise during switching transients. Available in HVT/SVT/LVT flavors.
    FILL64/32/16/8/4/3/2 Pure filler cells — contain only N-well extension and power rail continuity. No capacitance value. Used when DCAP cells are exhausted or unavailable at a particular width.
    Why sort by area descending? The sort produces a list ordered from the largest cell (64 sites) down to the smallest (2 sites). create_stdcell_fillers processes this list in order — it tries each cell type against each gap from largest to smallest. A 17-site gap gets filled with one FILL16 + one FILL1, not seventeen FILL1 cells. This minimizes the instance count and maximizes the decoupling capacitance added per gap.
    Log output: After each set command, ICC2 echoes the resulting string. You will see the full qualified cell name list:
    tcbn28hpcplusbwp40p140hvt/DCAP64BWP40P140HVT tcbn28hpcplusbwp40p140/DCAP64BWP40P140 ...

  • Insert Standard Cell Filler Cells (create_stdcell_fillers)

    Man page: create_stdcell_fillers -lib_cell <list> — scans all standard cell rows for unoccupied placement sites (gaps) and fills them by selecting the best-fitting cell from the provided list. The list must be ordered from largest to smallest. The command uses a 2D gap-fill engine that respects VT implant rules, OD spacing rules, and power/ground pin alignment.

    • -lib_cell — accepts a Tcl list of fully-qualified library cell names (library_name/cell_name format, as produced by get_object_name).
    • The command runs in two passes: Pass 1 fills standard gaps; Pass 2 cleans up any residual single-site gaps.
    create_stdcell_fillers -lib_cell $FILL_CELLS

    • CHF-011 warnings (e.g., filler ref cell FILL64BWP40P140HVT not marked filler type) — these are expected. The TSMC 28nm library does not set the ICC2 filler attribute on these cells; the tool uses them anyway and issues a warning. No action needed.

  • Connect Power and Ground Pins (connect_pg_net)

    Man page: connect_pg_net — scans all cell instances in the design for power (VDD, VDDG) and ground (VSS, VSSG) pins that are not yet connected to a power or ground net, and connects them to the corresponding net based on the net type. For filler cells, this connects their VDD/VSS pins to the power rails running through the standard cell rows.

    • Without this step, every newly inserted filler cell has floating power pins — LVS will report opens on VDD and VSS for every filler instance.
    • The command is run without -automatic here (implicit global mode) — it processes the entire design at once.
    connect_pg_net
    Log output — Power/Ground Connection Summary:
    • VDD: previous/current pin count = 411,488 / 779,131
    • VSS: previous/current pin count = 411,470 / 779,113
    • Information: connections of 735,286 power/ground pin(s) are created or changed.
    • The delta (779,131 − 411,488 = 367,643) matches exactly the number of filler cells inserted — confirming every filler cell VDD pin was connected.

  • Incremental Detail Routing After Filler Insertion (route_detail)

    Man page: route_detail -incremental <true/false> — runs the ICC2 detail router. In incremental mode (-incremental true), the router does not re-route already-routed nets from scratch. Instead, it focuses only on nets that are unrouted or have DRC violations — typically caused by filler cells blocking previously clean routing tracks or via access points.

    • Filler cells occupy physical sites and can obstruct lower metal layers (M1, M2) where local routing runs. The incremental routing pass re-routes any nets whose paths were blocked by newly inserted filler cells.
    • -incremental true dramatically reduces runtime compared to a full re-route — it skips the 99% of nets that are already clean.
    • The router also checks and fixes antenna violations in this pass.
    route_detail -incremental true
    Log output:
    • The router runs a full DRC check first, finding 32 violations across 1,024 partitions
    • Routing in incremental mode, starting from iteration 40 — continues from where the post-route router left off
    • Routing options: detail.antenna: true, detail.timing_driven: true, detail.insert_diodes_during_routing: true
    • 379,562 nets successfully extracted after routing
    • After routing: check_routes will show 0 violations — all 32 DRC issues are resolved
    ✅ Gate to move forward: After route_detail, there should be 0 open nets. Look for the line: Total number of open nets = 0 in the log. Any non-zero open count must be investigated before writing outputs.

  • Normalize Net and Instance Names (change_names)

    Man page: change_names -rules <format> — renames any net, port, or instance names in the design that contain characters illegal in the target format. The verilog rule set replaces characters such as [, ], /, $, and spaces with Verilog-legal alternatives (typically underscore _ or escaped identifiers).

    • ICC2 internally uses hierarchical path separators and bus indexing in net names (e.g., U1/net[3]). These are illegal in Verilog syntax.
    • This command must be run before write_verilog. If skipped, the resulting Verilog file will contain illegal identifiers that cause syntax errors in downstream tools (Formality, ModelSim, VCS).
    change_names -rules verilog
    What to check: The command outputs a count of names changed. Typical output: Changed N net names. If 0 names are changed, all names were already Verilog-legal — this is acceptable. Any name changes are printed in detail if needed with -verbose.

  • Write Gate-Level Verilog for LEC (write_verilog)

    Man page: write_verilog [options] <output_file> — writes a Verilog netlist of the current design to disk. Key options:

    Option Description
    -compress gzip Compresses the output with gzip. The file is written as <name>.gz. Large designs produce 200–500 MB netlists; gzip reduces this by ~8×.
    -exclude {scalar_wire_declarations leaf_module_declarations pg_objects end_cap_cells well_tap_cells filler_cells pad_spacer_cells physical_only_cells cover_cells} Excludes categories of content that have no logical counterpart in the synthesis netlist. LEC cannot map physical-only cells (filler, end-cap, tap) or power/ground wires — including them causes false "unmatched point" failures in Formality.
    -hierarchy all Preserves all module boundaries from the ICC2 hierarchy. Enables hierarchical LEC comparison which is significantly faster than flat mode for designs with 300K+ cells. 
    write_verilog -compress gzip -exclude {scalar_wire_declarations leaf_module_declarations pg_objects end_cap_cells well_tap_cells filler_cells pad_spacer_cells physical_only_cells cover_cells} -hierarchy all ./outputs/${design_name}.v
    Output: ./outputs/tile.v.gz — the LEC netlist. This file is handed to the Formality (or Conformal) team for gate-to-gate equivalence checking against the synthesis golden netlist. Verify the file exists and is non-zero in size before proceeding.

  • Write Gate-Level Verilog for LVS (write_verilog — LVS version)

    What is different: The LVS netlist includes a slightly different set of exclusions. The key difference is the use of empty_modules exclusion (removes empty module declarations) instead of the physical-only cell exclusions. The LVS tool needs to see power and ground connectivity but does not need physical-only cells.

    write_verilog -compress gzip -exclude {scalar_wire_declarations leaf_module_declarations empty_modules} -hierarchy all ./outputs/${design_name}.lvs.v
    Output: ./outputs/tile.lvs.v.gz — the LVS netlist. This file is used by Calibre or ICV LVS to verify the extracted layout netlist against the schematic reference. The LVS tool needs to see all functional cells; it handles physical-only cells differently than the LEC tool.
    💡 LEC vs LVS netlists — what changes:
    • LEC netlist: No physical cells, no PG objects. LEC compares logic only.
    • LVS netlist: Physical cells may be included; PG connectivity is visible. LVS compares full device connectivity including power rails.

  • Get Design Boundary and Insert Dummy Metal Fill (signoff_create_metal_fill)

    Man page — get_attribute: Returns the value of a named attribute from an object. [current_design] returns the active design object; bbox is the bounding box attribute — a pair of coordinates {{llx lly} {urx ury}} defining the die boundary.

    Man page — signoff_create_metal_fill: ICC2's sign-off quality dummy metal fill insertion command. Unlike the placement-stage create_fill, this command is optimized for the post-route state where all routing is final. It uses the current parasitic extraction state to compute timing impact of fill shapes before inserting them.

    • -track_fill generic — uses a generic track-based fill algorithm that inserts floating metal shapes on routing tracks, maintaining minimum spacing to existing wires. This is the industry-standard mode for track-aware fill.
    • The fill shapes are inserted on all interconnect layers (M1–M9) to meet the foundry's per-layer minimum metal density rule.
    • Shapes are placed away from timing-critical nets based on the extracted RC data — timing impact is minimized.
    set design_boundary [get_attribute [current_design] bbox]
signoff_create_metal_fill -track_fill generic
    ⚠️ Metal fill and CMP: Foundries specify a minimum metal density (e.g., 20% on M1) per analysis window (e.g., 50×50 µm). Regions below this threshold fail the foundry DRC. signoff_create_metal_fill automatically calculates which regions are deficient and inserts just enough dummy metal to meet the rule — without exceeding the maximum density limit either.

  • Write GDSII for Tape-Out (write_gds)

    Man page: write_gds [options] <output_file> — exports the complete physical layout as a binary GDSII stream file. This is the primary tape-out deliverable. Key options:

    Option Description
    -compress Writes a compressed GDSII file. Reduces file size by ~3–5×. The foundry must support compressed GDSII input.
    -hierarchy all Writes all hierarchical levels. Required to preserve the full design hierarchy in the GDSII cell tree.
    -lib_cell_view frame Uses the frame view from reference NDMs for standard cell geometry. The frame view contains boundary and pin information optimized for GDSII stream-out.
    -long_names Preserves full hierarchical instance and net names. Without this, names are truncated to fit GDSII's 32-character limit — making post-silicon debug harder.
    -keep_data_type Preserves the original GDSII data type numbers from merged cell files. Required for foundry DRC rule deck compatibility.
    -merge_files $GDS_FILE_LIST Merges the standard cell library GDS streams (LVT, SVT, HVT) directly into the output GDSII. The foundry receives one self-contained file with all cell geometry included — no separate PDK GDS files needed at their end.
    -merge_gds_top_cell $design_name Sets the top-level cell name in the merged GDSII to match the design name (tile). The foundry uses this to identify the top-level structure.
    -units 2000 Sets the GDSII database units to 2000 units per µm (0.5 nm resolution). Must match the DBU precision of the technology file and NDM libraries. TSMC 28nm uses 2000 DBU/µm. Using -units 1000 here would cause coordinates to be halved — misaligning all shapes and causing catastrophic DRC failures.
    -layer_map <file> Maps ICC2 internal layer names to GDSII layer/datatype numbers per the foundry's layer map. The TSMC 28nm 1P9M_4X2Y2R layer map is specified here. 
    set pdk_stdcell /efs/semicon_labs_pd/pdk/foundries/tsmc/N28/versions/v1.0/stdcells/9T
set GDS_FILE_LIST [list \
    ${pdk_stdcell}/lvt/gds/tcbn28hpcplusbwp40p140lvt.gds \
    ${pdk_stdcell}/svt/gds/tcbn28hpcplusbwp40p140.gds \
    ${pdk_stdcell}/hvt/gds/tcbn28hpcplusbwp40p140hvt.gds]

write_gds -compress -hierarchy all -lib_cell_view frame -long_names -keep_data_type \
    -merge_files $GDS_FILE_LIST -merge_gds_top_cell $design_name \
    -units 2000 \
    -layer_map /efs/semicon_labs_pd/pdk/foundries/tsmc/N28/versions/v1.0/metal_stack/1P9M_4X2Y2R/gdsmap/icc2/gdsout_4X2Y2R.map \
    ./outputs/${design_name}.gds
    ⚠️ After write_gds: The GDSII file must pass the foundry's full DRC deck (Calibre DRC or ICV) before final tape-out. ICC2's internal check_routes uses a simplified rule set and does not replace foundry DRC. Coordinate with the sign-off team to run Calibre DRC on tile.gds as the next step after chip finish.

  • Write DEF for Back-Annotation (write_def)

    Man page: write_def [options] <output_file> — writes the design in Design Exchange Format (DEF). DEF captures placement coordinates, routing, pin locations, and special net routing in a text-based format readable by other EDA tools.

    Option Description
    -compress gzip Compresses the DEF output file.
    -version 5.8 Writes DEF in version 5.8 format — the standard accepted by most downstream tools (PrimeTime, Calibre, StarRC).
    -include_tech_via_definitions Embeds via geometry definitions from the technology file directly into the DEF. Required when the downstream tool does not have access to the original technology LEF.
    -units 1000 Sets the DEF coordinate resolution to 1000 units per µm (1 nm resolution). This is the standard DEF precision and is independent of the GDS DBU precision. DEF consumers (PrimeTime, Calibre) expect 1000 units/µm. 
    write_def -compress gzip -version 5.8 -include_tech_via_definitions -units 1000 ./outputs/${design_name}.def
    Why is write_def needed? The DEF file is used by:
    • StarRC / ICV StarRC: For parasitic extraction (SPEF) after tape-out — reads DEF for routing topology
    • PrimeTime: For back-annotated timing sign-off using the final placed/routed DEF
    • Calibre: Can use DEF for hierarchical LVS and DRC flows
    • Future ECOs: DEF can be re-imported to restart a new ICC2 flow from the exact final physical state

  • Save the Chip Finish Block (save_block)

    Man page: save_block -as <name> — commits the current in-memory design state (including all filler cells, metal fill, name changes, and routing updates) to a permanently named block inside the NDM library. This creates a restore point labeled as the chip finish checkpoint.

    save_block -as $stage
    Result: Creates tile.ndm:chip_finish.design. Future sessions can reopen this exact state with open_block chip_finish.design to regenerate outputs or investigate issues without re-running the full chip finish flow.

  • Generate Sign-Off Reports

    All reports are generated after save_block so the checkpointed block and the reports are consistent. Reports are redirected to individual files in the reports/chip_finish/ directory for archiving and review.

    1. Timing Constraint Violations

    set report_dir ../reports/${stage}
file mkdir $report_dir
redirect -file ${report_dir}/chip_finish.report_constraint {report_constraint -all_violators -max_transition -max_capacitance -scenarios [all_scenarios]}
    What to check:
    • -all_violators — lists every endpoint that violates its constraint (not just the worst)
    • -max_transition — reports nets where rise/fall transition time exceeds the cell's max_transition limit. For tile: CTS_BUFFZCTSNET_238 has 0.28ns transition vs 0.35ns limit (slack −0.07ns VIOLATED) — a CTS buffer DRV, not a functional path
    • -max_capacitance — reports nets where total load capacitance exceeds the driving cell's max_capacitance limit
    • Action: Setup slack must be ≥ 0 on all functional paths. DRV (max_transition, max_capacitance) violations on CTS nets are acceptable at chip finish if they are in the clock tree — they indicate the clock buffers are slightly stressed but functional

    2. Setup and Hold Timing Reports

    redirect -file ${report_dir}/chip_finish.report_timing.max {report_timing -delay max -scenarios [all_scenarios] -input_pins -nets -transition_time -capacitance -attributes -physical -derate -report_by group}
redirect -file ${report_dir}/chip_finish.report_timing.min {report_timing -delay min -scenarios [all_scenarios] -input_pins -nets -transition_time -capacitance -attributes -physical -derate -report_by group}
    What to check:
    • -delay max = setup timing (max path); -delay min = hold timing (min path)
    • -report_by group — organizes paths by clock group (clk, r2r, i2r, r2o)
    • -derate — shows the OCV derate factors applied to each path segment
    • -physical — shows wire length and routing layer information inline with the timing path
    • For tile chip_finish: Worst critical path is in the clk group, scenario func_setup_ssg0p81v125c_rcw, through ifu_itlb
    • Action: If setup WNS < 0, the design did not meet timing — this must be resolved before tape-out

    3. QoR Summary

    redirect -file ${report_dir}/report_qor.rpt {report_qor}
    What to check (tile chip_finish results):

For tile, these violations were present in the route block and were not closed during chip finish (chip finish does not run timing optimization). 📚 Knowledge Assessment Quiz

1. After create_stdcell_fillers completes with CHF-100: 367,643 filler cells inserted, you run check_lvs and see hundreds of opens on VDD and VSS nets, all pointing to FILL* instances. What step did you miss and why does skipping it cause these LVS opens?

  • You skipped check_legality — legality violations prevent filler cell power pins from being resolved by ICC2.
  • You skipped connect_pg_net after filler insertion. create_stdcell_fillers places filler cell instances in the design but does not connect their VDD and VSS pins to the power grid. connect_pg_net must be run explicitly to create these connections — without it, every filler cell has floating power pins, which ICC2's LVS engine reports as opens on the VDD and VSS nets.
  • You skipped route_detail -incremental true — routing is required to establish power connections for new cells.
  • You skipped save_block before running check_lvs — the command only reads saved block state.
Correct! create_stdcell_fillers inserts filler cell instances but does not handle their power/ground connectivity — that is the job of connect_pg_net. In the tile log, connect_pg_net creates 735,286 new PG connections (matching the 367,643 filler cells × 2 pins each). Without this step, every filler VDD and VSS pin is floating and LVS reports opens.

2. Why is -units 2000 required in the write_gds command for a TSMC 28nm design, and what would happen if you used -units 1000?

  • 2000 units/µm is a GDSII format requirement — all modern foundries mandate this precision for manufacturing. Using 1000 would cause the GDSII reader to reject the file with a format error.
  • The TSMC 28nm PDK technology file and all NDM reference libraries use a database unit precision of 2000 DBU per µm (0.5 nm resolution). The -units parameter must match this precision. If you specify -units 1000, ICC2 scales all coordinates by 0.5 when writing the GDSII — every shape, via, and pin is written at half its correct size and position. The resulting GDSII has misaligned features that fail foundry DRC with thousands of spacing violations.
  • 2000 is the standard for DEF files; GDSII always uses 1000 units. Using 2000 doubles all coordinates, which is corrected automatically by the foundry's viewer.
  • The units setting only affects display precision in the GDSII viewer — it has no impact on the actual coordinate data written to the file.
Correct! The -units value in write_gds tells ICC2 how many GDSII integer units correspond to one micron. This must exactly match the DBU/µm precision of the loaded technology file. TSMC 28nm uses 2000 DBU/µm — so 1 nm = 2 database units. Specifying 1000 causes all coordinates to be halved during GDSII writing, displacing every geometric shape by half its distance from the origin. The resulting GDSII is geometrically invalid.

3. The report_clock_qor summary shows Trans DRC = 2 in the setup corners for the clk tree. How do you identify which specific nets are violated, and when does this require action before tape-out?

  • Trans DRC = 2 means 2 flip-flop clock pins have setup violations. Check report_timing.max and find the paths ending at those 2 flip-flops.
  • Open chip_finish.report_clock_qor.drc_violators (generated with report_clock_qor -type drc_violators -all) to see the exact net name and transition value. For tile, the violator is CTS_BUFFZCTSNET_238 with 0.28 ns transition vs 0.35 ns limit. This is a CTS buffer output net. Action is required if the violation causes the clock signal to not be recognized correctly at the sink registers (functional failure) — but if the silicon margin is sufficient and sign-off checks pass in PrimeTime, it may be waived with PDK team approval.
  • Trans DRC on clock nets is always a waivable issue — it indicates marginal timing but never causes functional failure in silicon. No action is required.
  • Run check_design -checks timing to get the full list of Trans DRC violators with location information.
Correct! report_clock_qor -type drc_violators -all generates a dedicated file listing every clock net with transition DRC violations, including the measured transition time and the limit. For tile, this reveals CTS_BUFFZCTSNET_238 — a CTS buffer clock distribution net. Whether this requires an ECO fix depends on whether PrimeTime sign-off (using actual SPEF) also sees the violation. Some CTS transition violations in ICC2's pre-sign-off model close cleanly in PrimeTime's more accurate extraction.

4. Two different Verilog netlists are written in chip_finish: tile.v (LEC) and tile.lvs.v (LVS). Both use write_verilog -hierarchy all but with different -exclude options. What is the key difference in the excluded content and why does each downstream tool need a different netlist?

  • The LEC netlist includes compressed binary encoding while the LVS netlist uses ASCII — different tools require different encoding formats.
  • The LEC netlist is written before signoff_create_metal_fill so it does not include metal fill shapes; the LVS netlist is written after and includes them. This lets LVS check the fill shapes for connectivity.
  • The LEC netlist excludes all physical-only cells (filler_cells end_cap_cells well_tap_cells pg_objects etc.) because the Formality/Conformal LEC tool compares logic only against the synthesis reference netlist — these cells have no logical counterpart and cause false "unmatched point" failures. The LVS netlist excludes only empty_modules (reducing verbosity) but retains all cells and connectivity so the LVS tool can verify the complete physical connection including power rails and device terminals.
  • The two netlists are functionally identical; the different exclude options only reduce file size and have no effect on the verification results.
Correct! LEC (Formality/Conformal) works by matching logic gates between the implementation netlist and the synthesis golden netlist. Physical-only cells — fillers, end-caps, tap cells — do not appear in the synthesis netlist. Including them in the LEC netlist produces "unmatched points" that the tool cannot resolve. LVS (Calibre/ICV), on the other hand, extracts the full device-level connectivity from the layout and compares it against the schematic. It must see all cells and their power connections — using the LEC-style netlist for LVS would miss power connectivity and produce false opens.
