💡 Hints

Hint 1 — Reading the MMMC config and physical data

Tempus uses read_mmmc to load the multi-mode multi-corner configuration, and read_physical -lef to load technology and cell LEF files. The MMMC config defines library sets, RC corners, delay corners, constraint modes, and analysis views. Look at what RC corner names are defined in mmmc_config.tcl — you will need those exact names when annotating SPEF files.

Hint 2 — SI analysis settings must be configured before reading SPEFs

Signal integrity analysis in Tempus requires several set_db commands to enable SI delay calculation, glitch propagation, and related features. These settings must be in place before you read SPEF files with read_spef. The key database attributes to configure include delaycal_enable_si, si_delay_separate_on_data, si_enable_glitch_propagation, and several others related to waveform modeling and glitch thresholds.

Hint 3 — Clock propagation and timing update sequence

Before calling update_timing, you must propagate clocks. This involves setting the interactive constraint mode to cover both setup and hold modes, then using set_propagated_clock on the clock sources. After propagation, reset the interactive constraint mode and then run a full timing update. Only after update_timing completes can you generate meaningful timing reports. For noise analysis, update_glitch must be called after the timing update.

🧠 Knowledge Assessment

1. If you forget to call update_timing -full before generating timing summary reports, what happens?

  • Tempus automatically runs an incremental timing update before each report command.
  • The reports are generated normally but with slightly less accurate results.
  • The timing reports will contain incomplete or stale timing data because the timing graph has not been fully propagated with the annotated parasitics and propagated clocks.
  • Tempus will throw a fatal error and refuse to generate any reports.
Correct! Without a full timing update, the timing graph does not reflect the annotated SPEF parasitics and propagated clock latencies. Reports generated in this state will have incomplete or incorrect timing data, leading to misleading signoff results.

2. The MMMC config defines four RC corners: rcworst_125, rcbest_125, cworst_m40, and cbest_m40. Why must the -rc_corner argument in read_spef match these names exactly?

  • It is just a naming convention — any name will work as long as it is consistent.
  • The RC corner name links the SPEF parasitics to the correct delay corner and analysis view defined in the MMMC config, ensuring each view uses the right parasitic data for timing calculation.
  • Tempus uses the RC corner name to locate the SPEF file on disk automatically.
  • The names must match because Tempus checks them against the QRC tech file headers.
Correct! Each delay corner in the MMMC config references a specific RC corner. When you annotate a SPEF file to an RC corner by name, Tempus associates those parasitics with all delay corners and analysis views that use that RC corner, ensuring accurate timing calculations per PVT condition.

3. You enable set_db timing_analysis_type ocv and set_db timing_analysis_cppr both. What would happen to hold timing results if you set CPPR to none instead?

  • Hold violations would disappear because CPPR only affects setup analysis.
  • There would be no difference because OCV mode does not interact with CPPR.
  • Hold timing would become pessimistic because common clock path reconvergence would not be removed, reporting artificial hold violations that do not exist in silicon.
  • Hold timing would become optimistic, hiding real violations.
Correct! CPPR (Common Path Pessimism Removal) eliminates the artificial pessimism that arises in OCV analysis when the same clock path segment is derated differently for launch and capture. Without CPPR, the tool over-reports hold violations that would not occur in actual silicon.

4. Your script saves two session databases: tile_session_timing.db and tile_session_noise.db. Why are two separate saves necessary rather than one at the end?

  • Tempus can only store one type of analysis per database file due to file format limitations.
  • The first save captures the timing state after update_timing and before noise analysis modifies the timing graph. The second save captures the state after update_glitch with SI noise data included. This lets you reload either the pure timing or the noise-annotated session independently.
  • The second save overwrites the first, so only the noise database actually persists.
  • Two databases are needed because setup and hold analyses cannot coexist in the same file.
Correct! Saving before and after noise analysis preserves two distinct analysis states. The timing-only database can be reloaded for timing ECO work without noise effects, while the noise database includes glitch and crosstalk data needed for SI signoff. This is standard practice in signoff STA flows.
