Problem Statement

GUIDED

You have an empty synthesis script at scripts/dc_syn.tcl. Your task is to fill it with all the DC Shell commands needed to synthesize the tile design from the OpenPiton processor, then run it inside DC Shell.

Follow each step below. Add the command(s) shown to dc_syn.tcl, read the explanation, and move to the next step. When all commands are written, source the script inside DC Shell and run make verify.

⚙ Synthesis Flow Overview

DC Shell synthesis runs in three broad stages. Every command in your script belongs to one of these:

  • Setup — configure search paths, load libraries, read RTL, elaborate the design.
  • Constraints — source the SDC, apply set_dont_use restrictions, configure clock gating.
  • Compile & Outputs — compile_ultra -gate_clock, generate reports, write netlist and DDC database.

    set_search_path tells DC Shell which directories to scan when looking for .db library files. This is why the library commands in the next step can reference files by filename alone — DC Shell resolves the full path automatically using this list. Two groups of directories are listed:

    • Standard cell CCS library directories (TSMC 28 nm HPHP, BWP40, HVT / LVT / SVT, SSG corner, −40°C) — Three separate directories hold the CCS-format .db files for each Vt flavor: /efs/semicon_labs_pd/pdk/foundries/tsmc/N28/versions/v1.0/stdcells/9T/hvt/lib/ccs, /efs/semicon_labs_pd/pdk/foundries/tsmc/N28/versions/v1.0/stdcells/9T/lvt/lib/ccs, and /efs/semicon_labs_pd/pdk/foundries/tsmc/N28/versions/v1.0/stdcells/9T/svt/lib/ccs. SVT is the primary cell flavor used for logic mapping; HVT is the fallback for low-power paths; LVT is loaded but blocked via set_dont_use.
    • SRAM macro library directories — the tile design contains multiple on-chip SRAM blocks (L1 instruction cache, L1 data cache, L2 cache, L1.5 tag, etc.). The paths use the ../../pdk symlink created by setup_lab.sh. Each directory holds the .db timing model DC Shell needs to perform setup/hold checks at the memory ports.
    Corner chosen (SSG, −40°C): The slow-slow-ground, cold-temperature corner represents the worst-case setup timing scenario — cells are slowest and voltage is lowest. If synthesis closes timing here, it will close at all other operating conditions.

    • set_target_library — lists the standard cell .db files that DC Shell is allowed to use during cell mapping. Only standard cells appear here — the three Vt flavors (HVT, LVT, SVT). SRAM macros are not included because DC Shell does not map logic onto them; they are fixed black boxes.
    • set_link_library — lists every library needed for cross-referencing and timing analysis, including all standard cell .db files plus the SRAM macro timing models. The leading * is mandatory — it tells DC Shell to also search the cells already loaded in the current design when resolving references.

  • Read the Design

    source ../inputs/Filelist.tcl
analyze -format verilog $RTL_SOURCE_FILES
    • source ../inputs/Filelist.tcl — executes the Tcl filelist, which sets the variable $RTL_SOURCE_FILES to the full list of Verilog source paths for the tile design.
    • analyze -format verilog $RTL_SOURCE_FILES — reads and parses every Verilog file listed in $RTL_SOURCE_FILES. DC Shell checks each file for syntax errors at this stage. If a file is missing or has a syntax problem, analyze reports an error that must be fixed before proceeding to elaboration.

  • Elaborate the Design

    elaborate tile
check_timing > ../reports/check_timing_before_sdc.rpt
    • elaborate tile — the top-level module name is tile. DC Shell connects all instantiated modules together, resolves parameter values, and builds the complete design hierarchy in memory. If any instantiated module is missing from the files you analyzed, you will see an unresolved reference error here.
    • check_timing > ../reports/check_timing_before_sdc.rpt — runs a timing sanity check before the SDC is applied. The report shows which paths have no timing constraints yet. This is a useful baseline to compare against the post-SDC check run later.

  • Apply Timing Constraints

    source ../inputs/tile.sdc

    source ../inputs/tile.sdc — loads the timing constraints for the tile design. Key constraints defined here:

    • Clock period on port clk
    • Input/output delays as fractions of the clock period
    • Max transition, max fanout, and load constraints

  • Restrict Cell Usage

    set dont_use_cell_list [get_lib_cells { */*LVT */*D0* */CK* */*D18* */*D20* */*D24*}]
set_dont_use [get_lib_cells $dont_use_cell_list]
set_dont_use [get_lib_cells */*CKLNQD8BWP40P140LVT*] dont_use false
    • First line — collects LVT cells (*/*LVT), minimum drive-strength cells (*/*D0*), clock-tree cells (*/CK*), and oversized drive-strength cells (*/*D18*, */*D20*, */*D24*) into a list.
    • Second line — applies set_dont_use to every cell in that list. LVT cells are blocked to minimize leakage; clock-tree cells are reserved for post-synthesis CTS; extreme drive-strength cells waste area and power on typical logic paths.
    • Third line — re-enables CKLNQD8BWP40P140LVT using DC Shell's dont_use false attribute syntax. This specific latch-based ICG cell must remain available for clock gating insertion by compile_ultra -gate_clock, even though all other LVT cells are blocked.

  • Configure Clock Gating

    set_app_var compile_clock_gating_through_hierarchy true
set timing_separate_clock_gating_group TRUE

set_clock_gating_style \
    -sequential_cell latch \
    -max_fanout 64 \
    -minimum_bitwidth 8 \
    -positive_edge_logic integrated:CKLNQD8BWP40P140LVT \
    -control_point before \
    -control_signal scan_enable \
    -num_stages 3

identify_clock_gating

set_app_var compile_delete_unloaded_sequential_cells true
    • compile_clock_gating_through_hierarchy true — allows DC to propagate clock-gating cells up and down the hierarchy, enabling more aggressive power reduction across module boundaries.
    • set_clock_gating_style — configures how compile_ultra -gate_clock will insert ICG cells:
      • -minimum_bitwidth 8 — only gate register groups of 8 or more bits. Gating fewer registers adds ICG overhead with minimal power benefit.
      • -max_fanout 64 — limits each ICG output to 64 register clock pins, preventing excessive fanout on the gated clock net.
      • -sequential_cell latch — use a latch-based ICG cell. The latch holds the enable signal stable to prevent glitches on the gated clock.
      • -positive_edge_logic integrated:CKLNQD8BWP40P140LVT — the exact BWP40 LVT latch-based ICG cell, re-enabled in the previous step for this purpose.
      • -control_point before — place the ICG cell before the register clock pin to maximize power savings.
      • -control_signal scan_enable — the ICG cell's scan enable input is connected to the design's scan_enable port, ensuring the clock is ungated during scan test.
      • -num_stages 3 — allows DC to build up to 3 levels of hierarchical ICG cells, balancing power savings against area and routing complexity.
    • identify_clock_gating — runs a pre-pass to find and tag register groups that are candidates for gating before compile_ultra begins. This improves ICG insertion quality.
    • compile_delete_unloaded_sequential_cells true — instructs DC to remove flip-flops whose outputs are not connected to anything. These registers waste power and area without contributing to the design function.

  • Run Synthesis

    compile_ultra -gate_clock
check_timing > ../reports/check_timing_after_compile.rpt
    • compile_ultra -gate_clock — the main synthesis command. It performs the full compile flow in one call: technology mapping, timing-driven optimization, and integrated clock gating insertion. DC Shell maps your RTL to the best available standard cells, fixes timing violations by swapping or restructuring logic, and inserts ICG cells according to the style configured in the previous step.
    • check_timing > ../reports/check_timing_after_compile.rpt — re-runs the timing check after compilation to confirm all paths remain properly constrained. Compare this with the pre-SDC report to verify constraints were applied correctly.
    Runtime note: Synthesizing the tile design takes several hours. Monitor the log file at logs/dc_synthesis.log for progress messages and any errors during compilation.

  • Generate Reports

    check_timing                     > ../reports/check_timing_after_compile.rpt
report_qor                       > ../reports/qor.rpt
report_timing -delay max -max_paths 100 -nosplit -path full_clock_expanded -nets -transition_time -input_pins \
                                 > ../reports/timing-max.rpt
report_area -hierarchy -physical -nosplit > ../reports/area.rpt
report_constraint -all_violators -nosplit > ../reports/constraint_violators.rpt
report_clock_gating -multi_stage -verbose -gated -ungated > ../reports/clock_gating.rpt
    • report_timing — detailed timing paths. For each violating path, the report shows every gate, its delay contribution, and the required/arrival time at each pin. Use this to understand the cause of any remaining violations.
    • report_qor — top-level quality-of-results summary: worst negative slack (WNS), total negative slack (TNS), number of violating paths, and total area. This is the first report to check after synthesis.
    • report_area — area breakdown by module hierarchy. Identifies which blocks in the design consume the most silicon area.
    • report_power — estimated dynamic and static power by module. Check this to confirm clock gating reduced dynamic power as expected.
    • report_design — design-level summary including top-level port count, library information, and design attributes set during synthesis.
    • report_constraints — lists all timing constraints applied and flags any that could not be satisfied (exceptions, violations).
    • check_design -summary — structural check for unconnected ports, multi-driven nets, and combinational loops after compilation.

  • Write Outputs and Exit

    write -format verilog -hierarchy -output ../outputs/tile.v
write_file -format ddc -hierarchy -output ../outputs/tile.ddc
write_sdc -nosplit ../outputs/tile.synthesis.sdc
exit
    • write -format verilog -hierarchy -output ../outputs/tile.v — writes the gate-level netlist in Verilog. Note: DC Shell uses write (not write_file) for the Verilog format. The -hierarchy flag preserves the module hierarchy. This is the primary output handed off to place-and-route.
    • write_file -format ddc -hierarchy -output ../outputs/tile.ddc — writes the complete DC Shell design database. The DDC format stores the netlist, applied constraints, and library references together. You can reload it later with read_file for incremental work or re-reporting without re-running synthesis.
    • write_sdc -nosplit ../outputs/tile.synthesis.sdc — writes the post-synthesis SDC constraints. The -nosplit flag keeps long lines intact. This SDC is passed to place-and-route as the timing budget.
    • exit — closes the DC Shell session and returns to the Linux shell.

  • Source the Script and Verify

    Save dc_syn.tcl. In the DC Shell terminal, source it to run every command in sequence: 

    source ../scripts/dc_syn.tcl

    DC Shell will execute the script from top to bottom. It exits automatically when it reaches the exit command at the end. Once you are back at the Linux shell, run the automated verifier: 

    make verify

🧠 Knowledge Assessment

1. In DC Shell, set_target_library and set_link_library both reference library files. What is the key difference?

  • set_target_library includes only SRAM macros; set_link_library includes only standard cells.
  • set_target_library lists cells DC Shell can map logic onto; set_link_library lists all cells (including * for in-memory cells) needed for timing analysis and cross-referencing.
  • They are interchangeable — either one can be used alone without the other.
  • set_link_library is used only when writing the output netlist.
Correct! set_target_library defines the cells available for technology mapping. set_link_library is broader — it includes everything DC Shell needs to resolve references and perform timing analysis, including SRAM macros and the * wildcard for cells already in memory.

2. What does analyze -format verilog do that elaborate does not?

  • analyze maps cells from the library; elaborate parses the RTL syntax.
  • analyze reads and parses RTL source files checking for syntax errors; elaborate then connects all modules and builds the full design hierarchy in memory.
  • Both commands do the same thing; only one is needed.
  • analyze is optional; elaborate reads the RTL source automatically.
Correct! analyze is the parsing step — it reads each source file and checks syntax. elaborate is the linking step — it resolves module instantiations and builds the complete hierarchical design in DC Shell memory.

3. Why are all LVT cells blocked with set_dont_use, but CKLNQD8BWP40P140LVT is selectively re-enabled?

  • CKLNQD8BWP40P140LVT is actually an HVT cell that happens to contain "LVT" in its name.
  • All LVT cells must remain available for compile_ultra to meet timing.
  • LVT cells are excluded to control leakage, but CKLNQD8BWP40P140LVT is specifically needed as the ICG cell for clock gating insertion by compile_ultra -gate_clock.
  • set_dont_use only blocks cells in set_target_library, not set_link_library.
Correct! LVT cells are excluded in bulk to minimize leakage. The single exception, CKLNQD8BWP40P140LVT, is the specific latch-based ICG cell named in set_clock_gating_style. Without re-enabling it, compile_ultra -gate_clock would have no available ICG cell to insert.

4. Why is the DDC file (tile_synthesis.ddc) written in addition to the Verilog netlist?

  • DC Shell requires the DDC to be written before it can produce the Verilog netlist.
  • The DDC saves the complete design state after synthesis — netlist, libraries, and constraints — so it can be reloaded for incremental work or re-reporting without re-running synthesis.
  • The DDC replaces the SDC file for place-and-route timing constraints.
  • DC Shell automatically generates the DDC; write_file just renames it.
Correct! The DDC database is a full checkpoint of the DC Shell session. Reloading it with read_file restores the exact synthesized state, allowing additional reports or incremental optimization without re-running the hours-long compilation.
