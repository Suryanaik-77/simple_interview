Problem Statement

GUIDED

You have completed static timing analysis on the tile design in Lab 28 using Tempus. The STA run produced a timing database that captures the design's timing state across all corners. Now you need to perform signoff-quality ECO (Engineering Change Order) optimization using Tempus in DMSA (Distributed Multi-Scenario Analysis) mode to fix setup, hold, and design rule violations before handing the design off to the physical implementation tool (Innovus) for final updates.

The Tempus DMSA ECO flow reads the timing database from Lab 28, applies targeted optimizations for setup timing, hold timing, and design rule violations (DRV), and generates an ECO script that Innovus can consume to implement the required cell changes in the physical design.

The script you will analyze and run produces the following key outputs:

../outputs/SETUP_eco.db        # Database after setup ECO optimization
../outputs/HOLD_eco.db         # Database after hold ECO optimization
../outputs/DRV_eco.db          # Database after DRV ECO optimization
../outputs/eco.tcl             # Final ECO commands for Innovus
../outputs/eco.db              # Final timing database with all ECOs applied
../reports/setup.final_summary.rpt    # Setup timing summary after all fixes
../reports/hold.final_summary.rpt     # Hold timing summary after all fixes
../reports/setup.final_violators.rpt  # Remaining setup DRV violators
../reports/hold.final_violators.rpt   # Remaining hold DRV violators

Your task: Understand each step of the Tempus DMSA ECO script, run the flow, and verify that all outputs and reports are generated successfully.

🔗 How Your Lab 28 Session Feeds This Lab

Session Database: tile_session_timing.db

The timing database you generated in Lab 28 contains the complete timing state of the tile design across all PVT corners and operating modes. It includes the loaded libraries, annotated SPEF parasitics, propagated clocks, SI settings, and the fully computed timing graph with delays and slacks for every path.

In this lab, the read_db command restores this entire state in one step — no need to re-read LEFs, re-load the netlist, re-configure MMMC views, or re-annotate SPEF files. Everything is already captured in the session database.

This is why DMSA is so powerful: the complex multi-corner STA setup happens once (in Lab 28), and then gets reused here for ECO optimization. The optimizer starts with signoff-quality timing data from the very first command, enabling it to make precise, multi-corner-aware ECO decisions immediately.

📝 Analysis

Signoff ECO optimization is a critical step in the chip design flow that bridges the gap between static timing analysis and physical implementation. After STA identifies timing violations, the ECO engine determines the minimal set of cell-level changes needed to fix them.

  • Why DMSA mode: In multi-corner multi-mode (MCMM) designs, timing must be clean across all operating conditions simultaneously. DMSA mode allows Tempus to consider all scenarios at once when computing ECO fixes, ensuring that fixing a violation in one corner does not introduce a new violation in another.
  • Why the order matters (Setup, then Hold, then DRV): Setup fixes may resize cells to faster variants, which can affect hold timing. Hold fixes typically insert delay buffers, which can affect transition times. DRV fixes address remaining design rule violations (max transition, max capacitance, max fanout) that may have been introduced by the earlier ECO steps. This ordering minimizes iteration.
  • Path groups for targeted optimization: Rather than optimizing all paths at once, the script defines path groups (register-to-register, input-to-register, etc.) so the ECO engine can focus on the most critical path categories and report results per group.
  • ECO output for Innovus: The final write_eco -format innovus command generates a TCL script containing cell swap, cell insertion, and net reconnection commands that Innovus can execute to physically implement the timing fixes.

This flow assumes you have already completed Lab 28 (Tempus STA) and that the timing database tile_session_timing.db is available in the inputs directory.

📝 Step-by-Step Solution

  • Step 1: Set Design Name and CPU Usage

    The script begins by configuring the number of CPU cores for parallel processing and defining the design name.

    ############################
# setting number of cpus
############################
set num_cores  8
set design_name tile
set_multi_cpu_usage -local_cpu $num_cores -remote_host $num_cores

    Explanation:

    • set num_cores 8 -- Defines a TCL variable holding the number of CPU cores to use.
    • set design_name tile -- Stores the design name in a variable. This is used later when reading the timing database file.

  • Step 2: Read Timing Database

    The next step loads the timing database that was generated by Lab 28's Tempus STA run. This database contains the complete timing state of the design including the netlist, parasitics, constraints, and timing results across all corners and modes.

    ############################
# reading timing DB
############################
read_db ../inputs/${design_name}_session_timing.db

    Explanation:

    • read_db -- Loads a previously saved Tempus session database. This is much faster than re-reading all the individual input files (libraries, netlist, SDC, parasitics) from scratch.
    • The path ../inputs/${design_name}_session_timing.db resolves to ../inputs/tile_session_timing.db. The script runs from the WORK/ directory, so ../inputs/ points to the testcase's inputs/ folder.
    • This database was produced by Lab 28 and contains MCMM timing data. The make check-env target in the Makefile automatically symlinks it from Lab 28's outputs if it is not already present.

  • Step 3: Source Path Groups

    Path groups categorize timing paths based on their start and end points. By grouping paths, you can control which categories the ECO engine optimizes and generate per-group timing reports for better visibility.

    ############################
# source path_group TCL files
############################
source ../scripts/path_group.tcl

    The path_group.tcl script defines six path groups:

    # Path group definitions for tile design
group_path -from [all_registers -clock_pins] -to [all_registers -data_pins] -name r2r
group_path -from [all_registers -clock_pins] -to [all_outputs] -name r2o
group_path -from [all_inputs] -to [all_outputs] -name i2o
group_path -from [all_inputs] -to [all_registers -data_pins] -name i2r
group_path -from [get_pins -hierarchical *CLK*] -to [all_registers -data_pins] -name m2r
group_path -from [all_registers -clock_pins] -to [get_pins -of [all_macro_cells]] -name r2m

set selected_groups {r2r r2o i2o i2r m2r r2m}

    Path Group Breakdown:

    • r2r (Register-to-Register): Paths from register clock pins to register data pins. These are the core sequential paths and typically represent the bulk of timing-critical paths in a design.
    • r2o (Register-to-Output): Paths from register clock pins to primary outputs. These represent output delay paths where data must arrive at output ports within the specified timing constraints.
    • i2o (Input-to-Output): Combinational paths from primary inputs directly to primary outputs. These are purely combinational feedthrough paths with no register in between.
    • i2r (Input-to-Register): Paths from primary inputs to register data pins. These represent input setup/hold paths where external data must arrive at internal registers within timing requirements.
    • m2r (Macro-to-Register): Paths from macro cell clock pins (matched by *CLK*) to register data pins. These capture timing paths originating from memory or IP block clock outputs.
    • r2m (Register-to-Macro): Paths from register clock pins to macro cell pins. These capture data paths feeding into memory or IP blocks.

    The selected_groups variable collects all six group names into a list. This variable is used in subsequent steps to tell the ECO engine which path groups to include in setup and hold optimization.

  • Step 4: Enable Multiple Incremental ECO

    By default, Tempus may restrict ECO operations to a single pass. This setting enables multiple incremental ECO passes so that setup, hold, and DRV fixes can be applied sequentially in the same session.

    set_db opt_signoff_allow_multiple_incremental true

    Explanation: When set to true, this attribute allows the opt_signoff command to be called multiple times in the same session, with each call building on the results of the previous one. Without this setting, running opt_signoff a second time would fail or produce unexpected results. This is essential for the three-phase optimization approach (setup, then hold, then DRV).

  • Step 5: Setup Timing Fix

    The first optimization phase targets setup timing violations. Setup violations occur when data arrives too late at a register's data pin relative to the capturing clock edge. The ECO engine fixes these by upsizing cells, swapping to faster cell variants, or restructuring logic.

    ############################
# setup fix
############################
set_db opt_signoff_include_setup_path_groups    $selected_groups
set_db opt_signoff_eco_file_prefix   ../outputs/SETUP_FIX
set_db opt_signoff_write_eco_opt_db  ../outputs/SETUP_eco.db

opt_signoff -setup -update_timing

    Explanation:

    • set_db opt_signoff_include_setup_path_groups $selected_groups -- Specifies which path groups to include in setup optimization. By passing all six groups (r2r, r2o, i2o, i2r, m2r, r2m), the engine will attempt to fix setup violations in all path categories.
    • set_db opt_signoff_eco_file_prefix ../outputs/SETUP_FIX -- Sets the prefix for ECO output files generated during this phase. Tempus will create files like SETUP_FIX.eco in the outputs directory.
    • set_db opt_signoff_write_eco_opt_db ../outputs/SETUP_eco.db -- Instructs Tempus to save a snapshot of the timing database after setup ECO optimization. This database captures the design state with setup fixes applied.
    • opt_signoff -setup -update_timing -- Executes the setup ECO optimization. The -setup flag targets only setup violations. The -update_timing flag forces a timing update after applying fixes, ensuring that subsequent operations (hold fix) see the current timing state.

  • Step 6: Hold Timing Fix

    The second optimization phase targets hold timing violations. Hold violations occur when data changes too quickly at a register's data pin after the capturing clock edge. The ECO engine fixes hold violations primarily by inserting delay buffers to slow down fast data paths.

    ############################
# hold fix
############################
set_db opt_signoff_include_hold_path_groups  $selected_groups
set_db opt_signoff_eco_file_prefix           ../outputs/HOLD_FIX
set_db opt_signoff_write_eco_opt_db          ../outputs/HOLD_eco.db

opt_signoff -hold -update_timing

    Explanation:

    • set_db opt_signoff_include_hold_path_groups $selected_groups -- Specifies path groups for hold optimization. The same six groups are targeted.
    • set_db opt_signoff_eco_file_prefix ../outputs/HOLD_FIX -- ECO output files for this phase will have the HOLD_FIX prefix.
    • set_db opt_signoff_write_eco_opt_db ../outputs/HOLD_eco.db -- Saves the database snapshot after hold fixes.
    • opt_signoff -hold -update_timing -- Executes hold ECO optimization with timing update.

    Why hold is fixed AFTER setup: Setup fixes often upsize cells to faster variants, which makes data arrive earlier. While this fixes setup violations, it can worsen or create hold violations because data now arrives too quickly. By fixing hold after setup, the hold ECO engine accounts for the cell changes already made and only inserts delay buffers where truly needed. Reversing this order would be inefficient -- fixing hold first and then changing cells for setup could undo the hold fixes.

  • Step 7: Design Rule Violation (DRV) Fix

    The third and final optimization phase addresses design rule violations. DRVs are physical constraints imposed by the technology library and foundry rules that must be satisfied for the design to function correctly in silicon.

    ############################
# drv fix
############################
set_db opt_signoff_eco_file_prefix  ../outputs/DRV_FIX
set_db opt_signoff_write_eco_opt_db ../outputs/DRV_eco.db
opt_signoff -drv -update_timing

    Explanation:

    • opt_signoff -drv -update_timing -- Targets design rule violations specifically. The three main DRV categories are:
      • max_transition: The signal transition time (slew) at a pin exceeds the library-specified maximum. This can cause excessive current draw and unreliable switching. Fixed by upsizing the driving cell or adding buffers to reduce load.
      • max_capacitance: The total capacitive load on a net exceeds the driving cell's rated maximum. This can lead to slow transitions and timing degradation. Fixed by inserting buffers to split the load or upsizing the driver.
      • max_fanout: A single output drives too many inputs. This is closely related to max_capacitance but is specified as a count limit. Fixed by cloning the driver or inserting buffer trees.

    DRV fixes are performed last because the setup and hold ECO steps may have introduced new cells (buffers, resized gates) that could create new DRV issues. By running DRV last, the engine addresses all remaining violations in a single pass.

  • Step 8: Generate Final Reports

    After all three optimization phases are complete, the script generates timing summary reports and constraint violation reports. These reports provide the final signoff-quality timing picture of the design.

    ############################
# final reports
############################
report_timing_summary -checks {setup drv} > ../reports/setup.final_summary.rpt
report_timing_summary -checks {hold drv}  > ../reports/hold.final_summary.rpt
report_constraint -late -all_violators -drv_violation_type {max_capacitance max_transition max_fanout} > ../reports/setup.final_violators.rpt
report_constraint -early -all_violators -drv_violation_type {min_capacitance min_transition min_fanout} > ../reports/hold.final_violators.rpt

    Explanation:

    • report_timing_summary -checks {setup drv} -- Produces a summary of setup timing and DRV status across all corners and modes. The output shows the worst negative slack (WNS), total negative slack (TNS), and violation counts per path group. This report goes to ../reports/setup.final_summary.rpt.
    • report_timing_summary -checks {hold drv} -- Same as above but for hold timing checks. Written to ../reports/hold.final_summary.rpt.
    • report_constraint -late -all_violators -drv_violation_type {max_capacitance max_transition max_fanout} -- Lists all remaining late-mode (setup-related) DRV violators. The -all_violators flag ensures every violation is reported, not just the worst. Output goes to ../reports/setup.final_violators.rpt.
    • report_constraint -early -all_violators -drv_violation_type {min_capacitance min_transition min_fanout} -- Lists all remaining early-mode (hold-related) DRV violators. Written to ../reports/hold.final_violators.rpt.

    Review these reports after the run completes. Ideally, the violator reports should show zero or minimal remaining violations. The timing summary reports will show the final WNS and TNS across all path groups.

  • Step 9: Generate ECO Script and Save Final Database

    The final step exports all accumulated ECO changes as an Innovus-format script and saves the complete timing database for future reference.

    ############################
# generate eco
############################
write_eco -format innovus ../outputs/eco.tcl
write_db -sdc ../outputs/eco.db

exit

    Explanation:

    • write_eco -format innovus ../outputs/eco.tcl -- Exports all ECO changes (from setup, hold, and DRV fixes) as a TCL script in Innovus format. This script contains commands such as ecoAddRepeater, ecoSwapCell, and ecoDeleteRepeater that Innovus can execute to physically implement the timing fixes in the placed-and-routed design. This is the bridge between signoff STA and physical implementation.
    • write_db -sdc ../outputs/eco.db -- Saves the final timing database including SDC constraints. This database captures the post-ECO timing state and can be reloaded for further analysis or verification without re-running the entire flow.
    • exit -- Closes the Tempus session.

    ECO workflow in practice: After generating eco.tcl, the physical design engineer sources this script in Innovus to apply the cell-level changes. Innovus then performs incremental placement and routing to accommodate the new or resized cells. After that, parasitics are re-extracted and a new Tempus STA run confirms that the fixes are effective in the updated physical context. This iterative loop continues until signoff closure is achieved.

🧠 Knowledge Assessment

1. Why is setup timing fixed before hold timing in the Tempus DMSA ECO flow?

  • Setup violations are always more numerous than hold violations.
  • Setup fixes upsize cells to faster variants, which can create or worsen hold violations; fixing hold afterward accounts for these changes.
  • Hold violations cannot be detected until setup is clean.
  • The Tempus license requires setup optimization to run first.
Correct! Setup fixes often swap cells to faster variants, causing data to arrive earlier. This can create new hold violations. By fixing hold after setup, the hold ECO engine sees the updated timing and only adds delay where truly needed.

2. What does the set_db opt_signoff_allow_multiple_incremental true setting enable?

  • It allows Tempus to run on multiple CPU cores simultaneously.
  • It enables the tool to read multiple timing databases in one session.
  • It allows multiple sequential opt_signoff calls (setup, hold, DRV) in the same session, each building on the previous results.
  • It permits overwriting existing ECO database files without confirmation.
Correct! By default, opt_signoff may restrict to a single invocation per session. Setting this attribute to true enables the three-phase approach where setup, hold, and DRV fixes are applied incrementally in sequence.

3. What is the purpose of the write_eco -format innovus ../outputs/eco.tcl command?

  • It generates a timing constraints file (SDC) for Innovus.
  • It exports the netlist in Verilog format for Innovus to read.
  • It creates a floorplan DEF file for Innovus placement.
  • It exports all accumulated ECO cell changes as a TCL script that Innovus can execute to physically implement the timing fixes.
Correct! The eco.tcl file contains Innovus-format commands (ecoAddRepeater, ecoSwapCell, etc.) that implement the cell-level changes determined by Tempus. Innovus uses these to update the physical design.

4. Which of the following is NOT a design rule violation (DRV) type addressed by opt_signoff -drv?

  • max_transition -- signal slew exceeds the library maximum.
  • max_frequency -- the clock period is shorter than the combinational delay.
  • max_capacitance -- the net load exceeds the driving cell's rated maximum.
  • max_fanout -- a single output drives too many inputs.
Correct! max_frequency is not a DRV type. Frequency-related issues are addressed through setup timing optimization, not DRV fixes. The three standard DRV types are max_transition, max_capacitance, and max_fanout.
