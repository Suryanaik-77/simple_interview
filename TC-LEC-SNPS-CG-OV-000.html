📚 Theory and Background

What is RTL-to-Gate LEC?

After synthesis, the gate-level netlist must be logically equivalent to the original RTL. Logic Equivalence Checking (LEC) formally proves this equivalence by comparing the Boolean function at every register output and primary output between the two representations. Unlike simulation, LEC is exhaustive — it proves equivalence for all possible input combinations.

The Synopsys Verification File (SVF)

During synthesis, Design Compiler and Genus automatically write an SVF file recording every structural transformation they performed: register renaming, constant propagation, sequential optimizations, and clock gating insertion. Formality reads this file before matching compare points so it knows how to correlate renamed or restructured logic between the two designs. Without the SVF, Formality relies on name matching alone and may fail on transformed logic.

Key rule: Always load the SVF with set_svf before any read_verilog command. Loading it after reading the designs has no effect.

Clock Gate Verification Attributes

When synthesis inserts Integrated Clock Gating (ICG) cells, the gate-level netlist contains latch-based enable logic that does not exist in the RTL. Formality must be told how to interpret these structures so it can correctly map the RTL enable signal to the ICG cell output. Three attributes control this:

  • set verification_clock_gate_reverse_gating true — tells Formality to reverse the clock gating transformation when matching, so the ICG cell in the implementation is mapped back to the original RTL enable logic. This is the most critical attribute. Without it, every ICG-gated register appears as an unmatched point and verification fails.
  • set verification_clock_gate_hold_mode low — specifies the hold phase of the clock gating latch (active-low). Must match the ICG cell type used in the PDK.
  • set verification_clock_gate_edge_analysis true — enables edge-sensitive analysis of gated clocks for more accurate mapping.
Common failure: Omitting verification_clock_gate_reverse_gating produces Verification FAILED with a large number of failing points at the outputs of ICG-gated registers. The Formality log will contain messages like FMR_ELAB-115 or unmatched sequential compare points.

Formality Flow Overview

A complete RTL-to-gate Formality run follows these steps in order:

  1. Set global verification attributes (clock gate settings, synopsys_auto_setup)
  2. Load SVF with set_svf
  3. Read reference design (RTL) with read_verilog -r
  4. Set reference top: set_top r:/WORK/<module>
  5. Read technology libraries with read_db
  6. Read implementation (gate-level netlist) with read_verilog -i
  7. Set implementation top: set_top -auto
  8. Match compare points: match
  9. Prove equivalence: verify
  10. Generate reports

🧠 Knowledge Assessment

1. What does set verification_clock_gate_reverse_gating true tell Formality to do?

  • Remove all clock gating cells from the gate-level netlist before verification.
  • Reverse the clock gating transformation so ICG cells in the implementation are mapped back to the original RTL enable logic for correct comparison.
  • Insert clock gating cells into the RTL reference design to match the implementation.
  • Disable clock gating analysis entirely and treat gated registers as ungated.
Correct! This attribute instructs Formality to undo the clock gating insertion during matching, correlating each ICG-gated register in the netlist back to its RTL flip-flop with enable logic.

2. Why must the SVF be loaded with set_svf before any read_verilog command?

  • Because read_verilog automatically reads the SVF from the same directory.
  • Because Formality checks the SVF file permissions at startup and rejects it if loaded later.
  • Because the SVF must be active before designs are read so Formality can apply SVF-guided transformations during the read and elaboration phases.
  • Because the SVF contains the file paths for the RTL source files that read_verilog needs.
Correct! Formality processes SVF directives during design reading and elaboration. Loading the SVF after read_verilog means those transformations are not applied, causing match failures on renamed or restructured logic.

3. Formality reports Verification FAILED with many failing points at register outputs. The most likely cause is:

  • The RTL filelist is missing one source file.
  • The technology .db library was not loaded.
  • The verification_clock_gate_reverse_gating attribute is missing, so ICG-gated registers cannot be matched.
  • The set_top command used the wrong module name.
Correct! When verification_clock_gate_reverse_gating is absent, Formality cannot correlate ICG cells in the implementation to RTL enables, producing failures at every clock-gated register output.

4. What is the purpose of the match command in the Formality flow?

  • It runs formal equivalence proof between all compare points.
  • It checks whether the RTL and netlist have the same number of flip-flops.
  • It pairs each RTL compare point (register output, primary output) with its corresponding gate-level counterpart, guided by the SVF and name matching.
  • It reads the SVF and applies all recorded synthesis transformations to the reference design.
Correct! match performs the compare-point pairing step. Only after a successful match can verify perform the formal proof on each paired point.
