Problem Statement

GUIDED

You will perform the complete Floorplan stage in ICC2 for the tile processor core. Starting from the initialized design block saved in the Design Init stage, you will size the die, place ports, import macro placement, build a full power distribution network, insert physical-only cells, and verify the result using five quality reports.

📄 Floorplan — Step-by-Step Command Explanation

Below is a complete walkthrough of every command you will write into ../scripts/script.tcl. Follow the workflow below: write your commands into the script in a separate editor, source the script inside ICC2, then exit.

  • Navigate to TC-PNR-SNPS-FP-GD-001 and Launch ICC2

    You have already set up the lab directory structure using the provided setup guidelines. The required input files are now available in the testcase directory. With the lab environment ready, proceed with the following steps.

    Navigate to the testcase directory and launch ICC2 using the Makefile:

    cd ~/pd/labs/PNR-SNPS-FP/TC-PNR-SNPS-FP-GD-001
make all

    This starts an interactive icc2_shell session. ICC2 is now waiting for commands — do not type anything yet.

    Open ../scripts/script.tcl in a new editor window directly from the shell using sh gvim:

    sh gvim ../scripts/script.tcl &

    Write each command into the script as you follow the steps below. Once all commands are written, source the script from inside icc2_shell:

    source ../scripts/script.tcl

    Observe what each command does as it runs — read the output carefully to understand the effect of each step before moving to the next.

  • Open the Design Library and Load the Init Block

    • open_lib — opens the NDM container on disk. ICC2 re-reads the technology file and all NDM reference library links stored inside it (standard cells + SRAM macros).
    • open_block init_design.design — loads the named block from the NDM. This restores the exact design state (netlist, MMMC, timing) saved at the end of Design Init.
    open_lib ../inputs/tile.ndm
open_block init_design.design
    Expected output: ICC2 prints Information: Loading library file '...tile.ndm' (FILE-007) followed by loading messages for each NDM reference library. If you get an error about a missing block, the Design Init lab was not completed — run it first and save the block.

  • Set Metal Layer Routing Directions and Ignored Layers

    Defines the preferred routing direction for each metal layer. ICC2 uses these to organize routing tracks and check wire direction violations. These must be set before initializing the floorplan so the router knows which layers are horizontal or vertical when building the site and track grid.

    • M1, M3, M5, M7, M9 → Horizontal: These layers carry wires left-to-right. M1 horizontal rails carry VDD/VSS to standard cells; odd signal layers route horizontally.
    • M2, M4, M6, M8, AP → Vertical: Even layers and the AP (aluminum pad) layer run vertically.
    • Alternating H/V directions between adjacent layers maximizes routing density and minimizes layer crossings.
    set_attribute [get_layers {M1 M3 M5 M7 M9}] routing_direction horizontal
set_attribute [get_layers {M2 M4 M6 M8 AP}] routing_direction vertical

    set_ignored_layers restricts signal routing to M1–M9. Layers outside this range (below M1 or above M9) will not be used by the router.

    set_ignored_layers -min_routing_layer M1 -max_routing_layer M9

  • Initialize the Floorplan (initialize_floorplan)

    This command creates the die boundary, core area, site rows, and routing track grid. Everything physical in the design lives inside the canvas this command creates.

    Option Meaning
    -side_ratio {1 1} Core aspect ratio (Width : Height). {1 1} produces a square core. Choose based on how macros fit and which edges have more routing demand.
    -core_offset {0.84 0.9} Gap between the core boundary and the die boundary. Format: {left/right top/bottom} in µm. These small offsets (0.5–2 µm at block level) prevent DRC violations when two blocks abut at the chip level.
    -core_utilization 0.7 70% of the core area will be occupied by standard cells + macros. The remaining 30% provides routing channels, space for clock tree buffers, and margin for timing fixes during placement. Starting at 70% is industry standard for complex designs. 
    initialize_floorplan -side_ratio {1 1} -core_offset {0.84 0.9} -core_utilization 0.7
    Expected output:
    Creating core...
    Core utilization ratio = 70.01%
    Creating site array... Creating routing tracks...
    Initializing floorplan completed.

    The minor difference (70.01% vs 70.0%) is normal — ICC2 rounds to the nearest legal site boundary. The core dimensions are computed automatically from total cell area and the utilization target.

  • Place Design Ports (create_pin_guide + place_pins)

    Ports are the interface between the tile block and the outside world. They must be placed on the die boundary on legal routing tracks before placement begins.

    create_pin_guide defines a rectangular region on the die boundary where ports will be placed. ICC2 restricts all port placement to inside this region.

    • -boundary {{1022.3100 1081.7450} {383.7500 1151.3750}} — two corners of the guide rectangle on the die periphery (in µm). These coordinates define a region on the top edge of the tile block where all ports will be placed.
    • -layers {M6} — place ports on Metal 6. M6 is a vertical layer that provides low-resistance block boundary connections with less congestion than lower metals.
    • -name O — name for this guide object. [get_ports *] applies it to all ports.
    create_pin_guide -boundary {{1022.3100 1081.7450} {383.7500 1151.3750}} \
    -layers {M6} -name O [get_ports *]

    place_pins automatically places all ports inside the guide on legal M6 routing tracks.

    place_pins -ports [get_ports *]
    Expected output: Information: Starting 'place_pins' (FLW-8000) ... Information: Ending 'place_pins' (FLW-8001) with Number of pins created: 1635. A warning about relaxed pin spacing (DPPA-004/DPPA-379) is normal for dense port designs — ICC2 relaxed the inter-pin spacing constraint to fit all 1635 ports.

  • Import Macro Placement from DEF (read_def)

    Reads the macro placement DEF file. This file specifies the exact X/Y coordinates and orientation of all 18 SRAM macros in the tile design. After this command, all macros appear at fixed locations inside the ICC2 canvas.

    • Macros placed via DEF get status FIXED — ICC2 will not move them during standard cell placement.
    • Macro placement quality matters: poor macro placement creates routing bottlenecks, hot spots, and timing issues downstream.
    • Good macro placement keeps SRAMs near the logic that accesses them and leaves clear routing channels between macro clusters.

    The script checks for the DEF file before reading it. If the file is missing, the script exits with a warning rather than silently continuing with no macro placement:

    set user_floorplan_file ../inputs/floorplan.def
if {[file exists $user_floorplan_file]} {
     puts "MyInfo: Souring floorplan file $user_floorplan_file"
     read_def $user_floorplan_file
} else {
    puts "MyInfo: No floorplan file exists $user_floorplan_file"
    return
}
    Expected output: MyInfo: Souring floorplan file ../inputs/floorplan.def followed by DEF reading messages ending with COMPONENTS: 18/18 — confirming all 18 SRAM macros were loaded. After read_def, verify in the GUI (start_gui) that all macros are inside the core area with no overlaps and clear routing corridors between macro groups.

  • Insert Boundary Cells (Endcaps)

    Endcap cells are physical-only cells (no logic) placed at the left and right ends of every standard cell row. They serve two purposes:

    • Well Proximity Effect (WPE) mitigation: During ion implantation, transistors near N-well edges shift their threshold voltage (Vth). Endcaps absorb this effect, shielding functional cells at row ends from unpredictable Vth variation and timing shifts.
    • DRC compliance: Satisfy well termination design rules at row boundaries required by the foundry.
    Command Description
    set_boundary_cell_rules
    -left_boundary_cell <lib/cell>
    -right_boundary_cell <lib/cell>
    -prefix ENDCAP    		 Registers the left and right endcap cell types from the HVT library. The -prefix sets the instance name prefix in the netlist. Must be called before compile_boundary_cells.
    compile_boundary_cells Inserts endcap cells at both ends of every standard cell row in the core. ICC2 automatically determines the correct orientation (normal/flipped) for each row.
    check_boundary_cells Verifies that all rows have valid boundary cells at both ends. Reports any missing or incorrectly placed endcaps. 
    set_boundary_cell_rules \
    -left_boundary_cell  tcbn28hpcplusbwp40p140hvt/BOUNDARY_LEFTBWP40P140 \
    -right_boundary_cell tcbn28hpcplusbwp40p140hvt/BOUNDARY_RIGHTBWP40P140 \
    -prefix ENDCAP
compile_boundary_cells
check_boundary_cells
    ICC2 T-2022 prints a deprecation warning for compile_boundary_cells — this is harmless. The command works correctly. The future replacement is compile_targeted_boundary_cells.

  • Create Power/Ground Nets and Block-Level Ports

    Before the power grid can be built, ICC2 must know which nets carry power and ground. These are declared as special PG net types, and matching block-level ports are created.

    Command Description
    create_net -power VDD Creates the VDD net and marks it as a power net. Power nets are treated differently by the PG router — they are not subject to signal routing DRC rules.
    create_net -ground VSS Creates the VSS net and marks it as ground.
    create_port -port_type power -direction in VDD Creates a block-level VDD power port — the physical connection point where power enters the tile block from the chip level.
    create_port -port_type ground -direction in VSS Creates the VSS ground port.
    connect_pg_net -net VDD [get_ports VDD] Connects the VDD port to the VDD net, establishing the top-level entry point for power into the block.
    connect_pg_net -net VDD
    [get_pins -physical_context */VDD]    		 Connects VDD pins of all cells to the VDD net. -physical_context ensures physically-placed macro pins are included. A separate call handles */VDDM pins used by some ARM SRAM macros.
    connect_pg_net -net VSS
    [get_pins -physical_context */VSS]    		 Same for all VSS pins across the entire design. 
    create_net -power VDD
create_net -ground VSS
create_port -port_type power -direction in VDD
create_port -port_type ground -direction in VSS
connect_pg_net -net VDD [get_ports VDD]
connect_pg_net -net VSS [get_ports VSS]

connect_pg_net -net VDD [get_pins -physical_context */VDD]
connect_pg_net -net VDD [get_pins -physical_context */VDDM]
connect_pg_net -net VSS [get_pins -physical_context */VSS]

  • Configure PG Routing App Options

    These app options tune the PG router to handle SRAM macro keepout margins correctly:

    App Option Why it is set
    plan.pgroute.treat_fat_blockage_as_fat_metal false ARM SRAMs create large keepout margins. By default ICC2 treats these as fat metal, enforcing wide DRC spacing that creates false violations. Setting this to false disables that behavior.
    plan.pgroute.via_site_threshold 1
    plan.pgcheck.via_site_threshold 1    		 Prevents PG vias from being inserted at sites where only a partial overlap exists with a macro boundary. Without this, vias near macro edges cause DRC violations during signoff. 
    set_app_options -name plan.pgroute.treat_fat_blockage_as_fat_metal -value false
set_app_options -name plan.pgroute.via_site_threshold -value 1
set_app_options -name plan.pgcheck.via_site_threshold -value 1

  • Build the Power Distribution Network (source power_plan.tcl)

    Sources the power planning script that builds the complete multi-layer power grid — from M1 standard cell rails up to M9 top-level power trunks, with inter-layer vias connecting every level.

    source -e -v ../inputs/power_plan.tcl

    What each section of power_plan.tcl does:

    Layer / Step Key Commands What it does
    Routing blockages on macros create_keepout_margin -type routing_blockage -layers {M1 M4 M5} Creates routing blockages on M1, M4, and M5 around every macro keepout margin. Prevents the PG router from placing power wires over restricted macro boundary zones.
    Disable auto vias set_app_options -name plan.pgroute.disable_via_creation -value true Suppresses automatic via insertion during compile_pg. All vias are created explicitly at the end, giving full control over via types and locations.
    M1 rails create_pg_std_cell_conn_pattern M1_rails -layers {M1} -rail_width 0.15
    set_pg_strategy M1_stg -core
    compile_pg -strategies M1_stg    		 Lays horizontal M1 VDD and VSS rails through every standard cell row. Width = 0.15 µm (minimum for this layer). VDD and VSS rails alternate between adjacent rows to match standard cell library pin layout.
    M4/M5 fine mesh create_pg_mesh_pattern M4M5_pattern
    set_pg_strategy ... -blockage {macros: all}
    compile_pg    		 Fine-pitch PG mesh: M4 vertical (0.15 µm wide, 7 µm pitch) and M5 horizontal (0.15 µm wide, 7 µm pitch). Mesh is blocked over macros so it does not route through SRAM internal areas. This mesh collects current from M1 rails and feeds it up to M6/M7.
    M6/M7 mid-level stripes create_pg_mesh_pattern M6M7_pattern
    set_pg_strategy ... -core
    compile_pg    		 Medium stripes: M6 vertical (0.5 µm wide, 7 µm pitch) and M7 horizontal (0.5 µm wide, 7 µm pitch). Wider than M4/M5 to carry more current over longer distances. These distribute power from the M8/M9 trunks down into the M4/M5 mesh.
    M8/M9 power trunks create_pg_mesh_pattern M8toM9
    set_pg_strategy top_pg -design_boundary
    compile_pg    		 Wide top-level trunks: M9 horizontal (3 µm wide, 7.3 µm pitch) and M8 vertical (3 µm wide). These carry the full chip supply current from external pads into the grid. -design_boundary extends stripes to the die edge for chip-level power connections.
    Vias M9→M4 create_pg_vias -from_layers M9 -to_layers M8
    (repeated for each adjacent pair: M8/M7, M7/M6, M6/M5, M5/M4)    		 Creates default inter-layer vias connecting adjacent metal layers from M9 down to M4. Standard minimum-size via types are adequate at these upper levels where spacing is generous.
    Vias M4→M1 (custom rules) set_pg_via_master_rule via1_rule -contact_code VIA12_1cut -via_array_dimension {1 1}
    create_pg_vias -from_layers M4 -to_layers M1 -via_masters {via1_rule via2_rule via3_rule}    		 Uses explicitly defined 1×1 single-cut via rules for M4→M3→M2→M1. Single-cut vias are required at lower layers where tight M4/M5 mesh pitch leaves limited room for wider via arrays.
    Vias over macro pins (M4→M6) set_pg_via_master_rule via4_macro_rule -via_array_dimension {3 1}
    create_pg_vias -from_types macro_pin -from_layers M4 -to_types stripe -to_layers M6    		 Creates 3×1 via arrays from SRAM macro PG pins (on M4) up to the M6 stripes. The larger array improves contact reliability and current-carrying capacity on macro PG pin connections.
    Expected log messages:
    USER_INFO: ####---Start of PG insertion---####
    USER_INFO: ####---End of PG insertion---####
    These puts markers in the script confirm the PG section ran. If a compile_pg call fails, check for missing net connections from Step 7 or overlapping keepout regions.

  • Insert Well-Tap Cells (create_tap_cells)

    Well-tap cells tie the N-well to VDD and the P-substrate to VSS throughout the core. This prevents latch-up — a destructive failure mode in CMOS.

    Why latch-up happens: CMOS contains parasitic P-N-P-N structures (two BJTs). Noise injection can forward-bias a BJT junction (>0.7V), triggering positive feedback and creating a low-resistance VDD-to-VSS short — potentially destroying the chip. Well-tap cells reverse-bias these junctions, preventing the trigger condition. The substrate has non-zero resistance, so taps must be spaced close enough that noise cannot build up sufficient voltage between a transistor and its nearest tap. TSMC 28nm rule: ≤30 µm between any transistor and its nearest tap.
    Option Meaning
    -lib_cell tcbn28hpcplusbwp40p140hvt/TAPCELLBWP40P140 The tap cell from the HVT library. This cell contains N-well and P-substrate contact structures with VDD/VSS connections but no logic.
    -distance 30 Maximum allowed spacing between adjacent tap cells in µm. Matches TSMC 28nm foundry rule.
    -no_1x Avoids inserting single-height tap cells, which can have incompatible well connections with adjacent standard cells in this library.
    -pattern stagger Inserts taps in a staggered (checkerboard) pattern — offset by half the pitch between alternating rows. This gives more uniform tap coverage than a straight column pattern.
    -prefix Welltap Instance name prefix in the netlist (e.g., Welltap_0001).
    -skip_fixed_cells Do not insert taps where a fixed cell (macro, endcap) already occupies the target site. 
    create_tap_cells \
    -lib_cell tcbn28hpcplusbwp40p140hvt/TAPCELLBWP40P140 \
    -distance 30 \
    -no_1x \
    -pattern stagger \
    -prefix Welltap \
    -skip_fixed_cells

  • Reconnect PG Nets and Remove Floating Wires

    Run connect_pg_net again after tap cell insertion to update ICC2's internal connectivity model to include the VDD/VSS pins of the newly inserted tap cells. Then run remove_objects [check_pg_connectivity] to delete any floating PG wire stubs before saving the checkpoint.

    connect_pg_net -net VDD [get_pins -physical_context */VDD]
connect_pg_net -net VSS [get_pins -physical_context */VSS]
remove_objects [check_pg_connectivity]
    check_pg_connectivity returns a collection of floating wire objects. Passing it to remove_objects deletes the dangling stubs in one step. This must be done before save_block — floating wires can cause spurious DRC violations in downstream stages.

  • Save the Floorplan Checkpoint (save_block)

    Creates a named snapshot of the completed floorplan inside tile.ndm. The block name floorplan identifies this checkpoint. The Placement stage will open this block to continue the PnR flow.

    save_block -as floorplan
    Expected: Information: Overwriting block 'floorplan.design' in library 'tile.ndm'. (or "Creating" on first run).

📚 Knowledge Assessment Quiz

1. After check_pg_connectivity you see 336,918 floating standard cells on VDD but 0 floating hard macros. What is your conclusion?

  • Critical failure — re-run connect_pg_net with a wider filter to connect all cells before proceeding.
  • Floorplan passes. Floating standard cells are expected at this stage (cells not yet placed). Only 0 floating hard macros is required for sign-off.
  • The M1 rails were not created — standard cells have no VDD connection point.
  • The power grid only covers macros; a second power grid for standard cells is needed.
Correct! At floorplan stage, standard cells have no physical placement yet, so their PG pins cannot touch the grid. The count of floating standard cells drops to 0 after placement and routing. Hard macros (SRAMs) must be PG-connected at floorplan stage because their pins are already physically placed at fixed coordinates.

2. You add a new SRAM macro to the design. After re-running power_plan.tcl, check_pg_drc reports spacing violations near the new macro. What is the most likely root cause?

  • The M1 rail width of 0.15 µm is insufficient for the new macro's current requirement.
  • The routing blockage for the new macro's keepout margin was not created before compile_pg, so PG wires route inside the macro's restricted zone.
  • The new SRAM NDM was not added to the reference library list in create_lib.
  • The tap cells are too close to the new macro boundary, causing spacing violations.
Correct! The first step in power_plan.tcl creates routing blockages on M1, M4, and M5 around each macro's existing keepout margin. A new macro needs its keepout margin defined first; otherwise the PG router has no knowledge of the restricted zone and may place stripes or vias inside it, causing DRC violations.

3. check_legality reports "A cell is not aligned with a site" for one of the SRAMs. What is the most likely cause?

  • The SRAM NDM does not define a site — regenerate it from the memory compiler.
  • The SRAM's X/Y coordinate in the DEF file is not an integer multiple of the site pitch — snap the coordinate to the nearest legal site.
  • The macro was placed with orientation N but the row requires orientation FN.
  • The core utilization is too high and there is no room for the SRAM at that location.
Correct! Every cell in ICC2 must be placed at coordinates that are exact multiples of the site dimensions (e.g., x-pitch = 0.084 µm in 28nm). If the DEF file specifies a coordinate like X=100.031 µm where the nearest legal site is at 100.044 µm, the cell is off-grid and the legality check fails. Fix the DEF coordinate to snap to the site grid.

4. Why does the power planning script use 3 µm wide stripes on M8/M9 but only 0.15 µm wide wires on M4/M5?

  • Upper layers have minimum width rules that require 3 µm; lower layers have a 0.15 µm minimum.
  • Thinner wires on M4/M5 reduce coupling capacitance to signal wires on adjacent layers.
  • M8/M9 carry the full chip supply current and must meet electromigration (EM) current density limits; M4/M5 carry only local currents to small cell clusters and can be narrow.
  • M8/M9 are reserved for clock routing so the PG stripes must be wide enough to leave room for signal routes.
Correct! Electromigration limits current density to ~1.5–2.5 mA/µm² for copper. M8/M9 top-level trunks carry the aggregate current of the entire chip, so they must be wide (3 µm) to keep current density within the EM limit. M4/M5 mesh wires connect to small local cell clusters, carrying only a fraction of the total current, so 0.15 µm is sufficient.
