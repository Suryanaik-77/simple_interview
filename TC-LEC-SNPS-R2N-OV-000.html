📖 Theory — RTL-to-Gate LEC

What is RTL-to-Gate LEC?

Logical Equivalence Checking (LEC) is a formal verification technique that mathematically proves whether two representations of a design are functionally identical. RTL-to-Gate LEC compares the RTL source code (the golden reference) against the synthesized gate-level netlist (the implementation). Unlike simulation, LEC provides 100% functional coverage by exhaustively verifying all possible input combinations using formal mathematical proof engines.

💡 Key principle: Synthesis tools apply aggressive optimizations — register merging, clock gating, constant propagation, logic restructuring. Each transformation can introduce a functional bug. LEC is the only scalable way to prove that none of these transformations changed the intended behavior.

The Eight Logical Stages of RTL-to-Gate LEC

An RTL-to-Gate LEC run always proceeds through the same eight stages, in a fixed order. Understanding what happens at each stage — and why the ordering is mandatory — is the foundation of diagnosing any LEC failure.

StageWhat HappensWhy Order Matters
1. InitializationRecommended settings are activated: scan flip-flop handling, tie-cell recognition, sequential naming heuristicsMust be first — these settings affect how every subsequent read and matching step behaves
2. SVF LoadingThe Synopsys Verification File is loaded. It records all naming changes and structural transformations the synthesis tool made to produce the netlistMust precede all design reads — Formality applies SVF records during the read phase; loading after reading means all transformation hints are missed
3. Reference ReadAll RTL source files are loaded into the Reference container (r:), the golden behavioral description of the designAll source files for the full design hierarchy must be present; missing files produce unmatched points
4. Reference TopThe top-level module in the reference container is identifiedMust match the synthesis top-level exactly; a wrong top causes all compare points to be unmatched
5. Library LoadLiberty timing databases (.db) are loaded so Formality knows the Boolean function of every standard cell in the implementationOnly needed for the implementation side — RTL is behavioral and needs no library. Missing .db files cause cells to be black-boxed with unknown logic
6. Implementation ReadThe gate-level netlist is loaded into the Implementation container (i:), the result of the synthesis runMust be the exact netlist produced by the same synthesis run that generated the SVF; using an older or newer netlist breaks SVF matching
7. MatchFormality pairs each compare point in the reference with its counterpart in the implementation using SVF guidance and name-based heuristicsMatch quality is the ceiling on LEC coverage — unmatched points are never verified
8. VerifyA SAT-based proof engine checks that every matched pair of logic cones is functionally identical for all possible inputsThe actual formal proof. Any failing point is a real functional difference between RTL and netlist
💡 Why every stage depends on the previous one: SVF records are applied as files are read — not after. Match quality determines what Verify can check. Verify results are only meaningful if Match achieved high coverage. If any earlier stage has a problem, every later stage's results are unreliable.

Common RTL-to-Gate Issues and Fixes

IssueRoot CauseFix
Unmatched compare pointsSVF not loaded or loaded after design reads — transformation records were not applied during container constructionMove SVF loading to the very top of the LEC script, before any design file is read

❓ Why is LEC Necessary?

Synthesis tools apply hundreds of transformations to convert RTL into a gate-level netlist. Each transformation — logic optimization, register merging, clock gating insertion, constant propagation — can silently introduce a functional bug. Functional simulation can only verify the behavior for the test vectors you provide. LEC mathematically proves that the netlist and RTL are identical for every possible input combination.

🔌 Simulation cannot replace LEC. Even with 100% code coverage, simulation only exercises the stimulus you provide. LEC exhaustively checks every possible state using formal mathematics — it closes the gap simulation cannot.
Risk Without LECWhere It Can Be IntroducedConsequence
Logic restructuring errorSynthesis optimizer (DC / Genus)Functional silicon bug — re-spin required
Register merge mistakeSequential optimization during synthesisState machine behavior changes silently
Clock gating logic errorClock-gate insertion passIncorrect enable condition disables valid cycles
Constraint mismatchSDC applied during synthesisDon’t-care conditions produce wrong netlist behavior

When to Run LEC

LEC is not tied to a specific PnR stage — it is triggered by a netlist change. Pure physical operations such as placement, routing, and filler insertion do not modify the gate-level netlist and do not require LEC. Operations that insert, remove, or swap logic cells — synthesis, CTS buffer insertion, hold-fix delay cell insertion, and ECOs — all produce a new netlist that must be re-verified.

Two LEC checkpoints are mandatory in every production sign-off flow: RTL-to-Gate after synthesis (this lab) confirms that the synthesis tool preserved the RTL intent; Gate-to-Gate before tape-out (Lab 14) confirms that the full PnR flow — CTS, hold fixing, and any ECOs — produced a netlist functionally identical to what synthesis delivered. Every ECO between those two bookmarks should also be spot-checked with a Gate-to-Gate run on the affected logic cone.

⚠ Sign-off rule: If the netlist changed, prove equivalence before moving forward. Skipping the pre-tape-out Gate-to-Gate LEC is a direct functional silicon risk that no amount of timing sign-off can compensate for.

⚙️ How Does LEC Work? (High-Level Overview)

Formality performs combinational equivalence checking — it does not simulate. It builds a formal model of both designs and mathematically proves (or disproves) that corresponding output functions are identical for all possible inputs.

The Three Phases

PhaseWhat HappensWhat Can Go Wrong
1. ReadFormality loads both designs into separate containers — RTL into the reference container, netlist into the implementation container. SVF guidance and library cell models are applied during this phase.Missing RTL files, wrong SVF ordering, or absent Liberty databases cause black boxes and unmatched points that propagate into all later phases
2. MatchFormality pairs each output point in the reference (RTL register, primary output) with its counterpart in the implementation (netlist register, primary output) using SVF records and name-based heuristics.Low match rate means large portions of the design are not verified. Always investigate unmatched points before accepting LEC results
3. VerifyFor each matched pair, Formality constructs a miter circuit and uses a SAT solver to check whether any input can produce different outputs between RTL and netlist. If no such input exists, the pair is equivalent.Failing points are real functional bugs. Aborted points indicate cones too complex for the solver — both require engineer investigation
💡 Miter circuit: A miter takes both implementations of the same logic function, XORs their outputs, and asks: “Can this XOR ever be 1?” If yes — the designs differ. If no — they are equivalent. This is the fundamental mathematical operation behind formal equivalence checking.

🔌 Logic Cones and Compare Points

Formality does not check the entire design at once. It divides both designs into logic cones, each bounded by a compare point. It checks each cone pair independently.

What is a Compare Point?

A compare point is any observable signal boundary where equivalence is checked. Formality verifies that the function feeding each compare point in the RTL is identical to the function at the corresponding point in the netlist.

Compare Point TypeExamplesWhy it Matters
Primary outputsModule output portsDirect functional outputs must match RTL exactly
Flip-flop data inputs (D-pins)State registersNext-state logic must be preserved after synthesis
Black-box inputsSRAM address/data/write-enable pinsInterface to unmodeled cells must be unchanged
Clock-gating enable pinsICG cell EN inputGating condition must be logically equivalent to RTL intent

Matched vs Unmatched vs Failing

Matched + FailingCounterpart found; logic differs — functional bugCauses FAILED
UnmatchedNo counterpart found — coverage gap, not a proven bugNot checked; investigate separately

🧐 Knowledge Assessment

❓ 1. What is the primary advantage of LEC over functional simulation for verifying synthesis?

  • A. LEC runs much faster than simulation for large RTL designs
  • B. LEC provides 100% functional coverage by mathematically proving equivalence for all possible inputs, not just the test vectors you supply
  • C. LEC can verify both timing and functionality in a single run
  • D. LEC requires no library files, making it faster to set up than simulation

✓ Correct! LEC uses formal mathematics to exhaustively check every possible state, providing 100% functional coverage. Simulation can only check the specific test vectors you provide, which may miss corner cases and bugs in rarely exercised logic paths.

❓ 2. Why must set_svf be called before any read_verilog command?

  • A. Formality aborts with a fatal error if SVF is loaded after read_verilog
  • B. Formality uses the SVF during the read phase to guide container construction and naming; loading SVF after read_verilog means those hints are missed entirely, leading to more unmatched points
  • C. The SVF is only used for the reference container, so order relative to read_verilog -i does not matter
  • D. set_svf must come before read_verilog only when the SVF is larger than 10 MB

✓ Correct! The SVF records all the naming changes and transformations that synthesis made. Formality applies these records while reading and building the design containers. If the SVF is loaded after reading, Formality has already created the containers without those hints, and match quality degrades significantly.

❓ 3. In RTL-to-Gate LEC, why does Formality need read_db for the netlist side but not for the RTL side?

  • A. RTL files are encrypted and need no library; netlist files are plain Verilog that require a key
  • B. The RTL side is behavioral — Formality reads the RTL logic directly. The netlist side instantiates standard cells whose Boolean functions are defined only in the Liberty .db files
  • C. read_db is optional in RTL-to-Gate LEC and only needed for SRAM macros
  • D. The .db files contain the RTL source code for each standard cell

✓ Correct! RTL describes behavior directly in Verilog constructs that Formality can parse and model without any library. The gate-level netlist, however, instantiates technology cells (NAND2, DFF, MUX, etc.) whose internal logic is only defined in the Liberty .db timing library files.

❓ 4. Formality reports "Verification SUCCEEDED" but also lists 8 unmatched points. What does this mean?

  • A. Verification SUCCEEDED is wrong — unmatched points always indicate a functional bug
  • B. The 8 unmatched points were all proven equivalent by a different method
  • C. The 8 unmatched points were excluded from checking — SUCCEEDED means every matched point is equivalent. The unmatched points are a coverage gap that should be investigated separately
  • D. Unmatched points always correspond to scan-chain flip-flops and can be safely ignored

✓ Correct! “Verification SUCCEEDED” applies only to the matched set. Unmatched points were not checked at all — Formality simply could not find a counterpart for them. They represent coverage gaps and must be investigated (check report_unmatched_points.rpt) to confirm they are benign.
