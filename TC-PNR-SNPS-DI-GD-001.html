  • Create the ICC2 Design Library (create_lib)

    What it does: This is the most important command in the entire init flow. create_lib creates a new ICC2 design library (tile.ndm) on disk. It links two critical inputs:

    • -technology — the process technology file (.tf). This defines all metal layers, via types, minimum spacing rules, and DRC parameters for TSMC 28nm. ICC2 uses this throughout the entire flow from floorplan to sign-off.
    • -ref_libs — a list of NDM reference libraries. These are the physical+timing cell views that ICC2 uses for placement, routing, and timing analysis. You must include every cell type your netlist instantiates: standard cells AND SRAM macros.
    ICC2 data structure — Library and Block:
    • Design Library (.ndm): The top-level container on disk. It stores the technology file pointer, all reference library links, and the design data itself.
    • Block: An individual design unit within a library. Each block is a snapshot of your design at a point in time. You can have multiple named blocks inside one NDM — for example init_design, placed, cts, routed — each representing a different stage checkpoint.
    • This block-based versioning means you can always roll back to a previous stage: if routing fails, open the cts block and try again without re-running the entire flow.
    create_lib \
    -technology ../../pdk/metal_stack/1P9M_4X2Y2R/tf/tsmcn28_9lm4X2Y2RUTRDL.tf \
    -ref_libs [list \

  • Load MMMC Configuration (source mmmc_config.tcl)

    Sources the MMMC configuration file, which defines all timing scenarios. Key commands inside the file:

    Command Description
    create_mode Allocates a named operating mode object. Only one mode is used here: func (functional). Each scenario will reference this mode and source the SDC constraints into it.
    create_corner Allocates a named corner object. This only creates the container — PVT values are set separately by the set_voltage, set_temperature, and set_process_number commands that follow.
    read_parasitic_tech Loads a TLU+ model file into the library under a given name (e.g. -name cw). The model is not yet linked to any corner — that is done by set_parasitic_parameters.
    set_voltage / set_temperature / set_process_number Sets the PVT operating point for the current corner. set_voltage 0.81 -object_list VDD sets the supply rail; set_voltage 0.00 -object_list VSS sets ground; set_temperature sets the junction temperature; set_process_number 1.0 uses nominal process (1.0 = no process skew beyond what the library corner encodes).
    set_operating_conditions -analysis_type on_chip_variation Enables OCV analysis mode for the corner — ICC2 will compute separate early and late delays for each path, allowing different derates to be applied to data and clock paths within the same scenario.
    set_parasitic_parameters -early_spec <name> -late_spec <name> -corners Associates a loaded TLU+ model with a corner for early (fast) and late (slow) RC extraction. For this design both early and late use the same model per corner (e.g. both -early_spec rcw -late_spec rcw for the rcw corner) — the OCV guard-band is handled by the derate values, not by different parasitic models.
    create_scenario Combines a mode and a corner into a named scenario — the unit ICC2 uses for timing analysis.
    source <sdc> Sources the SDC constraints into the active scenario. The same SDC file (tile.synthesis.sdc) is sourced once per scenario by switching current_scenario before each source call — all 4 scenarios receive identical timing constraints.
    set_scenario_status -setup true -hold false [get_scenarios *setup*] Enables setup analysis and disables hold for setup scenarios. Setup is checked at the slow (ssg) corner — hold checking here would give misleadingly loose results since hold violations only close at the fast corner.
    set_scenario_status -setup false -hold true [get_scenarios *hold*] Enables hold analysis and disables setup for hold scenarios. Hold is checked at the fast (ffg) corner — setup analysis here would be overly optimistic and not representative of worst-case timing. 
    source -e -v ../inputs/mmmc_config.tcl
    • -e — abort immediately if any error is encountered inside the script, preventing silent failures from propagating.
    • -v — echo every command as it executes, making it easy to pinpoint which line failed when debugging MMMC issues.

  • Apply OCV Derating Factors (source derate.tcl)

    Sources the OCV derate file, which applies per-corner timing guard-bands. Key commands inside the file:

    Command / Flag Description
    foreach_in_collection [all_scenarios] Loops over all active scenarios so derates are applied per-corner, not globally.
    current_scenario / current_corner Sets the active scenario and corner context before applying derates.
    -late Scales the late (slow) path — used for setup analysis. Value >1.0 adds pessimism to the slow path. ssg corners use 1.02; ffg corners use 1.10 (larger guard-band because the fast process corner needs more pessimism to stay safe).
    -early Scales the early (fast) path — used for hold analysis. Value <1.0 adds pessimism to the fast path. ssg corners use 0.90; ffg corners use 0.98.
    -cell_delay Scales gate delay to model transistor-level OCV — variation in drive strength across the die.
    -net_delay Scales wire (interconnect) delay to model RC variation due to manufacturing tolerances in metal width and spacing.
    -data / -clock Applies derate separately to data paths and clock paths. Clock paths use the same values here but can be tightened independently.
    -corner Scopes the derate to a specific corner so each corner gets its own guard-band values.
    report_timing_derate Prints the applied derate table per corner — use this to confirm all values were set correctly. 
    source -e -v ../inputs/derate.tcl

  • Save the Design Block (save_block)

    What it does: Commits the current state of the design — including the netlist, all MMMC scenario/corner/mode definitions, and OCV derate settings — to a named block inside the NDM library. The block name init_design labels this as the checkpoint for the initialization stage.

    save_block -as init_design
    💡 Why named blocks? ICC2 uses a block versioning system inside each NDM library. By saving with -as init_design, you create a permanent snapshot that can be loaded later with open_block ../outputs/tile.ndm:init_design. Subsequent stages (floorplan, placement) will save their own named blocks (fp_design, place_design, etc.) — you can always roll back to init_design if something goes wrong downstream.

  • Sanity Checks — Why They Cannot Be Skipped

    ⚠️ Golden Rule of Physical Design: Never proceed to the next design stage until all sanity checks pass. Issues compound as you move forward in the flow — a missing library caught here takes 5 minutes to fix; the same missing library discovered after routing takes hours to recover from. The checks in the following steps are mandatory before every handoff to floorplanning.

  • Verify Reference Libraries (report_ref_libs)

    What it does: Prints a table of all reference libraries currently linked into the design library. Each row shows the library Name, its Path on disk, and its resolved Location. Two prefix markers indicate library status: * means the library is currently open, + means it carries technology information.

    report_ref_libs > ../reports/ref_libs.rpt
    ⚠️ What to check:
    • All 15 NDMs must appear — 3 stdcell (tcbn28hpcplusbwp40p140hvt, tcbn28hpcplusbwp40p140, tcbn28hpcplusbwp40p140lvt) + 12 SRAM macros

  • Netlist Integrity Check (check_design -checks netlist)

    What it does: Validates the logical netlist for structural errors — floating ports, multiply-driven nets, open input pins, and other netlist issues that would cause incorrect behavior during physical design.

    check_design -checks {netlist} > ../reports/check_design_netlist.rpt
    What to check:
    • Errors must be 0 — 28,818 warnings are expected for tile; all are structural netlist conditions typical of a post-synthesis flat netlist with scan chains and unused interface ports
    • DCHK-004 (1814): undriven input pin of a hierarchical cell — expected for unused interface inputs
    • DCHK-008 (9): cell does not drive any net — floating output buffer or tie cell with no connection
    • DCHK-009 (8011): net has multiple/excess drivers — common on scan chain data ports and bus feedthroughs
    • DCHK-010 (7550): net has no drivers — undriven internal net, typically on unused scan or test ports
    • DCHK-017 (3794): input port is unloaded — acceptable for unused interface signals
    • DCHK-021 (3589): net connected to output port is not driven — floating output port, common for debug/observation ports
    • DCHK-023 (1717): output port connected directly to another port — feedthrough connection with no logic, acceptable for bus pass-throughs
    • DCHK-024 (22): port connected to a zero-width bus segment — typical for partial bus connections in synthesized netlists
    • DCHK-027 (2100): port connected to a net with a direction mismatch or multi-net connection
    • DCHK-045 (212): output pin of hierarchical cell is unconnected — expected for unused sub-block outputs

    🔎 Debugging TCK-002 — 82 Registers With No Fanin Clock

    TCK-002 means ICC2 found flip-flop clock pins (CP) that have no clock source — no create_clock or create_generated_clock reaches them. Before accepting this as harmless, always trace back to understand why. Here is the exact debugging workflow used on tile:

    Step 1 — Pick one of the flagged clock pins and find what net drives it:

    all_connected -leaf g_sparc_core_core_sparc0_lsu/lsu/qdp2/stb_dfq_byp2_ff_q_reg_75_/CP
    This returns the net connected to the CP pin. In the tile design the output is g_sparc_core_core_sparc0_lsu/lsu/qdp2/n640. This is a local logic net — not a global clock net — which is why ICC2 reports no clock fanin.

    Step 2 — Trace all sinks of that net to find the full scope of affected flops:

    all_connected -leaf g_sparc_core_core_sparc0_lsu/lsu/qdp2/n640
    The output lists all objects connected to n640:
    • U2/ZN — the driver (output pin of a cell)
    • stb_dfq_byp2_ff_q_reg_82_/CP through stb_dfq_byp2_ff_q_reg_67_/CP — 82 flip-flop clock pins, all driven by the same net
    This confirms all 82 TCK-002 flops are from the same group (stb_dfq_byp2) and share one driver cell U2.

    Step 3 — Identify the driver cell type:

    get_attribute [get_cells g_sparc_core_core_sparc0_lsu/lsu/qdp2/U2] ref_name
    Output: a tie-low cell (e.g. TIELBWP40P140). A tie-low cell permanently drives its output to logic 0. This means n640 is hardwired to 0 — the clock pin of all 82 flops is permanently disabled by design.

    Conclusion and action:

    • These 82 flops (stb_dfq_byp2_ff_q_reg_* in the LSU qdp2) are intentionally disabled — the RTL designer tied their clock to 0 to bypass this flip-flop bank in the current configuration.
    • They will never toggle, so they are not a functional or timing risk.
    • TCK-002 for these flops is expected and acceptable — no SDC change is needed.
    report_clocks > ../reports/clocks.rpt
    What to check:
    • Clock clk present with period 1.70 ns, waveform {0 0.85}, source clk
    • If no clocks appear, the SDC was not sourced correctly

  • Zero Interconnect Timing (ZIC) Analysis — 7-Step Flow

    What it does: The Zero Interconnect (ZIC) analysis temporarily removes all wire delay from the timing calculation, leaving only gate (cell) delays. This gives you a theoretical lower bound on the critical path — the fastest your design can ever be, regardless of how perfectly the routing is done. It helps identify whether timing violations are caused by excessive logic depth vs. routing congestion.

    Step 1 — Capture baseline timing (before ZIC):

    report_qor -summary > ../reports/report_qor_before_zic.rpt
    Save the current QoR report to a file before modifying any app options. This is your baseline — it captures timing with zero-interconnect already implicit at init stage (no routing yet), which lets you compare against Step 5.

    Step 2 — Enable zero interconnect timing mode:

    set_app_options -list {time.delay_calculation_style zero_interconnect}
    This switches ICC2's delay calculation engine to ignore all parasitic RC from the interconnect. Only gate delays remain active. Note: use curly braces {...} not parentheses (...) for the list argument.

    Step 3 — Set high fanout net handling:

    set_app_options -list {time.high_fanout_net_pin_capacitance 0pF}
set_app_options -list {time.high_fanout_net_threshold 50}
    High fanout nets (clock, reset, scan) can have thousands of loads. Setting their pin capacitance to 0 pF ensures they don't dominate the zero-interconnect timing picture. The threshold of 50 loads marks the boundary for "high fanout."

    Step 4 — Update timing with ZIC settings active:

    update_timing -full
    Forces a complete timing update using the new zero-interconnect settings. Always use -full when changing app options that affect the delay model — incremental updates may not recalculate all paths.

    Step 5 — Capture ZIC QoR report:

    report_qor -summary > ../reports/report_qor_after_zic.rpt
    What to check:
    • At init stage ICC2 already uses zero wire delay (TIM-101/102) — both before- and after-ZIC reports start from the same baseline
    • Explicit ZIC additionally zeroes pin capacitances on nets with >50 loads (clock, reset) — this shifts clock arrival times
    • For tile: WNS −0.05 ns → −0.06 ns (comparable); TNS −24.99 ns → −169.42 ns (more paths exposed)
    • TNS worsening is expected — removing clock-net load changes clock path delays, making more setup paths critical
    • All violations at init stage are logic-depth driven; routing cannot fix them — they must be closed in placement and CTS optimization

    Step 6 — Reset to normal timing calculation:

    reset_app_options {time.delay_calculation_style time.high_fanout_net_pin_capacitance time.high_fanout_net_threshold}
    Restores all three app options to their factory defaults. This is mandatory — if you leave the zero-interconnect mode active, all subsequent timing analysis in this session will give misleadingly optimistic results.

    Step 7 — Update timing back to normal mode:

    update_timing -full
    Final timing update restores the normal delay model.

  • Close the Design and Exit ICC2

    Add these final commands to ../scripts/script.tcl to cleanly close the library before exiting. This releases file locks on the NDM so other ICC2 sessions can open it, and ensures all buffered writes are flushed to disk.

    close_block -force
close_lib -all
    -force on close_block: If there are any unsaved changes, -force discards them without prompting. Since we already called save_block -as init_design earlier, there should be no unsaved changes — -force is just a safeguard to prevent the script from hanging on an interactive prompt.

    Once your script is complete, source it inside icc2_shell:

    source ../scripts/script.tcl

    After the script finishes successfully, exit ICC2:

    exit

    You are now back in the terminal. The design initialization stage is complete.

✅ Success Criteria

Design initialization is complete and correct when ALL of the following are true:

  • create_lib completes with no NDM-020 errors — NDM-020 means a listed file is not a valid NDM binary; all 15 NDM paths must resolve to valid files
  • link_block reports 0 unresolved references (no LNK-005 warnings; no LNK-074 summary)
  • MMMC quality checks show all expected scenarios, corners, and modes are defined
  • check_design -checks {dp_pre_floorplan} shows no FAILED checks
  • check_design -checks {netlist} reports 0 errors (warnings are acceptable)
  • check_timing -all shows 0 errors; TCK-001 (unconstrained scan paths) and TCK-002 (82 tie-low clocked flops in stb_dfq_byp2) are both traced and confirmed harmless
  • report_clocks lists all expected design clocks with correct periods
  • The block init_design is saved in ../outputs/tile.ndm on disk

📚 Knowledge Assessment Quiz

1. You ran create_lib successfully, but link_block produces a LNK-005: Unable to resolve reference to 'sram_l2_tag' warning. What is the most likely cause?

  • The gate-level netlist file is corrupt and needs to be re-synthesized
  • The NDM for sram_l2_tag was missing from the -ref_libs list in create_lib, so ICC2 has no physical or timing view for that cell
  • The technology file path is wrong — TSMC 28nm requires a different .tf for SRAM macros
  • The save_lib command was not run before read_verilog
Correct! LNK-005 means ICC2 found an instance in the netlist but has no cell definition to resolve it against. Since the cell is an SRAM macro, the fix is to add its NDM path to the -ref_libs list in create_lib and re-run the init flow.

2. After sourcing mmmc_config.tcl, report_corners -verbose shows only 2 out of 3 SRAM NDMs in the timing library list for the setup corner. What is the consequence if you proceed without fixing this?

  • ICC2 will refuse to run placement until all NDMs are loaded
  • The missing SRAM will be treated as a black box and placement will skip it
  • Timing analysis for the missing SRAM will use incorrect or missing delay data, potentially hiding real setup violations at the SRAM interface
  • The design will fail DRC after routing because the SRAM macro has no PR boundary
Correct! If an SRAM's NDM is not visible in a timing corner, ICC2 cannot compute accurate setup or hold slack for paths through that macro. Violations at that SRAM interface will be hidden, and silicon may fail timing even though the tool reports passing. This is why verifying the corner library list is a mandatory quality check.

3. At the init stage (no routing yet), your before-ZIC QoR shows WNS = −0.05 ns and TNS = −24.99 ns. After applying ZIC settings and running update_timing -full, the after-ZIC report shows WNS = −0.06 ns and TNS = −169.42 ns. What is the correct interpretation?

  • ZIC settings were applied incorrectly — WNS always improves when interconnect delays are removed
  • This is expected behavior at init stage. ICC2 was already using zero wire delay for both reports (TIM-101/102). The explicit ZIC settings additionally zero out pin capacitances on high-fanout nets, shifting clock arrival times and exposing more critical paths — hence the worse TNS. The key takeaway is that all violations are logic-depth driven.
  • The design has routing congestion — ZIC reveals interconnect is dominating the critical path
  • The SRAM macros are causing the discrepancy — ZIC removes their internal macro delays
Correct! At the init stage, ICC2 automatically uses zero wire delay (TIM-101/102). The explicit ZIC app options additionally zero out pin capacitances for high-fanout nets, shifting clock arrival times across many paths simultaneously — hence the large TNS increase. Both reports confirm timing violations are logic-depth driven before any routing is done.

4. Why is it important to use save_block -as init_design with a specific name rather than just save_block?

  • ICC2 requires a named block — save_block without -as will throw an error
  • Named blocks are compressed on disk; unnamed blocks are not
  • A named block creates a permanent, labeled checkpoint inside the NDM that can be opened by name in later sessions, allowing you to roll back to the initialized state without re-running the entire init flow
  • The named block enables ICC2's incremental timing update — without it, every update_timing call would be a full recompute
Correct! ICC2 stores design data as named blocks within the NDM library. By saving as init_design, you create a restore point that downstream scripts can open directly with open_block ../outputs/tile.ndm:init_design. Each stage saves a new named block, and you can branch or roll back at any block boundary.
