Problem Statement

GUIDED

You are performing signoff-quality Static Timing Analysis (STA) on a tile design using Cadence Tempus. The design is a multi-core tile from the OpenPiton SoC containing L1 instruction/data caches, an L1.5 cache, an L2 cache, and associated SRAM macros. The design has been placed and routed, and you now need to run comprehensive timing and noise analysis across multiple PVT corners to confirm signoff readiness.

In this testcase, you will execute the complete Tempus signoff STA flow by running:

cd ~/pd/labs/lab-28-signoff-sta-tempus/testcase1
make all

The make all target invokes the tempus_sta.tcl script, which performs the full signoff flow: MMMC setup, design loading, parasitic annotation, timing analysis (setup and hold), constraint checking, and SI noise analysis. After the run completes, you will verify that all expected reports and session databases were generated.

Your task: Follow each step below to understand every command in the Tempus signoff STA script. Learn what each command does, why it is needed at signoff, and how to interpret the generated reports.

📝 Analysis

Signoff STA is the final timing verification step before tapeout. Unlike implementation-stage timing (which uses simplified models), signoff STA uses the most accurate parasitic data (SPEF), CCS/ECSM timing libraries, and advanced analysis features such as CPPR, OCV derating, and signal integrity (SI) to ensure the design meets timing under all operating conditions.

  • Multi-Mode Multi-Corner (MMMC): Real chips operate across a range of process, voltage, and temperature (PVT) conditions. MMMC analysis defines multiple library sets, RC corners, delay corners, and analysis views so that setup and hold checks are performed under the worst-case conditions simultaneously. This lab uses four corners: slow/SS at 125C with RC-worst, slow/SS at -40C with C-worst, fast/FF at 125C with RC-best, and fast/FF at -40C with C-best.
  • Signal Integrity (SI): At advanced nodes like 28nm, crosstalk between neighboring nets can cause timing degradation (SI delay) and functional failures (glitches). Tempus models these effects using SPEF coupling capacitance data and reports noise violations that could corrupt signal values or shift clock edges.

The script you will study covers the entire signoff STA pipeline: design loading, parasitic annotation, timing updates, constraint checks, setup/hold reporting, and SI noise analysis. Each step is critical for tapeout signoff.

📝 Step-by-Step Solution

  • Step 1: Set Design Name and CPU Usage

    The script begins by defining the design name and configuring parallel CPU usage.

    set design_name tile
set_multi_cpu_usage -verbose -local_cpu 8

    The design name variable (design_name) is reused throughout the script for output file naming.

  • Step 2: Read MMMC Configuration

    The read_mmmc command loads the Multi-Mode Multi-Corner configuration file, which defines the complete analysis environment. This is the most important setup step in signoff STA because it establishes all PVT corners, timing libraries, RC extraction corners, and analysis views.

    read_mmmc ../inputs/mmmc_config.tcl

    The MMMC configuration file (mmmc_config.tcl) defines the following hierarchy of objects:

    • Library Sets: Groups of timing library files (.lib) for each PVT condition. This design uses four library sets: fast0p99vm40c_libs, fast0p99v125c_libs, slow0p81v125c_libs, and slow0p81vm40c_libs. Each set includes SVT, HVT, and LVT standard cell libraries plus SRAM macro libraries, all using CCS (Composite Current Source) models for highest accuracy.
    • RC Corners: Four parasitic extraction corners (rcworst_125, cworst_m40, rcbest_125, cbest_m40) that model interconnect resistance and capacitance variations. RC-worst models maximum resistance (longer delays), while C-worst models maximum capacitance (more crosstalk and coupling).
    • Delay Corners: Combine a library set with an RC corner to create a complete timing environment. For example, ss_125c_rcw pairs slow libraries at 125C with RC-worst parasitics -- the worst case for setup timing.
    • Analysis Views: Combine a delay corner with a constraint mode (SDC). Setup analysis uses the slow corners (func_ss125c_rcw, func_ssm40c_cw), and hold analysis uses the fast corners (func_ff125c_rcb, func_ffm40c_cb).

  • Step 3: Read Physical LEF Files

    The read_physical -lef command loads the Library Exchange Format files that describe the physical layout information for all cells and macros. LEF files provide the geometric data Tempus needs to correlate parasitics with the physical design.

    read_physical -lef { \
/efs/semicon_labs_pd/pdk/foundries/tsmc/N28/versions/v1.0/metal_stack/1P9M_4X2Y2R/tlef/tsmcn28_9lm4X2Y2RUTRDL.tlef \
/efs/semicon_labs_pd/pdk/foundries/tsmc/N28/versions/v1.0/stdcells/9T/lvt/lef/tcbn28hpcplusbwp40p140lvt.lef \
/efs/semicon_labs_pd/pdk/foundries/tsmc/N28/versions/v1.0/stdcells/9T/hvt/lef/tcbn28hpcplusbwp40p140hvt.lef \
/efs/semicon_labs_pd/pdk/foundries/tsmc/N28/versions/v1.0/stdcells/9T/svt/lef/tcbn28hpcplusbwp40p140.lef \
/efs/semicon_labs_pd/pdk/foundries/tsmc/N28/versions/v1.0/memory/sram/tile_mems/sram_1rw_128x78/lef/sram_1rw_128x78.lef \
/efs/semicon_labs_pd/pdk/foundries/tsmc/N28/versions/v1.0/memory/sram/tile_mems/sram_l15_data/lef/sram_l15_data.lef \
/efs/semicon_labs_pd/pdk/foundries/tsmc/N28/versions/v1.0/memory/sram/tile_mems/sram_l15_hmt/lef/sram_l15_hmt.lef \
/efs/semicon_labs_pd/pdk/foundries/tsmc/N28/versions/v1.0/memory/sram/tile_mems/sram_l15_tag/lef/sram_l15_tag.lef \
/efs/semicon_labs_pd/pdk/foundries/tsmc/N28/versions/v1.0/memory/sram/tile_mems/sram_l1d_data_128x144/lef/sram_l1d_data_128x144.lef \

/efs/semicon_labs_pd/pdk/foundries/tsmc/N28/versions/v1.0/memory/sram/tile_mems/sram_l1i_tag/lef/sram_l1i_tag.lef \

    There are three categories of LEF files loaded here:

    • Technology LEF (TLEF): The .tlef file (tsmcn28_9lm4X2Y2RUTRDL.tlef) defines the metal stack -- layer names, thicknesses, minimum widths, spacings, and via definitions for the 1P9M (1 poly, 9 metal) process. This file must be loaded first because it establishes the physical rules that all other LEFs reference.
    • Standard Cell LEFs: The three cell LEF files (LVT, HVT, SVT) define the pin locations, obstruction layers, and cell dimensions for all standard cells in the library. These are 9-track (9T) cells in the TSMC 28nm HPC+ process.
    • Macro LEFs: The twelve SRAM macro LEF files define the pin locations and physical boundaries of the memory macros (L1I data/tag, L1D data/tag, L1.5 data/hmt/tag, L2 data/dir/state/tag, and a 128x78 SRAM). These are hard IP blocks with fixed layouts.

  • Step 4: Read Netlist and Initialize Design

    This step loads the post-PnR gate-level netlist and initializes the design with power/ground net definitions. The netlist is the structural Verilog output from the place-and-route tool, containing all standard cells and macros with their interconnections.

    set input_netlist ../inputs/tile.pnr.v

read_netlist $input_netlist

set_db init_ground_nets {VSS}
set_db init_power_nets {VDD}

init_design

    Command breakdown:

    • read_netlist: Parses the post-PnR Verilog netlist (tile.pnr.v). This file contains only structural instantiations (no behavioral code) -- every gate, buffer, and macro instance with their exact connectivity.
    • set_db init_ground_nets / init_power_nets: Declares the global power supply net names. Tempus needs these to correctly identify power pins on cells and macros and to exclude power nets from signal timing analysis.
    • init_design: Completes the design initialization by linking the netlist, LEFs, MMMC configuration, and power/ground definitions together into a unified design database. After this command, the design is ready for timing analysis.

    Note: The set_db design_process_node 28 command (which follows in the script) tells Tempus that this is a 28nm design, enabling process-node-specific optimizations and checks in the timing engine.

  • Step 5: Configure Timing Analysis Settings

    These commands configure the core timing analysis engine for signoff accuracy. Each setting enables a feature that makes the analysis more realistic compared to the simplified models used during implementation.

    set_db design_process_node 28

set_db timing_analysis_cppr                       both
set_db timing_analysis_type                       ocv
set_db timing_enable_simultaneous_setup_hold_mode true
set_db timing_report_unconstrained_paths true
set_db timing_report_group_based_mode true

    What each setting does:

    • timing_analysis_cppr = both: Enables Clock Path Pessimism Removal (CPPR) for both setup and hold checks. Without CPPR, the tool applies separate derating to the launch and capture clock paths, even on their shared (common) segments. This creates artificial pessimism. CPPR removes this pessimism by identifying the common clock path and canceling the redundant derating, yielding more realistic slack values.
    • timing_analysis_type = ocv: Enables On-Chip Variation analysis. OCV accounts for the fact that transistors on the same die can have slightly different characteristics due to manufacturing variations. The tool applies derating factors (from AOCV or SOCV tables) to cell delays to model this uncertainty.
    • timing_enable_simultaneous_setup_hold_mode = true: Performs setup and hold analysis together in a single pass. This is more accurate than separate analysis because fixing a setup violation (by adding delay) can create a hold violation, and vice versa. Simultaneous mode catches these interactions.
    • timing_report_unconstrained_paths = true: Reports paths that have no timing constraints. These unconstrained paths are potential risks because the tool cannot check whether they meet timing. Identifying them ensures complete coverage.
    • timing_report_group_based_mode = true: Organizes timing reports by path groups (typically clock domains), making it easier to identify which clock domain has the worst violations.

  • Step 6: Configure Signal Integrity (SI) Settings

    Signal integrity analysis models the electrical effects of crosstalk between adjacent nets. At 28nm, wire spacing is small enough that coupling capacitance between neighboring signals can cause significant timing shifts and voltage glitches. These settings enable Tempus's SI engine.

    set_db delaycal_enable_si true
set_db delaycal_equivalent_waveform_model propagation
set_db si_delay_separate_on_data true
set_db si_delay_delta_annotation_mode lumpedOnNet
set_db si_enable_glitch_propagation true
set_db si_delay_enable_double_clocking_check true
set_db si_glitch_enable_report true
set_db si_glitch_input_threshold  0.3

    What each setting does:

    • delaycal_enable_si = true: Activates signal integrity-aware delay calculation. The timing engine now considers crosstalk-induced delay changes (delta delays) when computing path delays.
    • delaycal_equivalent_waveform_model = propagation: Uses a propagation-based waveform model for delay calculation. This provides higher accuracy than the default model by propagating the actual waveform shape through the circuit rather than using simplified step inputs.
    • si_delay_separate_on_data = true: Separates SI delay effects on data pins, allowing the tool to compute different delta delays for rise and fall transitions on the same net.
    • si_delay_delta_annotation_mode = lumpedOnNet: Annotates the total SI-induced delay change as a single lumped value on each net, simplifying the reporting while maintaining accuracy.
    • si_enable_glitch_propagation = true: Enables propagation of glitch waveforms through combinational logic gates. A glitch on one net can propagate through buffers and gates to affect downstream logic, and this setting models that behavior.
    • si_delay_enable_double_clocking_check = true: Checks for double-clocking scenarios where a crosstalk glitch on a clock net causes an extra clock edge. This can result in a flip-flop capturing data twice in one cycle -- a critical functional failure.
    • si_glitch_enable_report = true: Enables reporting of glitch analysis results so you can review which nets have problematic noise levels.
    • si_glitch_input_threshold = 0.3: Sets the glitch detection threshold to 30% of VDD. Any noise-induced voltage excursion above this threshold at a gate input is flagged as a potential glitch failure.

  • Step 7: Read SPEF Parasitics

    SPEF (Standard Parasitic Exchange Format) files contain the extracted resistance and capacitance values for every net in the design. These are produced by a parasitic extraction tool (such as Cadence QRC or Synopsys StarRC) after place-and-route, and they represent the actual interconnect delays. At signoff, you must annotate SPEF for every RC corner defined in the MMMC configuration.

    read_spef -rc_corner rcworst_125 ../inputs/tile.rcw_125.spef
read_spef -rc_corner rcbest_125  ../inputs/tile.rcb_125.spef
read_spef -rc_corner cworst_m40  ../inputs/tile.cw_-40.spef
read_spef -rc_corner cbest_m40   ../inputs/tile.cb_-40.spef

    Each read_spef command maps a parasitic extraction file to a specific RC corner:

    • rcworst_125: RC-worst extraction at 125C. Maximizes both resistance and capacitance, creating the longest interconnect delays. Used with slow libraries for worst-case setup analysis.
    • rcbest_125: RC-best extraction at 125C. Minimizes resistance and capacitance, creating the shortest interconnect delays. Used with fast libraries for worst-case hold analysis at high temperature.
    • cworst_m40: Capacitance-worst extraction at -40C. Maximizes capacitance (more coupling, more crosstalk) while using typical resistance. This corner is critical for hold analysis at low temperature.
    • cbest_m40: Capacitance-best extraction at -40C. Minimizes capacitance, yielding the least coupling. Used with fast libraries for hold checks at low temperature.

    Why four SPEF files? The RC parasitics vary with temperature and process. Using a single SPEF file would underestimate timing variations across corners. Signoff requires annotating each RC corner with its corresponding extraction to ensure accurate delay computation under all conditions.

  • Step 8: Clock Propagation

    After design initialization, clocks are treated as ideal (zero insertion delay, no skew). For signoff analysis, you must switch to propagated clocks so that the actual clock tree delays, skew, and jitter are included in timing calculations.

    set_interactive_constraint_mode [get_db constraint_modes -if {.is_setup || .is_hold}]
set_propagated_clock [get_db clocks .sources]
set_interactive_constraint_mode {}

    Command breakdown:

    • set_interactive_constraint_mode: Selects all constraint modes that participate in setup or hold analysis. This ensures the propagation setting is applied to every active constraint mode, not just one.
    • set_propagated_clock [get_db clocks .sources]: Marks all clock sources as propagated. This tells Tempus to compute the actual clock arrival time at each flip-flop by tracing through the clock tree (buffers, inverters, muxes), including the real delays from SPEF parasitics. The result is accurate clock skew and insertion delay at every endpoint.
    • set_interactive_constraint_mode {}: Resets the interactive constraint mode to its default state after making the change. This is a cleanup step to avoid unintended side effects on subsequent constraint modifications.

    Critical: If you forget to set propagated clocks, Tempus will assume zero clock insertion delay and zero skew. This makes setup analysis overly optimistic and hold analysis unreliable. Always propagate clocks at signoff.

  • Step 9: Update Timing and Save Session

    With all inputs loaded -- MMMC configuration, netlist, LEFs, SPEF parasitics, and clock propagation -- the next step is to run the full timing update and save the session database.

    update_timing -full

write_db -sdc ../outputs/${design_name}_session_timing.db

    Command breakdown:

    • update_timing -full: Triggers a complete timing update across all analysis views. Tempus recomputes all cell delays (using CCS library models), interconnect delays (from SPEF), clock tree delays (propagated), SI delta delays (from coupling), and OCV derating. The -full flag ensures everything is recomputed from scratch rather than incrementally.
    • write_db -sdc: Saves the complete timing session to a database file (tile_session_timing.db). This allows you to restore the session later without re-running all setup commands -- useful for interactive debugging or generating additional reports.

  • Step 10: Check Design and Timing Quality

    Before reviewing timing reports, you should validate that the design was loaded correctly and that timing constraints cover the design adequately. These sanity checks catch configuration problems early.

    check_netlist -out_file        ../reports/check.netlist.rpt
check_timing                 > ../reports/check.timing.rpt
report_analysis_coverage     > ../reports/check.coverage.rpt
report_annotated_parasitics  > ../reports/check.annotation.rpt

    What each check produces:

    • check_netlist: Verifies structural integrity of the netlist -- missing connections, floating pins, multiply-driven nets, and other physical/logical inconsistencies. Review check.netlist.rpt for any errors.
    • check_timing: Identifies timing constraint issues such as unconstrained endpoints, missing clock definitions, and unresolved clock relationships. The check.timing.rpt file reveals gaps in your SDC constraints.
    • report_analysis_coverage: Shows what percentage of timing paths are constrained. Ideally this should be close to 100%. Any uncovered paths represent potential timing risks. Review check.coverage.rpt for unconstrained path counts.
    • report_annotated_parasitics: Confirms that SPEF parasitics were successfully annotated on all nets. The check.annotation.rpt file shows the annotation coverage percentage. At signoff, you want 100% annotation -- any unannotated nets will use estimated wireload models, which are less accurate.

  • Step 11: Report Constraints

    These commands generate reports that describe the constraint environment -- clock definitions, case analysis settings, and disabled timing arcs. Reviewing these reports helps verify that the SDC constraints match your design intent.

    report_clocks                > ../reports/report.clocks.rpt
report_case_analysis         > ../reports/report.case_analysis.rpt
report_inactive_arcs         > ../reports/report.inactive_arcs.rpt

    What each report shows:

    • report_clocks: Lists all defined clocks with their period, waveform, sources, and attributes. Verify that clock frequencies match your design specification and that generated clocks (dividers, muxed clocks) have the correct master-clock relationships.
    • report_case_analysis: Shows all set_case_analysis constraints -- pins forced to constant 0 or 1. These are used to model specific operating modes (e.g., scan mode disabled, functional mode selected). Incorrect case analysis can mask real timing paths.
    • report_inactive_arcs: Lists timing arcs that have been disabled (via set_disable_timing or set_false_path). Disabled arcs are excluded from timing analysis. Review this report to ensure no critical paths have been accidentally disabled.

  • Step 12: Setup Timing Reports

    Setup timing analysis checks that data arrives at each flip-flop before the capturing clock edge (with margin for the setup time requirement). The following commands generate comprehensive setup timing reports.

    report_timing_summary -checks {setup drv} > ../reports/setup.analysis_summary.rpt
report_timing_summary -checks {setup drv} -expand_views > ../reports/setup.view_summary.rpt
report_timing_summary -checks {setup drv} -expand_views -expand_clocks launch_capture > ../reports/setup.group_summary.rpt
report_constraint -late -all_violators -drv_violation_type {max_capacitance max_transition max_fanout} > ../reports/setup.all_violators.rpt

    Report details:

    • setup.analysis_summary.rpt: A high-level summary showing the worst negative slack (WNS) and total negative slack (TNS) for setup checks, plus DRV (design rule violation) counts for max capacitance, max transition, and max fanout. This is your first stop to see if the design passes setup timing.
    • setup.view_summary.rpt: Expands the summary by analysis view, showing WNS/TNS for each corner (e.g., func_ss125c_rcw vs. func_ssm40c_cw). This reveals which PVT corner is the limiting factor for setup timing.
    • setup.group_summary.rpt: Further expands by launch/capture clock pairs, showing WNS/TNS for each clock domain crossing. This pinpoints which inter-clock or intra-clock paths have the worst violations.
    • setup.all_violators.rpt: Lists every path with a setup violation and every DRV violation (max cap, max transition, max fanout). The -late flag targets setup (late-arriving data). This is the detailed report you use to prioritize fixes.

  • Step 13: Hold Timing Reports

    Hold timing analysis checks that data remains stable at each flip-flop for a minimum time after the capturing clock edge. Hold violations cause functional failures that cannot be fixed by reducing clock frequency. The following commands generate hold timing reports with the same structure as the setup reports.

    report_timing_summary -checks {hold drv} > ../reports/hold.analysis_summary.rpt
report_timing_summary -checks {hold drv} -expand_views > ../reports/hold.view_summary.rpt
report_timing_summary -checks {hold drv} -expand_views -expand_clocks launch_capture > ../reports/hold.group_summary.rpt
report_constraint -early -all_violators -drv_violation_type {min_capacitance min_transition min_fanout} > ../reports/hold.all_violators.rpt

    Key differences from setup reports:

    • The -checks {hold drv} flag targets hold timing violations instead of setup.
    • The -early flag in report_constraint targets early-arriving data (hold violations occur when data changes too soon).
    • DRV checks use minimum thresholds (min_capacitance, min_transition, min_fanout) rather than maximum.
    • Hold analysis uses the fast corners (func_ff125c_rcb, func_ffm40c_cb) because faster cells with less interconnect delay create the worst-case conditions for hold violations.

    Important: Hold violations are more critical than setup violations because they cannot be resolved by reducing the clock frequency. Hold fixes typically require inserting delay buffers on the data path, which must be done during ECO (Engineering Change Order) before tapeout.

  • Step 14: SI Noise Analysis

    The final phase of signoff STA is signal integrity noise analysis. These commands check for crosstalk-induced glitches and double-clocking issues, then generate noise reports and save the noise session.

    report_double_clocking > ../reports/${design_name}_double_clocking.rpt
check_noise -all -verbose > ../reports/${design_name}_check_noise.rpt

update_glitch

report_noise -sort_by noise -failure -out_file ../reports/${design_name}_glitch.rpt
report_double_clocking -out_file ../reports/${design_name}_double_clock.rpt
report_noise -noisy_waveform -out_file ../reports/${design_name}_noisy_waveform.rpt

write_db -sdc ../outputs/${design_name}_session_noise.db

    Command breakdown:

    • report_double_clocking: Identifies clock nets where crosstalk could induce an extra clock edge (double clocking). A double-clock event causes a flip-flop to capture data twice in one cycle, leading to unpredictable functional behavior. The report lists vulnerable clock nets and the aggressor nets causing the risk.
    • check_noise -all -verbose: Runs a comprehensive noise check across all nets in the design and reports detailed information about noise violations. The -all flag ensures no net is skipped, and -verbose provides maximum detail.
    • update_glitch: Performs a full glitch analysis pass. Tempus computes the peak noise voltage at every gate input due to crosstalk coupling, propagates glitches through combinational logic, and flags any net where the noise exceeds the threshold (0.3 * VDD, as set in Step 6).
    • report_noise -sort_by noise -failure: Generates a report of all nets that fail the glitch check, sorted by noise magnitude (worst first). This is the primary report for identifying and prioritizing noise fixes. Saved to tile_glitch.rpt.
    • report_noise -noisy_waveform: Outputs the actual noisy waveform data for failing nets, showing the voltage excursion over time. This is useful for detailed analysis of specific noise violations.
    • write_db -sdc (noise session): Saves the complete session including noise analysis results to tile_session_noise.db, preserving all noise data for future reference or incremental analysis.

🧠 Knowledge Assessment

1. What is the purpose of enabling CPPR (Clock Path Pessimism Removal) in signoff STA?

  • To remove all clock tree buffers from the timing analysis.
  • To cancel redundant OCV derating on the shared portion of launch and capture clock paths, reducing artificial pessimism.
  • To propagate clocks through the clock tree instead of using ideal clocks.
  • To disable crosstalk analysis on clock nets.
Correct! CPPR identifies the common clock path between the launch and capture flip-flops and removes the pessimistic OCV derating applied twice on that shared segment, yielding more realistic slack values.

2. Why are four separate SPEF files annotated in this signoff flow?

  • Because each SPEF file corresponds to a different design block in the hierarchy.
  • Because Tempus requires exactly four SPEF files for any analysis.
  • Because each SPEF file represents parasitic extraction under a different RC corner (rcworst, rcbest, cworst, cbest), and each RC corner is paired with specific delay corners in the MMMC configuration.
  • Because the four files contain parasitics for different metal layers.
Correct! Interconnect parasitics (R and C) vary with temperature and process. Each RC corner models a different extreme of parasitic variation, and mapping the correct SPEF to each RC corner ensures accurate delay computation across all PVT conditions.

3. What is a "double clocking" event in the context of SI analysis?

  • When a flip-flop is driven by two different clock domains simultaneously.
  • When the clock period is halved due to a frequency divider error.
  • When crosstalk on a clock net induces a spurious extra clock edge, causing a flip-flop to capture data twice in one cycle.
  • When both setup and hold violations occur on the same path.
Correct! A double-clocking event occurs when crosstalk noise on a clock net creates an extra rising or falling edge that the flip-flop interprets as a valid clock transition, causing it to sample data at an unintended time.

4. Why are hold violations considered more critical than setup violations at signoff?

  • Because hold violations are harder to detect with simulation.
  • Because hold violations cannot be fixed by reducing the clock frequency -- they require physical changes such as inserting delay buffers via ECO.
  • Because hold violations only occur at high temperatures.
  • Because the hold time requirement is always larger than the setup time requirement.
Correct! Setup violations can be addressed by reducing the operating frequency, but hold violations are frequency-independent. They must be fixed structurally by adding delay to the data path, typically through ECO buffer insertion before tapeout.
