📖 Theory and Background

The Problem: Running Corners One at a Time

In the STA lab, you ran 4 separate PrimeTime sessions — one for each PVT corner. Each session produced its own timing reports, its own slack numbers, and its own list of violations. To find the true worst slack for any path, you had to open 4 different reports and manually compare them.

Now imagine a real tapeout design with 20+ corners, multiple operating modes (functional, test, low-power), and thousands of timing paths. Manually tracking the worst slack across all scenarios becomes impossible. Worse, fixing a violation in one corner can silently create a new violation in another — and you would not know until you re-ran every session individually.

There has to be a better way. And there is.

The Solution: DMSA

DMSA (Distributed Multi-Scenario Analysis) solves this by running all corners simultaneously inside a single PrimeTime environment. Instead of launching 4 independent sessions, you launch one master session that coordinates multiple worker sessions — each worker handles one PVT corner.

The master sees all corners at once. When you ask for the worst slack on a path, it queries every worker and returns the true worst across all scenarios in a single answer. When you apply an ECO fix, every worker evaluates the impact simultaneously — so you know instantly whether the fix helps one corner without breaking another.

This is how every production chip is signed off today. No engineer manually compares individual corner reports anymore — DMSA does it automatically.

Master-Worker Architecture

A DMSA session has two types of processes:

RoleWhat It Does
Master The single session you interact with. It receives your commands, dispatches them to all workers, collects results, and presents the unified worst-case answer. The master itself does not hold any design data — it is a coordinator.
Workers One per scenario (PVT corner + mode). Each worker loads a saved PrimeTime session from the STA lab and holds the full design with its corner-specific libraries, SPEF parasitics, and timing data. Workers run in parallel on the server.
Why saved sessions? The saved sessions you generated in the STA lab (stored in data/PT_SS/) are the inputs to DMSA. Each saved session contains the complete PrimeTime state for one corner — design, libraries, SPEF, timing graph, constraints. The DMSA master loads each saved session into a worker, avoiding the need to re-read netlists, re-annotate SPEF, or re-run timing updates. This makes DMSA startup fast even for large designs.

What You Can Do in DMSA

Once the master and workers are up, you can:

  • Query worst slack across all corners — one command gives you the true worst slack for any path, telling you which corner is the bottleneck
  • Generate unified reports — timing summary, QoR, and constraint violation reports that show the worst-case across all scenarios, not just one corner
  • Apply and validate ECO fixes — make a cell swap or buffer insertion, and instantly see the impact on all corners. No more guessing whether a fix in one corner breaks another
  • Identify the limiting corner per path — for each violating path, DMSA tells you exactly which PVT corner is the bottleneck, so you can focus optimization effort where it matters

DMSA in the Design Flow

DMSA sits at the very end of the physical design flow — after synthesis, after place-and-route, after parasitic extraction, and after individual-corner STA. It is the final checkpoint before tapeout. If DMSA reports clean timing across all corners and modes, the design is ready to go to the foundry.

The flow looks like this:

Synthesis → Place & Route → Parasitic Extraction → STA (per corner) → DMSA (all corners) → Tapeout

How Sessions Flow from Lab 27 to This Lab

When you run make run in Lab 27 testcase1, PrimeTime performs STA across 4 PVT corners and saves a timing session for each one. These 4 saved sessions are:

  • funceco_ss_0p81v_125c_rcworst — Slow-slow corner, 0.81V, 125°C, RC worst
  • funceco_ss_0p81v_m40c_cworst — Slow-slow corner, 0.81V, −40°C, C worst
  • funceco_ff_0p99v_m40c_cbest — Fast-fast corner, 0.99V, −40°C, C best
  • funceco_ff_0p99v_125c_rcbest — Fast-fast corner, 0.99V, 125°C, RC best

After make run completes in Lab 27, these sessions are automatically copied to this lab's inputs/PT_SS/ directory. No manual file copying is needed.

What Each Session Contains

Each saved PrimeTime session is a self-contained snapshot of the complete timing state for one PVT corner. It includes:

  • The gate-level design netlist
  • Corner-specific timing libraries (.db files)
  • Annotated parasitic data (SPEF) for that RC corner
  • SDC timing constraints and clock definitions
  • The fully computed timing graph with delays, slacks, and violations

Because each session captures everything, DMSA workers can restore the full timing environment in seconds — no need to re-read libraries, re-annotate SPEF, or re-propagate clocks.

Why DMSA Matters

DMSA loads all 4 sessions simultaneously as separate scenarios, enabling true multi-corner analysis in one unified environment. Without DMSA, engineers must manually check each corner separately and compare reports side by side — a tedious, error-prone process that scales poorly as corner counts grow.

With DMSA, you get:

  • A single unified view of worst-case timing across all corners — one command shows the true worst slack and which corner is the bottleneck
  • Cross-corner ECO validation — every fix is evaluated against all corners simultaneously, so you never fix one corner at the expense of another
  • Complete signoff coverage — no corner is left unchecked, eliminating the risk of a missed violation causing silicon failure
