Overview

GUIDED

In this testcase you will run the chip finish stage for the tile design. Starting from a completed post-route database, you will walk through every command in scripts/chip_finish.tcl and understand exactly what each output file contains, which downstream tool consumes it, and why it must be generated before tape-out.

By the end you will have generated all nine deliverables that a production tape-out requires: three Verilog netlists, two DEF files, a LEF abstract, two GDS files, and an hcell hierarchy list.

🛠 Step-by-Step Walkthrough

  • Set Environment Variables and Read the Post-Route Database

    The chip finish script begins by reading environment variables that locate the previous stage outputs and the current stage output directory. These variables are set by the job scheduler before Innovus starts.

    set design_name $env(BLOCK_NAME)
set tool_scripts $env(TOOL_SCRIPTS)
set prev_stage_dir $env(POSTROUTE_DIR)
set cur_stage_dir $env(CHIP_FINISH_DIR)

set stage chip_finish

read_db ${prev_stage_dir}/outputs/postroute.db

    Why environment variables? Using $env(...) instead of hard-coded paths means the same chip_finish.tcl script works for any block and any run directory. The three key variables are:

    • BLOCK_NAME — the design name (tile in this lab). Used to name every output file.
    • POSTROUTE_DIR — path to the routing stage outputs. read_db loads the completed post-route database from there.
    • CHIP_FINISH_DIR — path to this stage's working directory. All output files go into ${cur_stage_dir}/outputs/.

    read_db restores the complete Innovus design state (placement, routing, timing, PG) so that all subsequent write commands have a fully resolved database to export from.

    cd ~/pd/labs/lab-15-chip-finish/testcase1
make all

  • Write the Logic Netlist for LEC — tile.vg

    write_netlist -exclude_leaf_cells \
    ${OUTDIR}/[get_db [current_design] .name].vg

    What it produces: A Verilog gate-level netlist that contains every standard cell instance and their signal connections. The -exclude_leaf_cells flag prevents leaf-level primitives (individual transistor models) from being flattened into the netlist, keeping it at the logical gate level.

    Why it is needed: The Logical Equivalence Checker (LEC / Formality) compares this post-route netlist against the synthesis gate-level netlist to confirm that routing, CTS buffer insertion, and hold-fixing did not change the design's logical function. Every ECO change made after synthesis must be verified before tape-out.

    Note: [get_db [current_design] .name] evaluates to the design name at runtime. For the tile design it resolves to tile, so the file is written as tile.vg.

  • Write the PG-Annotated Netlist for LVS — tile.pg.vg

    write_netlist -include_pg_ports -exclude_leaf_cells \
    ${OUTDIR}/[get_db [current_design] .name].pg.vg

    What it produces: The same gate-level netlist as .vg, but with the -include_pg_ports flag added. This causes Innovus to include VDD and VSS port connections on every cell instance.

    Why it is needed: Layout Versus Schematic (LVS) verification compares the physical GDS layout against a schematic netlist. LVS requires power and ground connections to be explicitly present in the netlist — if a cell's VDD/VSS ports are absent, LVS reports a mismatch. The .pg.vg file is the schematic reference used during LVS of the logic hierarchy.

    Difference from .vg: The .vg file has only signal ports (suitable for LEC); the .pg.vg file adds power pins (required for LVS). Both exclude filler and decap cells.

  • Write the Full Physical Netlist for LVS — tile.fill.pg.vg

    write_netlist -include_phys_insts -include_pg_ports -exclude_leaf_cells \
    ${OUTDIR}/[get_db [current_design] .name].fill.pg.vg

    What it produces: The most complete netlist variant. The additional -include_phys_insts flag includes physical-only instances that have no logical function: filler cells (FILL*), decoupling capacitors (DCAP*), and spare cells. These cells exist in the GDS layout and must be present in the LVS schematic or LVS will report spurious device mismatches.

    Why it is needed: When running full-chip LVS that includes the physical well-fill and decap cells, the extracted layout contains all physical instances. If the schematic netlist omits them, LVS flags every filler cell as an unmatched device. The .fill.pg.vg file is used for LVS runs that verify the complete physical implementation including all inserted physical cells.

    Netlist hierarchy summary:
    • .vg — Logic only, no PG, no fill. For LEC.
    • .pg.vg — Logic + PG ports, no fill. For LVS of logic cells.
    • .fill.pg.vg — Logic + PG ports + filler/decap/spare. For full-physical LVS.

  • Write the Design Exchange Format File — tile.def

    write_def ${OUTDIR}/[get_db [current_design] .name].def

    What it produces: A DEF (Design Exchange Format) file that encodes the full physical database: die area, row definitions, all cell placements (coordinates and orientations), and all routing wire segments. DEF is a text-based ASCII format that other EDA tools can read without needing the proprietary Innovus database.

    Why it is needed:

    • Parasitic extraction: Calibre xRC or StarRC reads this DEF to extract post-route RC parasitics for signoff timing (PrimeTime).
    • SoC integration: When the tile block is instantiated in a top-level chip, the integration tool reads this DEF to understand the block's physical footprint and pin locations.
    • Physical verification setup: Calibre DRC and LVS can use the DEF plus the LEF to reconstruct the design hierarchy for rule checking.

  • Write the Routing DEF for IR Drop Analysis — tile.IR.def

    write_def -routing ${OUTDIR}/[get_db [current_design] .name].IR.def

    What it produces: A second DEF file with the -routing flag. This variant includes complete routing wire geometry with resistance and current-carrying information needed specifically for power integrity analysis.

    Why it differs from tile.def: The standard write_def may omit or simplify some routing details that are unnecessary for placement or parasitic extraction workflows. The -routing variant preserves the full detail of every power mesh wire segment, including all metal layers and vias. Power integrity tools (Cadence Voltus, Ansys Redhawk) need this level of detail to model the resistance of the power delivery network accurately and compute voltage drop (IR drop) and electromigration (EM) margins.

    Why IR drop matters at N28: At 28 nm, supply voltages are lower (typically 0.9 V nominal) and current densities are higher. A 50 mV IR drop is over 5% of the supply, which can cause functional failures in flip-flops near the power rails. Identifying and fixing IR drop hotspots before tape-out is mandatory.

  • Write the LEF Abstract for SoC Integration — tile_abstract.lef

    write_lef_abstract \
    ${OUTDIR}/[get_db [current_design] .name]_abstract.lef

    What it produces: A LEF (Library Exchange Format) abstract view of the tile block. The abstract contains:

    • The block's bounding box (die area / core area)
    • All pin shapes and metal layer assignments (boundary pins accessible from outside)
    • Routing blockages (areas where the top-level router must not route over)
    • No internal cell placement or routing detail

    Why it is needed: When the tile block is integrated at the chip level (e.g., in iguana_soc), the top-level PnR tool needs to know the block's physical footprint and pin locations without loading the entire post-route database. The LEF abstract provides exactly this compact representation. The top-level placer uses it to place the tile macro, and the top-level router uses the routing blockages to avoid routing over internal tile wires.

  • Write the PnR-Only GDS — tile.pnr.gds.gz

    write_stream \
    ${OUTDIR}/[get_db [current_design] .name].pnr.gds.gz \
    -map_file /proj1/dataIn/Rock_R2G/TSMC_28nm_collaterals/PDK/apr/\
PRTF_EDI_28nm_Cad_V19_1a/PR_tech/Cadence/GdsOutMap/gdsout_4X2Y2R.map \
    -unit 1000

    What it produces: A GDS II stream file containing only the PnR-generated geometry: wires on all routing layers, vias, and cell placement references. It does not contain the internal geometry of each standard cell (those are referenced by cell name only, as SREF records in GDS).

    Key parameters:

    • -map_file gdsout_4X2Y2R.map — Maps Innovus internal layer names to the TSMC N28 PDK GDS layer numbers. Without this map, the layer numbers in the output would not match what Calibre DRC expects.
    • -unit 1000 — Sets the database unit to 1000 units per micron (1 nm resolution), matching the TSMC N28 GDS convention.

    Why it is needed: This PnR-only GDS is used for standalone DRC runs on the tile block. Calibre reads this GDS together with the PDK standard cell GDS files to reconstruct the full physical view. Running DRC at the block level (before chip-level integration) catches violations early when they are cheaper to fix.

  • Generate the Hierarchical Cell List — hcell.list

    if {[file exists ${OUTDIR}/hcell.list]} {
    [file delete ${OUTDIR}/hcell.list]
}
foreach cl [lsort -unique [get_db insts .base_cell.name]] {
    puts "$cl $cl" >> ${OUTDIR}/hcell.list
}

    What it produces: A plain text file where each line contains two fields separated by a space: the GDS cell name and the LVS schematic cell name. For standard cells in this flow the two names are the same (e.g., NAND2D1BWP40P140HVT NAND2D1BWP40P140HVT).

    Why it is needed: Calibre LVS uses the hcell list to identify which GDS cells should be treated as hierarchical black boxes (matched by name) rather than expanded and verified transistor-by-transistor. Without hcell entries for standard cells, LVS would try to flatten every cell down to transistors and match them individually — an operation that would take orders of magnitude longer and produce meaningless mismatches against the gate-level schematic.

    Script logic: The if {[file exists ...]} {file delete ...} guard ensures a stale list from a previous run is removed before writing. get_db insts .base_cell.name collects all unique cell types instantiated in the design; lsort -unique deduplicates and sorts them alphabetically.

  • Write the Merged GDS for Tape-Out — tile.merged.gds.gz

    write_stream \
    ${OUTDIR}/[get_db [current_design] .name].merged.gds.gz \
    -merge {
        /proj1/pd/pdk/TSMC28HPHP/logic/tcbn28hpcplusbwp40p140lvt_180b/.../\
tcbn28hpcplusbwp40p140lvt.gds
        /proj1/pd/pdk/TSMC28HPHP/logic/tcbn28hpcplusbwp40p140_180b/.../\
tcbn28hpcplusbwp40p140.gds
        /proj1/pd/pdk/TSMC28HPHP/logic/tcbn28hpcplusbwp40p140hvt_180a/.../\
tcbn28hpcplusbwp40p140hvt.gds
    } \
    -map_file .../gdsout_4X2Y2R.map \
    -unit 1000

    What it produces: A complete, fully self-contained GDS II file. The -merge flag instructs Innovus to combine the PnR routing geometry with the GDS files from the TSMC N28 PDK for all three threshold voltage standard cell libraries:

    • tcbn28hpcplusbwp40p140lvt.gds — LVT (Low-VT) standard cell GDS
    • tcbn28hpcplusbwp40p140.gds — SVT (Standard-VT) standard cell GDS
    • tcbn28hpcplusbwp40p140hvt.gds — HVT (High-VT) standard cell GDS

    Why it is needed: The PnR-only GDS references standard cells by name (SREF) but does not contain their physical transistor-level geometry. Before sending a design to the foundry for fabrication, every cell reference must be resolved into actual mask geometry. The merged GDS is the tape-out deliverable that contains every polygon on every layer for the complete chip. The foundry uses this file to manufacture the photomasks.

    Why three separate PDK GDS files? TSMC distributes separate GDS libraries for LVT, SVT, and HVT cells because each threshold variant uses different implant layers and well doping profiles. All three may be instantiated in a single block (e.g., HVT for low-leakage paths, LVT for timing-critical paths), so all three must be merged into the final tape-out GDS.

1. SPEF (Standard Parasitic Exchange Format) is one of the key PnR outputs. What specific data does it contain and which downstream tool consumes it?

  • SPEF contains the gate-level netlist with power and ground connections — consumed by LVS tools for layout-versus-schematic verification
  • SPEF contains the physical placement coordinates of every cell — consumed by the floorplan tool when re-initializing a design
  • SPEF contains extracted parasitic resistance (R) and capacitance (C) values for every signal net in the routed design. It is consumed by static timing analysis (STA) tools like PrimeTime or Tempus for accurate sign-off timing, and by power analysis tools like Voltus for accurate dynamic power calculations
  • SPEF contains the scan chain connectivity — consumed by DFT tools for scan test pattern generation after routing is complete
Correct! SPEF (IEEE 1481 standard) captures the parasitic RC network of every net after routing. For each net, it describes the wire resistance sections (R entries) and node capacitances (C entries) extracted from the actual routed wire geometry. STA tools like PrimeTime load the netlist + SPEF to compute accurate delay values using the real wire RC rather than PnR tool estimates. Power analysis tools use SPEF capacitance values combined with switching activity to compute accurate dynamic power. Without SPEF, sign-off timing would use inaccurate estimates and might miss real timing violations in silicon.

2. GDS (GDSII or OASIS) is another critical PnR output. What is the GDS file used for and who receives it?

  • GDS is a text file containing the SDC constraints — provided to the timing verification team for sign-off analysis
  • GDS contains the logical netlist in a hierarchical binary format — used by the synthesis tool to check equivalence after ECO changes
  • GDS is the mask layout database containing the complete geometric description of every polygon on every layer. It is sent to the semiconductor foundry for photomask generation and wafer fabrication — it is the final physical deliverable that defines what gets manufactured in silicon
  • GDS contains the power grid topology — used by the power integrity team to run IR drop and electromigration analysis
Correct! GDSII (or its modern successor OASIS) is the universal semiconductor mask layout format. It contains hierarchical descriptions of all polygons on all metal, via, diffusion, and implant layers — essentially everything the foundry needs to create photomasks for each manufacturing step. The GDS file is the tape-out deliverable that physically defines the chip. It is merged with standard cell and PDK GDS libraries before submission, and must pass Calibre DRC and LVS sign-off before being released to the foundry.

3. Dummy metal fill is added after routing as part of chip finishing. What is its primary purpose?

  • Dummy fill reduces overall wire resistance by adding parallel metal paths alongside routed signals
  • Dummy fill provides additional routing tracks for ECO changes that may be needed after sign-off
  • Dummy fill maintains metal density uniformity across all layers to satisfy foundry CMP (Chemical Mechanical Planarization) requirements. Without fill, regions with sparse routing have low metal density, causing uneven polishing that creates thickness variations, which in turn cause resistance and capacitance variations across the chip
  • Dummy fill improves chip performance by reducing crosstalk between adjacent signal wires that are too far apart
Correct! CMP (Chemical Mechanical Planarization) is used after each metal layer deposition to planarize the wafer surface. CMP removal rate depends on local metal density — high-density areas polish faster than low-density areas, creating surface height variations (dishing in metal-dense areas, erosion in sparse areas). These height variations affect subsequent layer thickness, changing wire cross-sections and thus resistance and capacitance. Foundries specify minimum (typically 20–30%) and maximum (typically 70–80%) metal density rules for each layer. Dummy fill is inserted in sparse areas to bring density up to minimum, and routing blockages prevent exceeding maximum. Dummy fill polygons are electrically floating (connected to neither VDD nor VSS) and do not affect circuit function.

4. What are the two main types of ECO (Engineering Change Order) in physical design, and what triggers each?

  • Metal ECO and cell ECO — metal ECO changes wire routing, cell ECO changes cell placement. Both are triggered by timing violations
  • Pre-tape ECO and post-tape ECO — pre-tape changes are done in the PnR tool, post-tape changes are done at the mask level by the foundry
  • Functional ECO (logic changes required due to RTL bugs, DFT changes, or specification updates discovered after routing) and Timing ECO (sign-off violations like setup, hold, transition, or noise violations that the PnR tool did not fix). Functional ECOs change the netlist; timing ECOs only add/resize/move cells to improve timing
  • Hard ECO and soft ECO — hard ECOs require full re-routing of the chip, soft ECOs can be implemented using spare cells only
Correct! The two ECO categories have different causes and methods: Functional ECOs are driven by logic changes — RTL bugs found in simulation after routing, DFT (scan chain) modifications, or changed specification requirements. They require netlist changes (adding/removing logic gates) implemented using spare cells or partial re-routing. Timing ECOs are driven by sign-off analysis revealing violations that the PnR tool missed due to simplified models — adding buffers, upsizing drivers, adjusting placement of critical cells. Both types are normal parts of the production flow before tape-out. Prerequisites for ECO include setup WNS <50 ps, moderate hold violations, and sufficient whitespace for buffer insertion.
