📚 Theory and Background

What is Chip Finishing and Why Does it Exist?

After routing is complete and all DRC violations have been resolved, the design exists as a proprietary Innovus database file (postroute.db). This file contains the complete physical implementation — every cell position, every wire on every layer, every via — but it is in a format that only Innovus can read. No other tool in the design flow can consume it directly.

Chip finishing is the process of translating the Innovus database into standard industry formats that downstream tools can read. Each downstream tool has a different purpose and requires a different representation of the same physical design. The chip finish stage generates all of these representations in a single pass, reading the post-route database once and writing all required output files.

Chip finishing is purely an output generation step — it does not modify the design in any way. It is the last stage of the PnR flow before the generated files are handed off to signoff verification (DRC, LVS, timing, power integrity) and ultimately to the semiconductor foundry for fabrication.

The Downstream Verification Ecosystem

Understanding chip finishing requires first understanding the tools that consume its outputs. The signoff flow for a digital block involves several independent verification tools, each operating on a different representation of the design:

Verification Tool What it checks Input it needs
LEC (Formality) Logical equivalence: post-route netlist matches RTL Gate-level Verilog netlist (logic only)
Calibre LVS Layout vs. Schematic: GDS matches netlist structurally Merged GDS + Verilog with PG ports + filler cells
Calibre DRC Physical design rules: no spacing or width violations Merged GDS with all cell geometry present
Voltus / Redhawk IR drop and electromigration on power grid Routing-only DEF with full power mesh detail
StarRC / Quantus RC parasitic extraction for signoff timing Full DEF with all routing and cell placements
Chip-level PnR Place and route the full chip including this block as a macro LEF abstract with block outline, pins, blockages

The Three Verilog Netlists: Why Each Exists

Three different Verilog netlists are written from the same post-route database. They differ in what physical information is included:

Plain Netlist (.vg) — For LEC

Contains module instantiations and signal connections for all logic cells, with leaf-level primitives excluded. Power and ground ports are not included. This is what a logical equivalence checker expects: it compares the logical function of the gate-level netlist against the original RTL. PG ports would confuse the LEC tool, which reasons purely about logical signal connectivity. Filler cells, which have no logical function, are also excluded.

PG Netlist (.pg.vg) — For Power-Aware Verification

Identical to the plain netlist but with explicit VDD and VSS port declarations added to every cell instantiation. Power-aware simulation tools need these ports to model power-down events and analyze what happens to the circuit when supply voltage is removed from certain cells. LVS tools also use this format when verifying power connectivity separately from signal connectivity.

Full Physical Netlist (.fill.pg.vg) — For LVS

The most complete netlist: includes all logic cells, all physical instances (filler cells, decoupling capacitor cells, spare cells), and PG ports. This is the schematic reference for Calibre LVS. When Calibre compares the GDS layout against a schematic, it must find an instance in the schematic for every device in the layout. Since filler and decap cells appear as real cells in the GDS, they must also appear in the schematic netlist. Without them, LVS would flag every filler cell as an unmatched device in the layout.

The three netlists serve three different tools with three different models of what a "correct" design looks like. Using the wrong netlist for a given tool would produce false failures or false passes, neither of which is acceptable before tape-out.

Two DEF Files: Different Views for Different Tools

DEF (Design Exchange Format) is a text-based, tool-agnostic representation of the physical layout. The chip finish stage generates two DEF files with different content:

Full DEF (.def) — For Parasitic Extraction and SoC Integration

Contains everything in the physical database: cell placements, all routing wire shapes, special nets (power/ground routing), filler cells, and any metal fill inserted for density compliance. This is the authoritative physical description of the block. Parasitic extraction tools read this DEF alongside the technology LEF to compute the resistance and capacitance of every wire. The extracted parasitics are then used by signoff timing tools to compute accurate post-route slack. When the block is integrated at the chip level, the SoC integration tool also reads this DEF to understand the block's internal physical structure.

Routing DEF (.IR.def) — For Power Integrity Analysis

Contains only the routing wire shapes — no cell placement information, no filler cells. Power integrity tools (Voltus, Redhawk) build their own model of cell power consumption from transistor-level current profiles and need only the metal wire topology to compute the resistive network of the power delivery grid. Including cell placements in the DEF would add file size and parsing overhead without providing any additional useful information to the power analysis engine. The routing-only DEF is therefore smaller, faster to read, and equally accurate for IR drop and electromigration analysis.

LEF Abstract: The Interface for Hierarchical Integration

When a designed block (such as the tile) is used as a macro in a larger chip (such as iguana_soc), the top-level PnR tool needs to know the block's physical characteristics without loading the entire post-route database. The LEF abstract provides this compact physical interface:

  • Bounding box: The width and height of the block, so the top-level placer knows how much area it occupies
  • Pin shapes: The exact metal layer and location of every signal, power, and ground pin that connects to the block boundary, so the top-level router knows where to attach wires
  • Routing blockages: The metal layers and regions inside the block where the top-level router must not route — because those areas are occupied by the block's own internal wires
  • Power stripes: The location and dimensions of the block's internal power grid stripes, which must align with the chip-level power grid

What the LEF abstract deliberately does not contain is the internal cell placement or signal routing of the block. This information is proprietary IP and is also unnecessary for the top-level integration. The abstract is a boundary representation that reveals only the block's external physical interface — everything the surrounding chip needs to know, nothing more.

Without the LEF abstract, a block cannot be used as a hard macro in any hierarchical design. The top-level PnR tool has no way to determine where the block's pins are or how large a keep-out zone the block's internal routing requires.

GDS: From PnR Output to Tape-Out Deliverable

GDS II (Graphical Data System) is the industry-standard format for encoding chip layout as polygon geometry on specific layers. The foundry reads the GDS to generate the photomasks used in manufacturing. Every polygon on every layer of the chip must be present in the final GDS file before it can be sent to the foundry.

The chip finish stage generates two GDS files for different purposes:

PnR-Only GDS (.pnr.gds.gz) — For Block-Level DRC

Contains only the routing geometry generated by Innovus: wires on all metal layers, vias, and filler cell placements. Standard cells are represented as empty cell references (SREF records in GDS) — the cell name is recorded but its internal transistor and metal geometry is not included. This file is used for fast block-level DRC runs where Calibre reads the PnR GDS together with the separate PDK standard cell GDS files, allowing it to cache and reuse the standard cell rule-check results across multiple runs.

Merged GDS (.merged.gds.gz) — The Tape-Out Deliverable

Contains everything: the PnR routing geometry plus the actual transistor-level polygon geometry of every standard cell, copied from the PDK standard cell GDS libraries. For TSMC N28, three separate PDK GDS files must be merged — one each for LVT, SVT, and HVT standard cell variants — because each threshold variant uses different implant layers and well structures that are not interchangeable. The merged GDS is fully self-contained: every cell reference resolves to actual geometry within the file. This is the file submitted to the foundry for mask generation and manufacturing.

A GDS map file translates the layer names used internally by Innovus (which are human-readable strings like "M1" or "VIA12") into the numeric layer and datatype codes specified in the PDK. Without this mapping, the layer numbers in the output GDS would not match what the foundry expects, rendering the file unusable.

The hcell.list: Enabling Hierarchical LVS

Calibre LVS compares a GDS layout against a schematic netlist and checks that they describe the same circuit. It must decide for each cell whether to recurse into the cell's internal structure for detailed comparison or to treat the cell as a black box matched by name.

Standard cells in the PDK are pre-verified by the foundry — their internal transistor-level layout has already been confirmed to match their schematic. It would be redundant and extraordinarily slow to re-verify every NAND gate, flip-flop, and buffer at transistor level for every design. The hcell list tells Calibre which cells should be treated as hierarchical black boxes, matched by cell name rather than internal structure.

The hcell list is generated by iterating over every unique cell type instantiated in the design and writing each cell name twice on one line — the GDS cell name and the schematic cell name. When both names are the same (as they are for standard cells), Calibre matches the cell by name and does not recurse into it. Without the hcell list, Calibre would try to flatten every standard cell to transistor level and compare individual MOSFETs against the gate-level schematic, which describes NAND gates and flip-flops, not transistors. This mismatch would produce millions of false LVS errors and make the verification completely unusable.

Script Parameterization Through Environment Variables

The chip finish script accesses its input and output paths through shell environment variables rather than hard-coded directory paths. This design pattern serves two important purposes:

Reusability across designs and runs

The same chip_finish.tcl script works for any block — tile, iguana_soc, or any future design — without modification. The block name, the location of the post-route outputs, and the chip finish output directory are all set by the job scheduler or Makefile before Innovus starts. The script queries these values at runtime. This eliminates a class of bugs where the wrong block name is hard-coded in one or more write commands, which would silently overwrite the wrong files.

Integration with flow automation

In a production PnR environment, hundreds of blocks may be processed simultaneously by a job scheduler. Each job sets its own environment variables before launching Innovus, so the same script template runs concurrently for multiple blocks in different directories without interference. The chip finish outputs land in the correct per-block output directory because the output path is parameterized, not hard-coded.

📝 Knowledge Assessment Quiz

Question 1: Why does the chip finishing flow generate three different Verilog netlists rather than one?

  • A. The three netlists are used at different timing corners for setup and hold analysis
  • B. Different downstream verification tools require different levels of physical detail: LEC needs only logical connectivity, power-aware simulation needs explicit PG ports, and Calibre LVS needs both PG ports and all physical instances including filler cells
  • C. The three files are identical; the different extensions are a naming convention that has no effect on downstream tools
  • D. Innovus cannot write a single netlist that satisfies all downstream requirements due to a tool limitation

Correct! LEC compares logical functions and would be confused by PG ports. LVS physically compares the GDS layout against the schematic — since filler cells appear as real devices in the GDS, they must appear in the schematic too. Using the wrong netlist for a given tool would produce false failures, masking real issues or incorrectly passing designs with actual bugs.

Question 2: Why must standard cell GDS files (LVT, SVT, HVT) be merged into the final GDS for tape-out?

  • A. Calibre DRC cannot read multiple GDS files simultaneously
  • B. Merging reduces total GDS file size significantly by eliminating duplicate layer information
  • C. The PnR GDS contains only empty cell references for standard cells — no transistor or metal geometry. Merging copies the actual transistor-level silicon geometry from the PDK libraries into one self-contained file that the foundry can use to generate photomasks
  • D. The foundry requires a single GDS file as a contractual submission rule

Correct! Innovus generates GDS with standard cells as SREF (structure reference) records — a pointer to a cell name without internal content. The PDK GDS libraries contain the actual polygon geometry for every diffusion, gate, contact, and metal layer inside each standard cell. Merging resolves all SREF records by copying the referenced cell definitions, producing a complete layout where every layer of every cell is physically described.

Question 3: What would happen during Calibre LVS if the hcell.list file were not provided?

  • A. LVS would pass because Calibre automatically detects standard cells from the PDK installation
  • B. LVS would skip standard cell verification and only check custom cells and macros
  • C. Calibre would attempt to flatten all standard cells to transistor level and compare individual MOSFETs against the gate-level schematic, which describes logical gates — the structural mismatch would produce millions of false errors, making LVS completely unusable
  • D. LVS would complete but report every standard cell as an extra device in the layout

Correct! Without an hcell list, Calibre has no instruction to treat standard cells as hierarchical black boxes. It recurses into every cell's GDS geometry and tries to match individual transistors against the schematic, which describes NAND, NOR, and flip-flop gates. The structural levels are incompatible, generating massive false failure counts that make the LVS report meaningless.

Question 4: A block's LEF abstract is accidentally omitted from the chip finishing outputs. Which downstream flow immediately fails?

  • A. Calibre DRC cannot run because it uses the LEF abstract to identify routing blockages
  • B. LVS fails because the LEF abstract provides the schematic reference for pin connectivity
  • C. Chip-level PnR integration fails — the top-level tool has no information about the block's bounding box, pin locations, or internal routing blockages and cannot place or route to the block
  • D. Post-route timing signoff fails because PrimeTime uses the LEF abstract to model wire capacitance for the block's boundary pins

Correct! The LEF abstract is the only physical interface that the chip-level PnR tool sees for a hard macro. Without it, the block is an undefined macro — the top-level tool cannot place it because it does not know its dimensions, cannot route to it because it does not know where the pins are, and cannot route around it because it does not know the internal routing blockage pattern.
