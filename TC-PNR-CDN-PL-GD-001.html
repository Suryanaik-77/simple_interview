Scenario

GUIDED

You are performing standard cell placement for the tile design using Cadence Innovus. The floorplan database from the previous stage is provided in inputs/floorplan.db. Your task is to load that database and run the complete placement flow using scripts/placement.tcl, understanding every command in the script.

This guided exercise walks through the full production Innovus placement script step by step. You will learn:

  • How to load a prior-stage Innovus database as the starting point
  • How to establish power rail connectivity before placement begins
  • How IO buffers are inserted and padded
  • Why LVT and clock cells are excluded from placement
  • How placement density, congestion effort, and timing effort are configured
  • How tieoff and spare cells are set up and placed
  • What reports are generated and how to interpret them

Run the full flow from the testcase directory:

make all

Follow the step-by-step walkthrough below to understand exactly what each command in scripts/placement.tcl does and why it is there.

📝 Step-by-Step Walkthrough

  • Step 1 — Load the Floorplan Database

    The placement script begins by loading the Innovus database produced at the end of the floorplan stage:

    read_db ../inputs/floorplan.db

    read_db restores a complete Innovus session checkpoint — the placed floorplan, power grid, IO pin assignments, timing constraints (SDC), and all tool settings that were active when the floorplan database was saved. By reading the floorplan database as the first command, this placement script picks up exactly where the floorplan stage left off, with no need to re-read LEFs, netlists, or SDC files. Every subsequent command in the script operates on the design state captured in that .db file.

  • Step 2 — Power Rail Connectivity

    Before any cells are moved or inserted, power and ground rail associations must be declared:

    connect_global_net VDD -type pg_pin -pin_base_name VDD*
connect_global_net VSS -type pg_pin -pin_base_name VSS

    Standard cell rows have alternating VDD and VSS rails running across each row. When the placement engine inserts or flips a cell, it must orient the cell so its power pin aligns with the VDD rail and its ground pin aligns with the VSS rail. These two commands tell Innovus which net is power (VDD) and which is ground (VSS) by connecting all pins whose base name starts with VDD* to the global VDD net, and all pins named VSS to the global VSS net. Without this, cells could be inserted with reversed polarity — a catastrophic functional error.

  • Step 3 — IO Buffer Cell Padding and Insertion

    IO buffers are inserted on every port of the design. Before insertion, a padding margin is defined for the buffer cell type so the tool reserves extra empty sites around each inserted buffer:

    set_cell_padding -cells BUFFD4BWP40P140HVT -left_side 4 -right_side 4 -top_side 2 -bottom_side 2
add_io_buffers -exclude_clock_nets -in_cells BUFFD4BWP40P140HVT -out_cells BUFFD4BWP40P140HVT -port -status softfixed -suffix io_buff
set_inst_padding -inst *io_buff* -left_side 4 -right_side 4 -top_side 2 -bottom_side 2
    • set_cell_padding -cells BUFFD4BWP40P140HVT ... — declares padding for the cell type before insertion. This ensures the tool respects the margins when placing IO buffers. Left/right padding of 4 sites accommodates the routing from the buffer to its port pin; top/bottom padding of 2 sites prevents the buffer from touching cells above and below it in adjacent rows.
    • add_io_buffers — inserts a BUFFD4BWP40P140HVT buffer on every input and output port except clock nets. The -status softfixed option means the placer positions the buffers near their associated ports but retains freedom to optimize their exact location slightly. The -suffix io_buff names all inserted instances with the io_buff suffix for easy identification.
    • set_inst_padding -inst *io_buff* ... — applies padding only on the IO buffer instances (matched by the io_buff suffix). This is the correct scope: padding applies only to the inserted buffers, not to all BUFFD4 cells in the design.

  • Step 4 — Cell Library Constraints (dont_use)

    Cells that should not be used by the placement optimizer are excluded before placement begins:

    set_dont_use [get_lib_cells *LVT]
set_dont_use [get_lib_cells {*CKBD* *CKND* *CKAN* *CKMUX* *D18* *D20* *D24* *D32}]
    • set_dont_use [get_lib_cells *LVT] — excludes all Low Threshold Voltage cells. LVT cells switch faster than HVT cells but consume significantly more leakage power. In this flow, LVT cells are reserved exclusively for the Clock Tree Synthesis (CTS) stage, where their speed advantage directly reduces clock insertion delay. Keeping them out of logic placement prevents unnecessary leakage power increase on non-critical paths.
    • set_dont_use [get_lib_cells {*CKBD* *CKND* *CKAN* *CKMUX* *D18* *D20* *D24* *D32}] — excludes clock-specific cells (CKBD, CKND, CKAN, CKMUX) and very large drive-strength variants (D18, D20, D24, D32). Clock cells have special characteristics tuned for low clock skew and are managed by the CTS engine. Large drive-strength cells consume excessive area and power when inserted into logic paths where a smaller drive strength would suffice.

  • Step 5 — Placement Configuration Parameters

    Nine set_db commands configure the placement engine before the run:

    set_db opt_new_inst_prefix PNR_PLACE
set_db add_tieoffs_cells {TIEHBWP40P140HVT TIELBWP40P140HVT}
set_db add_tieoffs_max_fanout 3
set_db add_tieoffs_max_distance 50
set_db design_process_node 28
set_db place_global_cong_effort high
set_db place_global_timing_effort medium
set_db place_global_max_density 0.65
set_db place_detail_legalization_inst_gap 2
set_db add_fillers_no_single_site_gap true
    • opt_new_inst_prefix PNR_PLACE — any new cell instances created by the placement optimizer will be named with the prefix PNR_PLACE, making optimizer-added cells easy to identify in the netlist and reports.
    • add_tieoffs_cells {TIEHBWP40P140HVT TIELBWP40P140HVT} — specifies the tie-hi and tie-lo cell types used when add_tieoffs is called later. Tie-hi cells connect constant-1 nodes to VDD; tie-lo cells connect constant-0 nodes to VSS. Using dedicated tieoff cells prevents latch-up conditions.
    • add_tieoffs_max_fanout 3 — a single tieoff cell drives at most 3 loads. If more than 3 logic inputs need the same constant value in a region, additional tieoff cells are inserted nearby.
    • add_tieoffs_max_distance 50 — a tieoff cell must be placed within 50 microns of the loads it drives, limiting wire length and preventing long unintended antennas.
    • design_process_node 28 — informs Innovus that this design targets the TSMC 28nm process node. Some internal algorithms use the process node to select appropriate default parameters and design rule checks.
    • place_global_cong_effort high — directs the global placement engine to use the highest congestion-awareness effort, spreading cells more aggressively to reduce local density hotspots at the cost of longer runtime.
    • place_global_timing_effort medium — sets medium timing awareness during global placement, balancing runtime versus timing quality. Full timing closure is handled in post-placement optimization and CTS.
    • place_global_max_density 0.65 — limits placement to a maximum of 65% core utilization. The remaining 35% becomes available for routing wires. Exceeding ~70% density typically causes router congestion failures.
    • place_detail_legalization_inst_gap 2 — requires at least 2 site widths of empty space between adjacent cell instances during detailed legalization, improving local routing flexibility.
    • add_fillers_no_single_site_gap true — prevents filler cells from being placed in gaps only one site wide, ensuring gaps remain fillable by actual filler cells later in the flow.

  • Step 6 — Tieoff Net Connections

    Constant-value nets in the design are connected to power and ground through the global net mechanism:

    connect_global_net VDD -type tie_hi
connect_global_net VSS -type tie_lo

    These commands associate all tie-hi nodes in the design with the VDD global net and all tie-lo nodes with the VSS global net. This prepares the design for add_tieoffs, which runs after placement and inserts the physical tieoff cells defined in Step 4. Establishing the net connections before placement allows the tool to account for tieoff cell placement during congestion estimation.

  • Step 7 — Spare Cell Module Creation and Placement

    A spare cell module is defined and distributed across the core area for post-silicon ECO use:

    set celllist {MUX2D4BWP40P140 ND2D6BWP40P140 NR2D6BWP40P140 INVD8BWP40P140 BUFFD4BWP40P140 BUFFD2BWP40P140 TIEHBWP40P140 TIELBWP40P140 DEL025D1BWP40P140 SDFCNQARDBWP40P140}
create_spare_module -cells $celllist -module_name PNR_SPARE
place_spare_modules -prefix PNR_spare_cell -module_name PNR_SPARE -step_x 50 -step_y 50 -offset_x 5 -offset_y 5 -density 0.4 -max_width 15
    • set celllist {...} — defines the list of 10 cell types composing one spare module: MUX, NAND, NOR, inverter, buffers (two drive strengths), tie-hi/tie-lo, delay cell, and a scan flip-flop. These provide the logic primitives needed to implement small bug fixes using metal-only ECOs after manufacturing.
    • create_spare_module -cells $celllist -module_name PNR_SPARE — creates an Innovus spare module definition named PNR_SPARE containing one instance of each cell in $celllist. The module is a template for instantiation.
    • place_spare_modules ... — tiles instances of PNR_SPARE across the core on a 50×50 micron grid starting at offset (5, 5). The -density 0.4 option means spare cells occupy at most 40% of each grid cell, and -max_width 15 limits the bounding box of each placed spare group to 15 microns wide. Spare cells must be placed at this stage so the congestion estimator accounts for their area.

  • Step 8 — Source Timing Derates and Run Placement

    Before running the placement engine, on-chip variation (OCV) timing derates are loaded from a shared block script:

    source ../inputs/innovus_derates.tcl
place_opt_design
    • source ../inputs/innovus_derates.tcl — loads the timing derate factors for the tile design. Derates model process, voltage, and temperature (PVT) variation effects on cell and wire delays. These derates are applied to timing analysis during placement optimization, ensuring the placer places cells conservatively enough to account for real silicon variation.
    • place_opt_design — runs the complete Innovus placement engine. This single command performs global placement (assigns approximate cell positions to minimize wire length), legalization (snaps cells to legal row positions without overlaps), and post-placement optimization (PPO: inserts, resizes, and repositions cells to fix setup violations introduced by legalization). On completion, all cells have unique, legal, grid-aligned positions and timing has been optimized within placement constraints.

  • Step 9 — Post-Placement: Add Tieoffs and Reconnect Power Rails

    After placement completes, tieoff cells are inserted and power rail connectivity is re-established for all cells including newly inserted instances:

    add_tieoffs
connect_global_net VDD -type pg_pin -pin_base_name VDD*
connect_global_net VSS -type pg_pin -pin_base_name VSS
    • add_tieoffs — physically inserts tie-hi and tie-lo cell instances (as configured in Step 4) adjacent to the loads they drive, within the distance and fanout constraints. These cells occupy real sites in standard cell rows.
    • connect_global_net VDD/VSS ... — runs the power rail connection again after tieoff insertion. New cells added by add_tieoffs and by the place_opt_design optimizer need their power pins connected to the global VDD and VSS nets. Re-running connect_global_net ensures every cell in the final placed netlist is properly connected to power.

  • Step 10 — Placement Quality Reports

    Nine reports are generated to assess placement quality across multiple dimensions:

    check_place > ../reports/check_place.rpt
report_congestion -overflow > ../reports/report_congestion.overflow.rpt
report_timing -group reg2reg > ../reports/rereport_timing.reg2reg.rpt
report_timing -group in2reg > ../reports/rereport_timing.in2reg.rpt
report_timing -group reg2out > ../reports/rereport_timing.reg2out.rpt
time_design -pre_cts > ../reports/time_design.rpt
report_congestion -hotspot > ../reports/report_congestion.hotspot.rpt
report_density_map > ../reports/report_density_map.rpt
report_timing_summary > ../reports/report_timing_summary.rpt
check_floorplan -report_density > ../reports/tilisation.rpt
    • check_place — the primary placement legality check. Reports any cells that are overlapping, outside their assigned row, or misaligned to the site grid. This must show 0 violations before the design proceeds to CTS.
    • report_congestion -overflow — reports global routing tiles where routing demand exceeds the available track supply. Overflow hotspots predict where the router will fail to complete connections.
    • report_timing -group reg2reg/in2reg/reg2out — reports pre-CTS timing for the three main path groups using estimated wire delays. Significant negative slack at this stage indicates the design may not close timing after routing and CTS.
    • time_design -pre_cts — runs a full pre-CTS timing analysis and summarizes WNS, TNS, and violating path counts across all timing modes. This is the comprehensive timing health check before handoff to CTS.
    • report_congestion -hotspot — identifies specific regions of the core with the highest routing demand concentration. Hotspot count and severity indicate whether cell spreading needs to be increased.
    • report_density_map — generates a spatial density map showing cell utilization across the core. Areas of unusually high density may become congestion hotspots even if the global density is within target.
    • report_timing_summary — a compact tabular summary of timing violations across all corners and modes. Used as a quick pass/fail indicator for overall timing health.
    • check_floorplan -report_density — verifies that the floorplan boundaries are intact after placement and reports the final core utilization. Confirms that cell placement has not pushed any cells outside the legal core area.

  • Step 11 — Save the Database

    The placed Innovus database is written to the outputs directory:

    write_db -sdc ../outputs/place.db

    write_db -sdc ../outputs/place.db saves the complete Innovus placement database including the placed netlist, physical layout data, and embedded SDC timing constraints (the -sdc flag includes the timing constraints in the database file). This checkpoint is the input to the Clock Tree Synthesis (CTS) stage. Without -sdc, the SDC would need to be re-read at the start of CTS.

✅ Success Criteria

  • outputs/place.db exists and is non-empty
  • No **ERROR lines in logs/placement.log
  • reports/check_place.rpt shows 0 placement violations
  • Congestion hotspot count in reports/report_congestion.hotspot.rpt is below 100
  • No unplaced instances reported in the log

✅ Validation & Verification

After the flow completes, run the automated verification to confirm all success criteria:

make verify

The verify target checks for a valid .db file in outputs/, no **ERROR lines in logs, and a passing congestion hotspot check. A PASS result confirms placement completed successfully and the database is ready for CTS.

📝 Knowledge Assessment

1. Standard cell placement is divided into multiple sequential phases. What is the correct order of these phases?

  • Initial Optimization → Global Placement → HFNS → Detailed Placement → Final Optimization
  • HFNS → Global Placement → Initial Optimization → Detailed Placement → Final Optimization
  • Global Placement → HFNS → Initial Optimization → Detailed Placement → Final Optimization
  • Global Placement → Detailed Placement → HFNS → Initial Optimization → Final Optimization
Correct! The 5-phase placement flow is: (1) Global Placement — coarse placement of all cells with overlaps allowed, minimizing wirelength; (2) HFNS — buffer insertion on high-fanout nets to reduce large capacitive loads; (3) Initial Optimization — early timing and DRV fixes via buffer insertion and cell resizing; (4) Detailed Placement — cell legalization removing all overlaps, aligning to placement sites; (5) Final Optimization — timing-driven refinement of placement to close setup paths.

2. What does HFNS (High Fanout Net Synthesis) do during the placement flow, and why is it needed?

  • HFNS replaces high-fanout logic gates with multi-output versions to reduce the total cell count
  • HFNS redistributes flip-flops to equalize the number of cells connected to each clock domain
  • HFNS inserts buffers or inverter trees on nets with very high fanout (typically >32–50 loads), breaking a single large capacitive net into a buffered tree, reducing transition time and preparing the design for accurate timing optimization
  • HFNS analyzes net frequencies and moves high-frequency cells closer together to reduce dynamic power
Correct! A high-fanout net (e.g., a reset or enable signal driving thousands of cells) has enormous capacitance. Without buffering, the driver must charge this load, producing a very slow transition time and poor setup timing on all receiver paths. HFNS inserts a buffer tree so each driver sees a manageable load, transition times meet DRV limits, and the placement optimizer can work with realistic wire capacitances.

3. How does excessive IR drop in the power grid affect cell timing?

  • IR drop increases clock transition time but has no effect on data path delays
  • IR drop only affects hold timing because it slows the clock path, making the clock arrive later
  • IR drop reduces the effective supply voltage at a cell, which decreases transistor drive current. This slows cell switching speed, increasing cell delays — setup violations develop on data paths, and if the IR drop affects clock cells differentially, hold violations can also appear
  • IR drop has no timing impact because EDA tools account for supply variation in the worst-case .lib files
Correct! Cell delay is a strong function of supply voltage. When IR drop reduces VDD at a cell's power pins, the transistors switch more slowly than their characterized values at nominal voltage. This translates directly to increased cell delay. Setup violations arise when data-path cells slow down. If IR drop affects clock capture-path cells more than launch-path cells, the effective clock period is shortened, which can trigger hold violations.

4. In placement, "PPA" is described as a trade-off triangle. What do the three letters stand for and what fundamental tension exists between them?

  • Pad, Pin, and Area — describing the competing demands of I/O planning versus core area
  • Placement, Power grid, and Analysis — the three stages that must be iterated until convergence
  • Power, Performance, and Area — optimizing any one typically degrades the others: higher performance needs larger/faster cells (more area, more power); lower power needs smaller cells or less switching (less performance); smaller area increases density (routing congestion, harder timing closure)
  • Parasitic, Path, and Accuracy — reflecting the compromise between extraction accuracy and runtime
Correct! PPA (Power-Performance-Area) is the fundamental design objective space for chip implementation. Performance requires driving cells harder (bigger transistors = more area + power). Reducing power demands smaller cells with lower switching activity (less performance + smaller area). Minimizing area packs cells densely (less routing space, harder timing closure). Every design makes deliberate PPA trade-offs based on the product's requirements.
