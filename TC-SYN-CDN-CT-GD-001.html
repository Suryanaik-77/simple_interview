⏱ Create Clocks

Before writing any create_clock, first understand: Where is the clock coming from?

A register clock may come directly from a port or pass through logic like a MUX. So we should never assume — we must trace it.

Trace the clock path using all_fanin
Genus Trace
 all_fanin -to pin:rtl_halfcycle_crosspaths/r2_reg[1]/clk

 r2_reg[1]/clk clk

This shows that the register clock is directly coming from clk.

Genus Trace
 all_fanin -to pin:rtl_halfcycle_crosspaths/comm_reg_reg[0]/clk

 comm_reg_reg[0]/clk mux_117_24/z mux_117_24/ctl clk_sel mux_117_24/in_0 clk_new_1 mux_117_24/in_1 clk_new_2

Here, the clock is not directly coming from a port. It is passing through a MUX.

clk_sel (MUX control):
- Selects which clock reaches the register
- 0 → clk_new_1
- 1 → clk_new_2
The MUX is only selecting the clock. It is NOT generating the clock.

So the actual clock sources are:

Clock Sources
clk_new_1
clk_new_2
clk

Therefore, define clocks at these ports:

Create Clock
create_clock -name clk1 -period 1 [get_ports clk_new_1]
create_clock -name clk2 -period 2.2 [get_ports clk_new_2]
create_clock -name clk  -period 4.3 [get_ports clk]
Rule: Always define clocks at the origin, not inside logic.

5. Analyze New CTI Warnings After Clock Creation

After creating the primary clocks (clk, clk1, clk2), the timing intent improves significantly and most of the initial warnings are resolved.

At this stage, the remaining CTI warnings represent missing advanced constraints and incomplete I/O modeling. These are the final set of warnings that need to be analyzed and fixed to achieve a clean timing intent report.

1. Sequential clock pins without clock waveform (16 warnings)

Some sequential elements are driven by signals that behave like clocks but are not defined in the SDC.

To understand this, always trace the clock pin:

all_fanin -to pin:rtl_halfcycle_crosspaths/rd0_reg[0]/clk rd0_reg[0]/clk clk_div_reg/q clk_div_reg/clk

From this trace:

The register clock is not coming directly from the primary clock. It is coming from clk_div_reg/q, which means a flip-flop is generating a new clock signal.

What is happening?
The signal clk_div_reg/q is acting as a clock.
This typically happens in a clock divider circuit.

Since this clock is derived from another clock, it is called a:

Generated Clock

STA does not automatically understand this relationship, so we must explicitly define it.

To resolve this warning, define a generated clock at the source:

create_generated_clock -name gen_clk -source [get_ports clk] -divide_by 2 [get_pins clk_div_reg/Q]
Make sure the -source is the original clock and the generated clock is defined at the pin where it is created (Q of the divider flop).

2. Paths constrained with different clocks (1 warning)

This warning appears when timing paths exist between registers driven by different clocks.

Before fixing it, we must understand how these clocks are related.

In this design, gen_clk is derived from clk, so both belong to the same clock domain. On the other hand, clk1 and clk2 are independent clocks and have no relationship with clk.

In timing analysis, clocks derived from the same source should be treated as related, while independent clocks must be treated as asynchronous.

To inform the tool about this, we define clock groups as follows: 

set_clock_groups -asynchronous 
  -group {clk gen_clk} 
  -group {clk1} 
  -group {clk2}

This constraint tells the tool to ignore timing paths between different groups. For example, paths between clk or gen_clk and clk1 or clk2 will not be analyzed.

However, timing paths within the same group are still valid and will be checked. So timing between clk and gen_clk is analyzed correctly.

🔍 Remaining CTI Warnings Analysis

Although the timing intent report still shows 295 warnings, these warnings are expected in this design and can be safely ignored after analysis. The following sections explain why these warnings occur.

1. Sequential data pins driven by a clock signal (1 warning)

This warning occurs because a generated clock is created on the Q output of a flip-flop. Since the Q output feeds back into the D input of the same register through combinational logic, the tool detects that the data pin is being driven by a clock-derived signal.

In this design, this behavior is intentional and does not represent a functional problem, therefore this warning can be safely ignored.

2. Sequential clock pins with multiple clock waveforms (288 warnings)

These warnings are caused by a clock multiplexer used in the design. The multiplexer selects between two clocks (clk_new_1 and clk_new_2) depending on the functional mode of operation.

Since both clocks can potentially reach the same register clock pin through the mux, the tool reports that multiple clock waveforms are driving the same sequential clock pin.

However, only one clock is active at a time depending on the control signal, so this is expected behavior and these warnings can be ignored.

3. Timing exceptions with no effect (6 warnings)

These warnings indicate that certain timing exception constraints are currently not affecting any timing paths in the design.

This situation can occur when timing exceptions are defined for paths that are not active in the current configuration of the design. These warnings do not impact the correctness of the constraints and can therefore be ignored.

After reviewing these warnings and confirming their expected behavior, the timing constraints can be considered valid for this design.

All timing intent warnings have now been resolved successfully. This indicates that the design has been properly constrained and the synthesis tool now understands the intended timing relationships between clocks, inputs, and outputs.

A clean check_timing_intent report is an important milestone before proceeding with further synthesis optimization and timing analysis.
