Problem Statement

GUIDED

You will run the complete Clock Tree Synthesis (CTS) flow on the tile processor core using ICC2. The placed block saved in PNR-SNPS-PL is your starting point. Every command is explained in detail — what it does, why the parameter values were chosen, and what you should verify before proceeding.

By the end of this testcase you will have:

  • Activated all MMMC scenarios and configured LVT-only clock cell libraries
  • Created NDR rules and assigned them to root, internal, and sink clock nets
  • Enabled CCD and set CTS optimization targets (skew, latency, transition)
  • Run clock_opt in two phases: tree build + post-CTS hold/setup optimization
  • Added tie cells, switched to propagated clocks, updated IO latency, and saved the CTS block
  • Generated and interpreted the full suite of post-CTS quality reports

📄 CTS — Step-by-Step Command Explanation

Follow the steps below exactly. Navigate to the testcase directory, launch ICC2, write the commands into ../scripts/cts.tcl, and source it from inside icc2_shell.

  • Navigate and Launch ICC2

    You have already set up the lab directory structure using the provided setup guidelines. The required input files are now available in the testcase directory. With the lab environment ready, proceed with the following steps.

    Navigate to the testcase directory and start the ICC2 session:

    cd ~/pd/labs/PNR-SNPS-CTS/TC-PNR-SNPS-CTS-GD-001
make all

    Open the CTS script in a separate editor, write commands as you follow the steps, then source it:

    source ../scripts/cts.tcl

  • Open the Placed Library and Block (open_lib / open_block)

    What it does: Opens the NDM design library and loads the placed.design block — the output of the placement stage with all standard cells legally placed and timing-driven optimization complete.

    open_lib ../inputs/tile.ndm
open_block placed.design
    What to verify: Confirm ICC2 prints the block name placed.design with no error messages. If you see "block not found," check that the placement stage ran successfully and save_block -as placed was executed.

  • Activate All Scenarios — Setup AND Hold

    What it does: Activates every MMMC scenario — both setup corners (slow-slow process, low voltage, high temperature) and hold corners (fast-fast process, high voltage, low/high temperature). During placement only setup scenarios were active because hold analysis under ideal clocks is meaningless. Now that CTS will build a real clock tree, real skew exists and hold violations must be analyzed and fixed.

    set_scenario_status -active true [all_scenarios]
    Why all scenarios at CTS? Hold violations depend on clock skew — the difference in clock arrival time between two flip-flops. Under ideal clocks (placement), skew = 0, so hold is trivially satisfied. Once the clock tree introduces real latency differences, some paths that were fine under ideal clocks will have hold violations. The final_opto phase of clock_opt fixes these — but only if the hold scenarios are active.
    What to check: Run report_scenarios and confirm all 4 scenarios (2 setup + 2 hold) show Active=true.

  • Set Instance Name Prefixes

    What it does: Sets separate prefixes for two categories of new cells that will be inserted during CTS. This makes it easy to identify and filter CTS-inserted cells in the netlist and reports.

    set_app_options -name opt.common.user_instance_name_prefix -value "PNR_CTSOPT"
set_app_options -name cts.common.user_instance_name_prefix -value "CTS_BUFF"
    • PNR_CTSOPT — prefix for data-path optimization cells inserted during the clock_opt run (gate sizing, logic buffering for timing recovery).
    • CTS_BUFF — prefix for all clock tree buffers and inverters inserted by the CTS engine. In the structure report, every clock buffer will appear as CTS_BUFF*.

  • Configure Lib-Cell Purposes for CTS

    What it does: A two-step process to precisely control which cells the CTS engine can use.

    set_lib_cell_purpose -exclude optimization [get_lib_cells {*/CK* */*D24* */*D32* */*D20* */*D18* */*LVT}]
set_lib_cell_purpose -exclude cts [get_lib_cells */*]
set_lib_cell_purpose -include cts [get_lib_cells {*/CK*D4BWP*LVT */CK*D8BWP*LVT */CK*D12BWP*LVT */CK*D16BWP*LVT */CKND*D4BWP*LVT */CKND*D8BWP*LVT */CKND*D12BWP*LVT */CKND*D16BWP*LVT}]
    • Line 1 — exclude from optimization: Prevents the data-path optimizer from inserting high-drive or clock cells. Same as placement — clock cells are exclusively managed by the CTS engine.
    • Line 2 — exclude ALL cells from CTS: Starts with a clean slate — no cell in the entire library can be used as a clock tree buffer yet.
    • Line 3 — include only approved clock cells: Allows only LVT variants of TSMC 28nm clock buffers (CKBD4/8/12/16) and clock inverters (CKND4/8/12/16). LVT is chosen for its faster switching speed to minimize clock latency and meet the 0.28 ns transition target. Drive strengths D4–D16 cover the range from short local wires to long cross-chip runs.
    Why not D24, D32? Very high drive-strength cells create excessive current drive, increasing IR-drop and routing congestion in dense areas. D16 is sufficient for the longest clock branches in the tile design.

  • Derive Clock Cell References (derive_clock_cell_references)

    What it does: After the lib cell purpose is set, this command analyzes all cells marked for CTS use and builds the internal reference list that the CTS engine uses to select cells during tree synthesis. It automatically categorizes cells by drive strength and maps them to appropriate positions in the tree hierarchy.

    derive_clock_cell_references
    What to verify: ICC2 will print a table showing the number of clock buffer and inverter references found. Confirm it lists the D4, D8, D12, and D16 LVT variants. If 0 references are found, the set_lib_cell_purpose -include cts step had an error in the cell name pattern.

  • Create NDR Rules and Assign to Clock Net Types

    What it does: Creates two Non-Default Routing rules and assigns them to different portions of the clock tree based on net type.

    create_routing_rule -multiplier_width 2 -multiplier_spacing 2 cts_2w2s
create_routing_rule -multiplier_width 1 -multiplier_spacing 2 cts_1w2s
set_clock_routing_rules -net_type {internal} -rules cts_2w2s -max_routing_layer M7 -min_routing_layer M4
set_clock_routing_rules -net_type {root}     -rules cts_2w2s -max_routing_layer M7 -min_routing_layer M4
set_clock_routing_rules -net_type {sink}     -rules cts_1w2s -max_routing_layer M6 -min_routing_layer M3
    Net TypeRuleWidthSpacingLayersReason
    root, internalcts_2w2s2x2xM4–M7Long high-drive wires near the source — double width reduces resistance; double spacing prevents coupling to adjacent signal nets.
    sinkcts_1w2s1x2xM3–M6Short last-mile wires to flip-flop clock pins — default width is sufficient; double spacing prevents coupling noise from dense data nets.
    Layer selection rationale: M4–M7 for root/internal nets uses upper metal where wire resistance per unit length is lower — better for long clock branches. M3–M6 for sink nets allows the router to use intermediate layers for short local connections, which is appropriate given the short wire lengths at the bottom of the tree.

  • Enable CCD and Set CTS Optimization Targets

    What it does: Enables Concurrent Clock and Data optimization and sets the per-sink-pair skew and latency targets that the CTS engine will try to meet.

    set_app_option -name clock_opt.flow.enable_ccd -value true
set_clock_tree_options -target_skew 0.1 -target_latency 0.3
    • CCD enabled: ICC2 will jointly optimize the clock tree topology and data path timing. Instead of building a perfectly balanced tree first and then doing data-path timing repair, CCD intentionally introduces useful skew to relax critical setup paths — at the cost of hold violations that are fixed in final_opto.
    • -target_skew 0.1: The CTS engine targets a maximum per-sink-pair skew of 100 ps. In the tile design, the achieved global skew was 0.38–0.61 ns across corners — the target is an optimization goal, not a hard constraint.
    • -target_latency 0.3: Target insertion delay from the clock source to each sink is 300 ps. Actual achieved latency in tile was 0.51–0.82 ns across corners.

  • Apply Clock Uncertainty and Max-Transition Constraints

    What it does: Applies clock uncertainty (timing margin guard-bands) and maximum transition limits to all clocks across every scenario. The foreach_in_collection loop iterates through all defined scenarios to apply consistent values.

    foreach_in_collection scen [all_scenarios] {
    current_scenario  $scen
    remove_clock_uncertainty -setup [get_clocks *]
    set_clock_uncertainty 0.255  -setup [get_clocks *]
    set_max_transition 0.28 [get_clocks *] -clock_path
    set_clock_uncertainty -hold 0.050 [all_clocks]
}
    ConstraintValuePurpose
    Setup uncertainty0.255 nsGuard-band deducted from setup slack to account for OCV jitter and on-chip variation on the clock network. Replaced with exact value (old values removed first with remove_clock_uncertainty).
    Hold uncertainty0.050 nsA smaller margin added to hold slack requirement to guard against jitter reducing clock delay on the launch path.
    Max clock transition0.28 nsLimits the clock signal rise/fall time at any sink pin. A slow clock transition widens the flip-flop sampling window and degrades setup timing. Derived from t/6 of the clock period.
    Why remove_clock_uncertainty first? The SDC loaded at design init may already have clock uncertainty values set (e.g., from a synthesis SDC). Removing them first prevents stacking two uncertainty values on the same clock, which would create an over-conservative timing budget.

  • Pre-CTS Design Check (check_clock_trees)

    What it does: Validates the clock tree specification before building the tree. It checks that clock source pins are reachable, clock cells are correctly defined, the NDR rules are valid, and there are no constraint conflicts that would prevent the CTS engine from completing. This is a fast diagnostic step — running it before clock_opt avoids wasting time on a tree-build that will fail mid-way.

    check_clock_trees
    What to look for:
    • ERROR: These must be fixed before running clock_opt. Common causes: no CTS cells found (cell purpose not set correctly), clock source pin not reachable, or NDR rule name mismatch.
    • WARNING: Usually informational — review but often do not need to be fixed.
    • No issues reported: Safe to proceed to clock_opt.

  • Build and Route the Clock Tree (clock_opt -from build_clock -to route_clock)

    What it does: Runs the first phase of the CTS flow — synthesizing the clock tree structure, placing the clock buffer/inverter cells, legalizing them into the placement grid, and routing the clock nets using the NDR rules defined earlier.

    clock_opt -from build_clock -to route_clock
connect_pg_net -automatic

    The clock_opt flow phases covered by this call:

    PhaseWhat Happens
    build_clockSynthesizes the clock tree topology — places CTS_BUFF* cells at optimal locations to achieve the skew and latency targets. With CCD enabled, the tree is shaped to provide useful skew that benefits critical setup paths.
    route_clockRoutes all clock nets using the NDR rules: cts_2w2s on M4–M7 for root/internal nets; cts_1w2s on M3–M6 for sink nets. Clock routing gets priority over signal routing.
    Tile design result: 452 clock repeaters inserted, 25 tree levels, clock wire length 365,662 µm. Runtime for a design of this size is typically 60–120 minutes on a typical server.
    What to watch in the log during clock_opt: Look for the per-iteration skew improvement table printed by ICC2. Both the target skew and the current achieved skew appear after each tree optimization pass. If skew stops improving over several iterations, the CTS engine may be limited by congestion in the clock net routing area.

  • Post-CTS Optimization — Hold Fixing and Setup Recovery (clock_opt -from final_opto -to final_opto)

    What it does: Runs the final_opto phase of clock_opt — the post-CTS data-path timing optimization. This phase operates on the fully built and routed clock tree, using propagated clock delays. It fixes hold violations (by inserting delay cells) and improves remaining setup violations (by gate sizing and buffering).

    Before calling final_opto, update the instance prefix and enable cells for hold fixing:

    set_app_options -name opt.common.user_instance_name_prefix -value "PNR_POSTCTS_OPT"

set_lib_cell_purpose -include hold [get_lib_cells {*/DEL* */BUFFD1BWP* */BUFFD2BWP*}]
set_app_options -name opt.tie_cell.max_fanout -value 5

clock_opt -from final_opto -to final_opto
connect_pg_net -automatic
    • New prefix PNR_POSTCTS_OPT: Cells inserted by final_opto (hold buffers, gate sizing) are named differently from CTS-phase cells, making it easy to distinguish them.
    • Hold cells enabled: DEL* (pure delay cells) and small buffers BUFFD1/BUFFD2 are allowed for hold fixing only. These were excluded during placement to prevent artificial timing improvement before the real clock tree existed.
    • opt.tie_cell.max_fanout 5: Limits the fanout of tie cells that may be inserted to connect floating constant logic signals exposed by optimization.
    Critical check after final_opto: Run report_timing -delay min -scenarios [all_scenarios] mentally or check the log. All hold paths must show positive slack. If any hold violation remains after final_opto, it will become a DRC in the routed design and must be fixed before sign-off.

  • Insert Tie Cells

    What it does: Optimization during CTS may leave some cell inputs floating (not connected to any logic signal). Tie cells are used to connect these inputs to a constant logic-1 or logic-0 without creating long wires that are fragile to IR-drop or crosstalk. They are small, dedicated cells from the standard cell library.

    set tiehi [get_lib_cells */TIEHBWP40P140]
set tielo [get_lib_cells */TIELBWP40P140]
set_app_options -name opt.tie_cell.max_fanout -value 5
add_tie_cells -tie_high_lib_cells $tiehi -tie_low_lib_cells $tielo
    • TIEHBWP40P140 — Tie-high cell, drives a constant logic-1 to connected inputs.
    • TIELBWP40P140 — Tie-low cell, drives a constant logic-0.
    • max_fanout 5 — Each tie cell can drive at most 5 input pins. If more floating inputs are clustered in one area, multiple tie cells will be inserted nearby to keep wire lengths short.

  • Set Propagated Clocks and Compute IO Latency

    What it does: Permanently switches timing analysis from ideal to propagated clock mode, and updates IO path constraints to use the real clock network latency.

    set_propagated_clocks [all_clocks]
compute_clock_latency
    • set_propagated_clocks: Before this command, ICC2 uses zero clock latency for timing calculations (ideal mode). After this command, it uses the actual insertion delays computed from the built clock tree for all timing analysis. This must be called before generating post-CTS timing reports — otherwise all reported slack values are wrong.
    • compute_clock_latency: The SDC file specifies input_delay and output_delay constraints using a clock source latency estimate that was valid at synthesis. Now that the real clock network delay is known, this command recalculates the effective IO path timing so that paths from/to chip ports are analyzed correctly. Skipping this step results in over-optimistic or pessimistic slack on interface paths.

  • Save the CTS Block

    What it does: Saves the post-CTS design state as a new named block inside the NDM. The routing stage will open this block with open_block cts.design.

    save_block -as cts
    Always save before generating reports. Reports run timing analysis which can modify internal state. Saving first ensures you have a clean checkpoint to return to if anything goes wrong during reporting.

  • Generate Post-CTS Reports

    What it does: Runs the complete suite of post-CTS quality reports. These reports are the primary deliverables and the basis for deciding whether to proceed to routing.

    1. Constraint violation report:

    redirect -file ../reports/report_constraint.rpt {report_constraint -all_violators -max_transition -max_capacitance -scenarios [all_scenarios]}
    What to check: Look for max-transition violations on clock nets — these are the most critical. In the tile design, one clock net (CTS_BUFFZCTSNET_233) had a 0.05 ns transition violation at the ssg0p81v125c_rcw corner. A small number (<5) of marginal transition violations are acceptable if they are within 0.1 ns of the limit — they may close after routing adds real parasitics. Larger violations (>0.1 ns over limit) should be investigated by upsizing the driving clock buffer.

    2. Setup timing report (max delay):

    redirect -file ../reports/report_timing.max.rpt {report_timing -delay max -scenarios [all_scenarios] -input_pins -nets -transition_time -capacitance -attributes -physical -derate -report_by group}
    What to check:
    • The worst setup path WNS. Under propagated clocks, setup slack typically improves vs. post-placement because the clock tree introduces latency that shifts the clock edges. The tile design shows propagated clock arrival at 0.42 ns — this is factored into setup calculation.
    • The line clock network delay (propagated) in the path report confirms propagated clock mode is active. If it still says (ideal), set_propagated_clocks was not executed.
    • Paths with WNS worse than -0.5 ns should be analyzed — check if the bottleneck is logic depth, long wire delay, or high fanout.

    3. Hold timing report (min delay):

    redirect -file ../reports/report_timing.min.rpt {report_timing -delay min -scenarios [all_scenarios] -input_pins -nets -transition_time -capacitance -attributes -physical -derate -report_by group}
    What to check: All hold paths must show positive slack. Any negative hold slack after final_opto is a problem — it means hold fixing was not successful and the path will fail in silicon. Look at the path type — if it starts with a latch enable (ICG) rather than a flip-flop, it is an ICG hold path which is often harder to fix. In the tile design, the worst reported hold path was a latch-to-gate-check path starting at a positive slack of 0.03 ns — this is very tight and should be monitored through routing.

    4. Utilization report:

    redirect -tee -file ../reports/report_utilization.rpt {report_utilization}
    What to check: Post-CTS utilization for tile = 57.13%. Utilization increases slightly from post-placement (because CTS inserts 452 new clock buffer cells). The increase should be small (<3%). A large jump suggests the clock tree is over-buffered, which will worsen congestion.

    5. Congestion report:

    redirect -tee -file ../reports/report_congestion.rpt {report_congestion -layers [get_layers -filter "layer_type==interconnect"] -rerun_global_router -nosplit}
    What to check (tile design results):
    LayerGRC Overflow %Assessment
    M21.27%Slightly elevated — M2 is heavily used for local signal routing. Watch in detail routing.
    M30.01%Clean
    M4–M7<0.01%Clean — NDR clock routing occupies upper metal but within budget
    Total0.70%Acceptable — below 1% total overflow is a good placement+CTS result

    Total overflow below 1% after CTS is generally sufficient to proceed to routing. If M2 or M3 overflow exceeds 3–5%, investigate whether the clock tree routing is consuming those layers excessively.

    6. Legality check:

    redirect -file ../reports/check_legality.rpt {check_legality -verbose}
    What to check: Must report 0 violations. The tile design confirms 0 violations across all legality rule categories (overlap, spacing, PG DRC). Any legality error introduced by CTS buffer insertion must be resolved before routing — the detail router cannot complete over illegally placed cells.

    7. Clock QoR reports (CTS-specific):

    redirect -tee -file ../reports/report_clock_qor.summary    {report_clock_qor}
redirect -file ../reports/report_clock_qor.latency         {report_clock_qor -type latency -show_paths}
redirect -file ../reports/report_clock_qor.cell_area       {report_clock_qor -type area}
redirect -file ../reports/report_clock_qor.structure       {report_clock_qor -type structure}
redirect -file ../reports/report_clock_qor.drc_violators   {report_clock_qor -type drc_violators -all}

📊 How to Analyze Clock QoR Reports

The five report_clock_qor sub-reports cover different aspects of the clock tree. Here is how to read each one independently.

1. Summary Report (report_clock_qor)

The summary table is reported per PVT corner. Key columns:

ColumnMeaningTile ResultGood Target
SinksTotal clock sink pins (flip-flops + ICG enable pins)101,827Design-dependent
LevelsDepth of the clock tree in buffer/inverter stages25<30 levels for balanced tree
Clock Repeater CountNumber of CTS buffers/inverters inserted452Typically 0.3–0.5% of sink count
Repeater AreaTotal area of clock tree cells568.64 µm²Should be <2% of total standard cell area
Max LatencyLongest insertion delay from source to any sink0.56–0.82 nsShould be < half clock period
Global SkewMax latency − min latency across all sinks0.38–0.61 ns< 20% of clock period
Trans DRC CountNumber of sinks with transition violation1 (at ssg corner)0 (acceptable if marginal)
Cap DRC CountNumber of sinks with capacitance violation00
The summary is reported per scenario. Check all corners — the worst case is usually the slow corner (ssg, worst-case process) for latency and transition, and the fast corner (ffg, best-case process) for skew.

2. Latency Report (-type latency -show_paths)

Shows the 5 largest and 5 smallest insertion delay paths per clock. Use this to identify outlier sinks with unusually high or low latency:

  • L (Largest latency) sinks: Usually deep array macros (SRAM, register files). In tile, the worst latency sink is inside l2_data_wrap at 0.56 ns. Long clock wires to remote macros are expected.
  • S (Smallest latency) sinks: Usually ICG latch enable pins near the clock source. In tile, the smallest latency is 0.15 ns at ICG cells inside stb_cam.
  • Latency Std Dev: Should be small (0.03 ns in tile). A large std dev means the tree is unbalanced — some branches have significantly different delays.
  • Boundary Skew: Skew between hierarchical boundaries. If using hierarchical CTS, this identifies inter-hierarchy skew issues.

3. Structure Report (-type structure)

Prints the clock tree topology as a hierarchical tree, showing the complete path from the clock port to each sink. Each line shows: level number, cell instance name, reference cell, physical location, and fanout.

(0) clk [in Port] [Location (617.64, 1124.74)] [Net: clk] [Fanout: 1]
 (1) CTS_BUFFctosc_dly_trglat_inst_114554:I->Z [Ref: CKBD12BWP40P140LVT] [Location (619.78, 1119.60)] [Fanout: 1]
  (2) CTS_BUFFctosc_dly_trglat_inst_114553:I->Z [Ref: CKBD4BWP40P140LVT] [Location (613.90, 1119.60)] [Fanout: 2]
   ...
  • The indentation level shows tree depth. Level 0 = clock source port; higher levels = closer to sinks.
  • [ICG] annotations mark integrated clock gating cells — these are not CTS-inserted cells but pre-existing RTL gating logic that the clock tree passes through.
  • Check that all cell references are from the approved LVT clock cell list (CKBD*LVT, CKND*LVT). No SVT or HVT cells should appear in the clock tree.
  • [SINK PIN] marks the final destination — a flip-flop CP or ICG enable pin.

4. Cell Area Report (-type area)

Reports the area breakdown of clock tree cells per clock and corner. Use this to detect over-buffering:

  • Tile result: Repeater area = 568.64 µm², Standard cell area = 5067.47 µm².
  • Repeater area as % of std cell area = 568/5067 ≈ 11% — this is the clock tree overhead. Values above 15–20% suggest excessive buffering.
  • If repeater area is too high, consider raising -target_latency slightly to allow longer clock paths, which reduces the number of buffers needed to equalize latency.

5. DRC Violators Report (-type drc_violators -all)

Lists every clock net/pin that has a transition, capacitance, or fanout DRC violation. The tile design had 0 DRC violations at ffg corners and 1 marginal transition violation (-0.05 ns slack) at ssg corner:

  • Transition DRC: The net CTS_BUFFZCTSNET_233 driving multiple flip-flops had a transition of 0.33 ns vs. the 0.28 ns limit. The fix is to upsize the driving clock buffer to a higher drive strength (e.g., CKBD8 → CKBD12).
  • 0 violations = clean — the clock tree meets all physical constraints.
  • Review the CTS Tags legend at the bottom of the report to understand what each tag (sink, icg, trans, dt_cell, etc.) means when you see them in your own design.

✅ When to Proceed to Routing

CTS is complete and you are ready for routing when ALL of the following are true:

  • check_legality reports 0 violations — CTS buffer insertion did not create any placement conflicts
  • report_timing -delay min shows all hold paths with positive slack — no hold violations remain after final_opto
  • report_clock_qor -type drc_violators shows 0 or minimal marginal violations — clock tree DRCs are resolved
  • report_congestion shows total GRC overflow < 2% — routing overhead from clock NDR wires has not caused severe congestion
  • The block cts is saved inside the NDM (confirmed by open_block cts.design succeeding)
  • Post-CTS setup WNS is better than or equal to post-placement WNS — CCD did not worsen setup timing
  • report_timing -delay max confirms the path shows clock network delay (propagated) — propagated clocks are active

1. After running clock_opt -from build_clock -to route_clock, you check the log and see that the achieved global skew is 0.55 ns — significantly above the 0.1 ns target. check_clock_trees had no errors. What is the most likely explanation?

  • The 0.1 ns target is a hard constraint — if it is not met, CTS has failed and must be re-run with a looser target.
  • The target is an optimization goal, not a hard constraint. With CCD enabled, the tool intentionally introduces useful skew to improve setup timing, so achieved skew will often exceed the balanced-tree target. What matters is whether hold fixing in final_opto cleans up the introduced skew.
  • A global skew of 0.55 ns means the clock tree has serious structural imbalance — all branches on one side of the die have significantly longer wires than the other side.
  • The LVT clock cells are not providing sufficient drive strength — upgrading to SVT cells would reduce latency variance and lower the skew.
Correct! With CCD enabled, ICC2 deliberately skews the clock to relax critical setup paths (useful skew). This means the achieved global skew will routinely exceed the balanced-tree optimization target. The real acceptance criterion is not hitting the skew target — it is whether final_opto successfully fixes all hold violations that result from the introduced skew. If hold timing is clean after final_opto, the design is ready for routing regardless of the global skew value.

2. The check_clock_trees command reports: "Error: No clock references found for CTS. Run derive_clock_cell_references or specify references manually." What is the most likely cause?

  • The open_block command loaded the wrong block — init_design was opened instead of placed.design.
  • The NDR rules were not created before check_clock_trees — clock references depend on routing rules being defined first.
  • The set_lib_cell_purpose -include cts step used a cell name pattern that matched no cells in the loaded NDM libraries — so when derive_clock_cell_references ran, it found zero eligible clock cells.
  • CCD must be disabled during check_clock_trees — the command does not support pre-checking when CCD is enabled.
Correct! derive_clock_cell_references builds its clock cell list from cells that have been marked with set_lib_cell_purpose -include cts. If the glob pattern in that command (e.g., */CK*D4BWP*LVT) does not match any cell in the loaded NDM libraries — due to a typo in the cell name, a wrong lib variant, or a missing NDM — derive_clock_cell_references finds zero eligible cells and the CTS engine has nothing to work with. The fix is to run get_lib_cells *CKBD*LVT inside icc2_shell to see what clock cell names are actually available, then correct the pattern.

3. After clock_opt -from final_opto -to final_opto, report_timing -delay min shows 15 hold violations with slack ranging from -0.02 to -0.08 ns. All violations are on paths between flip-flops that share the same ICG cell output. What is the most targeted fix?

  • Re-run clock_opt -from build_clock -to route_clock with a tighter skew target to rebuild the entire clock tree with better balance.
  • Add more delay cells to the data path — insert DEL* cells manually on the affected nets to increase data path delay above the hold limit.
  • The ICG cell is creating a skew differential between its output clock (gated) and the main clock. Check whether the ICG is correctly modeled — if the main_gate output is treated as a generated clock, add a skew group pairing it with its source clock so ICC2 can balance them properly during the next final_opto.
  • The 15 violations are small (under 0.1 ns) — they are acceptable and will close naturally when routing adds real wire parasitics that increase data path delay.
Correct! When multiple hold violations share the same ICG output as the clock source, the common root cause is a skew mismatch between the ICG-gated clock (the capture clock) and the main clock (the launch clock). This happens when ICC2 builds separate sub-trees for the main clock and the ICG output without enforcing a relationship between their latencies. Creating a skew group that pairs the ICG output clock with the main clock forces the CTS engine to balance their latencies, eliminating the skew differential that causes hold violations on the affected paths.

4. You run report_timing -delay max after CTS and notice the path report header shows clock network delay (ideal) instead of (propagated). Setup slack looks unrealistically optimistic. What is the cause and fix?

  • The NDR rules were applied incorrectly — wire resistance is being underestimated because the clock nets were not routed with double-width tracks.
  • The setup corner scenario was deactivated during final_opto and needs to be re-activated before running report_timing.
  • set_propagated_clocks [all_clocks] was not executed before generating the timing report — ICC2 is still using ideal zero-latency clock propagation, producing unrealistic slack values that do not reflect the actual clock tree insertion delay.
  • compute_clock_latency must be run before set_propagated_clocks — running them out of order causes ICC2 to revert to ideal clock mode.
Correct! The (ideal) label in the path report header means ICC2 is computing clock arrival time using zero latency — the clock tree delays built by CTS are being ignored. This produces optimistic setup slack because the long clock latency (0.42–0.82 ns in the tile design) would normally be subtracted from the data path budget. The fix is to run set_propagated_clocks [all_clocks], which switches ICC2 to use the actual clock tree insertion delays. All timing reports generated after this command will show the correct propagated slack values.
