Problem Statement

GUIDED

You will perform the Floorplanning stage for the Tile in Cadence Innovus. Starting from the initialized database (init_design.db), you will read a pre-built floorplan DEF (without physical cells), assign I/O pins on the top edge, configure and insert endcap and well-tap physical cells, connect global power nets, execute the power plan script to create a VDD/VSS mesh on M4–M9, run power grid integrity checks, and save the floorplan database for the placement stage.

Key input: floorplan.def — a DEF file that captures the die boundary, core area, standard cell row definitions, and macro placement, but intentionally omits physical-only cells (endcaps, well-taps, fillers). These are added by the floorplan script itself so you have full control over cell type and placement rules.

📄 Floorplanning — Step-by-Step Command Explanation

  • Navigate to the Testcase and Launch Innovus

    cd ~/pd/labs/PNR-CDN-FP/TC-PNR-CDN-FP-GD-001
make all

    From the Innovus prompt, source the floorplan script:

    source ../scripts/floorplan.tcl

  • Load the Initialized Database (read_db)

    What it does: Reads the Innovus database saved at the end of the init_design stage. This restores the full design state — netlist, MMMC configuration, cell instances, and power connectivity — exactly as it was when write_db was called.

    read_db ../inputs/init_design.db
    What to check: Design name Tile appears in the Innovus display. Cell count, net count, and SRAM macro instances should match what was reported after init_design in the previous stage.

  • Read the Floorplan DEF (read_def)

    What it does: Reads the DEF (Design Exchange Format) file that defines the physical die dimensions, core area, standard cell row definitions, and pre-placed macro positions. The command read_def is used here instead of the older source command because read_def invokes Innovus's native DEF reader with full parsing, DRC awareness, and error reporting.

    The filename floorplan.def explicitly signals that this DEF contains only logical and macro placement data — physical-only cells (endcaps, well-taps, fillers) have been stripped out. This is the correct starting point because:

    • Endcap and well-tap cells are re-inserted by this script with updated cell names and parameters.
    • Importing pre-existing physical cells from an older DEF could conflict with the current PDK cell names or row definitions.
    • Starting clean avoids double-insertion or mismatched cell orientations.
    read_def ../inputs/floorplan.def
    What to check: Innovus Floorplan view updates to show the die boundary, core area, and placed SRAM macros. Standard cell rows are visible but empty of physical cells. Any macro overlap or out-of-bounds placement will be reported as an error during read_def.

  • Edit Pin Assignment (edit_pin)

    What it does: Places and fixes I/O ports on the die boundary. The flags used here:

    Flag Description
    -pin_depth 0.6Sets the pin depth (how far the pin extends into the die boundary).
    -fix_overlap 1Automatically resolves any pin overlap violations.
    -pattern fill_layerDistributes pins uniformly along the specified side using a fill pattern.
    -spread_direction clockwisePins are spread in clockwise order from the start coordinate.
    -side TopPlaces pins on the Top edge of the die.
    -layer {4 6}Pins are placed on metal layers 4 and 6.
     
    edit_pin -pin_depth 0.6 -fix_overlap 1 -pattern fill_layer -spread_direction clockwise -unit track -spacing 2 -side Top -start 425.77650 1178.71650 -end 765.04800 1178.70450 -layer {4 6} -pin [get_db [get_ports *] .name]
    check_pin_assignment > ../reports/check_pin_assignment.rpt
    What to check in check_pin_assignment.rpt: No overlapping pins, no pins outside the die boundary. All ports listed as FIXED.

  • Set Legalization and Filler Parameters

    These two set_db commands configure global rules that govern how Innovus legalizes instances and inserts filler cells later in the flow:

    set_db place_detail_legalization_inst_gap 2
set_db add_fillers_no_single_site_gap true
    What these do:
    • place_detail_legalization_inst_gap 2 — reserves a 2-site (2 × site width) gap between adjacent cell instances during detailed legalization, preventing minimum-spacing DRC violations on abutting standard cells.
    • add_fillers_no_single_site_gap true — prevents 1-site-wide gaps from remaining when filler cells are inserted later. Single-site gaps are problematic because many PDK filler cells do not include a 1x variant, leaving unresolvable gaps that cause DRC failures at chip finish.

  • Add Endcap Cells (add_endcaps)

    What it does: Inserts boundary cells at the left and right ends of every standard cell row. Endcap cells serve two purposes:

    • Well Continuity DRC: N-well and P-well regions cannot terminate in mid-air — the foundry requires a defined well-boundary cell at every row edge to properly close the well diffusion layer.
    • Well Proximity Effect (WPE) suppression: In 28nm and smaller nodes, ions implanted during N-well or P-well formation scatter laterally at the well boundary, shifting the threshold voltage (Vt) of transistors within ~1–2 µm of the edge. This is the Well Proximity Effect. Endcap cells are designed to absorb this scatter zone, keeping standard logic cells at their characterized Vt and preventing timing divergence between characterized models and silicon.

    Why the cell names appear reversed: BOUNDARY_RIGHTBWP40P140 is placed at the left edge of a row, and BOUNDARY_LEFTBWP40P140 at the right edge. This is correct — the naming reflects the physical orientation of the cell's well-boundary structure relative to the row. The RIGHT-boundary cell has its N/P-well termination on its right side, so it belongs at the left end of a row where it terminates the row's first cell. The LEFT-boundary cell mirrors this logic at the row's right end.

    set_db add_endcaps_left_edge BOUNDARY_RIGHTBWP40P140
set_db add_endcaps_right_edge BOUNDARY_LEFTBWP40P140

add_endcaps

check_endcaps > ../reports/check_endcaps.rpt
    What to check in check_endcaps.rpt: All standard cell rows should report endcaps at both left and right boundaries. Any row with missing endcaps is flagged as a violation — rows adjacent to macro hard-boundaries require special attention since read_def already split them at the macro edge.

  • Add Well-Tap Cells (add_well_taps)

    Why well-taps are required — Latch-up Physics: Standard CMOS cells contain an inherent four-layer p-n-p-n structure: P+ source → N-well → P-substrate → N+ source. This forms a parasitic silicon-controlled rectifier (SCR). Normally this SCR is off, but if the well or substrate potential is disturbed by a transient current (ESD event, power-up noise, or a large simultaneous-switching output), the SCR can turn on and create a low-impedance VDD-to-VSS short-circuit — latch-up. Once triggered, latch-up sustains itself until power is removed, and can permanently damage the chip.

    Well-tap cells provide direct ohmic contacts from metal to the N-well (tied to VDD) and to the P-substrate (tied to VSS). These low-resistance connections clamp the well and substrate at their supply potentials, preventing the voltage excursion that triggers the SCR. TSMC's 28nm design rules require a well-tap contact within 30 µm of any active transistor — exceeding this distance means a transistor's well is too resistive to be reliably clamped.

    Why checkerboard pattern: A simple row-by-row pattern places all well-taps in the same X-columns, leaving diagonal gaps between them. The checkerboard pattern staggers even and odd rows by half the cell interval, ensuring that every point in the 2D cell array is within 30 µm of a well-tap in both the horizontal and diagonal directions. This provides uniform latch-up immunity across the full core.

    set_db add_well_taps_cell TAPCELLBWP40P140

add_well_taps -cell_interval 30 -checker_board -prefix welltap

check_well_taps -max_distance 30 > ../reports/check_welltaps.rpt
    What to check in check_welltaps.rpt: No well-tap violations at max distance 30 µm. Any flagged violation means a region of rows has no well contact within the required distance. Dense macro regions with narrow routing channels require particular attention as the available row sites for well-taps are limited.

  • Connect Global Power Nets (Pre-Power-Plan)

    Before creating power stripes, connect global VDD and VSS to all cell PG pins. This ensures the power network connectivity model is current before the power plan script adds new routing objects.

    connect_global_net VDD -type pg_pin -pin_base_name VDD*
connect_global_net VSS -type pg_pin -pin_base_name VSS

  • Source the Power Plan Script (source power_plan.tcl)

    What it does: Executes the power plan script that creates the complete VDD/VSS multi-layer distribution mesh. The power plan is provided as an input (not generated from scratch here) because the stripe widths, spacings, and layer assignments have been pre-tuned for the Tile die dimensions and current requirements.

    Routing blockages over macros: Before creating lower-metal stripes (M4–M5), the power plan script places routing blockages on those layers over every hard-macro instance. This is necessary because macro power pins are on M4, and an M4 stripe running over the macro would directly short to the macro's internal M4 pins. The correct approach is to:

    1. Block M4/M5 routing over macros before creating stripes
    2. Create M4–M9 stripes in the standard cell area only
    3. Delete the temporary blockages after stripe creation
    4. Run update_power_vias to insert stacked vias explicitly at macro pin locations, connecting the macro supply pins upward to M5–M6 stripes

    The script builds power stripes from top-down M9 to M4:

    Layer Direction Width Purpose
    M9Horizontal3.0 µmTop-level power distribution across the full die
    M8Vertical3.0 µmOrthogonal main power grid layer
    M7Horizontal0.5 µmIntermediate distribution
    M6Vertical0.5 µmIntermediate distribution
    M5Horizontal0.15 µmLower-level distribution; blocked over macros before stripe creation
    M4Vertical0.15 µmConnects to cell row VDD/VSS rails; stacked vias to macro M4 pins via update_power_vias
     
    source ../inputs/power_plan.tcl

  • Reconnect Global Nets (Post-Power-Plan)

    After the power plan adds new routing geometries, run connect_global_net again so all new stripe and via objects are properly mapped to VDD and VSS in the connectivity database.

    connect_global_net VDD -type pg_pin -pin_base_name VDD*
connect_global_net VSS -type pg_pin -pin_base_name VSS

  • Power Grid Quality Checks

    Run all four power grid checks to validate the floorplan before proceeding to placement:

    check_drc > ../reports/check_drc.rpt
    What to check: Zero DRC violations on power stripes and endcap cells. Spacing violations on M4–M9 indicate stripe width or spacing parameters need adjustment. 
    check_connectivity -nets {VDD VSS} -ignore_dangling_wires > ../reports/check_connectivity.rpt
    What to check: VDD and VSS networks are fully connected — no isolated power islands. "Open nets" errors indicate missing via connections between stripe layers. 
    check_power_vias > ../reports/check_power_vias.rpt
    What to check: Stacked vias at stripe intersections are present and correctly formed. Missing vias reduce current capacity and increase IR drop. 
    check_pg_shorts > ../reports/check_pg_shorts.rpt
    What to check: Zero VDD-to-VSS short circuits. A PG short is a critical error — it means a power stripe and ground stripe are connected, which would short-circuit the supply.

  • Save the Floorplan Database (write_db -sdc)

    Save the completed floorplan state as the checkpoint for the placement stage.

    write_db -sdc ../outputs/floorplan.db
    The placement stage will read this as read_db ../inputs/floorplan.db.

📚 Knowledge Assessment Quiz

1. Core utilization is a key floorplanning metric. Which formula correctly calculates it?

  • (Total standard cell area + I/O cell area) / Die area × 100%
  • Total standard cell area / Die area × 100%
  • (Standard cell area + Macro area) / Core area × 100%
  • Standard cell area / (Core area − Macro area) × 100%
Correct! Core utilization measures how much of the core area is occupied by placed standard cells and macros together: (Standard cell area + Macro area) / Core area × 100%. This differs from Standard Cell Utilization, which divides only the standard cell area by the placeable area excluding macros. Die Utilization is a third metric that includes I/O cells and divides by the total die area. Understanding all three is essential for accurate floorplan sizing.

2. Why do floorplanning guidelines recommend starting with approximately 70% standard cell utilization rather than 100%?

  • 100% utilization would violate the foundry's maximum cell density design rule
  • Placement tools cannot converge when utilization exceeds 80%, so a safety margin of 30% is always required
  • Space must be reserved for clock tree buffers added during CTS, hold-fixing buffers added post-CTS, cell upsizing during optimization, routing detours, and post-route ECO changes — a design at 100% has no room for any of these
  • Lower utilization improves manufacturing yield because widely spaced cells are easier to etch accurately
Correct! Synthesis produces only setup-optimized netlist cells. During physical design, additional area is consumed by: clock buffers/inverters inserted during CTS, hold buffers inserted after CTS (when actual clock latencies are known), driver upsizing for timing closure, routing detours around congested areas, and ECO buffer insertions during sign-off. Starting at 70% leaves ~30% of the core as whitespace to absorb all these incremental area additions without causing routing or placement failures.

3. Endcap cells are inserted at the ends of every standard cell row. What is their primary purpose?

  • They provide local decoupling capacitance to reduce power supply noise at row edges
  • They act as physical barriers that prevent standard cells from being placed outside the core area
  • They mitigate the Well Proximity Effect (WPE) — ion implantation scatters at well boundaries, shifting transistor threshold voltage. Endcap cells place a designed well-termination structure at each row edge, keeping logic cells away from the high-scatter region
  • They complete the VDD and VSS power rails at row boundaries so that routing can connect to the power grid
Correct! The Well Proximity Effect (WPE) occurs because during well implantation, dopant ions scatter laterally near the well edge. Transistors within ~1–2 µm of a well boundary experience a threshold voltage (Vt) shift compared to their characterized values, causing unexpected timing variations. Endcap cells contain specifically designed well-boundary diffusion structures that absorb this scatter zone. They have no logic function — their purpose is purely structural: absorbing WPE at every row edge to ensure logic cells perform as characterized.

4. Well-tap cells are inserted throughout the core area at regular intervals. What catastrophic circuit failure do they prevent?

  • They prevent electromigration by providing additional current return paths near standard cells
  • They prevent latch-up — CMOS layouts contain a parasitic P-N-P-N (SCR) structure formed by the N-well, P-substrate, and source/drain diffusions. If triggered by a voltage spike or ESD event, this SCR turns on and creates a self-sustaining low-resistance path between VDD and VSS that can destroy the chip
  • They prevent antenna effect during routing by providing discharge paths near every transistor gate
  • They prevent threshold voltage variation caused by proximity to the die edge where mechanical stress is highest
Correct! In CMOS technology, the P-substrate, N-well, and source/drain diffusions form an unintentional four-layer P-N-P-N structure equivalent to a Silicon Controlled Rectifier (SCR). Voltage spikes, ESD events, or power supply noise can forward-bias this structure, triggering a positive feedback loop where two parasitic BJTs sustain each other's conduction. Well-tap cells provide direct low-resistance contacts from the N-well to VDD and from the P-substrate to VSS, clamping the well/substrate potentials and preventing the BJT base-emitter junctions from ever forward-biasing enough to trigger latch-up.
