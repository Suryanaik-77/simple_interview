Problem Statement

GUIDED

You will run the complete merged route and post-route flow for the tile processor core design. Starting from the cts.design block saved at the end of post-CTS, you will configure signal integrity analysis, enable timing and crosstalk-driven routing at every stage, configure antenna violation fixing via diode insertion and layer hopping, execute route_auto, insert redundant vias, then switch into post-route mode — tightening clock uncertainty from 0.255 ns to 0.204 ns and running route_opt to recover any remaining setup and hold violations. The full route and post-route report suite is generated after each major step.

📄 Route + Post-Route — Step-by-Step Command Explanation

Follow the walkthrough below. Write each command into scripts/route.tcl as you go, then source the script from inside icc2_shell.

  • Step 1 — Navigate to TC-PNR-SNPS-RT-GD-001 and Launch ICC2

    You have already set up the lab directory structure using the provided setup guidelines. The required input files are now available in the testcase directory. With the lab environment ready, proceed with the following steps.

    Navigate to the testcase directory and launch the flow using the Makefile:

    cd ~/pd/labs/PNR-SNPS-RT/TC-PNR-SNPS-RT-GD-001
make all

    This starts an interactive icc2_shell session. Open scripts/route.tcl in a separate editor window:

    sh gvim scripts/route.tcl &

    Write each command into the script as you follow the steps below. Once all commands are in place, source the script from inside icc2_shell:

    source scripts/route.tcl

  • Step 2 — Open the NDM Library and Post-CTS Block

    What it does: Opens the design library and loads the cts.design block — the named checkpoint saved at the end of the post-CTS stage. This is the starting point for routing; it contains the placed design with a fully synthesized and balanced clock tree.

    open_lib ../inputs/tile.ndm
open_block cts.design
    Why cts.design and not cts_build.design? In the CTS flow, two blocks are typically saved: cts_build.design (after CTS tree construction, before post-CTS optimization) and cts.design (after post-CTS optimization and clock uncertainty application). Routing must start from the fully optimized post-CTS checkpoint — cts.design.

  • Step 3 — Activate All Timing Scenarios

    What it does: Ensures every timing scenario (setup and hold, all PVT corners) is active for routing. ICC2's timing-driven router uses all active scenarios simultaneously to make wire placement decisions that satisfy both setup and hold constraints across all corners.

    set_scenario_status -active true [all_scenarios]

  • Step 4 — Set Instance Name Prefix for Route Stage

    What it does: Any new cell instances created by the router (such as antenna diodes or repeaters inserted during routing) will have this prefix prepended to their names. This makes it easy to identify which cells were added during the routing stage versus earlier stages.

    set_app_options -name opt.common.user_instance_name_prefix -value "PNR_ROUTE_"

  • Step 5 — Enable Signal Integrity Analysis

    What it does: Activates ICC2's signal integrity engine. With this option enabled, the timing analysis engine computes coupling-aware delays — crosstalk delta delay from aggressor switching — in addition to the base cell and wire delays. The router uses this information during routing decisions.

    set_app_options -name time.si_enable_analysis -value true
    Impact on routing: When SI analysis is enabled, the router identifies nets with high coupling sensitivity and applies SI-driven shielding and spacing. Without this option, coupling effects are ignored during wire placement, and SI violations discovered post-route are much harder to fix.

  • Step 6 — Configure Timing and Crosstalk-Driven Routing Options

    What it does: These six app options configure how each routing stage handles timing and crosstalk objectives. The table below explains the function of each setting:

    App Option Routing Stage Effect When True
    route.global.crosstalk_driven Global routing Separates coupled aggressor-victim pairs into different GCell routing regions
    route.global.timing_driven Global routing Routes critical timing paths with shorter, lower-resistance GCell paths
    route.track.crosstalk_driven Track assignment Assigns coupled nets to different tracks or layers to increase physical separation
    route.track.timing_driven Track assignment Assigns critical path nets to preferred (lower-resistance) tracks first
    route.detail.timing_driven Detail routing Minimizes wire length and via count on critical paths during exact wire placement 
    set_app_options -name route.global.crosstalk_driven -value true
set_app_options -name route.global.timing_driven    -value true
set_app_options -name route.track.crosstalk_driven  -value true
set_app_options -name route.track.timing_driven     -value true
set_app_options -name route.detail.timing_driven    -value true

  • Step 7 — Configure Antenna Violation Fixes

    What it does: These options configure how the detail router detects and fixes antenna violations during the routing process itself, rather than as a post-route correction step.

    set_app_options -name route.detail.hop_layers_to_fix_antenna    -value true
set_app_options -name route.detail.insert_diodes_during_routing -value true
set_app_options -name route.detail.diode_libcell_names          -value {ANTENNABWP35P140}
source antenna_rules.tcl
    hop_layers_to_fix_antenna true: When a long wire segment accumulates an antenna ratio above the foundry limit, the router attempts to break the antenna by jumping the wire up to a higher metal layer (via insertion). Higher layers have a shorter effective antenna history during the etch sequence, so the total antenna ratio is reset.
    insert_diodes_during_routing true + diode_libcell_names {ANTENNABWP35P140}: If a layer hop is not possible due to routing congestion, the router inserts an ANTENNABWP35P140 diode cell at the gate input. The diode shunts charge to substrate during the etch process without affecting the logic function. The cell name must exactly match a library cell in the NDM — verify this against your PDK's standard cell list before running.
    antenna_rules.tcl: This file defines the foundry-specific antenna ratio rules for each metal layer and via type. ICC2 reads these rules and uses them during routing to determine when a wire segment has exceeded the limit. The file is provided in the PDK and must be sourced before route_auto.

  • Step 8 — Run Routing, Add Redundant Vias, and Save

    route_auto: Executes global routing, track assignment, and detail routing in a single coordinated command. The router uses all the SI and timing settings configured in Steps 5–7. Expect this command to take several minutes on the tile design.

    add_redundant_vias: Post-processes the completed routing and upgrades eligible single-cut vias to multi-cut versions. This improves manufacturing yield and electromigration lifetime with no timing penalty.

    connect_pg_net -automatic: Reconnects any power and ground nets that may have lost connectivity after routing (for example, newly inserted diode cells need their VDD/VSS pins connected).

    route_auto
add_redundant_vias
connect_pg_net -automatic
save_block -as route
    Checkpoint naming: Saving as route creates a permanent snapshot of the design immediately after routing completes, before any post-route optimization. If route_opt introduces unexpected problems, you can always reopen the route block to restart post-route from a clean state.

  • Step 9 — Generate Route-Stage Reports

    Always generate reports immediately after saving the route block, before moving to post-route optimization. These reports establish the baseline quality of the raw routed design.

    redirect -file ../reports/route.report_constraint.rpt  {report_constraint -all_violators -max_transition -max_capacitance -scenarios [all_scenarios]}
redirect -file ../reports/route.report_timing.max.rpt  {report_timing -delay max -scenarios [all_scenarios] -input_pins -nets -transition_time -capacitance -attributes -physical -derate -report_by group}
redirect -tee -file ../reports/route.report_utilization.rpt {report_utilization}
redirect -tee -file ../reports/route.report_clock_qor.summary {report_clock_qor}
redirect -file ../reports/route.check_routes.rpt {check_routes}
redirect -file ../reports/route.check_lvs.rpt    {check_lvs -max_errors 0}
    check_routes — what to look for:
    • Spacing violations: Two wires on the same layer are closer together than the minimum spacing rule for that layer. Usually caused by congested regions.
    • Width violations: A wire segment is narrower than the minimum width rule. Can occur on high-resistance layers under tight routing constraints.
    • Antenna violations: Wire segments with an antenna ratio exceeding the foundry limit. Should be near zero if diode insertion and hop_layers options are correctly configured.
    • DRC errors target: 0 — any remaining DRC errors must be fixed before tape-out.
    check_lvs — what to look for:
    • Shorts: Two nets that should be electrically separate are connected by a wire or via. This is a critical error that will cause functional failure.
    • Opens: A net that should be connected has a break in its routing path. The receiving gate will float and produce random logic values.
    • LVS target: 0 shorts, 0 opens — any LVS error must be resolved before proceeding to chip finish.

  • Step 10 — Switch to Post-Route Stage: Set Instance Prefix

    The post-route section of the script begins here. Set a new instance name prefix so that any cells inserted by route_opt are distinguishable from cells inserted during the route stage.

    set_app_options -name opt.common.user_instance_name_prefix -value "PNR_ROPT"

  • Step 11 — Configure Library Cell Purposes for Post-Route Optimization

    What it does: These three commands control which library cells route_opt is allowed to use when resizing or inserting cells to fix timing violations.

    set_lib_cell_purpose -include optimization [get_lib_cells {*/*LVT}]
set_lib_cell_purpose -exclude optimization [get_lib_cells {*/CK* */*D24* */*D32* */*D20* */*D18*}]
set_lib_cell_purpose -include hold [get_lib_cells {*/DEL* */BUFFD1BWP* */BUFFD2BWP*}]
    Why enable LVT cells post-route? During pre-route optimization, LVT (low-threshold voltage) cells are typically excluded because their higher leakage current increases power consumption. Post-route, the leakage penalty is accepted in exchange for timing closure capability — LVT cells have faster switching speeds and can fix setup violations that SVT and HVT cells cannot resolve.
    Why exclude CK* and large drive strength cells? Clock cells (CK*) are managed by the clock tree and should not be touched by the combinational optimizer. Very large drive strength cells (D18, D20, D24, D32) have huge gate capacitance and consume excessive area — they are excluded to prevent the optimizer from inserting them in places where a more targeted fix would be better.
    Hold-fixing cells (DEL*, BUFFD1, BUFFD2): These are explicitly enabled for hold fixing. Delay cells (DEL*) add a controlled amount of propagation delay to a path without affecting its logical function, directly increasing hold slack. Small buffer cells (BUFFD1, BUFFD2) are used similarly. Larger buffers are excluded from hold fixing because they also significantly affect setup timing.

  • Step 12 — Update IO Latencies

    What it does: After routing, the actual wire delays of the clock tree are extracted from the routed geometry. compute_clock_latency recalculates the clock insertion delay and skew using these real extracted parasitics, updating the timing engine with accurate clock arrival times at each flip-flop.

    compute_clock_latency
    This command must be run before applying updated clock uncertainty values. The new latency numbers replace the estimated values used during CTS and give the timer a precise picture of when each clock edge arrives across the entire design.

  • Step 13 — Tighten Setup Clock Uncertainty for Post-Route

    What it does: Removes the CTS-era clock uncertainty from every clock in every scenario and replaces it with the tighter post-route values. The setup uncertainty drops from 0.255 ns (applied during CTS) to 0.204 ns. The hold uncertainty is set to 0.050 ns.

    foreach_in_collection scen [all_scenarios] {
    current_scenario $scen
    remove_clock_uncertainty [get_clocks *]
    set_clock_uncertainty -setup 0.204 [all_clocks]
    set_clock_uncertainty -hold  0.050 [all_clocks]
}
    Why 0.204 ns post-route? Clock uncertainty is a timing guard-band that accounts for clock skew, jitter, and process variation that has not yet been quantified at each stage. At CTS time, the clock tree has just been built and post-CTS routing parasitics are unknown — the 0.255 ns value includes a buffer for this uncertainty. After routing, the actual clock tree wire RC is extracted and the real skew is measured. The 0.204 ns post-route value reflects this more accurate picture. Removing 51 ps from the guard-band gives route_opt 51 ps more timing margin on every setup path — a significant benefit for a design at the margin of closure.
    Why iterate over all scenarios? Each scenario has its own clock uncertainty constraints. Using foreach_in_collection ensures that both setup and hold scenarios receive the updated uncertainty values. Omitting any scenario would leave its clock uncertainty at the CTS value, causing inconsistent timing results.

  • Step 14 — Run Post-Route Optimization (route_opt)

    What it does: route_opt performs ECO-style optimization on the routed design — resizing cells, inserting delay buffers, rerouting local congestion, and fixing remaining DRC and timing violations. It operates on the actual routed parasitics rather than estimates, making its decisions far more accurate than pre-route optimization.

    route_opt
connect_pg_net -automatic
save_block -as postroute
    route_opt can be run multiple times: If significant violations remain after the first run, a second call to route_opt often achieves further improvement because the timing numbers converge as each pass fixes violations and the parasitic extraction updates. This is standard practice on difficult timing closure designs.

  • Step 15 — Generate Post-Route Reports

    After route_opt and saving the postroute block, generate the complete post-route report suite. These are the reports used for timing sign-off review.

    redirect -file ../reports/postroute.report_constraint.rpt  {report_constraint -all_violators -max_transition -max_capacitance -scenarios [all_scenarios]}
redirect -file ../reports/postroute.report_timing.max.rpt  {report_timing -delay max -scenarios [all_scenarios] -input_pins -nets -transition_time -capacitance -attributes -physical -derate -report_by group}
redirect -file ../reports/postroute.report_timing.min.rpt  {report_timing -delay min -scenarios [all_scenarios] -input_pins -nets -transition_time -capacitance -attributes -physical -derate -report_by group}
redirect -file ../reports/postroute.check_legality.rpt     {check_legality -verbose}
redirect -tee -file ../reports/postroute.report_clock_qor.summary {report_clock_qor}
redirect -file ../reports/postroute.check_routes.rpt {check_routes}
redirect -file ../reports/postroute.check_lvs.rpt    {check_lvs -max_errors 0}
    report_timing.min.rpt (hold): Post-route is the first time hold timing is checked with real parasitics. Minimum delay (hold) violations must be fixed before tape-out — the hold fixing buffers enabled in Step 11 are the primary mechanism. Compare the min-delay report against the max-delay (setup) report to understand the overall timing health of the design.
    check_legality -verbose: Verifies that all cell placements remain legal after route_opt moved or inserted cells. Illegal placements (cells overlapping, cells outside floorplan boundaries, cells on non-site rows) must be resolved before chip finish.

✅ Success Criteria

The routing and post-route flow is complete and correct when ALL of the following are true:

  • check_routes reports 0 DRC errors after route_auto — no spacing, width, or antenna violations remain
  • check_lvs reports 0 shorts and 0 opens after routing
  • The route block is saved inside ../inputs/tile.ndm
  • The postroute block is saved inside ../inputs/tile.ndm
  • Post-route WNS (worst negative slack) is improved relative to the route-stage WNS — confirming that route_opt recovered timing margin
  • check_routes on the postroute block reports 0 DRC errors — route_opt ECO routing did not introduce new violations
  • check_lvs on the postroute block reports 0 shorts and 0 opens
  • check_legality -verbose reports 0 illegal placements after route_opt
  • All post-route reports are generated in ../reports/

📚 Knowledge Assessment Quiz

1. After running route_auto, check_routes reports 47 antenna violations even though route.detail.insert_diodes_during_routing is set to true. What is the most likely cause?

  • The antenna violations are on clock nets — clock nets are excluded from diode insertion automatically by ICC2 to protect the clock tree.
  • route_auto does not perform antenna fixing; you must run route_detail -fix_antenna as a separate post-processing step.
  • The diode cell name in route.detail.diode_libcell_names does not match any cell in the loaded NDM, so the router could not insert diodes and fell back to layer hopping — but hopping was also insufficient for some nets.
  • The antenna_rules.tcl was sourced before the routing options were set; it must be sourced after all set_app_options calls to take effect.
Correct! If the diode library cell name in route.detail.diode_libcell_names does not exactly match a cell in the loaded NDM reference libraries, ICC2 cannot insert diodes. It silently falls back to layer hopping only. For nets where hopping is not geometrically feasible (due to congestion or layer availability), no fix is applied and the antenna violation remains. Always verify the exact cell name against the PDK standard cell list before routing.

2. You run route_opt and find that WNS improved by only 0.008 ns — essentially no change. What should you check first before concluding that timing closure is impossible?

  • Check whether add_redundant_vias was run — multi-cut vias lower resistance and may recover the needed timing margin directly.
  • Check whether the clock uncertainty was updated before route_opt. If the uncertainty is still 0.255 ns from CTS rather than 0.204 ns post-route, the optimizer is working with 51 ps less margin than it should have — this alone can prevent convergence on many paths.
  • Check whether SI analysis was enabled before routing. If SI was disabled, route_opt cannot account for crosstalk delta delay and its fixes may be targeting wrong paths.
  • Check whether the postroute block was saved before running route_opt. ICC2 requires a prior save_block before running any optimization command.
Correct! If the clock uncertainty was not reduced from 0.255 ns (CTS) to 0.204 ns before route_opt, the optimizer sees a required setup slack that is 51 ps tighter than the post-route reality. Many paths that are actually passing under the correct uncertainty appear as violations under the old value, and the optimizer cannot find enough moves to fix them all. Always apply the tightened uncertainty before route_opt.

3. Why is connect_pg_net -automatic called after both route_auto and after route_opt, rather than just once at the very end?

  • Both route_auto (via diode insertion) and route_opt (via ECO cell insertion) can add new cell instances whose VDD and VSS pins are not yet connected to the power grid — each call to connect_pg_net -automatic ensures newly inserted cells are properly powered before subsequent steps analyze or optimize them.
  • ICC2 automatically disconnects all power nets after route_auto to allow route_opt to reroute them with lower-resistance paths — connect_pg_net must reconnect them each time.
  • Running connect_pg_net twice is a requirement of the Synopsys flow — a single call is not sufficient to process all net types in one pass.
  • The first call handles standard cell VDD/VSS connections; the second call specifically handles macro ring connections that are resolved only after route_opt completes.
Correct! Every time new cell instances are added — whether by the router inserting diode cells during route_auto or by the optimizer inserting delay buffers or resized cells during route_opt — their power pins need to be connected to the power grid. Calling connect_pg_net -automatic after each major step ensures no cell is left with floating power pins, which would cause LVS errors and incorrect power analysis.

4. The post-route report_timing -delay min (hold) report shows WHS (worst hold slack) = -0.032 ns in the hold corner scenario. What is the correct fix and which cells are configured for this purpose?

  • Increase the clock frequency — a faster clock reduces the hold window and eliminates hold violations automatically.
  • Replace the violating flip-flops with LVT versions — LVT flip-flops have longer hold times and naturally absorb the 32 ps violation.
  • Insert delay cells (DEL*) or small buffers (BUFFD1BWP*, BUFFD2BWP*) on the data path of the violating timing arc to add propagation delay and increase hold slack — these are enabled via set_lib_cell_purpose -include hold in Step 11.
  • Reduce the hold uncertainty from 0.050 ns to 0.030 ns — the 20 ps reduction converts the -0.032 ns violation into a passing path without any physical change.
Correct! Hold violations mean the data arrives at the flip-flop capturing edge too quickly — it changes before the setup window of the previous clock cycle has safely closed. The fix is to slow down the data path by inserting delay cells or small buffers. In Step 11, we explicitly enabled DEL*, BUFFD1BWP*, and BUFFD2BWP* cells for hold fixing using set_lib_cell_purpose -include hold. route_opt uses these cells to insert the exact amount of delay needed to bring hold slack to zero or better.
