Problem Statement

GUIDED

You will perform timing-driven global placement on the tile processor core design using ICC2. The floorplan block saved in the PNR-SNPS-FP stage is your starting point. In this exercise, every command is explained in detail — what it does, why it matters, and what you should verify in the tool output before proceeding to the next step.

By the end of this testcase you will have:

  • Opened the floorplan NDM block and configured setup-only scenario analysis
  • Inserted IO buffers and anchored them near ports using magnet_placement
  • Applied lib-cell dont-use rules to exclude clock, high-drive, delay, and LVT cells
  • Set congestion effort, density limits, fanout constraints, and disabled CCD
  • Executed place_opt and generated a full suite of placement quality reports

📄 Placement — Step-by-Step Command Explanation

Follow the steps below exactly as written. Navigate to the testcase directory, launch ICC2, and run the placement script.

  • Navigate to TC-PNR-SNPS-PL-GD-001 and Launch ICC2

    You have already set up the lab directory structure using the provided setup guidelines. The required input files are now available in the testcase directory. With the lab environment ready, proceed with the following steps.

    Navigate to the testcase directory and start the ICC2 session using the Makefile:

    cd ~/pd/labs/PNR-SNPS-PL/TC-PNR-SNPS-PL-GD-001
make all

    This starts an interactive icc2_shell session. Open the placement script in a separate editor window:

    sh gvim ../scripts/place.tcl &

    Write each command into the script as you follow the steps below. Once all commands are written, source the script from inside icc2_shell:

    source ../scripts/place.tcl

    Read the tool output carefully after each command executes — the output tells you whether the step succeeded and what actions ICC2 took.

  • Open the Floorplan Library and Block (open_lib / open_block)

    What it does: Opens the existing ICC2 design library that was built during PNR-SNPS-FP and loads the specific block named floorplan.design. This block contains the complete floorplan: die dimensions, power rings, power stripes, and macro placements. The placement commands you will run next all operate on this block.

    open_lib ../inputs/tile.ndm
open_block floorplan.design
    What to verify: ICC2 should print the block name and design statistics on open. Confirm the block name shows floorplan.design and no error messages appear. If the block name is wrong or the NDM cannot be found, check the path and the block name used in the FP stage.

  • Configure Scenario Settings — Activate Setup Scenarios Only

    What it does: Deactivates all currently active scenarios, then reactivates only those whose names match the pattern *setup*. This ensures place_opt analyzes only setup timing and does not waste time on hold optimization — which is meaningless before the clock tree is built.

    set_scenario_status -active false [all_scenarios]
set_scenario_status -active true [get_scenarios *setup*]
    Why setup only? During placement, ICC2 propagates clocks as ideal (zero skew). Hold violations only appear when there is real clock skew between launch and capture flip-flops. Under zero skew, hold analysis produces misleading results — it would insert hold buffers on paths that will not actually need them once the clock tree introduces real skew. Hold fixing is deferred to post-CTS optimization.
    What to check in the report: Open ../reports/report_scenarios.rpt and confirm that only *setup* scenarios show Active=true. All *hold* scenarios must show Active=false.

  • Define Signal Routing Layer Range (set_ignored_layers)

    What it does: Instructs ICC2 to use only metal layers M1 through M7 for signal routing estimation during placement. Layers above M7 (M8, M9) are reserved for power stripes and should not be consumed by signal routing congestion analysis at this stage.

    set_ignored_layers -min_routing_layer M1 -max_routing_layer M7
    Why this matters: The congestion estimator used internally by place_opt needs to know which routing layers are available for signal nets. If M8 and M9 are not excluded, the congestion map will underestimate real routing pressure because those layers are already consumed by power stripes from the floorplan stage.

  • Insert IO Buffers and Anchor Them Near Ports

    What it does: Inserts a BUFFD4BWP40P140 buffer on every data port (excluding clock, power, and ground), names the new instances with the prefix IO_buff, anchors them near the ports using magnet placement, and then freezes them so the optimizer cannot remove them.

    add_buffer -lib_cell BUFFD4BWP40P140 -new_cell_names IO_buff [remove_from_collection [get_ports *] {clk VDD VSS}]
magnet_placement -mark_legalize_only -logical_levels 1 [get_ports *]
set_dont_touch [get_cells *IO_buff*]
    • add_buffer: Inserts a drive buffer on each data port. BUFFD4BWP40P140 is a 4X drive-strength buffer from the TSMC 28nm BWP40 cell library, appropriate for typical IO load capacitances. The clock port (clk) and supply rails (VDD, VSS) are excluded because they do not need signal buffers.
    • magnet_placement -mark_legalize_only -logical_levels 1: Marks all port-connected cells as legalization magnets with a logical level depth of 1. During legalization, ICC2 will physically pull these buffer cells as close to their port locations as possible, minimizing the length of the port-to-first-buffer wire.
    • set_dont_touch [get_cells *IO_buff*]: Freezes all IO buffer instances so place_opt cannot delete, resize, or replace them during timing optimization iterations.
    Important: The lib-cell name BUFFD4BWP40P140 must match exactly what is available in the NDM reference libraries loaded during PNR-SNPS-DI. If the name is wrong, ICC2 will fail with an error such as Cannot find cell BUFFD4BWP40P140.

  • Set Instance Name Prefix for Optimization Cells

    What it does: Sets a user-defined prefix for all new cell instances that place_opt inserts during timing optimization (buffers, inverters, sizing changes). Using a consistent prefix makes it easy to identify optimizer-inserted cells in the netlist, distinguish them from designer-instantiated cells, and remove them systematically if needed.

    set_app_options -name opt.common.user_instance_name_prefix -value "PNR_PLACEOPT"
    All new cells inserted by place_opt will have names beginning with PNR_PLACEOPT_. In report_design and ECO scripts, you can quickly filter these cells with get_cells PNR_PLACEOPT*.

  • Configure Scan-Def and DFT Settings

    What it does: Tells ICC2 to continue even if no scan DEF file is provided, and disables scan chain reordering during optimization. Scan chain reordering can dramatically improve scan shift timing but is incompatible with a scan DEF that has been committed to the test team — disabling it keeps the scan order deterministic.

    set_app_options -name place.coarse.continue_on_missing_scandef -value true
set_app_options -name opt.dft.optimize_scan_chain -value false
    continue_on_missing_scandef true: Without a scan DEF, ICC2 would halt by default at the start of coarse placement. This option bypasses that check when scan data is not yet available at the placement stage.

    optimize_scan_chain false: Prevents place_opt from reordering flip-flops in the scan chain to improve scan shift timing. This keeps the scan chain order consistent with the committed scan DEF definition.

  • Apply Lib-Cell Dont-Use Rules for Placement Optimization

    What it does: Excludes specific categories of cells from being used or inserted during place_opt timing optimization. This prevents power blowup, congestion, and downstream CTS conflicts.

    set_lib_cell_purpose -exclude optimization [get_lib_cells {*/CK* */*D24* */*D32* */*D20* */*D18* */DEL* */*D0* */*LVT}]
set_dont_use [get_lib_cells {*/*LVT}]
    • */CK* — Clock cells: Clock buffers and clock inverters are managed exclusively by the ICC2 CTS engine during the clock_opt stage. Allowing the placement optimizer to insert them creates rogue clock networks that conflict with the CTS solution and cause skew violations.
    • */*D24*, */*D32*, */*D20*, */*D18* — Very high drive-strength cells: These cells have drive strengths of 18X to 32X and large physical widths. Inserting them during placement creates severe local congestion in tight areas. They are only warranted if routing analysis confirms the net is extremely long — a decision best made post-route.
    • */DEL* — Delay cells: Pure delay cells are used only for scan chain balancing or hold fixing. Inserting them during setup optimization creates false slack improvement that does not survive routing parasitics.
    • */*D0* — Minimum drive-strength cells: D0 cells have essentially no drive capability. The optimizer would immediately upsize them in the next iteration, wasting CPU cycles.
    • */*LVT — Low-Vt cells (set_lib_cell_purpose): Soft exclusion — prevents the optimizer from inserting LVT cells during timing fix passes.
    • set_dont_use [get_lib_cells {*/*LVT}]: Hard exclusion — applies the dont_use attribute directly, preventing any context from using LVT cells throughout the entire placement flow. This reinforces the soft exclusion above and ensures LVT cells are not selected even if the optimizer overrides purpose settings.

  • Set Placement Spacing Rules to Prevent 1X Gaps

    What it does: Configures ICC2 to avoid single-site gaps (1X gaps) between standard cells. A 1X gap is a single-track-wide space that is too narrow to fill with any standard cell or filler — it causes DRC violations in chip finishing. The advanced legalizer and minimum VT filler size settings eliminate these gaps during legalization.

    set_app_options -name place.rules.min_vt_filler_size -value 2
set_app_options -name place.legalize.enable_advanced_legalizer -value true
set_placement_spacing_label -side both -lib_cells [get_lib_cells */*BWP*] -name ALL_STD_CELLS
set_placement_spacing_rule {1 1} -labels {ALL_STD_CELLS ALL_STD_CELLS}
    • min_vt_filler_size 2: Requires that any gap between cells be at least 2 sites wide, ensuring it can be filled with a valid 2-site filler cell.
    • enable_advanced_legalizer true: Activates ICC2's advanced legalization algorithm which performs multi-cell displacement to resolve 1X gaps that the standard legalizer cannot fix by local swapping alone.
    • set_placement_spacing_label / set_placement_spacing_rule: Defines an explicit spacing rule that requires at least 1 site of spacing between BWP standard cells on both sides, which prevents adjacent cells from creating sub-minimum-filler gaps.

  • Configure Placement Effort Settings

    What it does: Sets the suite of application options that control how aggressively ICC2 optimizes during place_opt. These settings trade off runtime for placement quality.

    set_app_options -name opt.common.max_fanout -value 32
set_app_options -name opt.common.max_net_length -value 400
set_app_options -name opt.timing.effort -value high
set_app_options -name place_opt.place.congestion_effort -value high
set_app_options -name place.coarse.congestion_analysis_effort -value high
set_app_options -name place.coarse.congestion_layer_aware -value true
set_app_options -name place.coarse.cong_restruct_effort -value high
set_app_options -name place.coarse.max_density -value 0.6
set_app_options -name place.coarse.congestion_driven_max_util  -value 0.83
    • opt.common.max_fanout 32: Sets the maximum fanout limit. Nets with more than 32 loads will be buffered to bring fanout below 32, preventing timing degradation from heavily loaded nets and improving signal integrity.
    • opt.common.max_net_length 400: Limits net length to 400 units (typically microns in this technology). Nets exceeding this length will be buffered during optimization to avoid excessive RC delay from long wires.
    • opt.timing.effort high: Instructs the timing optimizer inside place_opt to use its most thorough algorithms — more optimization passes, wider search space for sizing and buffer insertion decisions. This increases runtime but produces better WNS and TNS.
    • place_opt.place.congestion_effort high: Tells the outer place_opt loop to spend more iterations resolving congestion hotspots after each timing optimization pass.
    • place.coarse.congestion_analysis_effort high: Increases the accuracy and granularity of the congestion estimate computed during coarse placement, giving the placer a more reliable signal to spread cells away from congested areas.
    • place.coarse.congestion_layer_aware true: Enables per-layer congestion estimation during coarse placement, so layers already occupied by power stripes are correctly excluded from the available routing resource budget.
    • place.coarse.cong_restruct_effort high: Activates high-effort cell cluster restructuring during coarse placement to break up dense logic clusters by distributing them across multiple placement regions.
    • place.coarse.max_density 0.6: Limits local cell density to 60% per placement tile, providing 40% routing headroom. More conservative than the default 70% — used here because the tile design has high routing demand from dense logic clusters near SRAM macros.
    • place.coarse.congestion_driven_max_util 0.83: During congestion-driven spreading, individual placement tiles may be pushed up to 83% utilization when timing demands tighter clustering, but no higher. Works in tandem with max_density 0.6 — coarse placement targets 60%, congestion-driven optimization may push local tiles to 83% maximum.

  • Disable Concurrent Clock and Data Optimization (CCD)

    What it does: Disables ICC2's Concurrent Clock and Data (CCD) mode, which jointly optimizes clock tree topology and data path timing. CCD requires a nearly complete clock tree structure to make valid decisions. At the placement stage, no clock tree exists, so enabling CCD produces no quality benefit and only adds runtime.

    set_app_options -name place_opt.flow.enable_ccd -value false
    When to use CCD: CCD is enabled during the clock_opt command at the CTS stage, where the real clock tree topology and its interaction with data paths can be jointly optimized. Do not enable it during placement.

  • Add Placement Spacing Rules for AOI and OAI Cells

    What it does: Defines minimum spacing rules between AOI (AND-OR-INVERT) and OAI (OR-AND-INVERT) complex logic cells to prevent metal DRC violations caused by their internal diffusion geometry. These cells have wider diffusion regions than simple gates, so adjacent placement without spacing causes poly/diffusion pitch violations.

    set_placement_spacing_label -side both -lib_cells [get_lib_cells */*AOI*] -name ALL_AOI_CELLS
set_placement_spacing_rule {0 2} -labels {ALL_AOI_CELLS ALL_AOI_CELLS}

set_placement_spacing_label -side both -lib_cells [get_lib_cells */*OAI*] -name ALL_OAI_CELLS
set_placement_spacing_rule {0 2} -labels {ALL_OAI_CELLS ALL_OAI_CELLS}
set_placement_spacing_rule {0 2} -labels {ALL_AOI_CELLS ALL_OAI_CELLS}

#create_keepout_margin -outer {1 1 1 1} [get_flat_cells * -filter "ref_name =~ *AO*"]
#create_keepout_margin -outer {1 1 1 1} [get_flat_cells * -filter "ref_name =~ *OA*"]
    • set_placement_spacing_label -name ALL_AOI_CELLS: Creates a named label for all AOI cells in the library. Labels are used as operands in spacing rules — you attach a rule to two labels rather than enumerating individual cell pairs. The -side both option applies the spacing to both the left and right sides of each labeled cell.
    • set_placement_spacing_rule {0 2} -labels {ALL_AOI_CELLS ALL_AOI_CELLS}: Enforces a minimum spacing of 2 sites between any two AOI cells placed adjacent to each other. The rule format is {min_space max_space} — 0 means no maximum constraint, 2 is the minimum number of sites that must exist between these cell groups.
    • OAI rules: The same 2-site spacing is applied between OAI–OAI pairs and between AOI–OAI mixed pairs. In TSMC 28nm BWP40P140, both AOI and OAI cells use wider transistor stacks that cause DRC violations when placed with no gap.
    • Commented-out keepout margins: create_keepout_margin is an alternative approach that creates soft placement blockages around each AO/OA cell instance. It is commented out here because the label-based spacing rules above are more efficient — they are evaluated globally during coarse placement rather than per-instance during legalization.

  • Run Placement Optimization, Connect PG, and Save the Block

    What it does: Executes the complete integrated placement flow — coarse placement, legalization, and timing-driven optimization — followed by a power/ground connection check and a named block save.

    place_opt
connect_pg_net -automatic
save_block -as placed
    • place_opt: Runs the full placement and optimization flow using all the settings configured in the previous steps. Runtime for the tile design is typically 30–60 minutes depending on the server load. Observe the per-iteration WNS and TNS improvement in the tool log to confirm progress.
    • connect_pg_net -automatic: After placement, ICC2 may have inserted new cells (buffers, inverters) that do not yet have their power and ground pins connected to the PDN. This command automatically connects all floating PG pins to the nearest PG net, ensuring no power shorts or open PG pins exist in the placed netlist.
    • save_block -as placed: Saves the placed design as a new named block placed inside tile.ndm. The CTS stage will open this block with open_block placed.design.
    What to watch during place_opt: The tool prints a table of optimization iterations. Monitor the WNS (Worst Negative Slack) and TNS (Total Negative Slack) columns. Both should decrease (become less negative) with each iteration. If WNS does not improve after several iterations, check for undriven high-fanout nets or congestion overflow messages in the log.

  • Generate Placement Quality Reports

    What it does: Runs a comprehensive suite of placement quality reports to assess timing, constraint violations, utilization, congestion, and legality. These reports are the primary deliverables from the placement stage.

    Constraint violation report:

    redirect -file ../reports/report_constraint.rpt {report_constraint -all_violators -max_transition -max_capacitance -scenarios [all_scenarios]}
    What to check: Look for max-transition and max-capacitance violations. Transition violations indicate nets with too-slow rise/fall times — typically caused by high-fanout or long-wire nets. Capacitance violations indicate nets with too many loads. Both must be reduced before CTS.

    Setup timing report:

    redirect -file ../reports/report_timing.max.rpt {report_timing -delay max -scenarios [all_scenarios] -input_pins -nets -transition_time -capacitance -attributes -physical -derate -report_by group}
    What to check: The worst setup path WNS should ideally be better than -0.3 ns after placement. Paths with more than 0.5 ns of violation should be investigated — check whether they are dominated by logic depth or wire length. The -physical flag adds physical location information to each stage in the path, helping identify where the longest wires are.

    Setup design violation analysis:

    analyze_design_violations -type setup -stage preroute -output ../reports/analyze_design_violations.setup.rpt
    What to check: This command performs a higher-level analysis that groups setup violations by root cause (congestion, high fanout, logic depth). The report will identify which design modules contribute the most to total negative slack (TNS), helping you prioritize fixes.

    Max-transition violation analysis:

    analyze_design_violations -type max_trans -stage preroute -output ../reports/analyze_design_violations.max_trans.rpt
    What to check: Lists all nets that violate the maximum transition time constraint defined in the SDC. Sort by violation magnitude — the worst violators are often heavily-loaded clock-enable or scan-enable nets that need buffering before CTS.

    Utilization report:

    redirect -tee -file ../reports/report_utilization.rpt {report_utilization}
    What to check: Core utilization should be approximately 58–62% for the tile design (macros are excluded from the calculation). Utilization above 80% indicates insufficient core area — the placer is forced to pack cells too tightly, leading to congestion and routing failures. Utilization below 50% means the die is too large and the design will be unnecessarily expensive to manufacture.

    Design summary report:

    redirect -file ../reports/report_design.rpt {report_design -library -netlist -floorplan}
    What to check: Confirms the total cell count, macro count, and die dimensions. Cross-check the total cell count against the init_design stage to confirm no cells were accidentally deleted during placement optimization.

    Congestion report:

    redirect -tee -file ../reports/report_congestion.rpt {report_congestion -layers [get_layers -filter "layer_type==interconnect"] -rerun_global_router -nosplit}
    What to check: The -rerun_global_router flag forces a fresh global route to give accurate congestion data. Look at the overflow count per layer. Zero overflow is the target. M3 and M4 are typically the most congested layers in standard cell designs. Any layer with overflow > 5% of total tracks indicates a congestion hotspot that will likely prevent the detail router from completing.

    Legality check:

    redirect -file ../reports/check_legality.rpt {check_legality -verbose}
    What to check: The legality check must report 0 errors. Any error indicates cells are overlapping, placed off-grid, or violating site alignment rules. Common causes are disabled legalizer settings or macro blockage conflicts. Legality errors will cause the CTS stage to fail — they must be resolved before proceeding.

    Scenario status report:

    report_scenarios > ../reports/report_scenarios.rpt
    What to check: Confirms which scenarios were active during place_opt. Verify that only the *setup* scenarios show Active=true — all *hold* scenarios must be Active=false. This report is a trace record that documents the timing configuration used for this placement.

    Boundary utilization report:

    create_utilization_configuration config1 -capacity boundary
report_utilization -config config1
    What to check: -capacity boundary computes utilization based on the drawn floorplan boundary, which includes macro blockage areas subtracted from the available placement area. For the tile design, the boundary-capacity utilization accurately reflects the density of standard cells in the usable core region. Compare this number against the default report_utilization output — they will differ if macros occupy significant core area.

    End of stage message:

    puts "MyInfo: End of $stage on $design_name @ [sh date]"

exit
    Purpose: Prints a timestamped completion message to the tool log. This makes it easy to measure actual placement runtime by searching for "MyInfo: End of" in the log file. The exit closes the ICC2 session cleanly.

✅ Success Criteria

Placement is complete and correct when ALL of the following are true:

  • place_opt completes without errors — the tool log shows "place_opt complete" with no FATAL messages
  • check_legality -verbose reports 0 errors — all cells are legally placed on the site grid with no overlaps
  • report_utilization shows core utilization of approximately 58–62% for the tile design (hard macros excluded from the calculation)
  • connect_pg_net -automatic reports 0 unconnected PG pins
  • The named block placed is saved inside ../inputs/tile.ndm
  • All report files exist in ../reports/: report_constraint.rpt, report_timing.max.rpt, report_utilization.rpt, report_congestion.rpt, check_legality.rpt

📚 Knowledge Assessment Quiz

1. After running set_scenario_status -active false [all_scenarios] followed by set_scenario_status -active true [get_scenarios *setup*], you check report_scenarios and find that one hold scenario still shows Active=true. What is the most likely cause?

  • The all_scenarios collection was empty — no scenarios had been defined when the deactivation command ran.
  • The hold scenario name contains the substring "setup" (for example func_hold_setup_corner), so it matched the *setup* wildcard and was reactivated incorrectly.
  • ICC2 always keeps at least one hold scenario active during placement to guard against hold violations on short paths.
  • The set_scenario_status command requires a -hold false flag to deactivate hold analysis specifically.
Correct! The wildcard *setup* matches any scenario name containing the string "setup" anywhere in the name. If a hold scenario is named with "setup" somewhere in its identifier, it will be incorrectly reactivated. The fix is to either rename the scenarios so hold names never contain "setup," or to use a more precise wildcard pattern that matches only the intended scenario names.

2. place_opt completes but check_legality -verbose reports 47 overlap errors. All errors involve cells adjacent to a hard macro boundary. What setting most directly addresses this?

  • Increasing place.coarse.max_density to 0.9 so more cells can fit near the macro boundary.
  • Disabling set_placement_spacing_rule to allow cells to be placed directly against the macro.
  • Ensuring place.legalize.enable_advanced_legalizer true is set — the standard legalizer cannot resolve macro-boundary overlaps that require multi-cell displacement, but the advanced legalizer can.
  • Re-running connect_pg_net -automatic to properly assign PG connections near the macro, which resolves placement overlaps.
Correct! The standard legalizer resolves overlaps by locally shifting individual cells. Near macro boundaries, cells may be trapped with no room to move in one direction — the standard legalizer fails in this case. The advanced legalizer performs multi-cell displacement, shifting groups of cells simultaneously to create valid placements near macro boundaries. If it was not enabled before place_opt, re-enable it and re-run legalize_placement or a full place_opt iteration.

3. report_utilization after place_opt shows core utilization of 87%. What is the most likely consequence if you proceed to CTS with this utilization?

  • CTS will fail immediately with an error because ICC2 refuses to synthesize a clock tree in designs with utilization above 85%.
  • The router will encounter severe congestion overflow because there is insufficient routing track availability. Detail routing will be incomplete, leaving unrouted nets and DRC violations that cannot be fixed without reducing cell density.
  • Hold violations will increase dramatically during post-CTS optimization because high-density placement reduces the effectiveness of hold buffer insertion.
  • Utilization of 87% is within the acceptable range for a high-performance design — no action is needed before proceeding to CTS.
Correct! Core utilization above ~80% leaves insufficient routing track headroom for signal routing. With 87% utilization, the global router will show significant congestion overflow, and the detail router will fail to complete all nets. The fix is to increase the floorplan die area (going back to FP stage), reduce max_density below 0.7, or manually spread cells in the congested regions using interactive placement commands before re-running place_opt.

4. You forget to run set_dont_touch [get_cells *IO_buff*] before place_opt. What is the most likely result?

  • ICC2 will throw an error during place_opt because unprotected IO buffers violate the port-driver design rule.
  • The IO buffers will be moved away from the port boundary during legalization, increasing the port-to-first-buffer wire length.
  • The timing optimizer inside place_opt may delete or replace the IO buffers with different cells if it determines that doing so improves timing on other paths, undoing the IO buffer insertion step.
  • The magnet_placement attribute is automatically preserved by place_opt and the IO buffers will remain in place regardless of the dont-touch setting.
Correct! Without set_dont_touch, the ICC2 timing optimizer treats IO buffer instances as freely optimizable cells. During gate sizing and buffer insertion passes, it may delete the IO buffers if it finds that reorganizing the port-connected logic path improves WNS on other critical paths. Setting dont_touch before place_opt ensures the IO buffers are treated as immovable, unmodifiable instances throughout the entire optimization flow.
