🧭 What this challenge is

A single-file lab where the monitor publishes a transaction on every cycle valid_in is high instead of waiting for valid_out.

💡 The concept being tested

Tests whether the learner understands pipeline timing: add_dut registers sum and valid_out one clock after a, b, and valid_in are presented, so a monitor sampling on the input-side handshake captures a stale (previous-cycle, or reset-value) sum instead of the result for the transaction it thinks it's observing.

🛠️ Debugging Guide
🔴 Symptom — what you see when you run it

Every published add_item pairs the current cycle's a/b with a sum that doesn't equal a+b — the self-check's expected-value comparison fails, and because add_item has a c_nonzero constraint forcing b > 0, even the very first observed transaction is guaranteed to mismatch (the sampled sum is still its reset value of 0).

🔎 How to investigate
  1. Locate the if (vif.valid_in) condition in the monitor's run_phase and note which signal it gates transaction capture on.
  2. Compare that against add_dut's always_ff block in the same file: sum and valid_out are assigned from a/b/valid_in one clock edge later, not the same edge.
  3. Trace a single item through the pipeline by hand: on the cycle the driver presents a, b, valid_in, what does intf.sum actually hold at that moment versus one cycle later?
  4. Note the c_nonzero constraint on add_item (b > 0) and consider why it guarantees the very first sampled transaction will mismatch if sampling happens too early.
🧭 Fix direction

In the monitor's run_phase, change the sampling condition from if (vif.valid_in) to if (vif.valid_out) so the transaction is only captured once the DUT has actually registered and asserted the result as valid.

✅ How to confirm your fix

Rerun the simulation and verify every observed transaction's sum equals its a + b, with no mismatch errors reported, including for the first item in the sequence.
