Golden Example
🧭 What this lab is

The reference lab builds a small FIFO-style testbench (fifo_agent, fifo_driver, fifo_env) whose structural components deliberately do NOT raise objections, illustrating the standard UVM division of responsibility: structure vs. lifetime control.

💡 The concept

In UVM, only one part of the testbench should typically own the phase's objection lifetime — usually the test (or the sequence it starts). Every other component just does its job for as long as the phase happens to be alive. fifo_driver::run_phase runs a forever loop pulling items from the sequencer; that loop has no natural end, so it relies entirely on an external drop_objection to be killed off when the phase concludes. If a component were to raise its own objection but forget to drop it, the phase — and the whole simulation — would hang; if nothing ever raises an objection, the phase ends before any real work happens.

⚙️ How it works

fifo_agent::build_phase creates driver, monitor, and sqr (a uvm_sequencer#(fifo_txn)); its connect_phase wires driver.seq_item_port to sqr.seq_item_export so the driver can pull transactions, and connects driver.drv_ap to monitor.item_fifo.analysis_export to short-circuit driven items into the monitor (there is no physical DUT). fifo_driver::run_phase runs a forever loop calling seq_item_port.get_next_item(item), waits #10 to simulate pin-wiggling, and bumps push_count/pop_count depending on item.operation. Notice there is no raise_objection/drop_objection anywhere in fifo_driver or fifo_agent — the comments explicitly call this out. fifo_env::build_phase creates agent and scoreboard, and connect_phase links agent.monitor.mon_ap to scoreboard.analysis_imp, completing the data path driver → monitor → scoreboard. Because none of these components raise objections, the entire simulation's lifetime is controlled elsewhere (the test), and when that objection drops, UVM tears down the forever loop in fifo_driver::run_phase mid-iteration.

🎯 What you'll learn
  • Recognize which components should raise/drop objections (tests/sequences) versus which should stay silent (agents, drivers, monitors, env)
  • Understand that a forever task in run_phase (like fifo_driver's) is forcibly killed when the phase's objection count reaches zero, not stopped gracefully
  • See how TLM connections (seq_item_port, drv_ap, mon_ap) route data independently of who controls phase lifetime
⚠️ Common mistakes
  • Adding raise_objection inside a driver's forever loop 'just in case' — since the loop never naturally ends, this can make the phase hang indefinitely if the matching drop_objection is never reached
  • Assuming the agent or env needs to manage objections because it 'owns' the driver/monitor, when in UVM that responsibility belongs to the test/sequence layer
