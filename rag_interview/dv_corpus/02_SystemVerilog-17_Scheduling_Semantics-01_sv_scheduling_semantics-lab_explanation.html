🧭 What this lab is

17_Scheduling_Semantics.sv is a multi-module reference file that isolates specific scheduling pitfalls one at a time — starting with race_condition_demo for a classic same-time-step race and nba_solution for the NBA fix — and tb_17_Scheduling_Semantics.sv instantiates all of them (plus blocking_vs_nba_pipeline, zero_delay_demo, event_control_demo, stratified_event_queue_demo, fork_join_scheduling) so their $display output can be compared side by side.

💡 The concept

The core idea is that within one simulation time step, the scheduler processes events in a strict order: the Active region runs blocking assignments and evaluates RHS expressions for non-blocking assignments (but does not yet update the LHS); the NBA region then commits all those pending non-blocking updates atomically; the Observed region re-evaluates properties/assertions; and Reactive regions handle program blocks. Because blocking assignments take effect immediately within the Active region, two always blocks both triggered by the same event and both using = can execute in either order — a race. Non-blocking assignments sidestep this because every <= in a given time step samples its RHS from the pre-update values and only applies the write after all Active-region activity finishes, in the NBA region.

⚙️ How it works

race_condition_demo declares logic a, b and two always @(a) blocks that both fire whenever a toggles: the first does b = a; and the second does b = ~a;. Since both are blocking and both trigger on the same event in the same Active region, the simulator is free to run either block last, so b's final value (and the $display trace showing Block 1 vs Block 2) is non-deterministic. nba_solution contrasts this directly: it generates clk with initial begin clk = 0; forever #5 clk = ~clk; end, then drives count_blocking with a blocking count_blocking = count_blocking + 1; and count_nba with a non-blocking count_nba <= count_nba + 1;, both in separate always @(posedge clk) blocks. A third always @(posedge clk) block reads and $displays both counters in the same clock edge — because count_nba's update is deferred to the NBA region, this display sees the *old* count_nba value but potentially the *new* count_blocking value depending on block execution order, making the difference directly observable in the transcript.

🎯 What you'll learn
  • Recognize when two procedural blocks triggered by the same signal edge constitute a race, and why blocking assignments make the outcome execution-order-dependent
  • Explain why non-blocking assignments (<=) are the correct choice for modeling sequential/clocked logic so all RHS reads use pre-edge values
  • Trace which event region (Active, NBA, Observed) a given assignment or read actually executes in, and predict what a monitor reading a signal 'in the same cycle' will see
  • Use $display placement and $time to empirically observe scheduling order rather than assuming it
⚠️ Common mistakes
  • Mixing blocking and non-blocking assignments to the same signal across different always blocks (or even within one block), which reintroduces races even though the code 'looks' synchronous
  • Assuming a value read immediately after a non-blocking assignment in the same time step already reflects the new value, when it actually still holds the pre-edge value until the NBA region commits it
