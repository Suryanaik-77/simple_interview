🧭 What this lab is

If_statement_in_SV.sv defines the if_statement_demo module, which shows the same input pair (a, b, sel, enable) driving four different if-based computations, and tb_If_statement_in_SV.sv exercises each of them with dedicated test tasks.

💡 The concept

An if statement evaluates a condition and executes exactly one branch; chaining conditions with else if creates a priority order where the first true condition wins and later conditions are never checked. Nested ifs let a decision depend on the outcome of an outer decision. The unique/priority keywords tell the simulator (and synthesis tool) that the listed conditions are meant to be mutually exclusive or exhaustive, so it can flag violations and infer a parallel mux instead of a priority encoder.

⚙️ How it works

In if_statement_demo, basic_result is a plain if-else on enable: true adds a + b, false forces 8'h00. chain_result uses an if-else-if chain keyed on sel (2'b00/01/10 pick a, b, or a+b, with a final else doing a-b) to show priority selection across more than two cases. nested_result nests ifs inside the enable branch: first checking sel[1], then sel[0] within it, to combine a/b with &, |, or ^ depending on which inner branch is taken. The testbench tb_If_statement_in_SV drives these through tasks test_basic(), test_chain(), test_unique_priority(), and test_state_machine(), toggling enable, sel, and a/b on @(posedge clk) and printing the sampled result each time.

🎯 What you'll learn
  • Writing if-else if chains to encode priority among mutually exclusive selector values
  • Modeling nested conditional logic correctly inside an always_comb block
  • Understanding how unique if / priority if change simulation checking and synthesis inference versus a plain if
  • Structuring clocked testbench tasks that drive DUT inputs and sample outputs after @(posedge clk)
⚠️ Common mistakes
  • Forgetting the final else in an always_comb if-chain, which infers an unintended latch for the output
  • Using several independent if blocks instead of an else-if chain, so a later condition silently overwrites a result set by an earlier one
