Guided Example

GPIO controller module demonstrating APB-like register interface implementation with control, status, output, and interrupt registers. Showcases proper parameterization of register addresses, signal organization, and hierarchical port naming conventions for bus-based peripherals.

🎯 What You'll Learn
  • APB protocol register address mapping and localparam usage
  • Hierarchical signal naming conventions (ctrl_*, stat_*, etc.) for register fields
  • Port organization for complex peripherals (clock/reset, bus interface, GPIO pins, interrupts)
  • Register field bit allocation and documentation (e.g., [0] RW notation)
  • Separation of concerns between interface logic and GPIO pin control

🧠 Knowledge Check

Q1: What is the role of <code>uvm_config_db#(T)::set()</code>?

  • Creates a new UVM component
  • Stores a value in the config DB so any component can retrieve it by path
  • Connects a TLM port to a socket
  • Registers a sequence with the sequencer

uvm_config_db::set() deposits a typed value at a hierarchical path. Components call ::get() to retrieve it. This decouples configuration from the test hierarchy.

Q2: A uvm_driver calls <code>seq_item_port.get_next_item(req)</code>. What must it do before calling it again?

  • Call seq_item_port.put(req)
  • Call seq_item_port.item_done()
  • Nothing — get_next_item is non-blocking
  • Call seq_item_port.try_next_item()

item_done() signals the sequencer that the driver has finished with the current item and is ready for the next one. Omitting it stalls the sequence.

Q3: In the UVM factory, what does <code>type_override_by_type()</code> accomplish?

  • Replaces all instances of one component/object type with another without changing test code
  • Renames the component in the hierarchy
  • Changes the parent of a component
  • Disables a component type globally

Factory overrides let you substitute derived types (e.g., a specialized driver) for base types across the entire testbench without modifying the original build code.

Q4: Which UVM phase executes the actual simulation stimulus?

  • build_phase
  • connect_phase
  • run_phase
  • report_phase

run_phase is a time-consuming phase where sequences run and stimulus is applied. The other phases (build, connect, report) are zero-time.

Q5: What does raising an objection (<code>phase.raise_objection(this)</code>) do?

  • Causes the simulation to end immediately
  • Prevents the run_phase from ending until the objection is dropped
  • Blocks other components from running
  • Starts a new phase

UVM ends the run_phase when all objections are dropped. A component raises an objection to signal it still has work to do and drops it when done.
