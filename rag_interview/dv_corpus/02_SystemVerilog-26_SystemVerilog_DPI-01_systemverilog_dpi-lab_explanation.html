🧭 What this lab is

The reference lab (26_SystemVerilog_DPI.sv with tb_26_SystemVerilog_DPI) declares a full catalog of import "DPI-C" and export "DPI-C" functions covering simple math, strings, open arrays, context/pure qualifiers, and chandle-based opaque objects, then the testbench exercises equivalent local SV stand-ins since no real C code is linked in simulation.

💡 The concept

DPI functions are declared with import "DPI-C" (callable from SV, implemented in C) or export "DPI-C" (implemented in SV, callable from C). Each argument must specify a direction (input/output/inout), and SV types map to fixed C types (int↔int, real↔double, string↔char*, chandle↔void*). A context function may query the calling SV scope (e.g. via svGetScope), while a pure function promises no side effects and therefore cannot take output/inout arguments, since the simulator may cache or reorder its calls.

⚙️ How it works

26_SystemVerilog_DPI.sv imports simple functions c_add, c_multiply, c_sqrt; string functions c_get_message/c_print_message; an open-array function c_sum_array; a context function c_context_function; a pure function c_pure_add; and chandle-based object functions c_create_object, c_destroy_object, c_get_object_value, c_set_object_value. It also declares three export "DPI-C" functions (sv_callback, sv_get_time, sv_generate_random) that C code could call back into; sv_callback is implemented to $display its argument and return double the value. Since no C library is actually linked, tb_26_SystemVerilog_DPI instantiates dpi_import_demo, dpi_export_demo, dpi_data_types_demo, and dpi_use_cases_demo, and defines local SV shadow functions sim_c_add, sim_c_multiply, and sim_c_sqrt (a Newton-Raphson approximation) which the test_simulated_dpi task calls to demonstrate the same behavior an actual DPI call would produce.

🎯 What you'll learn
  • Writing legal import "DPI-C" prototypes with correct argument directions and C-compatible types
  • Choosing between plain, context, and pure DPI function qualifiers based on side effects
  • Mapping SV types (string, chandle, open arrays) to their C counterparts
  • Implementing export "DPI-C" functions in SV so C code can call back
⚠️ Common mistakes
  • Omitting input/output direction on import arguments, causing a mismatch with the actual C signature
  • Marking a function pure while still giving it output/inout arguments or side effects
  • Assuming raw C arrays can be passed without using SV's open-array argument syntax
