🧭 What this challenge is

The same 4-bit counter and self-checking testbench from the guided lab, but counter_flow.v has one planted bug. Run the compile→elaborate→simulate flow, read the mismatch the testbench reports, find the bug in the RTL, and fix it so the run ends in RESULT: TEST PASSED.

💡 The concept being tested

Whether the counter correctly gates counting on its en input. A counter that increments on every clock regardless of enable is a classic control bug that a clean compile will never catch — only the simulate-stage self-check exposes it.

🛠️ Debugging Guide
🔴 Symptom — what you see when you run it

The testbench prints FAIL: lines starting from the very first cycle where enable is low, e.g. FAIL: cycle 2 - expected count=0, got count=1 (en=0). The DUT keeps counting even while en=0, so it runs ahead of the reference model and the overall verdict is FAIL.

🔎 How to investigate
  1. Note from the FAIL lines that the DUT diverges precisely on the cycles where en=0 — it increments when it should hold.
  2. Open counter_flow.v and read the always @(posedge clk) block.
  3. Compare the non-reset branch against the spec in the header comment: "count up by one only while en is high, hold otherwise."
  4. Observe that the increment happens under a plain else — the en condition is missing.
🧭 Fix direction

Change the else that increments count into else if (en) so counting is gated by the enable and the counter holds its value when en is low.

✅ How to confirm your fix

Re-run ./run.sh vcs (or make). The FAIL lines should disappear and the run should end with RESULT: TEST PASSED; verify then reports the sequence as passed.
