🧭 What this lab is

22_SystemVerilog_parameters.sv defines basic_params, a memory module whose width, depth, reset value, and name are all configurable via parameter, with several localparams derived from them. Its testbench, tb_22_SystemVerilog_parameters, instantiates a family of demo modules (clog2_demo, param_override_demo, param_array_demo, param_expressions_demo, specparam_demo, type_params) to show the different parameter techniques side by side.

💡 The concept

parameter declares a constant that a parent module can override at instantiation using #( .NAME(value) ); localparam declares a constant that is computed from parameters/other localparams but can never itself be overridden — it exists to prevent accidental re-derivation errors. $clog2 computes the minimum number of bits needed to address a given number of entries, which is why it's the standard tool for sizing pointers/addresses from a depth parameter. SystemVerilog also allows type parameters (a parameter whose value is a data type, e.g. logic [7:0]), parameter arrays/structs, and expressions (arithmetic on parameters) evaluated once at elaboration.

⚙️ How it works

In basic_params, parameter int WIDTH, DEPTH, logic [7:0] INIT_VAL, and string NAME are overridable inputs. From these, localparam int ADDR_WIDTH = $clog2(DEPTH) sizes the pointer width automatically, while DATA_BYTES and TOTAL_BITS are simple derived arithmetic localparams. The mem array is declared [0:DEPTH-1] wide by WIDTH bits, and wr_ptr/rd_ptr are declared [ADDR_WIDTH-1:0] — so every width-dependent signal traces back to the single DEPTH/WIDTH parameters rather than being hardcoded. The always_ff block resets data_out to INIT_VAL and walks the memory each cycle; an initial block $displays every parameter/localparam value tagged with NAME so you can see the actual resolved numbers in the log. In the testbench, param_array_demo is instantiated with a parameter array override (.WIDTHS('{8,16,32,64})), param_expressions_demo is overridden with .DATA_WIDTH(32), .NUM_WORDS(1024), .FREQUENCY(100.0e6) to show real-valued/expression parameters, and type_params is instantiated multiple times with .DATA_T(logic [7:0]) and .DATA_T(word_t) — a type parameter — to build byte-wide and word-wide FIFOs from the same source using typedefs (word_t, dword_t, tagged_data_t) declared in the testbench.

🎯 What you'll learn
  • Distinguish parameters that should be overridable (parameter) from values that must always be derived and locked (localparam)
  • Use $clog2(DEPTH) to size address/pointer fields so they automatically track a depth or count parameter
  • Override parameters positionally vs. by name (#(.WIDTH(32), .DEPTH(64))) and use type parameters (.DATA_T(...)) to make a module generic over data type
  • Read elaboration-time $display output to sanity-check what values parameters actually resolved to for a given instance
⚠️ Common mistakes
  • Hardcoding a width/pointer size instead of deriving it with localparam ... = $clog2(DEPTH), so the module silently breaks when a different DEPTH is passed in
  • Treating a parameter like a runtime signal (trying to assign it from testbench stimulus) — parameters are fixed at elaboration, not driven during simulation
