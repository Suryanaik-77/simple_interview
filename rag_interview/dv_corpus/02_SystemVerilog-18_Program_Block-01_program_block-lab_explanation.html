🧭 What this lab is

18_Program_Block.sv pairs a simple_dut (driven through simple_bus_if's dut_mp modport) with several small program blocks — basic_program_demo, automatic_program, exit_demonstration, module_comparison, and program_comparison — instantiated from tb_18_Program_Block to contrast program-block behavior against ordinary modules.

💡 The concept

Program blocks execute in the Reactive region, which runs after all Active-region (always_ff/always_comb) and NBA updates for the current time step have settled. This lets testbench code sample DUT outputs the same cycle they change without extra #0/#1 delay hacks. Variables declared inside a program default to automatic lifetime (a fresh copy per call/thread), unlike a module where they default to static — this is what protects tasks from corrupting shared state when invoked repeatedly or concurrently. Idiomatic stimulus in a program is written as an initial process (often wrapped in forever) rather than an always process.

⚙️ How it works

simple_bus_if declares tb_cb (outputs data, valid; inputs ready, ack, sampled input #1step output #0) for the testbench side and dut_cb for the DUT side, exposed via modports tb_mp and dut_mp. simple_dut connects through bus.dut_mp and its always_ff captures bus.data into captured_data whenever bus.valid && bus.ready, then pulses bus.ack and drops bus.ready, printing [DUT] @%0t: Received data = %h. In tb_18_Program_Block, bus_if and u_dut are wired up first, then the comparison programs are instantiated: basic_program_demo drives prog_data/prog_valid, automatic_program and exit_demonstration are instantiated with no ports, and module_comparison/program_comparison are wired together (program_comparison's clk comes from u_module_comp.clk) to show module vs program scheduling side by side.

🎯 What you'll learn
  • distinguish module (Active/NBA) vs program (Reactive) scheduling and why it matters for sampling DUT signals
  • drive/sample a DUT only through the interface's clocking block (tb_cb) and modport instead of raw signals
  • rely on a program block's automatic-by-default variable lifetime instead of module-style static variables
⚠️ Common mistakes
  • driving or sampling bus.data/bus.valid directly instead of through tb_cb, reintroducing the exact race the clocking block was meant to remove
  • assuming a task's local variables inside a program are private like automatic locals in a module, when static declarations (or a non-automatic program) can make them shared and get corrupted by concurrent calls
