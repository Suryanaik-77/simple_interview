🧭 What this lab is

The reference lab (event_pkg.sv, tb_top.sv, test.sv) walks through the full uvm_event API using twelve test classes — from base_test's feature overview down to focused tests like wait_ptrigger_test, callback_test, and race_condition_test — each isolating one method or behavior of the event class.

💡 The concept

uvm_event_base is the abstract root providing state/timing methods (wait_on(), wait_off(), wait_trigger(), wait_ptrigger(), is_on()/is_off(), get_trigger_time(), reset(), get_num_waiters(), cancel()), while uvm_event#(T) extends it with data-carrying methods (trigger(data), get_trigger_data(), wait_trigger_data(), wait_ptrigger_data()) and callback registration (add_callback()/delete_callback()). The key conceptual distinction the lab drives home is wait_trigger() (misses a trigger that already fired) versus wait_ptrigger() (persistent — catches a trigger even if it already happened), which is exactly what race_condition_test is built to demonstrate.

⚙️ How it works

event_pkg.sv defines transaction, a uvm_object with rand bit [7:0] addr/data registered via uvm_object_utils_begin/end, used as the payload passed through trigger(data). It also defines my_event_cb, which extends uvm_event_callback and overrides pre_trigger() (prints via uvm_info and $casts the incoming uvm_object to transaction to log it, returning 0 so the trigger is never skipped) and post_trigger() (logs after the trigger completes). In test.sv, base_test::run_phase creates uvm_event#(uvm_object) e1 = new("e1"), then runs a fork...join with one branch calling e1.trigger() after #10ns and the other branch calling e1.wait_trigger() immediately, showing the basic rendezvous pattern before the other tests dig into each individual method.

🎯 What you'll learn
  • Choosing wait_trigger() vs wait_ptrigger() based on whether the trigger might fire before the wait starts
  • Passing and retrieving typed payload data through trigger(data)/get_trigger_data() using $cast
  • Registering uvm_event_callback objects to hook pre_trigger()/post_trigger() logic
  • Sharing an event across components via uvm_event_pool::get_global() instead of manual handles
  • Using get_num_waiters()/cancel() and is_on()/is_off()/reset() to introspect and control event state
⚠️ Common mistakes
  • Calling wait_trigger() after the triggering process has already fired the event, permanently missing it because wait_trigger() is not persistent
  • Registering a callback but forgetting it only affects trigger() calls made after add_callback() runs, or forgetting to add it at all so pre_trigger()/post_trigger() never execute
