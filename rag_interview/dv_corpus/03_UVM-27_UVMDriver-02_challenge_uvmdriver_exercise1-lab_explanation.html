🧭 What this challenge is

A variant of add_driver inside buggy_driver_ex1.sv where the run_phase loop drives operand a and valid_in onto add_if but omits driving operand b.

💡 The concept being tested

A driver must translate every randomized field of the sequence item (add_item.a and add_item.b) onto its corresponding interface signal — driving only a subset of fields silently corrupts the transaction the DUT actually receives, even though the item itself was randomized correctly.

🛠️ Debugging Guide
🔴 Symptom — what you see when you run it

The self-check comparing DUT sum/valid_out results against the expected a+b values (tracked via exp_q) fails for every transaction where b != 0, since c_b { b > 0; } guarantees b is always nonzero — the DUT effectively always computes a + 0.

🔎 How to investigate
  1. Look at the add_if interface declaration and list every signal a driver for this protocol must set: a, b, valid_in.
  2. In add_driver::run_phase, find the block that assigns interface signals from req after get_next_item(req) and check which of req.a / req.b are actually assigned.
  3. Check where exp_q is populated — does the expected-value push happen for the full req.a + req.b, confirming the DUT is being compared against the correct sum even though it isn't receiving b?
  4. Confirm the c_b { b > 0; } constraint on add_item — this guarantees the missing assignment is always observable in the mismatch.
🧭 Fix direction

In add_driver::run_phase, add the missing pin assignment for operand b (e.g. vif.b <= req.b;) alongside the existing vif.a/vif.valid_in drives, so every field of add_item reaches the interface before the clocked wait.

✅ How to confirm your fix

Re-run the lab and verify the self-check reports all 8 results matching (no mismatches for nonzero b values).
