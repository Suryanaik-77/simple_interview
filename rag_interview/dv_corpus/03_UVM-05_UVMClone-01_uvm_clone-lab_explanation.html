🧭 What this lab is

clone_pkg includes clone_item.sv (the transaction classes) and clone_test.sv (clone_demo_test), which runs a sequence of five demo tasks that each exercise a different facet of clone() — from the basic $cast requirement to deep-cloning nested objects and scoreboard-style usage.

💡 The concept

clone() is not user-written directly for the demo classes here — it comes for free from uvm_object_utils_begin/end field automation. Every field wrapped in a \uvm_field_* macro inside that block is what copy() (and therefore clone()) actually transfers into the new object; anything left out of the macro block is silently skipped by the automatic copy. This matters most for handle-type fields (like a nested uvm_object), where \uvm_field_object(..., UVM_DEEP) is required to make the clone allocate its own nested object rather than share the original's handle.

⚙️ How it works

basic_transaction extends uvm_sequence_item and registers address, data, xfer_type, length, label, and sequence_num inside \uvm_object_utils_begin/end, so copy()/clone()/print() all work on those fields automatically. transfer_config extends uvm_object and models a nested config object (channel_id, prio_level, use_burst) used to demonstrate deep cloning of an embedded handle. In clone_test.sv, clone_demo_test::run_phase raises an objection and calls five tasks in sequence: demo_basic_clone() creates an original basic_transaction via type_id::create, randomizes it, then calls original.clone() into a uvm_object clone_result handle and requires $cast to get back a usable basic_transaction. demo_clone_vs_copy(), demo_clone_nested_objects(), demo_scoreboard_scenario(), and demo_clone_with_do_copy() build on this to show clone vs. plain copy(), cloning through a nested transfer_config, why scoreboards need independent clones of transactions pulled off an analysis port, and overriding do_copy()` for custom copy behavior.

🎯 What you'll learn
  • Why clone() returns uvm_object and must always be paired with $cast before use
  • How field automation macros (\uvm_field_int, \uvm_field_object, etc.) determine exactly what copy()/clone() transfer
  • The difference between a shallow copy (shared nested handle) and a deep copy (UVM_DEEP flag, independent nested object)
  • Why scoreboards and analysis-port subscribers must clone incoming transactions instead of storing the raw handle
⚠️ Common mistakes
  • Forgetting the $cast after clone() and trying to use the returned uvm_object handle as the derived type directly
  • Adding a nested uvm_object field to a class but forgetting to register it with \uvm_field_object, so clone()/copy()` silently leave it untouched
  • Assuming \uvm_field_object without UVM_DEEP` gives an independent nested object, when by default it may only copy the handle
