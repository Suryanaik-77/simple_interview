🧭 What this challenge is

The same adder DUT and driver/sequence infrastructure as the guided lab, but the scoreboard's reference model computes the wrong arithmetic operation.

💡 The concept being tested

Tests whether the learner understands that a reference model must be built from the DUT's specification (a registered adder, sum <= a + b), not an arbitrary or copy-pasted formula — and that a scoreboard bug looks identical to a DUT bug from the report output alone.

🛠️ Debugging Guide
🔴 Symptom — what you see when you run it

report_phase prints TEST FAILED with a nonzero UVM_ERROR count; nearly every one of the 8 transactions mismatches, even though the DUT is functioning correctly.

🔎 How to investigate
  1. Run the simulation and read the UVM_ERROR mismatch messages — note what expected value they report versus the DUT's actual sum.
  2. Look at add_dut's always_ff block to establish the DUT's real specification: intf.sum <= intf.a + intf.b.
  3. Find the scoreboard's write() (or equivalent compare) method and compare its expected-value computation against that specification.
  4. Notice the constraint c_b { b > 0; } on add_item — this exists specifically to guarantee the wrong operation is observable on every transaction.
🧭 Fix direction

In the scoreboard's reference-model computation, change the operator so expected mirrors the DUT's actual behavior (addition), not the planted subtraction.

✅ How to confirm your fix

Re-run the simulation: all 8 checked transactions should match and report_phase should print TEST PASSED with UVM_ERROR : 0.
