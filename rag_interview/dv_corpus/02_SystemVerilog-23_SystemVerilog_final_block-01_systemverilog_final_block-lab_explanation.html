🧭 What this lab is

The reference design 23_SystemVerilog_final_block.sv builds up final-block usage from a single simple module to a full testbench with several cooperating final-reporting modules, all instantiated together and exercised by tb_23_SystemVerilog_final_block.

💡 The concept

A final block cannot contain any timing controls (no #, @, or wait) because it executes in zero time after the simulation has already concluded — it can only read final variable values and print them. Unlike an initial block, which competes with other processes and can be interrupted or race against $finish, a final block is guaranteed to run exactly once, after everything else, making it the reliable place to compute simulation duration (end_time - start_time), tally counters, and print a closing report. A design can have multiple final blocks (even across separate modules), and SystemVerilog executes all of them, though the relative order between blocks in different modules is not strictly guaranteed by the LRM.

⚙️ How it works

basic_final_demo declares transaction_count, error_count, warning_count, start_time, and end_time, initializes them in its initial block (capturing start_time = $time), then drives 100 iterations of simulated activity using $urandom_range to randomly bump error_count/warning_count. Its final block captures end_time = $time, then prints a formatted "Basic Final Block Report" banner showing total simulation time and the three counters. The top-level tb_23_SystemVerilog_final_block testbench instantiates six such demo modules side by side — u_basic (basic_final_demo), u_stats (statistics_collector), u_coverage (coverage_reporter), u_multi (multiple_final_demo), u_compare (final_vs_initial_demo), and u_class (class_final_demo) — so the run shows all their final reports together at shutdown. In its own initial block, the testbench forks generate_transactions() and track_coverage() in parallel, waits #500, then calls $finish, which is what triggers every final block in the hierarchy. generate_transactions() declares a final_block_pkg::txn_type_e txn_type variable and randomly assigns it TXN_READ/TXN_WRITE/etc. across 50 iterations using a case ($urandom_range(0,3)) statement.

🎯 What you'll learn
  • Recognize that final blocks run once, in zero time, strictly after $finish/end-of-sim — never mid-simulation
  • Use a paired initial/final block idiom to measure elapsed simulation time reliably (start_time captured at time 0, end_time captured in final)
  • Understand that final blocks may not contain timing controls, and why that restriction exists
  • See how several independently-instantiated modules can each contribute their own end-of-sim report via their own final blocks
⚠️ Common mistakes
  • Trying to add a #delay, @(posedge clk), or wait inside a final block, which is illegal since the block must execute in zero time
  • Reading $time inside final and assuming it reflects a specific event time rather than the time simulation actually stopped
