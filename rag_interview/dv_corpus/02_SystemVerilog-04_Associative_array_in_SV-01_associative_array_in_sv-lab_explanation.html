🧭 What this lab is

The reference lab (Associative_array_in_SV.sv with its testbench tb_Associative_array_in_SV.sv) walks through declaring associative arrays with several different index types inside a single class and shows how sparse entries are written and displayed.

💡 The concept

An associative array is declared as data_type array_name [index_type], where index_type can be an integral type (int), a string, a packed vector (like addr_t), or the wildcard * which accepts any integral index type at elaboration time. Unlike a fixed-size array, no storage exists until a key is assigned, which is what makes indices like 10000 or -50 legal without allocating a huge array. Built-in methods exists(), delete(), num(), and the iteration pair first()/next() (and last()/prev()) let you query and walk the sparse contents safely instead of guessing which keys are populated.

⚙️ How it works

The assoc_array_pkg package defines addr_t/data_t typedefs and a transaction_t struct (addr, data, id, name). The AssocArrayDemo class then declares five associative arrays covering the main index styles: mem_int[int] for a sparse integer-indexed memory, config_str[string] as a string-keyed lookup table, memory[addr_t] as a bit-vector-indexed memory model, generic_mem[*] using the wildcard index, and txn_table[int] storing a transaction_t struct per entry. The method demo_int_index() demonstrates sparse storage concretely by writing mem_int[0], mem_int[100], mem_int[10000], and mem_int[-50] — showing that negative and far-apart indices are all valid and each $display reads the value straight back. In the testbench tb_Associative_array_in_SV, the DUT assoc_memory_model (parameterized by ADDR_WIDTH/DATA_WIDTH) is instantiated alongside its own set of associative arrays — aa_int[int], aa_str_idx[string], aa_logic[logic[15:0]], and aa_wildcard[*] — used to exercise the same index-type variety against a clocked, reset-driven environment.

🎯 What you'll learn
  • Declaring associative arrays with int, string, bit-vector, and wildcard [*] index types
  • Understanding that associative arrays only allocate storage for keys actually written (sparse semantics)
  • Storing structs (like transaction_t) as associative array values
  • Reading back entries safely and recognizing how index type constrains what can be used as a key
⚠️ Common mistakes
  • Assuming an associative array preserves insertion order — iteration order via first()/next() follows key ordering (numeric/string sort), not the order entries were written
  • Reading a key that was never written and not realizing the read can implicitly create a default-valued entry if not guarded with exists() first
