🧭 What this challenge is

A single-file lab where the monitor correctly waits for reset and samples a, b, and sum whenever valid_out is high, but never actually publishes what it captured.

💡 The concept being tested

Tests whether the learner understands that a monitor's uvm_analysis_port is not automatic — sampling data into a local transaction object accomplishes nothing for the rest of the environment until ap.write(tr) is explicitly called.

🛠️ Debugging Guide
🔴 Symptom — what you see when you run it

The driver drives all 8 add_items correctly and the DUT computes the right sums, but the subscriber's transaction count never advances past 0, so the self-check expecting 8 received transactions fails (no PASS marker, or an explicit count-mismatch error at the end of the run).

🔎 How to investigate
  1. Find the monitor's run_phase and confirm it does build an add_item tr with a, b, and sum populated whenever valid_out is sampled high.
  2. Check the subscriber's write() method — verify it is implemented to increment its counter, which tells you the problem isn't on the receiving side.
  3. Search the monitor code for any call to ap.write(...) — note that the transaction is constructed but the analysis port method is never invoked.
  4. Confirm the analysis port itself (ap) is declared and built in the monitor, ruling out a connection problem versus a missing-call problem.
🧭 Fix direction

In the monitor's run_phase, immediately after the sampled add_item tr is fully populated (a, b, sum) on a valid_out cycle, add the call ap.write(tr); so the completed transaction is actually broadcast to subscribers.

✅ How to confirm your fix

Rerun the simulation and check that the subscriber's received-transaction count reaches 8 (matching the number of items add_sequence generated) and the self-check reports PASS instead of a zero-transaction failure.
