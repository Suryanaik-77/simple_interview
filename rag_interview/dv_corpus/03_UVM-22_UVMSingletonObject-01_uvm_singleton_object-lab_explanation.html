🧭 What this lab is

The reference lab is built from singleton_pkg.sv (which includes test.sv) and driven by tb_top.sv. It defines two singleton uvm_object classes, singleton_obj and singleton_config, each implementing the static-handle-plus-guarded-factory pattern, and tb_top prints an explanation of the pattern along with the list of available tests (base_test, basic_singleton_test, same_instance_test, config_singleton_test, lazy_init_test, shared_access_test).

💡 The concept

The core idea is lazy initialization guarded by a null check: a class declares a static handle (e.g. static singleton_obj s_obj;) that is shared across every reference to the class, not per-object. A static function (get_instance()) checks whether that handle is still null; if so it calls new() exactly once and stores the result, printing a message such as "SINGLETON: Creating new singleton instance"; on every subsequent call it skips creation and prints "SINGLETON: Returning existing singleton instance", handing back the same object. Because SystemVerilog has no true private constructor, the pattern relies on discipline — callers are expected to always go through get_instance() rather than calling new() directly — and a reset_instance() helper is provided so tests can deliberately clear the cached handle (setting it back to null) to force fresh creation, which is useful for isolating test cases.

⚙️ How it works

singleton_obj extends uvm_object and holds a static singleton_obj s_obj handle plus rand bit [7:0] addr and data fields registered via uvm_object_utils_begin/uvm_field_int. Its static function get_instance() is the factory: if (s_obj == null) it builds s_obj = new("singleton_obj") and logs the creation message, else it logs that the existing instance is being reused, then always return s_obj. static function void reset_instance() simply sets s_obj = null, letting a test start the singleton fresh. singleton_config follows the identical shape but models a shared configuration object: static singleton_config s_cfg, plus num_transactions, base_address, enable_coverage, enable_checking, and test_name fields (registered with uvm_field_int/uvm_field_string), with sensible defaults assigned in new() (e.g. num_transactions = 100, base_address = 32'h1000_0000). Its get_instance() mirrors singleton_obj's guarded creation, printing "SINGLETON_CFG: Creating new config singleton" the first time it allocates s_cfg. tb_top doesn't instantiate these classes itself — it just imports singleton_pkg and prints the conceptual walkthrough of the pattern and the list of tests that exercise it.

🎯 What you'll learn
  • How a static class member is shared across all handles/callers instead of being duplicated per object
  • How to implement lazy initialization with a null-check guard inside a static function factory method
  • Why callers must go through the factory method (get_instance) rather than calling new() directly to preserve the singleton guarantee
  • How a reset_instance()-style hook lets you deliberately re-create a singleton for controlled testing
⚠️ Common mistakes
  • Forgetting the static keyword on the instance-holder variable, so each object ends up with its own private copy instead of one shared handle
  • Omitting the if (handle == null) guard in the factory method, so it unconditionally calls new() and creates a fresh object every time it's invoked
  • Bypassing get_instance()/get_inst() altogether and calling new() directly on the class, which silently breaks the singleton contract
