Challenge Exercise

A FIFO queue implementation using SystemVerilog extern methods with multiple bugs in pointer arithmetic and boundary conditions. The write pointer modulo uses (depth+1) instead of depth, and the is_full() condition incorrectly checks (count>=depth-1) instead of (count>=depth), causing incorrect full/empty detection and pointer wraparound behavior.

🐛 Challenge Exercise

🔍 Debug Strategy

  1. Observe the write_data() function: wr_ptr is wrapped as (wr_ptr+1)%(depth+1), but read_data() uses (rd_ptr+1)%depth—these have different modulo divisors
  2. Check the is_full() condition: it returns true when count >= depth-1, but a FIFO should be full when count == depth
  3. Trace through Test 7: after writing 4 items to a depth-4 FIFO, check what the actual count value is and compare against the expected full condition

💡 Why It Matters

Extern methods are a cornerstone of OOP in SystemVerilog, and pointer/counter management bugs in circular buffers are extremely common in RTL and testbench code. Mismatched modulo operations between write and read pointers lead to silent data corruption and hard-to-debug test failures in production.

🧠 Knowledge Check

Q1: What is the result of calling a virtual method through a base-class handle that points to a derived object?

  • The base-class method executes
  • The derived-class method executes (runtime dispatch)
  • Compile error — cannot call via base handle
  • Behaviour is undefined

Virtual methods use dynamic dispatch: the actual type of the object (not the handle) determines which method runs. This is the key mechanism behind polymorphism.

Q2: When does a shallow copy differ from a deep copy for a class object?

  • When the object has only integer fields
  • When the object contains handles to other objects
  • When the class uses the virtual keyword
  • Shallow and deep copy are always identical for classes

A shallow copy duplicates the handle values, so both copies reference the same sub-objects. A deep copy recursively allocates new sub-objects. Bugs arise when one copy mutates a shared sub-object.

Q3: A class has a static property. How many copies of it exist across all instances?

  • One per instance
  • One shared across all instances
  • One per file
  • Zero — static properties are compile-time only

Static class properties are shared across all instances (like C++ static members). Modifying the property in one instance changes it for all.

Q4: What is <code>this</code> inside a class method?

  • A copy of the current object
  • A handle to the current object instance
  • A pointer to the parent class
  • A reference to the class type

this is an implicit handle to the object on which the method was invoked. It is the same type as the class and is used to disambiguate member names.

Q5: What happens if you call <code>new()</code> on a class variable that already holds an object?

  • Compile error
  • The old object is automatically destroyed and a new one allocated
  • The variable is overwritten; the old object may be garbage-collected if no other handles exist
  • The new object is discarded; the original is retained

SV uses reference counting / garbage collection. Reassigning the handle drops the reference; if no other handle points to the old object it becomes eligible for collection. There is no explicit destructor call.
