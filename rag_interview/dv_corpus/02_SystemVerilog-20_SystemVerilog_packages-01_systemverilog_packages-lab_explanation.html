🧭 What this lab is

20_SystemVerilog_packages.sv defines a small chain of packages — constants_pkg and types_pkg (with more, such as functions_pkg and verification_pkg, referenced from the testbench) — and tb_20_SystemVerilog_packages.sv exercises them by importing every package, instantiating demo modules, and running a series of tasks that print out package contents.

💡 The concept

The lab shows the two core package mechanics: (1) definition — constants_pkg holds parameter values (widths, timing constants, protocol bytes) and derived parameters computed with $clog2; types_pkg builds enumerations on top of those constants; and (2) consumption — a consumer can either selectively import constants_pkg::DATA_WIDTH; a single name (as types_pkg does) or wildcard-import pkg::*; everything (as the testbench does). It also touches package dependency order: types_pkg depends on constants_pkg, so constants_pkg must elaborate first.

⚙️ How it works

constants_pkg declares DATA_WIDTH, ADDR_WIDTH, FIFO_DEPTH, CLK_PERIOD, RESET_DELAY, SYNC_BYTE, END_BYTE, and the derived FIFO_PTR_WIDTH (via $clog2(FIFO_DEPTH)) and DATA_BYTES. types_pkg selectively imports constants_pkg::DATA_WIDTH and constants_pkg::ADDR_WIDTH, then defines the opcode_e, response_e, and size_e enum typedefs (and a transaction struct) built from those widths. In tb_20_SystemVerilog_packages, the module wildcard-imports verification_pkg::*, types_pkg::*, constants_pkg::*, and functions_pkg::*, instantiates import_demo and verification_demo, and declares transaction_t read_txn/write_txn/burst_txn, response_t resp, and a parameterized Scoreboard #(transaction_t) txn_sb. The initial block waits #200 for the demo modules, then calls demonstrate_constants(), demonstrate_types(), demonstrate_functions(), demonstrate_scoreboard(), and demonstrate_scope_resolution() before print_summary(). demonstrate_constants() simply $displays DATA_WIDTH, ADDR_WIDTH, FIFO_DEPTH, FIFO_PTR_WIDTH, and DATA_BYTES to prove the imported constants are visible.

🎯 What you'll learn
  • Defining parameters, typedefs, and derived constants inside a package
  • Choosing selective import pkg::item versus wildcard import pkg::* and knowing the tradeoffs
  • Using pkg::item scope resolution to reach an item without importing it
  • Understanding package compile/elaboration order when one package depends on another
  • Sharing a common type (e.g. transaction_t) across a scoreboard class and a testbench module
⚠️ Common mistakes
  • Forgetting to import a package (or importing the wrong one) and getting an 'identifier not found' style elaboration error for a name like DATA_WIDTH or opcode_e
  • Wildcard-importing two packages that define the same identifier, causing an ambiguous-symbol conflict instead of a clean override
