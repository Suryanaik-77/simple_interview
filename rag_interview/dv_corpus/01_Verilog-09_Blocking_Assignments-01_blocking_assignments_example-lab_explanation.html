🧠 Knowledge Check

Q1: In an always block, <code>a = b; c = a;</code> uses blocking assignments. What is c after both statements?

  • The old value of a
  • The new value of b (same as a after first assignment)
  • Undefined — race condition
  • The old value of b

Blocking assignments execute sequentially within the same always block. After a = b, a holds b's new value, so c = a assigns that same value to c.

Q2: Why is it dangerous to mix blocking and non-blocking assignments to the same variable?

  • It causes a compile error in all tools
  • Scheduling order is undefined — tools may produce different simulation results
  • The variable will hold x permanently
  • Only the non-blocking assignment will take effect

The IEEE standard warns that mixing = and <= for the same variable leads to race conditions. Different simulators may schedule them differently, producing non-reproducible results.

Q3: An always block has blocking assignments. Can it model registered (flip-flop) logic correctly?

  • Yes — blocking assignments can model registers
  • No — non-blocking assignments must be used for correct sequential logic
  • Yes, but only for synchronous resets
  • It depends on the simulator

Non-blocking assignments (<=) are the standard for sequential logic. They schedule the update to happen at the end of the time step, correctly modelling simultaneous register updates across many flip-flops.

Q4: What does the Verilog scheduler do between the active region and the NBA (non-blocking assignment update) region?

  • Executes $monitor callbacks
  • Processes blocking assignments from all always blocks
  • Evaluates all RHS of non-blocking assignments in the active region, then writes LHS values in the NBA region
  • Advances simulation time

The NBA region is where non-blocking LHS updates are applied after all active-region events settle. This ensures flip-flop outputs are stable before being read by other blocks in the same time step.

Q5: Which statement best describes when to use blocking vs. non-blocking assignments?

  • Blocking for combinational logic; non-blocking for sequential (registered) logic
  • Non-blocking for all logic; blocking is deprecated
  • Blocking for faster simulation; non-blocking for accuracy
  • They are interchangeable as long as you are consistent

The golden rule: use = in always_comb/initial blocks and <= in always_ff blocks. This maps cleanly to hardware intent and avoids race conditions.
