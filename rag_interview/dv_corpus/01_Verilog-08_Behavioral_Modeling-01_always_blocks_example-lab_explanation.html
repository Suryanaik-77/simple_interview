Demonstrates behavioral modeling in Verilog using always blocks for both combinational logic (always @(*)) and sequential logic (always @(posedge clk)), including procedural assignments, event controls, and common design patterns like multiplexers, counters, and ALUs.

🎯 What You'll Learn
  • Combinational vs sequential always blocks and their sensitivity lists
  • Blocking assignments (=) in combinational logic and non-blocking (<=) in sequential logic
  • Procedural control structures (if/else, case) within behavioral descriptions
  • Clock-driven design patterns and reset logic implementation
  • Multi-module testbench architecture with multiple DUT instantiations

🧠 Knowledge Check

Q1: In an event-driven simulator, what is a 'delta cycle'?

  • A unit of simulation time equal to 1 ps
  • A zero-time evaluation step used to propagate signal changes before advancing time
  • The time between two consecutive clock edges
  • A cycle used exclusively by non-blocking assignments

A delta cycle is a zero-time iteration that lets combinational effects propagate to a stable state before simulation time advances. Multiple delta cycles may occur at the same simulation time.

Q2: You have a bug where the testbench shows 'PASS' but the RTL is wrong. What is the most likely cause?

  • The simulator has a bug
  • The testbench does not exercise the faulty code path or does not check the output correctly
  • The compiler optimised away the bug
  • The clock period is too long

A WRONG_PASS result means the testbench lacks coverage of the faulty path or the checker does not verify the correct signal. Always review both stimulus and checker logic.

Q3: What does <code>$finish</code> do vs <code>$stop</code>?

  • Both terminate simulation identically
  • $finish exits the simulator; $stop pauses simulation (interactive mode)
  • $stop exits; $finish pauses
  • $finish only works in formal verification

$finish exits the simulation process. $stop pauses it and (in interactive simulators) drops you into a debug prompt.

Q4: When should you use <code>always_comb</code> instead of <code>always @(*)</code>?

  • Only for synchronous logic
  • always_comb is preferred in SV — it auto-infers sensitivity list, flags latches, and is synthesisable
  • They are identical — always_comb is just an alias
  • always_comb is for simulation only; always @(*) is for synthesis

always_comb is a SV construct that automatically computes the sensitivity list, warns if combinational feedback creates a latch, and communicates design intent to tools.

Q5: A module port is declared <code>output reg [7:0] data</code>. In an instantiation, what do you connect to it?

  • A parameter
  • A wire or reg from the parent scope — reg is fine for outputs
  • Only a wire — reg outputs cannot be connected to regs
  • Nothing — output ports cannot be connected

In Verilog, an output reg port drives a net at the boundary. The parent can connect any compatible net/variable. In SV, prefer output logic.
