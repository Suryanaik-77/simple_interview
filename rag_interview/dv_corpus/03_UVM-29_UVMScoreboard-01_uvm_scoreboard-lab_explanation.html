Golden Example
🧭 What this lab is

The reference lab drives an 8-bit registered adder DUT (add_dut) with 8 randomized operand pairs generated by add_sequence, then self-checks every completed operation in a scoreboard that receives transactions through a uvm_analysis_imp subscriber port and independently recomputes the expected sum.

💡 The concept

The core pattern is push-based TLM: a monitor observes DUT activity and calls write() on the scoreboard's analysis imp once per completed transaction — the scoreboard never polls or samples signals directly. Inside write(), the scoreboard runs a reference model (here, plain SystemVerilog addition, expected = t.a + t.b) that is written from the specification, completely independent of the DUT's implementation, and compares that expected value against the value the monitor observed on the DUT (t.res). This independence is what makes the check meaningful: if the reference model were derived from the DUT's logic, a shared bug would never be caught.

⚙️ How it works

add_item (extends uvm_sequence_item) carries rand bit [7:0] a, b for stimulus and a bit [8:0] res field that only gets populated once the monitor observes the DUT's output — the driver only ever fills in a/b. add_sequence loops 8 times, creating an add_item, randomizing it, and running it through start_item/finish_item on the sequencer. add_driver (a uvm_driver #(add_item)) pulls items off the sequencer and drives them onto vif, the virtual add_if handle obtained from uvm_config_db. The DUT, add_dut, is a simple registered adder: on every clock its always_ff block sets intf.sum <= intf.a + intf.b and propagates valid_in to valid_out. The scoreboard subscribes via uvm_analysis_imp #(add_item, my_scoreboard) imp; its write(add_item t) callback computes the reference-model expected value and calls compare(expected, t.res), and report_phase summarizes match/mismatch counts as TEST PASSED/TEST FAILED with a UVM_ERROR tally. tb_top provides the clock, instantiates add_if/add_dut, publishes the virtual interface via uvm_config_db#(virtual add_if)::set, and calls run_test("scoreboard_test") under a uvm_fatal safety timeout.

🎯 What you'll learn
  • Wiring a uvm_analysis_port (monitor) to a uvm_analysis_imp (scoreboard) in connect_phase
  • Implementing a write() callback that runs an independent reference model per transaction
  • Keeping stimulus generation (sequence/driver) architecturally separate from checking (monitor/scoreboard)
  • Using report_phase and the UVM error count to produce a deterministic pass/fail verdict
⚠️ Common mistakes
  • Deriving the scoreboard's reference model from the DUT's own RTL logic instead of the specification, so a shared bug is never caught
  • Caching or reusing state across write() calls (e.g. comparing against a value left over from a previous transaction) instead of computing everything the current transaction needs within the same callback
