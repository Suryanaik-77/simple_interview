🧭 What this lab is

25_SystemVerilog_callback.sv builds a callback_base hierarchy and exercises it through callback_demo and observer_demo (instantiated as u_callback/u_observer in tb_25_SystemVerilog_callback), layering a default no-op callback, a data-modifying callback, a threshold-based stopping callback, and a statistics-collecting callback on top of the same abstract interface.

💡 The concept

The pattern starts with callback_base, a virtual class that cannot be instantiated directly and declares three pure virtual functions: pre_operation, post_operation, and should_continue. Every concrete callback must implement all three, which guarantees any object holding a callback_base handle can call these methods polymorphically regardless of which concrete callback is plugged in. pre_operation/post_operation take data by ref, so a callback can actually mutate the value the host is operating on rather than just observing it. should_continue lets a callback influence control flow — a stopping callback can tell its host to halt after some condition. Each callback also gets a unique callback_id from the shared static int callback_id_counter, useful for identifying which instance produced which $display message when several callbacks are chained.

⚙️ How it works

callback_base defines the contract (pre_operation, post_operation, should_continue) and auto-assigns callback_id in new() from callback_id_counter. default_callback implements all three as pass-through logging ($display of data in hex) and always returns 1 from should_continue. modify_callback adds mask/xor_val fields with defaulted constructor arguments, intended to transform data in its pre_op... override. Inside tb_25_SystemVerilog_callback, two more callbacks are defined directly in the testbench: conditional_callback tracks a threshold and stop_count, flags in pre_operation when data > threshold, and its should_continue returns (stop_count < 3) so it stops the host after three violations. statistics_callback accumulates sample_count, sum, min_val, and max_val across every pre_operation call and exposes a report() function that computes the average via real'(sum) / real'(sample_count).

🎯 What you'll learn
  • Declaring an abstract callback API with virtual class + pure virtual function so every implementation is forced to honor the same interface
  • Using ref arguments in callback methods so a callback can transparently modify caller data (as in modify_callback/pre_operation)
  • Letting a callback influence control flow through a should_continue()-style return value (see conditional_callback)
  • Accumulating cross-call state inside a callback object (statistics_callback's running sum/min_val/max_val) instead of in the host
⚠️ Common mistakes
  • Forgetting a callback method is pure virtual and must be overridden in every derived class, causing elaboration/compile failure
  • Passing callback data by value instead of ref and then expecting a modifying callback (like modify_callback) to actually change the caller's variable
