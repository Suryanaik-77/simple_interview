🧭 What this lab is

Tasks.sv and tb_Tasks.sv walk through task fundamentals from a plain package task, through class-based tasks (instance, static, and ref-argument variants), to testbench-only tasks that use timing control and fork-join constructs, all invoked from the tb_Tasks initial block.

💡 The concept

A task's argument list can mix input, output, and ref directions, letting one call both consume and return multiple values - something a function cannot do as cleanly. Because tasks can block on time or events, automatic matters: a module-level task defaults to static storage, so if two calls could overlap in time they would clobber each other's locals unless declared automatic. Class methods declared as task behave like automatic per-object calls by default, and static task shares one copy of storage across all instances of the class.

⚙️ How it works

tasks_pkg::simple_task is an automatic task that just prints its input with $time, showing a task that consumes no simulated time but still benefits from being automatic. tasks_pkg::compute_stats takes an input int values[] and three output int arguments (sum, average, min_val, max_val), looping with foreach (values[i]) to accumulate results - a canonical multi-output task. The TaskDemo class has display_info (a plain class task), modify_array (an automatic task taking ref int arr[] and doubling each element in place), and static_task (a static task shared across instances). demo_basic_tasks, demo_stats_task, and demo_modify_array are functions that call these tasks and print results. In tb_Tasks, the DUT-like helper module task_testbench_demo (instance tb_tasks) exposes tasks called hierarchically from the initial block: tb_tasks.wait_cycles(5), tb_tasks.send_data(8'hAB), tb_tasks.send_burst(3), tb_tasks.parallel_ops() (a fork...join task), and tb_tasks.race_ops() (a fork...join_any task). The testbench also drives rtl_task_example (rtl_dut) by pulsing start with din set, then uses wait(done) to catch the single-cycle done pulse before sampling dout.

🎯 What you'll learn
  • Using output/ref arguments so one task call can return several computed values, as in compute_stats
  • Choosing automatic for reentrant/time-consuming tasks versus static for shared-state tasks like static_task
  • Calling tasks hierarchically across module instances (tb_tasks.wait_cycles(5)) to drive a DUT
  • Using fork...join versus fork...join_any (parallel_ops vs race_ops) to control when parallel branches synchronize
⚠️ Common mistakes
  • Forgetting automatic on a module-level task that consumes time - without it the task defaults to static storage and concurrent/overlapping calls corrupt each other's local variables
  • Calling wait() on a pulse signal after the pulse already occurred, as the testbench comment notes for wait_for_reset() - the wait blocks forever (or is skipped) because the edge already passed
