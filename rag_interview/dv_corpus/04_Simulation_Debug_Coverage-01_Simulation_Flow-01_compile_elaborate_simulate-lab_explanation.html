🧭 What this lab is

This lab walks through the three stages every RTL simulation goes through — compile, elaborate, and simulate — using a small, deterministic device-under-test: counter_flow, a 4-bit synchronous up-counter. A self-checking testbench, tb_counter_flow, drives it and confirms every count against a reference model, so the focus stays on the flow and its controls rather than on complex logic.

💡 The concept

A simulator turns source into results in stages. Compilation parses each .v/.sv file into an internal representation and reports syntax errors. Elaboration builds the design hierarchy — instantiating modules, resolving port connections, and sizing nets — producing a runnable model (VCS emits the simv binary here). Simulation then executes that model over time, evaluating events and running the testbench. VCS folds compile+elaborate into the single vcs command that produces simv; running ./simv is the separate simulate stage. Xcelium's xrun performs all three in one invocation. Runtime behaviour is tuned with plusargs — here +NUM_CYCLES=<n> sets the run length without recompiling.

⚙️ How it works

counter_flow resets synchronously to 0 (reset has priority), counts up by one only while en is high, and holds otherwise, wrapping naturally at 4 bits. The testbench builds an identical ref_count reference model, holds reset for two clocks, then drives a deterministic enable pattern (high except every 4th cycle) for NUM_CYCLES cycles. One delta after each rising edge it compares count against ref_count; a mismatch prints a line beginning FAIL:, and a clean run prints RESULT: TEST PASSED. That single, greppable verdict line is what common/evaluate.mk reads to decide PASS/FAIL. Run it with ./run.sh vcs (or make), and try NUM_CYCLES=40 ./run.sh vcs to see the plusarg change the run length.

🎯 What you'll learn
  • The distinct roles of the compile, elaborate, and simulate stages and where each error surfaces
  • How VCS (two-step: vcs then ./simv) and Xcelium (single-step xrun) map onto those stages
  • Passing runtime configuration into a simulation with plusargs (+NUM_CYCLES) instead of recompiling
  • Why a self-checking testbench prints one machine-readable verdict line that a verify flow can score
⚠️ Common mistakes
  • Confusing a compile error (bad syntax, caught by vcs) with an elaboration error (unconnected/misnamed port, caught while building simv)
  • Editing the source but re-running the old simv without recompiling, so the change never takes effect
  • Expecting a plusarg to work when the testbench never reads it via $value$plusargs
