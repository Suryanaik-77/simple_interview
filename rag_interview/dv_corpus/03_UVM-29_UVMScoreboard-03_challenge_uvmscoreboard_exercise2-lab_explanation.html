🧭 What this challenge is

Same DUT and stimulus setup, but the scoreboard keeps its expected value in a single scalar (prev_expected) and updates it in the wrong order relative to the compare.

💡 The concept being tested

Tests understanding that write() must compute and compare each transaction's expected value entirely within that same callback — any cached/scalar state left over from the previous call introduces an off-by-one comparison.

🛠️ Debugging Guide
🔴 Symptom — what you see when you run it

report_phase prints TEST FAILED; every transaction mismatches in a deterministic, systematic way (operand pairs are chosen with strictly increasing sums so the staleness is guaranteed to be visible).

🔎 How to investigate
  1. Run the simulation and observe that every single transaction mismatches, not just a random subset — this pattern suggests a structural/ordering bug rather than a one-off calculation error.
  2. Open the scoreboard's write() method and find the two key statements: the compare/if (t.res !== prev_expected) check and the prev_expected = t.a + t.b assignment.
  3. Trace the order of execution: is prev_expected used in the compare before or after it gets updated for the current item's operands?
  4. Consider what value prev_expected actually holds at the moment of comparison — whose transaction does it belong to?
🧭 Fix direction

Reorder write() so a local expected value is computed from THIS transaction's operands (t.a + t.b) and compared immediately, rather than comparing against the stale prev_expected scalar left over from the prior call.

✅ How to confirm your fix

Re-run the simulation: all 8 transactions should now be checked against their own operands, matching every time, with report_phase printing TEST PASSED and UVM_ERROR : 0.
