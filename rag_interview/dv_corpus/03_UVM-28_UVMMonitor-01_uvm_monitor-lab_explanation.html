Golden Example
🧭 What this lab is

The reference lab builds a tiny registered 8-bit adder DUT (add_dut) driven by add_driver through the add_if interface, then relies on a monitor to reconstruct each add_item transaction (a, b, sum) from the pins and publish it over an analysis port so a counting subscriber can confirm all items were seen.

💡 The concept

The monitor's job is strictly observe-then-publish: it must never write to add_if signals, only read them. It waits out reset (rst_n), then on every clock edge checks the DUT's output-valid handshake before treating sum as meaningful, since add_dut registers sum and valid_out one cycle after a, b, and valid_in are presented. Once a transaction is complete, the monitor packages it into an add_item and calls ap.write(tr) on its uvm_analysis_port, which fires that transaction out to every connected subscriber in the same delta cycle, with no return value and no knowledge of who is listening.

⚙️ How it works

In tb_top.sv, the add_if interface carries clk, rst_n, a, b, valid_in, sum, and valid_out between add_dut and the testbench; add_dut is a simple always_ff adder that registers intf.sum <= intf.a + intf.b and intf.valid_out <= intf.valid_in on each clock. tb_top publishes the virtual interface with uvm_config_db#(virtual add_if)::set(null, "*", "vif", intf) and starts run_test("monitor_test"). In monitor_pkg.sv, add_sequence::body() creates 8 randomized add_item transactions (fields a, b, with sum left for the monitor to fill in) and sends them through start_item/finish_item. add_driver fetches the same vif via uvm_config_db#(virtual add_if)::get(...) and drives a, b, and valid_in from each item. The monitor (declared later in the same package) fetches the identical vif, waits for rst_n to deassert, then each cycle samples pins and, once the DUT's valid_out confirms sum is valid, builds an add_item and calls ap.write(tr) to publish it. Downstream, a uvm_subscriber-based component's write() callback increments a transaction counter so monitor_test's report_phase can print a clear PASS once all 8 items are accounted for.

🎯 What you'll learn
  • How to structure a monitor's run_phase around wait-for-reset then sample-on-clock
  • Why a monitor must key off a DUT's output-valid signal rather than its input-valid signal when the DUT is registered
  • How uvm_analysis_port and ap.write(tr) decouple a monitor from its subscribers
  • How a uvm_subscriber's write() callback is used to passively count or check transactions
⚠️ Common mistakes
  • Sampling outputs on the same cycle inputs are presented, ignoring that the DUT registers its result a cycle later
  • Building the transaction object correctly but forgetting to call ap.write(tr), so subscribers never see anything even though the monitor itself looks correct
