🧭 What this lab is

The reference lab's tb_top.sv prints a walkthrough of the uvm_heartbeat API (new, set_mode, set_heartbeat, add, remove, start, stop) and then runs one of several tests defined in test.sv, each exercising a different aspect of heartbeat monitoring using two helper components, hb_component and limited_component.

💡 The concept

The core idea demonstrated is that a uvm_heartbeat object is bound to a uvm_objection and a list of components; on each heartbeat event it checks that the components it is tracking raised that objection recently. hb_component models a healthy component that keeps raising hb_obj forever in run_phase, while limited_component models a component that raises the objection only max_count times and then goes quiet — simulating a hang the heartbeat is supposed to catch. The three modes (UVM_ALL_ACTIVE, UVM_ONE_ACTIVE, UVM_ANY_ACTIVE) described in tb_top.sv change how strict the check is across multiple registered components.

⚙️ How it works

hb_component holds a uvm_objection hb_obj handle, a delay (default 40) and an enable bit; its run_phase runs a forever loop that waits #delay, then — if enable is set and hb_obj is non-null — calls hb_obj.raise_objection(this) and logs raised objection #%0d via uvm_info using an incrementing count. limited_component is similar but uses repeat(max_count) instead of forever, so after max_count (default 3) raises it logs Stopped raising objections - simulating hang and returns, deliberately going silent so tests like fail_test can show the heartbeat catching a stalled component. base_test extends uvm_test, raises its own phase objection in run_phase, and prints header info before/around the demo. Other tests referenced by tb_top.sv (success_test, fail_test, mode_any_active_test, mode_one_active_test, mode_all_active_test) build on these two components, wiring their hb_obj handles to a shared uvm_objection, registering them into a uvm_heartbeat via set_heartbeat/add, and picking a mode with set_mode to show the pass (always-active) versus fail (component stops, UVM_FATAL-style failure) behavior.

🎯 What you'll learn
  • How to wire a shared uvm_objection handle into multiple components so a uvm_heartbeat can watch their activity
  • How to register components with uvm_heartbeat using set_heartbeat/add and start/stop monitoring at the right phase
  • How to choose between UVM_ALL_ACTIVE, UVM_ONE_ACTIVE, and UVM_ANY_ACTIVE modes depending on how strict the liveness check needs to be
  • How to simulate a hang deliberately (like limited_component's repeat(max_count)) to validate that a watchdog mechanism actually fires
⚠️ Common mistakes
  • Creating a uvm_heartbeat and calling set_heartbeat but forgetting to add every component you actually want monitored, leaving the heartbeat with an empty (or partial) component queue
  • Letting a component's hb_obj stay null (e.g. a config_db lookup that silently fails) so it never raises the shared objection, making the heartbeat think nothing is alive even though the component is fine
