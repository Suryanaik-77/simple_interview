🧭 What this challenge is

The same 4-bit counter and self-checking testbench from the guided lab, with a different one-line bug planted in counter_flow.v. Run the flow, read the mismatch, locate the bug in the RTL, and fix it so the run ends in RESULT: TEST PASSED.

💡 The concept being tested

Whether the counter advances by the correct step. The enable gating is correct here, but the increment amount is wrong — the kind of off-by-a-constant error that compiles cleanly and only shows up as a growing numeric divergence at simulation.

🛠️ Debugging Guide
🔴 Symptom — what you see when you run it

The testbench prints FAIL: lines only on enabled cycles, e.g. FAIL: cycle 3 - expected count=1, got count=2, and the gap grows: expected 2 vs got 4, expected 3 vs got 6. The DUT is counting in the right places but by twice as much each step.

🔎 How to investigate
  1. Notice the mismatch is not a wrong time (enable gating is fine) but a wrong magnitude — got is always double expected.
  2. Open counter_flow.v and read the enabled-count branch: else if (en) count <= count + 4'd2;.
  3. Check it against the spec in the header comment: "stepping by exactly ONE each enabled clock."
  4. Confirm the increment constant is the culprit.
🧭 Fix direction

Change the increment from count + 4'd2 to count + 4'd1 so the counter advances by one per enabled clock.

✅ How to confirm your fix

Re-run ./run.sh vcs (or make). The FAIL lines should disappear and the run should end with RESULT: TEST PASSED; verify then reports the sequence as passed.
