Challenge Problem

INDEPENDENT WORK

You will now independently perform the complete Floorplan stage for the iguana_soc design. This is a larger SoC design with its own netlist, macro placement DEF, and power plan. All required inputs are provided in the inputs/ directory.

Using the concepts and commands learned in the Guided Testcase, write your complete floorplan script from scratch into ../scripts/script.tcl. No step-by-step guidance is provided here — apply what you know.

Key difference from the guided testcase: iguana_soc is a full system-on-chip with more macros and a larger netlist than the tile processor core. The same flow applies — the parameters (side ratio, core offset, cell names, boundary coordinates) will differ to match this design's inputs.

📋 Requirements & Deliverables

Your floorplan script must accomplish all of the following:

  • Open iguana_soc.ndm and load the init_design block.
  • Initialize the floorplan with appropriate side ratio, core offsets, and core utilization.
  • Create a pin guide and place all design ports on a legal boundary layer.
  • Set correct routing directions for all metal layers.
  • Set the min/max routing layers using set_ignored_layers.
  • Import macro placement from floorplan.def.
  • Insert boundary (endcap) cells and run check_boundary_cells.
  • Create VDD and VSS nets, ports, and connect all PG pins.
  • Set required app options for PG routing.
  • Source power_plan.tcl to build the complete power grid.
  • Insert well-tap cells at the correct spacing and pattern.
  • Reconnect PG nets after tap cell insertion.
  • Save the block as floorplan inside outputs/iguana_soc.ndm.
  • Generate all five quality reports in reports/.

💡 Hints

Hint 1 — Where to find cell names for boundary and tap cells
The library and cell names for boundary and tap cells are the same as in the guided testcase — iguana_soc uses the same TSMC 28nm HVT library (tcbn28hpcplusbwp40p140hvt). Use BOUNDARY_LEFTBWP40P140, BOUNDARY_RIGHTBWP40P140, and TAPCELLBWP40P140.
Hint 2 — initialize_floorplan parameters
Use the following command to initialize the floorplan for iguana_soc: 
initialize_floorplan -side_ratio {1 1} -core_offset {0.84 0.9} -core_utilization 0.7
{1 1} gives a square core. -core_offset {0.84 0.9} sets the gap between core and die boundary (left/right 0.84 µm, top/bottom 0.9 µm). 70% utilization leaves enough headroom for routing and clock tree buffers.
Hint 3 — create_pin_guide boundary coordinates
The port placement guide boundary and layer for iguana_soc are: 
create_pin_guide -boundary {{1022.3100 1081.7450} {383.7500 1151.3750}} \
    -layers {M6} -name O [get_ports *]
place_pins -ports [get_ports *]
These coordinates define the region on the top edge of the block where all ports will be placed on M6. Run place_pins immediately after to apply the guide.

📚 Knowledge Assessment Quiz

1. While running the iguana_soc floorplan, check_pg_drc reports spacing violations on M5 near two adjacent SRAM macros that are placed very close together. What should you investigate first?

  • Reduce M5 stripe pitch from 7 µm to 3.5 µm so stripes avoid the gap between the two macros.
  • Check whether the routing blockages on M5 around each macro's keepout margin were properly created — they may overlap or miss the region between the two macros, allowing M5 stripes to route into a restricted zone.
  • Remove the M5 layer from the power grid entirely and rely on M4 and M6 for those areas.
  • Change the SRAM macros to a different orientation (FN instead of N) to move their PG pins away from the gap.
Correct! When two macros are closely placed, the routing blockages created from each macro's keepout margin may leave a gap between them where the PG router still routes M5 stripes — and those stripes may violate spacing to the adjacent macro keepout boundary. Review and extend the routing blockage definitions in power_plan.tcl to fully cover the channel between closely-placed macros.

2. You set -core_utilization 0.85 for iguana_soc. After running the complete flow, placement reports very high congestion and the router cannot complete. What was the most likely consequence of high utilization?

  • The power grid was too dense and blocked all signal routing resources.
  • The tap cell spacing of 30 µm was violated because there was not enough space for tap cells at high utilization.
  • With only 15% of the core area free, there were insufficient routing channels for clock tree buffers, hold buffers, and signal wires — leading to unroutable congestion hotspots.
  • ICC2 cannot save the block as a floorplan when utilization exceeds 80%.
Correct! 85% core utilization leaves only 15% of the core area for routing. Complex designs like iguana_soc require significant free space for: signal routing tracks, clock tree buffers inserted by CTS, hold buffers inserted during placement optimization, and ECO changes during timing closure. Starting at 85% almost always results in routing congestion failures. The recommended starting point is 65–70% for complex SoC designs.

3. check_pg_connectivity reports "Number of floating hard macros: 3" for VDD. You confirm the macros are present in the design and their connect_pg_net command ran. What is the next thing to check?

  • Re-run initialize_floorplan to recreate the site rows — the macros may have been placed outside the legal routing grid.
  • Check whether the via creation step from macro M4 pins to M6 stripes completed successfully, and verify the M6 stripes actually pass over those three macros.
  • The three macros are likely from a different library that uses a different power net name (e.g., AVDD) — check the NDM and add a separate connect_pg_net call.
  • Increase M4 mesh pitch to ensure stripes reach those macro locations.
Correct! The most common cause of floating hard macros after power planning is a failed or incomplete via creation between macro PG pins (M4) and the PG stripe above (M6). Check: (1) Did create_pg_vias for macro pins complete without errors? (2) Do M6 stripes actually pass over the three macro locations (the -extension and blockage settings might prevent this)? (3) Are the macro PG pins correctly named VDD/VSS in the NDM?

4. You run check_pin_placement -self and find 12 "Technology Spacing" violations where two ports are too close together on M6. What is the best approach to fix this?

  • Move the port violations to M7 by changing -layers {M7} in create_pin_guide — M7 has more relaxed spacing rules.
  • Widen the pin guide boundary to give place_pins more edge length to spread the ports, reducing the density that causes spacing violations.
  • Remove the pin guide and let ICC2 place ports anywhere on the die boundary without a constraint.
  • Run create_pin_guide a second time with a different boundary to override the first guide.
Correct! Technology Spacing violations on ports mean the ports are packed too densely. The number of ports, the metal pitch, and the guide boundary length determine port density. If the boundary is too narrow, ports are forced close together violating the minimum spacing rule. Widening the pin guide boundary gives place_pins more edge length to distribute the same number of ports at a lower density, resolving the violations.
