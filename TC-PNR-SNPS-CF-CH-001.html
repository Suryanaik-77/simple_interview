📚 Knowledge Assessment Quiz

1. You run create_stdcell_fillers but the log shows that after inserting FILL64, FILL32, and FILL16 cells, thousands of 1-site gaps remain unfilled and check_legality reports violations. What is the most likely cause?

  • The filler cells were sorted in ascending order instead of descending — large fillers ran out before the 1-site gaps could be filled.
  • The -lib_cell option was omitted, so ICC2 used the default filler set which does not include 1-site or 2-site cells.
  • The filler cell list is missing the smallest sizes (FILL3, FILL2, FILL1 or equivalent) — ICC2 can only fill a gap with a cell whose width matches or is smaller than the gap. Without 1-site and 2-site cells in the list, single-site gaps at the ends of rows cannot be filled, leaving legality violations.
  • The NDM library was not refreshed after filler insertion; ICC2 requires a save_lib before check_legality can see the new cells.
Correct! ICC2 fills gaps by matching cell width to gap size. If only large filler cells (FILL64–FILL16) are provided, all gaps wider than those cells are filled, but residual 1-site and 2-site gaps at row ends are left empty. Always include the full size range down to FILL2 (or FILL1 if available) to ensure complete row filling. Legality violations from unfilled gaps show up as site-occupancy errors.

2. After running chip finish on iguana_soc, check_lvs reports 847,000 "open" errors — all on power/ground pins of filler cells. What step was most likely skipped?

  • route_detail -incremental true was not run — the routing DRC engine fails to connect power pins when there are unresolved short violations.
  • connect_pg_net was not run after create_stdcell_fillers. Filler cells expose VDD and VSS pins, but those pins are not automatically connected to the power grid. connect_pg_net walks the design and hooks each filler's power pins to the nearest net segment of the appropriate net (VDD or VSS). Without it, every filler cell pin is floating — causing an LVS open for each one.
  • change_names -rules verilog renamed power nets, breaking the LVS connectivity comparison between the schematic net name and the layout net name.
  • The LVS netlist was written before filler insertion, so the physical database has filler cells but the netlist does not — creating a count mismatch that ICC2 reports as opens.
Correct! connect_pg_net must always follow create_stdcell_fillers. Filler cells have explicit VDD and VSS pins on their top-level ports. These pins need to be formally connected to the power grid nets in the ICC2 database. Without connect_pg_net, the power pins exist physically (the metal is there) but are not logically assigned to any net in the connectivity graph — so LVS sees them as disconnected pins and reports one "open" per pin on every filler cell.

3. What is the difference between the LEC Verilog netlist and the LVS Verilog netlist written by chip finish — and why do they use different -exclude options?

  • The LEC netlist is flat (single module) while the LVS netlist is hierarchical. The -exclude difference controls hierarchy preservation, not cell filtering.
  • The LEC netlist excludes timing-critical paths so the equivalence checker runs faster; the LVS netlist retains all timing paths for accurate resistance extraction.
  • The LEC netlist excludes all physical-only cells (fillers, end-caps, well-taps, pad spacers, pg_objects) because the synthesis reference netlist has no equivalent for these cells — their presence in the implementation netlist causes false unmatched-point failures in Formality/Conformal. The LVS netlist keeps all physical cells (excludes only empty_modules) because Calibre LVS must extract connectivity from every cell that physically exists in the layout — missing a physical cell in the netlist creates a false open in LVS comparison.
  • Both netlists use the same -exclude options; the difference is only in the output filename — one uses .v and the other uses .lvs.v to indicate which tool should use it.
Correct! LEC and LVS serve opposite purposes: LEC compares logic only and needs a netlist that perfectly matches the synthesis reference (no extra physical cells). LVS verifies physical connectivity and needs every cell instance in the layout to be present in the netlist (all physical cells included). Using the same netlist for both would cause either false LEC failures (if physical cells are included) or false LVS opens (if physical cells are excluded). Two separate write_verilog calls with different -exclude options solve this by producing one netlist optimized for each downstream tool.

4. The iguana_soc report_timing.min shows 312 hold violations with WNS = −0.03 ns in the ffg0p99v125c_rcb scenario. Is this a blocker for chip finish sign-off?

  • Yes — any hold violation is a blocker. The chip will fail hold timing in fabricated silicon and the design must go back to post-route optimization before chip finish can complete.
  • Yes — but only if the violations are on paths that cross power domains. Hold violations within a single power domain can be waived.
  • Not necessarily — if these same hold violations existed in the postroute block before chip finish, they are pre-existing and not introduced by chip finish operations. Chip finish does not perform timing optimization; its job is to not worsen timing. If chip finish introduced no new hold violations and no new violating paths compared to the postroute block, it passes. Pre-existing hold violations are resolved in a targeted hold ECO before tape-out.
  • No — hold violations in the ffg (fast-fast-global) corner are always false positives caused by overly optimistic RC extraction. They can be ignored entirely regardless of count or severity.
Correct! Chip finish does not run timing optimization — it inserts fillers, metal fill, and writes outputs. Its timing gate is: "did chip finish introduce any new violations?" Compare the postroute block QoR to the chip_finish block QoR. If WNS, TNS, and violation count are the same (or better), chip finish passes. Pre-existing hold violations are the responsibility of a subsequent hold ECO pass, which inserts delay buffers on violating paths before tape-out. Blocking chip finish sign-off on pre-existing hold violations would incorrectly attribute those violations to the chip finish stage.
