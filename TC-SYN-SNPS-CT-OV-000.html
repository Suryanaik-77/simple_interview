📖 Theory and Background

What is Timing Intent Verification?

After reading RTL and elaborating a design, the synthesis tool needs to understand the timing intent of the design — which signals are clocks, how fast they run, when inputs arrive relative to clocks, and when outputs must be stable. All of this information is provided through the SDC (Synopsys Design Constraints) file.

The timing check command audits these constraints and reports any gaps. If an input port has no delay constraint relative to a clock, the tool does not know when data arrives and cannot perform accurate timing analysis. If a clock is missing entirely, registers driven by that clock will not be timed at all.

A clean timing check report (no warnings) is a critical milestone before proceeding with synthesis optimization and timing closure. Any missing constraint means the tool is guessing or ignoring timing paths, which leads to unreliable results.

Common Warning Categories

The timing check audits several categories of timing intent. The most common warnings you will encounter in this lab are:

Warning Category What It Means
Unconstrained endpoints Registers or output ports have no timing relationship defined — often because a clock definition is missing from the SDC
Inputs without clocked external delays Input ports do not have arrival time relationships defined relative to a clock — the tool cannot analyze input-to-register paths
Outputs without clocked external delays Output ports do not have required timing defined — the tool cannot analyze register-to-output paths
No driving cell / no transition Input ports have no driving cell specified — the tool cannot model how fast the input signal transitions
Outputs without external load Output ports have no load capacitance defined — the tool cannot accurately compute output delay
Sequential clock pins with multiple clock waveforms A register clock pin is reachable by more than one clock through a multiplexer — usually expected behaviour in muxed-clock designs

The Debugging Workflow

Fixing timing intent warnings follows a systematic loop:

  1. Run the timing check and read the warnings
  2. Pick a warning — identify which ports or registers are affected
  3. Trace the issue — find the clock source driving the affected register by working backwards from its clock pin
  4. Add the missing SDC constraint to the SDC file
  5. Re-run the timing check to confirm the warning is gone
  6. Repeat until the report is clean
Key insight: Each warning is a clue. The tool is telling you exactly what timing information is missing. Your job is to trace the issue back to its root cause and provide the correct SDC constraint.

Generated Clocks and Clock Muxes

Some designs contain clock dividers — flip-flops whose output is used as a clock for other registers. These derived clocks must be explicitly defined in the SDC so the tool knows the frequency relationship between the source clock and the derived clock.

Designs may also contain clock multiplexers that select between two clock sources. When the timing check reports “Sequential clock pins with multiple clock waveforms,” it means a register can be clocked by more than one clock through a mux. This is usually expected behavior — only one clock is active at a time depending on the control signal. These warnings can typically be waived after confirming the design intent.

🧠 Knowledge Assessment Quiz

Question 1: What is the purpose of the timing intent check in Design Compiler?

  • A. It runs the full timing analysis and reports setup/hold violations.
  • B. It audits the SDC constraints and reports any missing or incomplete timing intent.
  • C. It compiles the RTL into a gate-level netlist.
  • D. It generates the final timing signoff report.

Correct! The timing intent check verifies whether all ports, clocks, and endpoints have proper timing constraints defined in the SDC. It does not run actual timing analysis — it only verifies the timing intent is complete.

Question 2: What does the warning “unconstrained endpoints” typically indicate?

  • A. The output ports have too much capacitive load.
  • B. The RTL has a syntax error.
  • C. Registers or output ports are not timed because a clock definition or output delay is missing.
  • D. The technology library is incompatible with the design.

Correct! Unconstrained endpoints mean the tool has no timing requirement for those registers or ports — usually because a clock or output delay constraint is missing from the SDC.

Question 3: Why might a register appear under “unconstrained endpoints” even after primary clocks are defined?

  • A. The register has a timing violation.
  • B. The register is not used in the design.
  • C. The register is clocked by a generated clock (e.g., from a divider) that has not been defined in the SDC.
  • D. The register has a reset signal connected.

Correct! If a register is driven by a derived clock from a divider circuit, defining only the primary clock is not enough. The generated clock must also be explicitly defined in the SDC so the tool knows those registers are timed.

Question 4: Why is a clean timing check report important before proceeding with synthesis?

  • A. It is required to generate the GDSII output file.
  • B. It proves the design has no functional bugs.
  • C. It is only needed for place-and-route, not synthesis.
  • D. Missing constraints mean the tool is guessing or ignoring timing paths, leading to unreliable optimization results.

Correct! If timing constraints are incomplete, the synthesis tool cannot accurately optimize the design. Unconstrained paths may be over- or under-optimized, leading to timing failures that only surface later in the flow.
