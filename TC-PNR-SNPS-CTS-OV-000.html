📘 Theory and Background

What is Clock Tree Synthesis?

After placement, every flip-flop in the design needs to receive its clock signal at nearly the same time — otherwise, data may be captured before it is valid (hold violation) or arrive too late (setup violation). CTS is the stage that builds a physical clock distribution network — a tree of buffers and inverters — so that the clock arrives at every flip-flop with controlled latency and minimal skew.

  • Clock skew — the difference in arrival time of the clock at two different sink pins. Ideally zero; in practice kept below ~100 ps.
  • Clock latency — the total time from the clock source pin to a flip-flop clock pin. Includes source latency (PCB/package) and network latency (the clock tree).
  • Clock transition — the rise/fall time of the clock signal at each sink. A slow transition degrades setup slack because the flip-flop sampling window is wider.

Why CTS Is Done After Placement

  • The CTS engine needs to know the physical location of every flip-flop to build a balanced tree — locations are only finalized after placement.
  • During placement, clocks are treated as ideal (zero latency, zero skew). Hold violations under ideal clocks are meaningless — they will be fixed in post-CTS optimization when real skew is known.
  • The clock tree itself occupies routing resources. Planning it before signal routing ensures clock nets get priority access to wide NDR routing tracks.

Why Special Clock Cells (CK*)?

Regular combinational cells (e.g., BUF, INV) suffer from duty cycle distortion — their rise and fall delays are unequal due to different PMOS/NMOS transistor sizing. When such cells are placed in the clock tree, the 50% duty cycle of the clock degrades with every level of buffering. Clock-specific cells (CKBD*, CKND*) are designed with matched PMOS/NMOS to preserve duty cycle through the entire tree.

Why LVT clock cells? LVT cells switch faster, reducing clock network latency and transition times. In the tile design, only LVT variants of CK* cells are used in the clock tree: CKBD4/8/12/16BWP40P140LVT (buffers) and CKND4/8/12/16BWP40P140LVT (inverters). The higher leakage of LVT is acceptable for clock cells since there are relatively few of them compared to the data path.

Non-Default Routing (NDR) Rules for Clock Nets

Clock nets require more robust routing than signal nets because clock DRCs cause timing failures across the entire design. NDR rules apply wider wire widths and wider spacing specifically to clock nets:

Rule NameWidth MultiplierSpacing MultiplierApplied ToLayer Range
cts_2w2s2x2xRoot & Internal netsM4–M7
cts_1w2s1x (default)2xSink netsM3–M6
  • Root/Internal nets — high-drive, long-wire segments near the clock source. Double-width double-spacing reduces resistance and improves SI.
  • Sink nets — short last-mile wires to each flip-flop. Double-spacing alone prevents coupling noise from adjacent data nets.
  • M4–M7 for root/internal — upper metal layers for long horizontal runs with lower resistance per unit length.
  • M3–M6 for sink — lower layers for short local connections to flip-flop clock pins.

CCD — Concurrent Clock and Data Optimization

CCD (clock_opt.flow.enable_ccd true) is ICC2's technique for jointly optimizing the clock tree shape and data path timing in a single pass. Instead of first building a perfectly balanced tree and then optimizing data timing, CCD intentionally introduces useful skew — it slightly delays the clock arrival at the launch flip-flop or advances it at the capture flip-flop to borrow time on critical setup paths. This is the opposite of what is done in a balanced tree approach.

Key trade-off: CCD improves setup WNS by using skew to relax tight paths, but it requires hold fixing to compensate for the deliberately introduced skew mismatch. This is why both setup and hold scenarios must be active when CCD is used — hold fixing happens in the final_opto phase of clock_opt.

Two-Phase clock_opt Flow

The ICC2 clock_opt command runs in distinct phases. In the tile CTS script, it is called twice:

Phase RangeWhat It Does
build_clock → route_clockSynthesizes the clock tree (places buffers/inverters), legalizes them, and routes the clock nets using NDR rules.
final_optoPost-CTS timing optimization: fixes hold violations, improves setup WNS, and sizes data-path cells with a propagated-clock timing model.

The split into two calls lets you insert tie cells and update prefixes between the clock build phase and the final optimization phase.

Propagated Clocks and IO Latency

  • set_propagated_clocks [all_clocks] — Switches timing analysis from ideal clock mode (used at placement) to propagated mode. ICC2 now uses the actual clock tree insertion delays when computing setup/hold slack. This is the permanent switch — all STA from this point forward uses real clock latencies.
  • compute_clock_latency — After the clock tree is built and propagated, this command calculates the clock network latency seen at IO ports and updates the input_delay/output_delay constraints to reflect the actual clock latency. This is critical for interface timing paths (paths from/to chip IOs) that reference the same clock.

📄 CTS Flow Steps

The steps below outline the ICC2 CTS flow used in the tile design.

STEP 1 Open the placed NDM block and activate all MMMC scenarios (both setup and hold).
STEP 2 Configure instance name prefixes for CTS buffers and optimization cells.
STEP 3 Set lib-cell purposes — exclude all cells from CTS use, then include only the approved LVT clock cells. Run derive_clock_cell_references.
STEP 4 Create NDR routing rules and assign them to clock net types (root, internal, sink) with layer constraints.
STEP 5 Set CTS optimization targets: skew, latency, max transition. Apply clock uncertainty values for setup and hold analysis.
STEP 6 Run pre-CTS checks (check_clock_trees) to catch constraint and cell issues before the build phase.
STEP 7 Run clock_opt -from build_clock -to route_clock to synthesize and route the clock tree.
STEP 8 Enable hold cells, run clock_opt -from final_opto -to final_opto to fix hold violations and improve setup timing.
STEP 9 Insert tie cells, switch to propagated clock mode, update IO latency, and save the block as cts.
STEP 10 Generate clock QoR reports, timing reports (setup and hold), constraint violation reports, utilization, congestion, and legality reports.

📝 Knowledge Assessment Quiz

Test your understanding of the CTS concepts above. Click on your answer.

1. Why are hold scenarios activated during CTS but not during placement?

  • Hold violations cannot be fixed during placement because delay cells are not available in the lib cell library at that stage.
  • During placement, clocks are ideal (zero skew), so hold analysis is meaningless — hold violations only appear when there is real clock skew, which only exists after the clock tree is built at CTS.
  • ICC2 automatically activates hold scenarios during clock_opt regardless of the user setting, so it does not matter what the scenario status is before CTS.
  • Hold scenarios require propagated clocks to run, and ICC2 refuses to activate them until set_propagated_clocks is called first.
Correct! Hold timing violations depend on the difference in clock arrival time between the launch and capture flip-flops (clock skew). Under ideal clock propagation — used during placement — skew is zero by assumption, so hold violations computed at this stage are meaningless and would cause ICC2 to insert hold buffers on paths that do not actually need them. Once CTS builds the real clock tree and introduces real skew, hold analysis becomes valid and hold fixing is performed in the final_opto phase.

2. Why are only LVT variants of clock cells (CKBD*LVT, CKND*LVT) used in the clock tree, while LVT cells were excluded from data path optimization during placement?

  • LVT cells are only qualified for clock nets in the PDK — the foundry prohibits using them on data paths for reliability reasons.
  • Clock cells are relatively few in number, so their leakage power impact is small and acceptable. LVT speed is needed to meet tight clock transition targets and keep the clock tree compact. Data paths use far more cells, so free LVT use there would blow up static power.
  • ICC2 automatically selects SVT cells for data paths and LVT cells for clock trees based on internal heuristics — no user configuration is needed.
  • LVT cells have better duty cycle characteristics than SVT cells, which is why they are required specifically for clock buffers to preserve the 50% duty cycle.
Correct! A typical design with 100,000 flip-flops might use only 400–500 clock repeater cells (as seen in the tile design with 452 repeaters). The leakage power from 500 LVT cells is negligible compared to hundreds of thousands of data path cells. LVT speed is critical for clock trees because clock transitions must be fast (target <0.28 ns in the tile design) and latency must be minimized. Using LVT freely on data paths during placement would add thousands of LVT cells, often exceeding the leakage power budget before any power analysis has been done.

3. What does compute_clock_latency do and why is it needed after CTS?

  • It rebalances the clock tree to equalize latency across all sinks after the initial clock_opt run.
  • It computes the maximum clock tree latency and automatically adjusts the SDC clock period to match it.
  • It updates the IO path timing constraints to reflect the actual clock network latency, so that interface paths (from/to chip IOs) are analyzed with the correct clock arrival time rather than the SDC-specified ideal clock source latency.
  • It estimates the power consumed by the clock tree and reports it in the clock QoR summary.
Correct! Input and output timing constraints in the SDC reference clock edges using an ideal source latency. After CTS, the actual insertion delay through the clock tree is known and may differ from this ideal value. compute_clock_latency propagates this real clock network latency to IO timing paths, ensuring that report_timing on input-to-register or register-to-output paths uses the correct clock arrival times and does not report false violations or false passes on interface paths.

4. In the tile CTS result, the report_clock_qor summary shows Target Skew = 0.26 ns but Global Skew = 0.41 ns at the ffg corner. What does this mean and should you be concerned?

  • It means CTS failed — any skew above the target is a fatal error that prevents sign-off.
  • It means the CTS engine used the wrong clock cell library — clock cells with insufficient drive strength were selected.
  • The target skew (0.10 ns per-sink-pair, which expands to 0.26 ns globally) is the optimization goal, not a hard constraint. A global skew of 0.41 ns is an acceptable result — the design passed hold fixing, so timing closure is the real acceptance criterion, not hitting the skew target exactly.
  • The target and global skew numbers are measured on different clock nets — comparing them directly is not meaningful.
Correct! The skew target set via set_clock_tree_options -target_skew 0.1 is a per-sink-pair skew goal that the CTS engine tries to achieve. The global skew shown in report_clock_qor is the difference between the maximum and minimum insertion delays across all sinks — it is a summary metric. If hold violations were fixed cleanly by final_opto, the design can proceed to routing even if global skew exceeds the target. The target is a guide, not a hard pass/fail threshold.
