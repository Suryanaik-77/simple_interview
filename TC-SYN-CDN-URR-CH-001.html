Challenge Problem

INDEPENDENT WORK

You are given a Cadence Genus synthesis script for the AES Cipher Top (aes_cipher_top) design. When you run make all, the synthesis script runs but check_design -unresolved writes reports/check_design.rpt showing a non-zero unresolved reference count, and the check_unresolved proc exits the run early.

Your Challenge: Apply the debug loop from Testcase 1 independently — run → check_design.rpt → log for details → fix → re-run — until reports/check_design.rpt shows Unresolved References 0 and synthesis completes cleanly.

⚠️ This is an independent exercise. No step-by-step instructions are provided. Check reports/check_design.rpt first after every run, then use logs/genus_synthesis.log to identify which specific modules are missing. Hints are available below if you are stuck.

📋 Requirements & Deliverables

Fix All Unresolved References in AES Cipher Top

  • Identify which RTL module(s) are missing from inputs/file_list.tcl by checking reports/check_design.rpt and the synthesis log
  • Locate the corresponding source file(s) and add them to the read_hdl list
  • Confirm reports/check_design.rpt shows Unresolved References 0
  • Verify that the gate-level netlist is generated in outputs/

🔧 Recommended Workflow

Apply the same debug loop you followed step-by-step in the guided testcase — independently this time:

  1. Navigate to the testcase directory and run make all
  2. Open reports/check_design.rpt — find the Unresolved References count
  3. Check the synthesis log to identify which specific module name is missing
  4. Decide the fix: plain Verilog module name → edit inputs/file_list.tcl; standard cell name → edit set_db link_library in the script
  5. Apply the fix and re-run with make run
  6. Re-check reports/check_design.rpt — repeat until Unresolved References 0
  7. Run make verify

Hint 2 — Where is the missing file?

All AES source files reside in the same directory. Look at the paths already in file_list.tcl — the missing file follows the same naming convention and is in the same directory as the files already listed.

Hint 3 — Watch for a second issue

There is a reference file inputs/file_list_fixed.tcl in the testcase. Read it carefully — it adds the missing module but also contains a subtle Tcl command typo. If you copy from it, you must fix the typo too, otherwise Genus will report a command not found error.

📝 Knowledge Assessment

1. After make all exits early on the AES design, what is the first file you should open to determine the scope of the problem?

  • logs/genus_synthesis.log to search for error messages
  • reports/check_design.rpt to read the Unresolved References count
  • inputs/file_list.tcl to count the source files
  • scripts/genus_syn.tcl to review the library setup
Correct! reports/check_design.rpt is the primary signal — it shows the exact count of unresolved references. Once you know the count, use the log to identify which specific module names are missing so you can determine the correct fix.

2. In Cadence Genus, which command triggers the resolution of all module instantiations against their definitions?

  • link
  • elaborate
  • syn_generic
  • check_design
Correct! In Genus, elaborate performs the design hierarchy assembly — it reads all module definitions, resolves instantiations, and reports TUI-273 for any it cannot find. check_design queries the post-elaborate state to count unresolved references; it does not itself resolve them.

3. The check_unresolved proc in genus_syn.tcl calls exit 1 when unresolved references are found. What is the purpose of this guard?

  • It prevents Genus from using too much memory during synthesis.
  • It speeds up the synthesis run by skipping mapping for incomplete designs.
  • It stops the flow early so students do not waste time running syn_generic, syn_map, and syn_opt on a design that will produce an incorrect or incomplete netlist.
  • It is a licensing check to verify the tool is authorized.
Correct! Synthesizing a design with unresolved references produces a netlist with black-box stubs for the missing modules. That netlist is functionally incorrect and cannot be used for PnR. The guard catches this early and forces the user to fix the issue before proceeding.

4. What does reports/check_design.rpt show when all AES modules are correctly resolved after the fix?

  • It shows the timing slack for all paths.
  • Unresolved References: 0 — indicating all module instantiations were matched to definitions.
  • It lists all gate-level cells in the synthesized netlist.
  • It shows the synthesis runtime and memory usage.
Correct! The check_design command in Genus generates a summary report. The key field to verify is Unresolved References — after correctly adding all missing .v files, this line must read 0 before synthesis can be trusted to produce a correct gate-level netlist.
